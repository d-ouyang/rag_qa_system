# 从 0 到 1 搭一个 AI Agent 项目：倒推设计法

> 这篇文档解决的唯一问题：**跟着视频会敲，自己开新项目不会下手。**
>
> 原因不是记性差——视频给的是「结果序列」（先写 A 再写 B），缺的是「决策依据」（为什么 B 必须排在 A 后面）。
> 补上决策依据，你就能自己推导顺序。

---

## 一、核心方法：倒着设计，正着实现

**AI 项目的模块是依赖关系，不是功能清单。**

所以不要从"第一个文件写什么"开始想，而是先锁定终点，再一路往回追问。问六次，模块顺序自己就出来了：

| 追问 | 得到的模块 |
|------|-----------|
| ① 终点：用户问一句话，得到带出处的答案 | 先定目标 |
| ② 要生成答案，最后一步需要什么？需要一个「问题 + 上下文」的 prompt | `rag_chain` |
| ③ 上下文从哪来？检索器从向量库捞 Top-K | `retriever` |
| ④ 向量从哪来？文档切块后由嵌入模型算出来 | `embedding` + `vector_store` |
| ⑤ 文本块从哪来？上传 → 解析 → 切分 | `document_loader` |
| ⑥ 上面这些参数谁提供？配置层统一给 | `config` |

**倒推出来的是依赖方向，实现时按相反顺序（配置 → 数据 → 向量 → 检索 → 生成 → 组装 → 接口）。**

---

## 二、七步实现，每步都要能独立验收

这是全套方法里最重要的一条：**每一步都必须有独立的验收手段，任何一环不通过就不往下写。**

> 前端类比：你写组件会先在 Storybook 里单独渲染出来，确认没问题再接进页面。
> 后端同理——**组件级验证永远优于系统级调试。**

| # | 模块 | 要解决什么 | 为什么在这个位置 | 不做的后果 | 验收方式 |
|---|------|-----------|-----------------|-----------|---------|
| 1 | `config` | 所有可变参数集中一处 | 依赖树的根，其他模块都读它 | 模型路径散落各处，换模型改 8 个文件 | 打印出全部配置；`data/ upload/ vector_db/` 自动创建 |
| 2 | `document_loader` | 把文档变成干净的文本块 | 数据流源头，没 chunk 后面无法测 | 无数据可存，写不下去 | 加载真实 docx，打印块数 + 每块前 100 字 |
| 3 | `embedding` + `vector_store` | 文本 → 向量 → 可检索 | 维度耦合，必须一起设计 | 换模型不重建库 → 检索全错**但不报错** | 存一条 → 搜相似句 → 分数合理（归一化后接近 1） |
| 4 | `retriever` | 按语义捞出最相关的 K 条 | **分水岭**：RAG 失败 90% 在检索 | 先接 LLM 则分不清「没捞到」还是「不会答」 | 问已知答案的问题，正确片段出现在 Top-3 |
| 5 | `llm_client` | 统一多供应商调用 | 最简单且不被检索依赖，放在检索之后 | 供应商差异渗进业务代码 | 裸调一次，返回文本 |
| 6 | `rag_chain` + `memory` | 组装成端到端问答 | 依赖前 5 步全部就绪，属「组装」非「开发」 | — | 问一句得到答案+来源；追问「那第二个呢」能正确指代 |
| 7 | `api` → 前端 | 暴露服务、渲染界面 | 接口是验收面，前端只是渲染 | 业务逻辑渗进前端，换框架重写一遍 | curl 先通，再开浏览器 |

### 三个最值钱的判断

**① 切分粒度比换模型重要得多。**
RAG 效果差，第一嫌疑人永远是切分参数，不是嵌入模型。检查方法：把 chunk 打出来读，看有没有半句话。

**② rerank 要基于观测再加，不要基于教程就加。**
先跑纯向量检索，当观测到"正确片段在 Top-10 但不在 Top-3"时，才引入重排。**优化由观测驱动，不由教程驱动**——这是工程思维与抄作业的分界线。

**③ 记忆必须在检索之前介入。**
"那第二个呢"这类追问，要先经 LLM 改写成完整问题，否则检索拿到的是一句残句，必然捞错。这就是 `history_aware_retriever` 存在的理由。

## 三、AI 项目 vs CRUD 项目：多了一层不确定性

| | 传统 CRUD | AI Agent 项目 |
|---|---|---|
| 链路 | 表 → 接口 → 页面 | 数据 → 向量 → 检索 → 生成 |
| 确定性 | 输入 A 必得 B | 中间层不确定：可能捞错、可能胡说 |
| 调试手段 | 读报错栈 | **看中间产物** |
| 额外必需 | — | **可观测性** |

因为中间层不确定，排查时你无法靠"代码逻辑对不对"来定位，只能靠**看见中间产物**：

- 检索捞到了什么片段、相似度多少
- 最终拼给模型的 prompt 长什么样
- 模型返回的原始文本

**前端类比**：调 CSS 会开 DevTools 看「计算后的样式」；AI 项目同理，你得能看见「模型实际收到了什么」。没有这层可观测性，调试就只能靠猜，而猜是最贵的调试方式。

**落地做法**：
1. 每个模块关键路径打日志（捞到什么、分数多少、拼了多长）
2. 加一个 debug 接口，返回「问题 → 检索片段 → 最终 prompt」
3. 单元测试直接断言中间产物，而不是只断言最终答案

## 四、下次开新项目的三十分钟定型流程

**第一步 · 写下终点（5 分钟）**
一句话说清：输入是什么、输出是什么、凭什么可信。
例：*用户用自然语言提问，返回一句由知识库文档支撑的答案，并附引用来源。*

**第二步 · 倒推依赖链（15 分钟）**
反复问"要产出这个，上一环需要什么"，直到问到底层数据。
把答案写成列表，顺序就是实现顺序的反向。

**第三步 · 给每一环配验收方式（10 分钟）**
对每个环节问："我**怎么知道**它是对的？"
答不出来的，说明这一步的边界没想清楚，先别写。

这三步做完，你不需要任何人教你顺序。
