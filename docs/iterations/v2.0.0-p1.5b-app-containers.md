## 3. 关键设计决策

### 3.1 应用服务必须挂在 `full` profile 下（本版第一个决定）

决策 D1 定的是「日常开发 = 中间件容器 + 应用裸跑」，因为只有裸跑才有热重载和断点调试。
如果四个应用服务直接进默认 profile，`make infra`（= `docker compose up -d`）会把它们一起拉起来，
**和宿主机上正在裸跑的 8000 / 3000 / 5173 直接撞端口**。

挂在 `profiles: [full]` 之后：不带 `--profile` 的命令看到的仍然只有 mysql + redis，
行为与 P1-5a 时期完全一致，两种模式互不干扰。

- 否掉的方案：**另起一份 `docker-compose.full.yml`**。代价是六七个服务的定义要抄两份，
  中间件那部分必然漂移（改了一处忘了另一处，症状是「本地能起、服务器起不来」）。
  profile 是同一份文件里的开关，没有重复定义的风险。
- 代价：`--profile full` 是个容易忘的参数。忘了的表现是「起了，但 frontend 打不开」——
  所以 Makefile 里封装成 `make stack-up`，并在 `stack-ps` 里能一眼看出少起了谁。

### 3.2 主机名：靠 compose 的 `environment` 覆盖 `env_file`（两种模式共存的落点）

`.env` 里写的是 `MYSQL_HOST=localhost`（裸跑用），容器网络里必须变成 `mysql`。
两个值都要存在，因为两种模式都要能跑。

落点是 **compose 里 `environment` 的优先级高于 `env_file`**：
`env_file: .env` 注入全部配置（密钥也走这条路，不进镜像层），
`environment` 里只写「容器网络下必须改的那三个」：

```yaml
MYSQL_HOST: mysql
REDIS_URL: redis://redis:6379/0
REDIS_QUEUE_URL: redis://redis:6379/1
```

- 否掉的方案：**让 `.env` 直接写容器名**。那样裸跑就连不上了 —— 而裸跑是日常开发形态，
  不可能为了容器化牺牲它。
- 否掉的方案：**维护两份 `.env`**（`.env.local` / `.env.container`）。
  两份配置必然漂移，而且漂移的症状全是「连不上数据库」这种不带上下文的报错。
- **注意 Redis 与 MySQL 的表达方式不同**：MySQL 是 `HOST` + `PORT` 两段，Redis 是完整 `URL`。
  所以 Redis 要覆盖的是两个 URL 而不是 HOST。

> 顺带发现一个误导项：`.env` 里的 `REDIS_HOST` **代码根本不读**（settings 里没有这个字段，
> 实际生效的是 `REDIS_URL`）。计划书里写过「`MYSQL_HOST` / `REDIS_HOST` 必须做成变量」，
> 但落地时 Redis 走了 URL 形式，HOST 就成了没人用的摆设。
> 已在 `.env.example` 里标注「改它不会生效」—— 留着不标注，将来一定会有人改它然后困惑半天。

### 3.3 nginx 会在启动时解析 upstream 主机名（必须绕开）

这是个不写就一定会踩的坑：nginx 在**启动时**解析写死的 upstream 主机名。
compose 起来时 gateway 容器可能还没就绪（甚至还没创建），nginx 会以
`host not found in upstream "gateway"` **直接退出**；配上 `restart: unless-stopped` 之后
就是反复重启刷一片日志，看起来像「网关挂了」，实际是 nginx 自己起不来。

解法是把解析推迟到**请求发生时**：用变量 + `resolver` 指向 Docker 内嵌 DNS（`127.0.0.11`）：

```nginx
resolver 127.0.0.11 valid=30s ipv6=off;
location /api/ {
    set $gateway_upstream "http://gateway:3000";
    proxy_pass $gateway_upstream;
    ...
}
```

- 否掉的方案：**靠 `depends_on` 保证 gateway 先起来**。depends_on 只保证容器**创建顺序**，
  不保证 nginx 启动时 DNS 已有记录；而且 frontend 重启时 gateway 也可能已在运行中 ——
  这个方案在「frontend 单独重启」的场景下依然会炸。
- 代价：`set` + 变量让配置稍微绕一点，且**必须写 resolver**（不写的话变量形式的
  proxy_pass 会用系统默认 DNS，解析不到容器名）。

### 3.4 `proxy_buffering off` —— 流式的命门，错了还不报错

nginx 默认开响应缓冲。后端逐字吐出来的 NDJSON 会被攒在 nginx 的缓冲区里，
前端表现是「转圈十几秒然后一次性糊出来」。

**这一行的特点是：不配不会报错，只是流式看起来"效果不好"** ——
很容易被当成模型慢、网络慢，然后去查错方向。
所以它在 nginx.conf 里配了注释，也在本文档里单列一节。

同时配了 `proxy_read_timeout 300s`：一次问答（检索 + 重排 + 生成）正常几十秒，
nginx 默认 60s 读超时会在长回答上掐断连接。

### 3.5 后端必须单进程，不许加 `--workers`

多进程会同时改写同一个 Chroma `persist_directory`，导致 HNSW 索引不一致
（查询返回 `documents=None` → langchain 构造 `Document` 直接 `ValidationError` → **问答接口 500**；
详见 `p0.4a` 文档 §3.6，以及 `p0.4c` 排障时遇到的「上传了却答不知道」）。

`CMD` 里是裸的 `uvicorn api.main:app`，没有 `--workers`，并在 Dockerfile 注释里写明不要加。
要横向扩容，前提是先把向量库换成 Chroma server 模式（见 §6 遗留项第 2 条）。

### 3.6 Worker 复用后端镜像，且关掉 reranker

**复用镜像**：解析（Worker）与问答（后端）必须跑在**完全同一套依赖**上。
分成两个镜像，两边 requirements 会各自漂移，漂移的结果是「Worker 写进去的切片，
后端读出来不认识」—— 这类问题只在跨进程时现形，单测测不到。
两个服务写相同的 `build` 配置 + 同一个 `image` 名，Docker 只会真正构建一次。

**关掉 reranker**（`USE_RERANKER: "false"`）：解析链路只用嵌入模型，用不到重排。
关掉约省 **1.1GB 常驻内存**，是 4C4G 服务器上「跑不跑得动」的关键（PLAN §11.1 对策①）。
语义无损 —— 重排只发生在问答链路（后端容器），不影响解析结果。

> 这条本是 P1-6 的对策，提前落地的原因：写 compose 时它就是一个环境变量，
> 现在写上比以后补更省事，而且内存预算是**从第一天就成立**的硬约束，不该等。

### 3.7 `vector_db` / `upload` 用 bind mount，不用命名卷

| 方案 | 好处 | 代价 |
|------|------|------|
| **bind mount**（选用） | 直接复用宿主机已有的知识库数据；备份可以直接 `rsync` 目录 | 目录属主/权限要留意；换机器要带着目录走 |
| 命名卷 | Docker 托管，跨平台一致 | 本地预演时容器里是**空的**（宿主机已有数据进不去）；备份要绕 `docker run --rm -v` 中转 |

选 bind mount 的直接原因：本机 `vector_db` 里已经有 18 片真实切片、
`upload` 里有 5 份文档。用命名卷的话，全栈起来后知识库是空的，
**第一反应会是「容器化把数据搞丢了」** —— 而其实只是卷是新的。
P2-10 的备份策略（rsync 到 COS）也更适合目录而不是卷。

### 3.8 `models` 走 bind mount 且只读（承接 P1-6 方案）

镜像里不放模型：模型约 2GB，COPY 进去镜像会膨胀到没法分发，而且换模型要重新构建。
挂载成 `:ro` 是防止应用误写模型目录。

⚠️ **已知风险**：本机 `models` 是**软链**到 `~/Downloads/rag_qa_system/models`。
Docker Desktop 是否跟随宿主机软链取决于文件共享设置，软链目标不在共享目录内时容器内会看到空目录。
**上服务器前必须换成真实目录** —— 这是 P1-6 的收尾项，本版未处理。

### 3.9 后端不映射 8000 到宿主机

网关 `proxy.controller.ts` 的注释里明确要求「后端必须只在内网可达」。
全栈模式下访问入口是 frontend(8080)，API 走 gateway(3000)，后端没有理由对外。
要连后端调试：`docker compose --profile full exec backend ...`。

### 3.10 Worker 不配 healthcheck

Celery 没有 HTTP 端口。常见的替代做法是 `celery inspect ping`，
但它探的是「有没有 worker 应答自己」，在单 worker + `prefetch=1` 场景下会时通时不通
（任务执行中的 worker 不一定及时回 inspect），容易把健康的 worker 判死并重启。

不配健康检查的代价是「worker 死了没人知道」—— 这条由后端 `/api/v1/system/queue`
暴露队列积压来兜（P2-10 观测项）。**宁可不探，也不要探错。**

### 3.11 容器连宿主机服务：`host.docker.internal`

容器里的 `localhost` 是容器自己。`.env` 里 `OLLAMA_BASE_URL=http://localhost:11434`
在容器里连不到宿主机的 Ollama，症状只是「连接被拒绝」，看不出是地址语义错了。

compose 里给 backend / worker 加了 `extra_hosts: ["host.docker.internal:host-gateway"]`
（Docker 20.10+ 的跨平台写法，Linux 上自动解析成宿主机网桥 IP，不用手工查）。
当前 provider 是 siliconflow（公网 API），不受影响；将来切本地模型时改 URL 即可。

**新增命令**：`make stack-up` / `stack-ps` / `stack-logs` / `stack-down` / `stack-rebuild s=<服务>`。

**无 HTTP 接口变化、无数据结构变化。** 运行时版本 `PROJECT_VERSION`：`2.0.0-p0.4c` → `2.0.0-p1.5b`。

## 6. 已知边界与遗留项

1. **未构建、未联调**（本版最大的遗留）。静态检查过了不等于能跑起来 ——
   真正的风险点集中在构建期（`npm ci` 在 alpine 上能否装全、torch 的 wheel 是否可用）
   和运行期（Chroma 共享卷、nginx resolver）。
2. **Chroma 多进程共享问题没有被容器化解决，反而被固定下来了**：
   backend 与 worker 挂载同一个 `vector_db`，worker 写入不进后端的 HNSW 索引
   （`p0.4c` 排障时实测过：新进程能召回、在线后端零召回）。
   容器化之后这个结构没变，规避动作是**重启 backend 容器**。
   根治只有两条路：① Chroma server 模式（单独容器 + `HttpClient`，要改 `core/vector_store.py`）；
   ② 把「写 Chroma」收敛到 worker 单进程（后端删除文档也改成投任务）。
   两条都不在本版范围，见 PLAN §11.2。
3. **`models` 软链**（本机 `models → ~/Downloads/...`）在容器里可能失效 → P1-6 收尾。
4. **`reindex-apply` 的闸门在容器里怎么表达**：原闸门是「后端在线就拒绝执行」（退出码 2）。
   全栈模式下必须先 `make stack-down` 停掉 backend + worker，再在**宿主机**跑脚本 ——
   脚本要连的是容器里的路径（bind mount 后路径内容一致，但脚本按 `BASE_DIR/upload` 扫描，
   宿主机跑没问题）。这条要在联调时确认一次。
5. **日志写进容器层**：`app.log` 由 `RotatingFileHandler` 写在 `/app/app.log`，
   容器删即失。stdout 那份（`StreamHandler`）能被 `docker logs` 拿到，够日常排查；
   持久化归 P2-10 观测。
6. **未加非 root 用户**：容器以 root 跑。加用户要连带处理三个 bind mount 的属主，
   在没联调的情况下贸然加会引入权限类故障 → 归 P2 安全加固。
7. **`ALLOWED_ORIGINS`**（后端的 CORS）仍写着 `localhost:5173/3000`，
   全栈模式下前端走同源反代不受影响；服务器部署时归 P2-8 一起清理。
8. **module9 / module10 的测试清空问题**依然存在（与本次无关，见 `p0.4a` 文档 §6）。
