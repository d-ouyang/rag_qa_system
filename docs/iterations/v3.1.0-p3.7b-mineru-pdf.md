## 1. 背景（结论先行）

**PDF 表格入库此前必丢结构**：PyMuPDF 抽的是纯文本流，表格按行线性化、
合并单元格（rowspan/colspan）信息直接消失，无参数可救。本版新增
`core/mineru_client.py`，PDF 可路由到 MinerU 版面模型，拿回保留表格结构的
markdown/HTML 再进 p3.7a 的 title 切分（表格行组原子天然可用）。

**真实链路已实测通过**：一张含 6 行 4 列表格的 A4 PDF，从上传到拿到
markdown 全程 **7 秒**，输出 `<table>` HTML 连 `rowspan/colspan` 属性都完整
还原 —— 这是 PyMuPDF 永远给不了的。（账号当日余量显示 0 但未拦截小任务，
真实额度约束以 mineru.net 账单为准。）

## 2. 方案（实现了什么）

```
PDF 上传
  │
  ├─ MINERU_ENABLED=false 或 key 缺失 ──────→ PyMuPDF（行为与 p3.7b 之前一致）
  ├─ 文件 > MINERU_MAX_BYTES（20MB）────────→ PyMuPDF
  └─ 其余 ──→ MinerU batch 流（§3 踩坑纠正后的正确流程）
                  │ 成功 → markdown（表格为 HTML）
                  │         └─ 一律走 title 模式切分（表格行组原子只在这条路上有）
                  └─ 任何失败（额度 0 / 超时 / 结构异常 / 网络）
                            → WARN 日志带原因 → PyMuPDF 降级，绝不阻塞上传
```

- **路由判据 = 强制开关 + 大小阈值**（PLAN 原设计），「健康探活」没做：
  预检有竞态，省不掉失败分支，降级路径反正要写。
- **MinerU markdown 不问 CHUNK_MODE 一律走 title 切分**：fixed 的
  RecursiveCharacterTextSplitter 会把表格从中间切断，行组原子只在 title 路径上。
- **表格两种形态都原子**（p3.7a 已建 md 管线表逻辑，本版补 HTML 表）：
  · md 管线表（`|` 开头连续行）：整表 ≤ chunk_size 整块存；超长按行组切+表头重复；
  · HTML 表（MinerU 把整表输出成**单行** `<table>...</table>`）：同上，
    超长时按 `<tr>` 正则行组切，每片重组为合法 `<table>` 且首行表头重复。
- **配置**（`config/settings.py` + `.env*`）：`MINERU_ENABLED`（代码默认 false，
  `.env.example` 占位 false）、`MINERU_API_KEY`、`MINERU_API_BASE`、
  `MINERU_MAX_BYTES`、`MINERU_MODEL_VERSION`（pipeline/vlm）、轮询间隔与超时。
  key 已从桌面 langChain 项目 `.env` 复制入本项目 `.env`（不入仓）。

## 3. 踩坑记录（对本项目此后任何 MinerU 集成都有用）

1. **桌面 langChain 项目的调用方式是错的，且从未被真实验证过**：它把
   `/file-urls/batch` 拿到的 presigned URL 再提交给 `/extract/task` —— 官方文档
   明确说明该端点只收**公网可读 URL**，MinerU 自家 OSS 的签名链接是 PUT-only
   （实测 GET 403），服务端读不了 → 任务必然 `failed: failed to read file`。
   本项目首版照抄后实测复现此错，对照官方文档纠正。
2. **正确流程是「自动提交」**：`POST /file-urls/batch`（带 model_version）→ PUT
   上传 → **系统自动扫描已上传文件并提交解析，无须调用任务提交接口** →
   轮询 `GET /extract-results/batch/{batch_id}`（注意是 extract-**results**，
   与提交端点不同名；langChain 版连这个路径也是错的 `extract/task/batch/{id}`）。
3. **结果认领用 data_id**：batch 响应列表按 `data_id`（请求时自造的 uuid）认领，
   不能按 file_name（可重名）也不能按位置（多文件时不可靠）。
4. **HTML 表是单行的**：MinerU 输出整表一行，`|` 前缀检测完全失灵 ——
   行组切分按 `<tr>` 正则重组，这条是拿真实输出对着切分器跑出来的。

## 5. 否掉的方案与代价

- **quota 预检**（先查 /quota 再提交）：预检通过后额度仍可能被并发消耗，
  失败分支省不掉 —— 删。
- **HTML 表超长直接截断**：行数据丢失，表格问答直接错 —— 改为 `<tr>` 行组重组。
- **MinerU 失败时重试**：解析类失败（文件坏/额度不足）重试结果不变，
  白烧额度；网络类失败由降级兜底 —— 上传侧不重试，人工重传即可。

## 6. 遗留与待拍板

1. **`MINERU_ENABLED` 生产值**：本项目 `.env` 已置 true（实测需要），
   `.env.example` 占位 false。线上部署是否开启由用户拍板 —— 开 = PDF 上传
   走 MinerU 计费额度，关 = 行为与旧版一致。
2. **golden 表格类问题未补**（PLAN §6.2 第 4 点）：当前知识库 35 篇全是 md，
   没有表格 PDF 可标 relevant —— 补题的前提是先有表格类文档入库。
   触发条件：第一批含表格 PDF 入库时，补 3~5 条（跨页表/合并单元格表）再跑
   `make eval-retrieval` 出 B 的召回数字。
3. **扫描件 OCR**：`is_ocr` 固定 false（快、省额度）；扫描版 PDF 走 MinerU
   会被当纯文本抽，需要时加配置项再开。
