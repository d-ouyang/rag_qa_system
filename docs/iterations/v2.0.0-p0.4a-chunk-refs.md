# v2.0.0-p0.4a 向量元数据对齐 + 知识库重建（后端）：切片可反查、可溯源、可重建

- **版本**：`2.0.0-p0.4a`
- **日期**：2026-09-23
- **对应计划**：`docs/PLAN-v2.0.0.md` → P0-4 向量元数据对齐 + 知识库重建
  —— 本版只做 **a 阶段（后端）**，前端「点引用展开正文」是 `p0.4b`（见 §1「明确不做」）
- **上游基线**：`v2.0.0-p0.3b`（`2.0.0-p0.3b`，前端异步解析轮询）
  —— P0-4 直接依赖 P0-3a 写进 metadata 的 `doc_id` / `chunk_index`，这也是执行顺序 P0-3 → P0-4 的原因
- **一句话**：给每个切片发一张**自描述的身份证** `chunk_id = "<doc_id>:<chunk_index>"`，
  把它写进 Chroma metadata、带回问答接口、落进 `chat_message.ref_ids`，
  再补一个 `GET /api/v1/chunks/{chunk_id}` 让「点引用」能拿到切片全文与源文档信息；
  配套一个**可中断可重跑**的重建脚本 `scripts/reindex.py`，把历史上缺 metadata 的切片一次性补齐并清掉孤儿。

## 3. 关键设计决策

### 3.1 为什么 `chunk_id` 是 `<doc_id>:<chunk_index>`，而不是 Chroma 自带的 UUID

三个理由，按重要性排：

1. **拿不到**。本项目用的是 `langchain-community 0.3.x` 的 `Chroma`（`langchain_chroma` 未安装），
   它的 `similarity_search_with_score()` **不回填 Chroma 的 id**，`Document.id` 恒为 `None`。
   要拿就得绕开 langchain 直接调 `collection.get(include=...)`，等于为「取一个键」再开一条通路。
2. **会失效**。UUID 每次重建全变，`chat_message.ref_ids` 里存的历史引用会**集体作废**；
   而 `doc_id:chunk_index` 在「同一文件、同一切分参数」下重建后**保持不变**，历史引用照样能查到正文。
3. **自描述**。日志里看到 `202:7` 就知道是 202 号文档的第 8 片，
   排查「这条引用到底指向哪儿」不需要再查一次库。

**代价（必须记住）**：切分参数（`CHUNK_SIZE` / `CHUNK_OVERLAP`）一改，
同一个 `chunk_id` 会解析到**另一段正文** —— 比「查不到」更糟，因为它看起来是正常的。
兜底约定写在这里：**改切分参数 = 整库重建 + 清空历史引用**，别指望旧引用还能对得上。

写入顺序也有讲究：`doc_id` / `chunk_index` 先写，`chunk_id` 最后由 `build_chunk_id()` 拼。
反过来的话，切分参数变了 `chunk_id` 就与坐标脱钩，重建时对不上。

### 3.2 为什么 `isdigit()` 不够，以及为什么必须先挡 `bool`

`parse_chunk_id()` 要把 `"12:3"` 拆成 `(12, 3)`，两个数字都得 `int()`。
校验用 `isascii() and isdigit()` 而不是单写 `isdigit()`，因为：

- `isdigit()` 对**全角数字**（`"１２"`，一字一码位）与**上标**（`"²"`）都返回 `True`，
  但 `int("²")` 直接抛 `ValueError` —— 表现是「校验通过、转换炸掉」，接口回 **500 而不是 400**。
  测试里专门留了一条 `"1:²"` 的用例守着。

另一半是 `bool`：`True == 1` 在 Python 里为真，`isinstance(True, int)` 也是真。
不显式挡掉的话，`True` 会被当成「文档 1 / 第 1 片」，或者让「有效文档集合」里混进一个 `True`。
所以 `_match_chunk_index()` / `_resolve_chunk_id()` / `_normalize_doc_id_safe()` 三处都先挡 bool 再判 int。

同理，Chroma 的 `where={"doc_id": N}` 要求**类型精确匹配**（int 11 ≠ str "11"），
写入侧统一写 int，读取侧做归一而不是「两边都试试」。

### 3.3 `_resolve_chunk_id()` 的三级取值：为什么不让老切片整库重建

| 情况 | 取值 | 为什么 |
|------|------|--------|
| metadata 里有 `chunk_id` | 直接采用 | P0-4a 之后入库的切片 |
| 只有 `doc_id` + `chunk_index` | 现拼一个 | P0-3a 期间入库的那批：正文完好、反查通道也通，**唯一缺的就是键** |
| 连 `doc_id` 都没有 | 返回 `None` | P0-3 之前的遗留切片，**本来就无法反查** |

第二条是关键：**为一个派生字段整库重灌一遍不划算**，在这里补一次就够了。
第三条返回 `None` 而不是退化成 `source` 路径 —— 后者会让前端以为「有键可查」，点下去必然 404。
前端据此把引用渲染成不可点击的纯文本。

### 3.4 反查接口的四种返回，各有分工

| 情况 | 状态码 | 文案 / 标记 | 为什么是这个 |
|------|--------|-------------|--------------|
| 格式非法（`abc` / `12:` / `-1:0`） | **400** | `chunk_id 格式非法：…` | 客户端传错了，是请求的问题 |
| 文档已删 | **404** | 「引用内容已随文档删除」 | 这是**预期内**的终态，前端据此降级展示 |
| 文档在、切片没了 | **404** | 「引用片段已失效（文档已重新解析或正在解析），请刷新后重试」 | 与上面**必须区分开**：一个是永久失效，一个是暂时不一致 |
| 切片在、MySQL 记录没了 | **200** | `document_exists=false` | 正文确实还在，**不给用户报错**；`false` 是给运维的信号：该跑重建脚本了 |

顺序也有讲究：先 `parse_chunk_id` 校验（400 优先于 404），再查 Chroma，最后查 MySQL
（查 MySQL 只是为了给错误分类 + 补文件名/上传时间/归属项目）。

### 3.5 重建脚本为什么不「先 `clear_all()` 再重灌」

`clear_all()` + 逐个重灌看起来更干净，但**中途失败不可续跑**：库已经清空，旧数据回不来，
一个 1.2MB 的 PDF 解析失败就变成了「知识库没了」。改成三步：

1. **补登记**（磁盘有、MySQL 没有的文件建 `pending` 行，文件名优先取向量库老 metadata 的 `file_name`）；
2. **逐文档幂等重灌**（`parse_and_index()` 自己会先 `delete_by_doc_id` 再写，同一文件重解析得到同一组 `chunk_id`）；
3. **最后清孤儿**。

每一步都可以中断、可以重跑，最坏情况也只是「多跑了一遍」。
默认干跑，`--apply` 才动手；另有 `--no-purge` / `--only-doc N` / `--force`。

### 3.6 两道闸门：worker 在线不跑、后端在线不跑（本版踩得最深的一个坑）

第一道好理解：worker 在跑时并发 `parse_and_index()`（先删再写）交错会让**切片翻倍**。

第二道是实测撞出来的：**多进程同时改写同一个 Chroma `persist_directory`，会让 HNSW 索引不一致**。
现象有两种，都很吓人：

- 查询返回 `documents=None` → langchain 拿 `None` 构造 `Document` 直接 pydantic `ValidationError`
  → **问答接口 500**；
- hnswlib 抛 `RuntimeError: Cannot return the results in a contigious 2D array. Probably ef or M is too small`。

Chroma 官方就不支持多进程共享同一个 `persist_directory`。
所以脚本在 `--apply` 时先探 `8000` 的 `/api/v1/qa/health`，在线就拒绝执行（退出码 2，
文案里直接写明后果是「问答接口 500」）。
代价是重建必须停服 —— 这是可以接受的：重建本来就是一次性运维动作，
脚本执行完还会打印「⚠️ 下一步：把后端服务重启一遍」。

### 3.7 「重置单例」不等于「重启进程」

发现上面那个坑时，第一反应是「句柄陈旧，重置一下单例就好」，
于是加了 `reset_rag_retriever()` + `reset_vector_store_manager()` —— **实测照样崩**。
原因：chromadb 在同一进程内按 `(目录, collection)` **共享集合实例**，
「重置」之后拿回来的还是同一个对象，索引状态没变。

真运维里对应的动作是**重启后端进程**；验收脚本里的等价做法是 `probe()`：
把检索 + 库体检放进一个**全新子进程**（临时 `.py` + stdout 标记回传 JSON），
跑完即弃。换进程 ≈ 换句柄，这才验得出「重建之后库是好的」。

顺带改掉的一个隐患：验收脚本开头会先清掉上一轮 `p04a_*` 残留，
否则重建脚本会把它们当成「磁盘上有、库里没有」的文件补登记，污染后面的断言。

### 3.8 为什么本版故意让前端处在「对不上」的状态（P0-4b 的由来）

与 P0-3a 同一套打法：后端契约先落地并验完，前端再按新契约改。
反过来（两端同时改）的代价是「联调时不知道错在哪一端」。

但这次留了一个**明确的交接物**：`chunk_id` 已经出现在 `GET /api/v1/qa/ask`
与会话历史的 `sources` 里，P0-4b 只需要把它渲染成可点击的按钮 + 调反查接口。
**没有这个交接物，P0-4b 就得先回头改后端。**

### 3.9 为什么重建脚本用 `repo.list_all()`，而不是 `list_documents(limit=99999)`

`list_documents()` 是给分页列表页用的，将来一旦有人给它加上限（防一次拉爆），
重建脚本会**静默只重建一部分** —— 而脚本自己还报「成功」。
所以单独开一个语义明确的 `list_all()`：不分页、按 `doc_id` 升序，注释里写明「这是重建专用的全量通道」。

### 3.10 本版最贵的坑：`response_model` 会**静默丢字段**

`_extract_sources()` 里加了 `chunk_id`，module10 的 84 项全绿、验收脚本 41 项全绿，
然后浏览器里一问 —— **接口返回的 `sources` 里根本没有 `chunk_id`**，且不报任何错。

根因：FastAPI 的 `response_model` 不是透传，是**按 pydantic 字段过滤**；
pydantic 默认 `extra='ignore'`，`SourceItem` 里没声明的键被直接丢掉。
修法只有一行（给 `SourceItem` 加 `chunk_id: str | None`），但**教训值钱**：
「后端日志里有」不等于「接口返回里有」。

补的守卫不是「断言 chunk_id 存在」，而是更强的：

```python
_produced_keys = set(src_new[0]) | set(src_old[0]) | set(src_legacy[0])
_missing_fields = _produced_keys - set(SourceItem.model_fields)
check("**_extract_sources 产出的每个键都在 SourceItem 里声明过**", not _missing_fields, ...)
```

以后再往 `sources` 里加字段却忘了同步 `SourceItem`，这条立刻红 ——
不管新字段叫什么名字。

> 顺带否掉的方案：给 `SourceItem` 加 `model_config = ConfigDict(extra="forbid")`。
> 它同样能立刻暴露问题，但暴露方式是**线上 500**（而不是测试红），
> 对一个「多给一个字段」这种无害 drift 来说处罚过重。选测试守卫。

### 3.11 回归测试不能全表清空（本版顺手修的）

`tests/test_module10_chunk_refs.py` 第一版照抄了 module9 的
`sa_delete(document_table)`（不带 `WHERE`）。**本机 MySQL 里同时放着真实知识库文档**，
跑一次 module10 就把它们抹掉，而它们的切片还留在 Chroma 里 ——
下一次问答会召回一堆 `document_exists=false` 的「幽灵引用」，
且没有任何报错提示是谁干的（我就是这么丟了一次数据才发现的）。

已改为按 `file_name LIKE 'm10_<uuid>%'` 限定，与 `_cleanup_files()` /
`_cleanup_sessions()` 的前缀口径一致；结尾「按 `storage_path` 删文件」那段同样加了前缀过滤
—— 那段遍历的是 `repo.list_all()` 全表，不收窄会连带删掉 `upload/` 下的原始文件。

> **module9 仍然是全表清空的**（它的 `total_documents == 1`、「列表已空」等断言依赖空表），
> 收窄会让那 166 项大面积变红，属于另一件事。已列入 §6 遗留项。

### 3.12 验收里的「并列」不是「漂移」

第一次跑验收时「重建前后引用键一致」红了：`150:0` 和 `152:0` 换了位置。
根因不在代码而在夹具：夹具用「同一句话重复 40 遍」凑长度，
切出来的多片**正文完全相同** → 重排分并列 → 两次检索之间的顺序本来就是任意的。

两处修改：夹具每条带序号；断言改成**多重集**比较（`Counter` 而不是列表顺序）。
并列是合法的，漂移才是 bug —— 断言要能区分这两件事。

## 4. 配置与接口变化

### 新增配置

**无**。本版没有引入任何新的 `.env` 配置项 —— chunk_id 是派生字段，不需要开关。

### HTTP 接口

| 接口 | 变化 |
|------|------|
| `GET /api/v1/chunks/{chunk_id}` | **新增**。返回 `chunk_id` / `doc_id` / `chunk_index` / `content` / `char_count` / `page` / `file_name` / `file_type` / `file_size` / `upload_time` / `project_id` / `document_exists` / `document_status`。四种返回见 §3.4 |

## 5. 验证证据

### 5.1 验收脚本：计划书四条标准逐条实测

`make accept-p04a` → **41 通过 / 0 失败**：

| 计划书标准 | 实测 |
|------------|------|
| 1. 删除文档后磁盘 / 向量 / 记录三处无残留 | 三处均 True；反查该文档切片返回 404「已随文档删除」；兄弟文档零损伤 |
| 2. 点引用 → `chunk_id` → 切片正文 + 源文档信息 | 文件名 / 上传时间 / 归属项目均来自 MySQL，`document_exists=true`；非法输入 3 例均 400 |
| 3. 重建后同一问题检索到的内容与重建前一致 | 正文**逐字一致**；引用键按多重集一致 |
| 4. Chroma 里不存在缺 `doc_id` 的切片 | 缺 `doc_id` = 0 条、孤儿 = 0 条、总量 19 条 |

## 6. 已知边界与遗留项

1. **前端仍是断的（P0-4b）**：引用现在只是一段摘要，点了没反应。
   交接物已备好（`sources[].chunk_id` + 反查接口），P0-4b 只做渲染与交互。
2. **`module9` 的清理仍不带 `WHERE`**：跑 `make test` 会清空 MySQL 的 `document` 表，
   并删掉 `upload/` 下由这些记录指向的文件。module10 已收窄（§3.11），module9 因为
   有断言依赖空表，改动面较大，单独留一件。
   **当前应对**：跑完 `make test` 想要回演示数据，执行 `make reindex-apply` 即可（补登记 + 重灌）。
3. **改切分参数 = 整库重建 + 清空历史引用**：见 §3.1 的代价。约定写在那里，没有代码强制。
4. **重建必须停服**：worker 与后端都得停（§3.6）。这是 Chroma 的硬限制，不是脚本偷懒。
5. **文档删除后历史引用查不到正文**：既定结论（§11 D3），换来的是「删除彻底」——
   敏感文档不会以快照形式残留在历史 JSON 里。
6. **网关在本机只能走 `node dist/main.js` 起**：`nest start --watch` 会被环境的批量删除保护拦住
   （它启动时要清 `gateway/dist`），卡住不报错、端口也不监听。
   现象是「3000 有进程占着但 `/api/health` 超时」。绕过方式：直接用已有编译产物起。
