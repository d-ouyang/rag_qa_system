## 1. 背景（一个没有守卫的读路由）

下载链路：`KnowledgeView` 的「下载」按钮 → `GET /api/v1/documents/download?doc_id=`
→ `FileResponse` 读服务器磁盘 `upload/`。

**这条路由一条 kb ACL 都没有**：网关 JWT 之后，**任何登录用户都能下载任意文档**。
对照同一个文件里的 `upload` / `reparse` / `delete` —— 它们都在 P2-14a 挂了守卫，
唯独下载没有。原因不难理解：它是 GET，而 14e 立的规矩是「读路由不挂守卫」
（知识库全公司共用、不隔离读）。

但这两件事不是一回事：

| | 问答检索类读接口 | 下载 |
|---|---|---|
| 吐出来什么 | 切片摘要（几百字，且已在引用里展示过） | **原始文件全文** |
| 消耗什么 | 一次向量检索 | **服务器出网带宽** |
| 拿到之后 | 多知道一点事 | **整份原件离开系统** |

「人人都能**问**」是业务决策；「人人都能把原件整份拷走」从来没有人拍过。
加上轻量机的峰值带宽会被下载挤占（P2-22 修流式那个坑时已经领教过），
所以本项给下载加两道闸门：**kb ACL + 部署开关**。

---

## 2. 方案

```
GET /download?doc_id=
  ① DOC_DOWNLOAD_ENABLED=false  →  404 功能未开放
  ② kb_acl.can_download(kb_role) →  403（只读档 none）
  ③ 查库 → 路径校验 → FileResponse
```

- **开关先判，判在查库之前**：关掉时连「这份文档在不在」都不回答。
- **开关关掉 → 404 而不是 403**（见 §3.2）。
- **capabilities 增 `download` 键** = `ACL ∩ 开关`，前端按它显隐按钮
  （对齐 P2-14d「判据来自后端」的惯例，前端不读开关、不读档位）。

## 3. 被否掉的方案 / 要紧的取舍

### 3.1 「qa 及以上才能下」（PLAN 原文的 `can_qa 及以上`）— 否掉

采用 **除只读档之外都能下（ops / qa / dev / superadmin）**。

`ops` 是**日常维护知识库**的人（可上传、可删除）。他能删掉一份文档，
却不允许把原件取回来核对 —— 这个组合没有任何人能解释得通，
而「没人能解释得通的权限表」迟早会被某个人随手改掉。

真正的边界在 `none`（**只读**档）：他能问、能看引用片段，但不该把整份原件拷走。
与 `reindex` 的差别要记住：`reindex` 会弄坏**所有人**的答案，所以只给 qa+；
`download` 只影响下载者自己 + 服务器带宽。

### 3.2 开关关掉时返回 403 — 否掉

403 的语义是「有这东西，不给你」，它会诱导人去找管理员要权限，
而管理员那边**根本没有这个开关** —— 那是把一次部署决策
变成一个永远解决不了的工单。所以关掉 = 404（功能不存在）。

### 3.3 把开关塞进 `kb_acl.capabilities()` — 否掉

`capabilities()` 至今是**纯 ACL**（不起库、不读配置，与 `status_of` 同形状）。
把部署开关混进去，它就成了「ACL ∩ 配置」，于是
「这个人没权限」与「这个功能没开」在后端就不可分了。
合并**只在路由层做一次**（`my_kb_capabilities`），
而前端拿到的就是合并结果 —— 两种情况下界面完全一致（不渲染按钮），
这正是我们想要的：用户不需要知道区别。

### 3.4 「读路由一律不挂守卫」这条旧规矩 — 收窄为显式白名单

14e 那条断言的完整表述应该是「**问答检索类**读接口不隔离」，
但它被写成了全称命题「所有 GET 不挂守卫」。P3-2 把它改成
**白名单 `/download` + 断言白名单里的条目真的挂了守卫**：
下次再有人给某个 GET 挂守卫，断言依然红，逼他把理由写进那张表。
白名单的语义不是「放行」，是「这条例外是被讨论过的」。

### 4.0 🔴 顺手修掉的门禁故障：`make test-sandbox` 从 2026-10-08 起**只跑了一半**

`compare_metadata()` 有一条恒定红的 diff：`department.leader_user_id` 的**列注释**
在迁移 0003 与 `core/schema.py` 里不一致（P2-14 作废 D13 时只改了 schema.py）。

它的代价不是「多一条红」：`scripts/test_sandbox.sh` 是 `set -e` 遇错即停，
于是从 module8 失败那一刻起，**后面的 9/10/11/12/13/15/18 全部模块一次都没跑过**
—— 一条注释漂移让整个回归门禁静默失效了三个版本，
而每次跑完看到的都是「82/1」，很容易被当成「就那一条老问题」。

修法：**新加迁移 `0008_dept_leader_comment.py`（只改注释）**。
不直接改 0003（它已应用，改了对现存库完全无效，只会让全新安装与老库升级分叉）；
也不改 schema.py（那版描述的才是现实，改回去等于让守卫保护一个错误的事实）。

> **这条教训比修复本身值钱**：回归脚本在第一个失败处停下时，
> 「只有一条失败」会变成「只剩一条被执行」。

### 4.0b module9 的接口组：从 P2-14a 起就没通过过（P3-2 顺手修）

修掉上面那条之后，沙箱回归暴露出下一处：`test_module9_async_pipeline` 的
「HTTP 接口层」组 **upload 返回 403**（连带 7 条）。

根因与下载无关：本组用 `TestClient` 直打 HTTP 且**不带身份头**，dev 模式回落到
break-glass 超管，而它的 `kb_role` 是 `none`（14a 的刻意设定：它不在库里，
没人给它授权过）—— 于是 upload / delete / reparse 从 2026-10-08 挂守卫那天起
就全都是 403。

修法是**注入一个被授权的 Actor**（`dependency_overrides[current_actor]`），
而不是把断言改成 403：本组要验的是「解析链路对不对」，不是「权限矩阵」
（后者由 `test_module12_write_acl` 与本模块的 `test_module18` 管）。
把断言改成 403 等于把这道题整道删掉 —— 那种改法会让测试继续「绿」，
而 upload 链路从此再无人验。

module9：**167 / 0**（沙箱，此前 7 红）。

### 4.1 🔴 顺手修掉的真 bug：`set_kb_role` 的 `KeyError → 500`

`core/admin_service.py` 的「管理员不能收回自己的知识库权限」分支里
写死了一份三键字典：

```python
names = {"upload": "上传", "delete": "删除", "reindex": "重建索引"}
f"…（会失去：{'、'.join(names[a] for a in lost)}）"
```

而 `lost` 遍历的是 `capabilities()` 的键 —— P3-2 加了 `download` 之后，
管理员给自己降权会直接 **500 `KeyError: 'download'`**。

**更值得记的是它当时是绿的**：那个测试只断言「抛了异常」，
`KeyError` 也算。所以修复不是补一个键，而是**把第三份清单删掉**
（`ACTION_LABELS` 进 `kb_acl`，与 `ACTIONS` 同生共死），
并加一条断言钉住「`capabilities()` 的每个键都有中文名」——
这次的判据是**结构性**的，下次加任何动作都躲不过去。

## 6. 风险与已知边界

1. **ops 可以下载原件**：这是 §3.1 的取舍，不是疏漏。若将来出现
   「运营外带」的真实风险，改 `MIN_KB_ROLE_BY_ACTION[download]` 一行即可。
2. **开关关掉时前端只是不渲染按钮**：直连接口会拿到 404，
   但**旧版本前端**（缓存里的静态资源）仍会显示按钮 —— 那是一次 404，
   不会造成越权，属于可接受。
3. **下载仍走 `FileResponse` 整读**（不是流式分块）：50M 上限下无压力；
   若将来放开大文件，这里要另外评估。
4. **带宽是真瓶颈**：关掉下载省的是**服务器出网带宽**，不是 COS 流量
   （COS 只用于整站备份，`scripts/backup_to_cos.sh`）。别照着「省存储」来理解这个开关。
