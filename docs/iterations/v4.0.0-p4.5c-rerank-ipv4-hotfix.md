|----------|--------------------------------|
| **tag** | `v4.0.0-p4.5c` |
| **默认行为** | 重排结果逐位不变（实测同 payload 分数完全一致）；镜像写入从「每轮必失败」变成功 |

## 1. 症状与定位（用户实测：一轮问答 122s，之前很快）

日志分步计时直接锁定：

```
远程重排完成 | 模型=BAAI/bge-reranker-v2-m3 候选=20 保留=2 耗时=120.46s   ← 每次恒定 ~120s
流式问答完成 | 耗时=122862ms tokens=675+69                                ← 整轮 122.9s，生成只占 2s
```

排除法实录（每步都有实测）：

| 假设 | 实测 | 结论 |
|------|------|------|
| siliconflow 服务慢/排队 | 同 payload **curl 直连 0.55s**（连测两次） | ✗ |
| 走了 Clash 代理 | 代码是 `ProxyHandler({})` **显式绕代理** | ✗ |
| payload 太大（20 chunk 全文 31.9KB） | curl 发同一份 payload 仍 0.55s | ✗ |
| **urllib 客户端连接层** | **同 payload urllib 150.38s，返回分数与 curl 逐位一致** | ✓ |

## 2. 根因（两层叠加）

1. `api.siliconflow.cn`（阿里云 ALB）带 **AAAA 记录**；开发机 **IPv6 路由黑洞**——实测 `connect` v6 地址 **75.003s 超时**（Errno 60）。
2. 远程重排用 **urllib**（`build_opener(ProxyHandler({}))`），`socket.create_connection` 按 getaddrinfo 顺序**串行**尝试：2 个 v6 地址各挂 75s ≈ 150s 才轮到 v4 成功。curl 有 Happy Eyeballs（并行）所以快。应用里观测 ~120s（两个 v6 地址的等待有波动）。

**为什么 LLM/embedding 不慢**：它们走 httpx（连接池复用 + 本机代理环境），只有 rerank 这一处是「绕代理直连」的 urllib，每次调用都要新建连接、都撞 v6。**为什么之前快**：大概率阿里云 ALB 近期才下发 AAAA 记录（或本机网络环境变化），属外部条件触发，非代码回退。

**修复**：远程重排 urllib → **httpx**（`trust_env=False` 保持绕代理语义 + `HTTPTransport(local_address="0.0.0.0")` 强制 IPv4）。实测同一负载：**120.46s → 0.36s**，top1=0.9954 与 curl 逐位一致。

## 3. 顺带修复：qa_trace 镜像每轮必失败（P4-5b 自留 bug）

日志：`pymysql.err.DataError: (1265, "Data truncated for column 'rrf_top' at row 1")`。

首版把 `rrf_top` 建成 DOUBLE（以为是「RRF 最高分」），实际 hybrid trace 里它是**首位 chunk_id 字符串**（如 `"822:0"`）→ 混合检索开着时镜像每轮必炸（fail-open 挡住了，用户无感，但溯源页永远空）。修正：`rrf_top` 改 `VARCHAR(64)`（schema.py + 0012 同步，本地 downgrade/upgrade 重放），module27 补字符串落库回归锚（43/0）。教训：**镜像表的列类型必须对着 trace 的真实值建，不能按字段名想当然**——「top」这个词指 ID 还是分数，查了才知道。

## 5. 遗留

- `LLM_TIMEOUT`（60s）是 urllib 时代的兜底，httpx 版下挂死场景已消除；超时语义不变。
- 溯源页 rrf_top 改显示 chunk_id（mono 样式）；若日后想要「RRF 分数」，得先在 hybrid trace 里加分数字段（现在是 ID），届时再加列。
- 生产服务器部署后建议实测一次重排耗时（服务器 v6 环境不同，v4 强制无副作用）。
