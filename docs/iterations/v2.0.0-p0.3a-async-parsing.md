# v2.0.0-p0.3a 异步解析链路（后端）：上传即返回 + Worker 消费队列

- **版本**：`2.0.0-p0.3a`
- **日期**：2026-09-23
- **对应计划**：`docs/PLAN-v2.0.0.md` → P0-3 异步解析链路（队列 + Worker）
  —— 本版只做 **a 阶段（后端）**，前端轮询改造是 `p0.3b`（见 §1「明确不做」）
- **上游基线**：`v2.0.0-p0.1b`（`2.0.0-p0.1b`，业务数据落 MySQL）
  —— P0-3 直接依赖 P0-1 建的 `document` 表，这也是执行顺序 P0-1 → P0-3 的原因
- **一句话**：把「上传 → 解析 → 入库」从**一个 HTTP 请求里同步做完**改成
  「上传只落盘 + 写 pending 记录 + 投一条队列消息（立即返回 202）」，解析交给独立 Worker 进程；
  文档状态由 MySQL 的 `document.status` 状态机统一裁决，用**原子 UPDATE 抢任务**保证幂等，
  并补了「僵尸 parsing 回收」与「全链路失败兜底」。

## 3. 关键设计决策

### 3.1 为什么是 Celery + Redis，而不是 `BackgroundTasks` / `threading`

**否掉的方案**：`fastapi.BackgroundTasks` 或自己开一个线程池。

否掉的代价说明（这是本节的重点）：

- FastAPI 的 `BackgroundTasks` **跑在 Web 进程里**。解析要加载嵌入模型（本地 bge-small-zh，
  常驻约几百 MB）并且是 CPU 密集的 —— 放进 Web 进程等于把 GIL 和内存一起吃掉，
  只是把「阻塞 HTTP」换成了「阻塞整个服务」，比同步还糟；
- 线程池同理，且没有进程级别的内存回收；
- 更要紧的是**部署形态**：解析进程和 Web 进程的内存预算差一个量级
  （计划书 §11.1：backend 1.8~2.2G vs worker 500~700M）。同一个进程就没法分别给资源，
  4C4G 的服务器上这是硬约束。

选 Celery 的直接代价是引入了一整套依赖（amqp / kombu / billiard …）和一个需要单独运维的进程。
在 4C4G 上这个代价是划算的，因为**它买到了「Web 进程不被解析拖垮」这条硬保证**。

### 3.2 为什么把 P0-4 的一部分（metadata）提前到 P0-3 做

计划书里「向量 metadata 扩成 `{doc_id, project_id, chunk_index, ...}`」属于 **P0-4**。
本版提前把 `doc_id` / `project_id` / `chunk_index` 写进去了。理由是**补不回来**：

> 切片写进向量库之后，**事后无法从切片内容反推它属于哪次上传**。
> `chunk_index` 更是如此 —— 一旦写错，片段顺序就变成随机，而且不会报错。

所以「重建一次向量库」这件事的成本，取决于 metadata 是什么时候写进去的：
本版写进去，P0-4 的重建就是「顺手跑一遍」；本版不写，P0-4 就多一个**必须整库重建一次**
的一次性成本，而且那次重建之前的所有切片都是废的。

**代价**：P0-3 的改动面比「只做异步化」大了一圈（`vector_store.py` 被动）。接受。

### 3.3 僵尸 `parsing`：为什么加一列，而不是「worker 启动时把 parsing 全重置」

**问题**：worker 被 `kill -9`（或容器被 OOM Killer 干掉）时，记录冻在 `status=parsing`。
而抢任务的条件是 `status IN ('pending','fail')` —— **一条冻在 `parsing` 的记录永远抢不回来**，
表现为「文档一直转圈，怎么点重解析都不动」。

**否掉的方案**：「worker 启动时把库里所有 `parsing` 重置为 `pending`」。

否掉的代价：**多 worker 场景下会误伤正在干活的兄弟进程**。
A 进程正常解析一个 200MB 的 PDF，B 进程启动（扩容、滚动重启都会触发），
B 把 A 正在跑的那条重置成 `pending` → A 跑完写 `success`，但同时可能有第三个进程又抢了一次
→ 同一条文档被并发解析两次。用一个「启动副作用」去修一个「运行期状态」，
副作用的作用域就不可控了。

**采用的方案**：加 `parse_started_at`，把「`parsing` 且开始时间早于阈值（默认 900 秒）」
也算作可抢。于是：

- 正常解析（秒级~分钟级）不会被抢走；
- 被 kill 留下的僵尸，超时后自动可被任意 worker 重新抢走；
- 判定依据是**数据**而不是**某个进程的启动时刻**，多 worker 下依然正确。

配套的边界：

- 该列**可空**，不用 `DEFAULT CURRENT_TIMESTAMP`。默认值会让所有历史行都得到一个假的开始时间，
  而那些行从没被解析过；
- 用 `DATETIME(6)` 而不是 `DATETIME`：阈值比较是秒级的，但同一秒内「刚写进去」与
  「已超时」的区分能力越细，越不容易在边界上打架（module9 第 3 组就是在 900s/50s 两个点上卡的边界）；
- 成功 / 失败时把该列**清空**（`parse_started_at=None`），让「非空」严格等价于「正在解析」。

### 3.4 幂等靠 MySQL 原子 UPDATE，不靠 Redis 锁

```sql
UPDATE document
   SET status='parsing', attempt_count=attempt_count+1, parse_started_at=now()
 WHERE id=? AND (status IN ('pending','fail') OR (status='parsing' AND parse_started_at < now()-threshold))
```

**为什么不用 `SELECT ... 判断 ... UPDATE`**：两者之间有竞态窗口。两个 worker 同时读到
`status=pending`，然后都去写 —— 两次解析、两份切片。

**为什么不用 Redis 分布式锁**：锁的生命周期与数据不一致。worker 拿到锁之后如果被 `kill -9`，
锁只能靠 TTL 过期；而 TTL 期间那条记录既没被解析也没人再抢。用 MySQL 行锁则**锁与被保护的数据
在同一个事务边界内**，进程死了事务自然回滚，不需要额外的过期机制 ——
这和 P0-1b 把会话级锁从 Redis Lua 锁改成 `SELECT ... FOR UPDATE` 是同一个判断。

验收证据：module9 第 2 组用 **16 个线程同时抢同一条**，结果必须恰好 1 个成功、
`attempt_count == 1`。

### 3.5 Celery 的投递语义：为什么不开自动重试、不用 result backend

| 配置 | 值 | 为什么 |
|---|---|---|
| `task_acks_late` | `True` | worker 崩溃时消息回到队列，而不是被当成「已交付」丢掉 |
| `worker_prefetch_multiplier` | `1` | 预取多条会在 worker 崩溃时让多条消息一起回到队列，配合 `acks_late` 容易放大重复消费 |
| `task_reject_on_worker_lost` | `True` | 配合 `acks_late`：进程被杀时明确拒收而不是静默丢 |
| `task_ignore_result` | `True` | **不配 result backend**。状态真相是 MySQL `document.status`，再存一份只会带来一致性麻烦和白耗内存 |
| 自动重试 | **不开** | 「文件损坏」重试 N 次结果完全一样，只是把 CPU 烧 N 遍。失败一律落到 `status=fail`，要不要再试由人决定（`POST /reparse`） |
| `visibility_timeout` | 900s | 与 `TASK_STALE_PARSING_SECONDS` 对齐：Redis 传输层认为「消息丢了」的时间，不该早于业务层认为「任务超时」的时间 |
| `task_time_limit` / `task_soft_time_limit` | 600 / 540 | 坏文件能把 worker 卡死，软超时先给一次机会 |

软超时抛的 `SoftTimeLimitExceeded` 会被翻译成人话（`_INFRA_FAILURE_HINTS`），
否则用户看到的 `fail_reason` 只有一行英文类名、消息还是空的。
翻译表按**类名**匹配而不是 `except Cake...`：`core/` 不该 import 队列框架，
否则「只想重建向量库」的运维脚本也被迫装 Celery。

### 3.6 macOS 上必须换掉 prefork 池（本版踩得最深的一个坑）

**现象**：worker 起来了、能看到队列、也能收到消息，但**每条任务都在子进程里瞬间炸掉**：

```
ValueError: not enough values to unpack (expected 3, got 0)
  File ".../celery/app/trace.py", line 762, in build_tracer
    tasks, accept, hostname = _loc
```

**根因**（不是 Celery 的 bug，是两个设计的冲突）：

1. billiard 在 **darwin 上默认改用 spawn** 而不是 fork（CPython `bpo-33725`：
   macOS ≥10.14 起，fork 之后执行任意代码不可靠）；
2. 但 Celery 的 prefork 池依赖**父进程里的模块级状态** —— `celery/app/trace.py` 的
   `_localized` 是父进程初始化时填的。spawn 出来的子进程是干净解释器，`_localized = []`；
3. Celery 本来有个补丁 `setup_worker_optimizations()` 来重建这个状态，
   但它只在 `FORKED_BY_MULTIPROCESSING` 环境变量被设置时才执行
   （`celery/concurrency/prefork.py:66`）—— 而 **spawn 路径永远不设这个变量**。
   于是补丁不生效，子进程带着空 `_localized` 去解包，当场炸。

**采用的修法**：在 `worker/app.py` 里按平台选池。

```python
_WORKER_POOL = "solo" if sys.platform == "darwin" else "prefork"
```

**否掉的方案**：设 `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` 强行让 billiard 回到 fork。
否掉的代价：这正是 `bpo-33725` 警告要避免的行为，等于用一个已知不安全的 fork 换掉一个
明确报错的 spawn —— 出错的地方从「任务炸掉」变成「随机死锁」，更难查。

**代价（必须写清）**：`solo` 池 = 任务在 worker **主进程**里跑，因此
`worker_max_tasks_per_child`（防内存泄漏的子进程回收）在**本地开发机上失效**。
服务器是 Linux，走 `prefork`，那套内存保护照常生效。
本机跑验收时内存由开发者自己承担 —— 这是「本地能跑」与「服务器上对」分开处理的取舍。

### 3.7 切片写入顺序：先解析、再删、再写（**不是**先删再解析）

一眼看去「先删旧的、再解析、再写新的」更整齐，但这里刻意反过来，因为中间那段是**数据不可用窗口**：

- 先删再解析：一个大 PDF 要几分钟，这几分钟里该文档**检索不到、引用反查拿不到正文**，
  而在用户看来它只是「重新解析了一下」；
- 先解析再删再写：窗口缩短到毫秒级。

额外好处：解析失败时旧切片**原封不动** —— 而旧切片的内容与本次尝试的是同一个文件，
保留它严格优于把它删掉（fail 的文档仍能被检索到，比「越重试越查不到」合理）。

### 3.8 为什么本版故意让前端处在「对不上」的状态（P0-3b 的由来）

上传接口不再返回 `chunks_added` —— 那个数**在响应那一刻根本不存在**。这不是省略，是异步化的必然结果。
于是前端的旧契约（读 `chunks_added`、按 `source` 路径查切片）在本版之后必然失效。

**为什么不在本版一并改前端**：

1. 一次改动同时跨「后端状态机 + 队列 + 前端轮询」，任何一处出问题都难定位；
2. 前端改造本身要重新设计交互（提交后轮询、按状态置灰按钮、失败原因展示），
   是一个独立的、可独立验收的交付；
3. 后端接口先用 module9 的 HTTP 层测试锁住形状，前端改造时有一个**已经稳定的靶子**，
   否则改前端的每次联调都会同时怀疑两边。

**代价**：本版之后到 p0.3b 之前，前端知识库管理页**不可用**。这是刻意选择的短期断点，
不是「忘了改」。已在 §6 的遗留项里列为第一项。

### 3.9 路径穿越的判定：先 `resolve()`，再比 `parents`

```python
path = resolve_storage_path(storage_path).resolve()   # ← 必须先展开 .. 与符号链接
upload_root = settings.UPLOAD_DIR.resolve()
return path if upload_root in path.parents else None
```

两个容易写错的点：

- **先判断后 resolve 等于没判断**：`upload/../../etc/passwd` 在**字符串层面**确实以 `upload/` 开头；
- **用 `parents` 而不是 `startswith`**：`/a/uploadx` 通过了字符前缀检查，但它并不是 `/a/upload` 的子路径。

验收里用 `README.md` 当靶子（它是仓库里真实存在、可验证的文件），
而**不用 `/etc/passwd`** —— 后者要求测试拥有删除权限才能证明「没被删」，
断一个恒为真的条件等于没断言。

### 3.10 依赖锁定必须 `uv pip compile -o <已存在的 lock 文件>`

**踩过的坑**：直接 `uv pip compile requirements.in -o requirements.lock.txt.new` 再覆盖，
会**重新解析全部依赖**，于是与 celery 无关的一堆包（`emoji` / `filelock` / `fsspec` / `langsmith` …）
也跟着漂移了 85 行。这种漂移极难 review：真正要看的只有 celery 相关那几行。

**做法**：`-o` 直接指向**已存在**的 lock 文件，让 uv 保留既有 pin、只补新增。
结果：本次 lock 的 diff **纯新增** 11 个包（`amqp` / `billiard` / `celery` / `kombu` / `vine` …），
没有一行无关改动。

### 3.11 删掉 `worker-dev` 目标：不要留一个「看起来能用」的假目标

最初写了 `make worker-dev`，用 `watchmedo` 做热重载、并带 `|| ` 兜底。
后来删掉了，两个原因：

- `watchmedo` 属于 `watchdog` 包，**本项目没装**，那个 `||` 兜底会让它在缺依赖时静默退化成
  不热重载的普通启动 —— 用户以为在热重载，实际改了代码没生效，这种「静默降级」比直接报错难查得多；
- 真正需要热重载的是 Web 层（改一行马上看效果）。Worker 改动频率低得多，
  而且它的「热重载」语义模糊：正在跑的任务要不要中断？中断了记录就冻结成 `parsing`。

删掉比留着一个会骗人的目标好。

### 3.12 `worker_alive()` 是个慢调用，所以超时做成配置项

Celery 的 `inspect().ping()` **无从知道有几个 worker 应该应答**，所以只能把窗口开到超时才收
—— 这是它的接口语义决定的，不是实现懒惰。实测：

- 首次调用约 **2.2 秒**（要建立 pub/sub 订阅）；
- 之后每次约 **1.0 秒**（等满 `QUEUE_WORKER_PING_TIMEOUT_SECONDS=1.0`）。

所以：① 这个超时做成配置项而不是写死（写死 5 秒会让监控接口慢到没人调，
写死 0.1 秒会把正常但稍慢的 worker 误判成死了）；② 监控接口的响应里**显式暴露这个超时值**
（`ping_timeout_seconds`），让调用方知道这个接口最慢会慢多少；③ 不查 `active()` / `stats()`
—— 存活探测只该问最小的问题。

### 3.13 为什么入队失败返回 `False` 而不是抛异常

入队是**尽力而为**的动作。如果投递失败就 500，用户会以为「文件没上传成功」→ 于是重传一遍
→ 磁盘上多一份、MySQL 里多一条。所以：

- 返回 `False` + 接口响应里带 `"queued": false` 与一句「可稍后用 reparse 补投」；
- 文件**不回滚**（它已经落盘、记录已经建好，回滚反而制造不一致）。

真相源是 MySQL 的 `status`：投递失败时文档停在 `pending`，Redis 恢复后补投即可。
这也是「不指望 Redis 持久化」的落地方式。

| `DOC_UPLOAD_MAX_BYTES` | `52428800` | 50MB 上限。判定是 `>` 而不是 `>=`，所以**恰好 50MB 可以上传**（验收里验了这个边界） |

| `WORKER_CONCURRENCY` | `1` | 解析是 CPU 密集 + 模型吃内存，并发只会互相抢 |
| `WORKER_MAX_TASKS_PER_CHILD` | `20` | 定期回收子进程防泄漏。**macOS 本地走 solo 池时该值不生效**（见 §3.6） |

### HTTP 接口

| 接口 | 变化 |
|---|---|
| `POST /api/v1/documents/upload` | **改 202 立即返回** `{doc_id, file_name, status:"pending", file_size, file_type, project_id, queued}`；**不再返回 `chunks_added`**；超过上限 → 413；后缀不支持 → 400；同名同项目 → 先彻底清掉旧文档（磁盘 + 切片 + 记录） |
| `GET /api/v1/documents/` | **改读 MySQL**（支持 `?status=` / `?project_id=` / `?limit=` / `?offset=`），响应含 `counts` 四态分布 |
| `GET /api/v1/documents/stats` | 不变（向量库统计） |
| `GET /api/v1/documents/download?doc_id=` | **新增**，`FileResponse` + 原始文件名；路径越权 → 403 |
| `GET /api/v1/documents/{doc_id}/chunks` | **改按 `doc_id` 查**（不再按磁盘路径），按 `chunk_index` 升序 |
| `POST /api/v1/documents/{doc_id}/reparse` | **新增**，202；`success` 的文档 → 409；磁盘文件丢了 → 409 |
| `DELETE /api/v1/documents/{doc_id}` | **改执行三件事**（磁盘 + Chroma + MySQL），顺序刻意是「先删可再生的（切片、文件），最后删那条指向它们的索引」 |
| `GET /api/v1/system/queue` | **新增**，`{queue:{name,broker_ok,depth,unacked,detail}, worker:{ok,workers,detail}, documents:{...}, ping_timeout_seconds}`；broker / worker 不在也返回 200 |

> 路由声明顺序有语义：所有字面量路径（`/stats`、`/download`）都排在参数化路径
> （`/{doc_id}/...`）之前。Express 之外的 FastAPI 同样按注册顺序匹配 ——
> 现在没出问题只是因为段数不同，但一旦将来加了 `GET /{doc_id}`，`/download` 就会被吃掉。

### 新增命令

| 目标 | 作用 |
|---|---|
| `make worker` | 起解析 Worker（池/并发/超时全在 `worker/app.py` 按 settings 配，**命令行不传参**，避免两处配置打架） |
| `make accept` | 跑验收脚本。**要求跑之前没有别的 worker 在跑**（它自己管 worker 生命周期，否则会误杀） |

> `make test`（回归）与 `make accept`（验收）是两件事，写在 Makefile 注释里了：
> 前者打桩、离线可跑、必须永远全绿；后者真链路、需要中间件、测的是「承诺成不成立」。

## 5. 验证证据

### 5.1 验收脚本：计划书 5 条标准逐条实测，全绿

`tests/acceptance_p0_3a.py` —— **一处不打桩**：真 MySQL、真 Redis db1、真 Worker 进程、
真向量库目录，全部走 HTTP 接口。它自己管 worker 生命周期
（起 → kill → 重启 → 停），因为验收第 3 条要求「kill 后重启」。

```
$ .venv/bin/python tests/acceptance_p0_3a.py

MySQL：localhost:3306/rag_qa
队列 ：rag.parse | 当前积压=0
向量库：chroma | 当前总量=15

==================================================================
计划书 5 条验收标准的结论
==================================================================
  1. [成立] 上传 50MB 文件，HTTP 响应立即返回（不含解析耗时） （实测 0.57s）
  2. [成立] 提交后关闭浏览器，任务照常跑完，重开页面状态正确 （5 片）
  3. [成立] 人为让同一 doc_id 入队两次 → Chroma 不出现重复切片 （5 片，与单次解析一致）
  4. [成立] 上传损坏文件 → status=fail + fail_reason 可读，前端能重试
  5. [成立] 手动 kill Worker 后重启，pending 任务继续被消费

断言：55 通过 / 0 失败
```

几条值得单独看的实测数字：

**① 50MB 上传耗时 0.575s，1KB 上传耗时 0.495s** —— 差 0.08 秒。
`耗时由磁盘写决定，不随文件大小爆炸` 这条断言就是这么来的：
如果解析还在 HTTP 里，50MB 的耗时会是分钟级。而且这一条是在 **worker 停着**的情况下测的，
所以「快」不可能是「解析很快」造成的。

**② 关掉浏览器后任务照常跑完。** 具体做法是：用客户端 A 上传 →
`client_a.close()`（等价于浏览器关掉，本进程不再持有该请求）→ 三秒后用
**新客户端 B** 从 MySQL 读状态。

```
  · 浏览器已关闭（连接断开，本进程不再持有该请求）
  >>> 提交后关闭浏览器，任务照常跑完，重开页面状态正确 → 成立 （5 片）
```

**③ 重复入队：两条消息、只有一条真的抢到。**

```
    · 对照：doc_id=67 单次解析得 5 片
    · 两条消息跑完：status=success | 本文件 5 片 | attempt_count=1
```

`attempt_count=1` 是这里的关键 —— 它证明**只有一条消息真正抢到了任务**，
而不是「两条都跑了但因为 `delete_by_doc_id` 幂等所以看起来没重复」。
再补一刀：直接调 `run_parse_task(doc4_id)` → `claimed=False`。
另外顺带钉住一条状态机约定：`reset_for_reparse` **拒绝 `success`**
（否则「重解析」会变成语义模糊的操作：删掉旧切片重建，还是叠加？）。

**④ 损坏文件的 `fail_reason` 是给人看的：**

```
    · fail_reason = 「解析失败或没有可提取文本（文件可能已损坏）：p03a_7bd35e99_坏文档.docx」
```

没有 Traceback、没有裸类名、**指明了是哪个文件**、长度在列宽（512）以内。
「前端能重试」也实测了：`POST /{doc_id}/reparse` → 202、`attempt_count` 递增。

**⑤ kill worker 后 pending 留在原地等。**

```
  · kill worker            （SIGKILL，不是优雅退出）
    · 8 秒后 status=pending | 队列积压 depth=1 unacked=0
  · 重启 worker
    · worker 已重启：['celery@ouyangdingdeMacBook-Pro.local']
  >>> 手动 kill Worker 后重启，pending 任务继续被消费 → 成立
```

kill 掉之后 `worker_alive().ok == False`、`/api/v1/system/queue` 仍然 200 且如实报告
「worker 不在」；上传仍然 202（消息进队列只是没人消费）；重启后自动被消费完，
且 `attempt_count == 1`（没有重复消费）。

## 6. 已知边界与遗留项

1. **前端此刻是坏的（`p0.3b` 必修）**。`frontend/src/api/documents.ts`、
   `stores/documents.ts`、`views/KnowledgeView.vue`、`types.ts` 仍按旧契约
   （`chunks_added`、按 `source` 查切片、删除返回体）编写，从本版起与后端对不上。
   后端接口形状已被 module9 第 9 组锁住，前端改造时有一个稳定的靶子。见 §3.8。

2. **P0-4 的两件事没做**：
   - `GET /api/v1/chunks/{chunk_id}`（引用反查：`chunk_id` → 切片正文 → `metadata.doc_id` → MySQL 取文件名/时间）；
   - `scripts/reindex.py`（扫描 `upload/` 逐个重灌）—— **必须复用 `core/parsing.parse_and_index()`**，
     不允许出现第二套解析逻辑，否则 metadata 字段名会出现第二种写法，而且不会报错。

3. **macOS 本地走 `solo` 池，`WORKER_MAX_TASKS_PER_CHILD` 不生效**（见 §3.6）。
   服务器（Linux）走 `prefork`，内存保护照常。本地跑大量解析时要注意内存不回收。

4. **`worker_alive()` 最慢约 1 秒**（首次约 2.2 秒）。它调用的 `/api/v1/system/queue`
   因此不适合放在高频轮询里。已在响应里暴露 `ping_timeout_seconds`，让调用方知道最坏耗时。

5. **Redis 重启仍然会丢未消费的任务**。这是刻意接受的设计：真相源是 MySQL `status`，
   兜底手段是「手动 reparse」+ 将来的「扫描 pending 补投」脚本。**不做 Redis 持久化**
   —— 那会把一个「尽力而为的队列」变成一个需要保证一致性的存储。

6. **`document` 表的物理清理策略未定**。删除是物理删行（不是软删），
   历史回答对已删文档的引用会查不到 —— 这是 P0-4 决策 D3「引用只存 `chunk_id` 不存快照」
   的既定代价，前端将降级展示「引用内容已随文档删除」。

7. **未做上传并发限流**。同一个人连点 10 次上传会往队列里塞 10 条任务
   （幂等保证不会重复解析，但会白占 worker 时间）。网关侧限流已存在（P0-2 的 `@nestjs/throttler`），
   但它是按请求数限的，不是按「同 doc_id 待处理任务数」。属于 P2-8 的范围。

8. **仍是既有缺陷（本版刻意未修）**：`core/memory_manager.py` 里 `add_exchange` 调
   `_normalize_meta()` 的位置导致轮元数据整体错位一格。与 P0-3 无关，
   修它会污染「问答链路零改动」这条验收证据（§5.4）。修法见
   `iterations/v2.0.0-p0.1-redis-session-store.md` §6.1。
