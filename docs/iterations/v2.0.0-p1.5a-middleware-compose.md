# v2.0.0-p1.5a 本地中间件容器化：MySQL + Redis 起来

- **版本**：`2.0.0-p1.5a`
- **日期**：2026-09-23
- **对应计划**：`docs/PLAN-v2.0.0.md` → P1-5 **a 阶段**（P1-5a）
  —— 计划书 §5 明确它是 **P0-1 的前置**：本地没装 MySQL / Redis，不先把容器起来后面没法开发
- **上游基线**：`v2.0.0-p0.2`（`2.0.0-p0.2`，鉴权网关）
- **一句话**：把 MySQL 与 Redis 用一份 compose 文件在本地跑起来，端口只绑回环地址，
  并配了两级健康检查与一个 12 项自检脚本；**应用仍裸跑，Python / NestJS / Vue 代码一行未改**。

**做了**：

- 新增 `docker-compose.yml`：`mysql:8.0` + `redis:7-alpine` 两个服务，命名卷持久化，healthcheck 分级；
- `.env` / `.env.example` 新增 MySQL 配置段与 Redis 队列分库配置；`PROJECT_VERSION` → `2.0.0-p1.5a`；
- `Makefile` 新增 `infra` / `infra-check` / `infra-logs` / `infra-stop` / `infra-down` 五个目标；`make help` 同步；
- 新增 `scripts/infra-check.sh`：容器状态 + MySQL 账号/字符集/时区/DDL 权限 + Redis 容量策略 + 宿主机端口可达性；
- 修了一个环境问题：本机 Docker Hub registry 端点不可达，给 Docker Desktop 配了镜像加速（见 §3.7）。

**明确不做**（留给后续迭代）：

- **不做应用容器化**：backend / worker / gateway / frontend 的 Dockerfile 与 compose 编排属于 **P1-5b**，
  排在 P0 之后 —— P0 期间应用要频繁改动，裸跑热重载效率高得多；

  本版只保证「库存在、字符集正确、账号可连、有 DDL 权限」；
- **不改任何应用代码**：`config/settings.py` 没加 MySQL 配置项，`MEMORY_BACKEND` 仍只支持 `memory|redis`，
  Python 侧一行未动。配置项先落 `.env`，读取逻辑等 P0-1 一起做；
- 不引入 Celery（P0-3）、不引入 Alembic（P0-1）。

## 3. 关键设计决策

### 3.1 为什么中间件容器化、应用裸跑（决策 D1）

计划书 §11.3 的决策 D1 已定：**A 方案**。理由：

- P0 阶段应用改动频繁，裸跑保留热重载与断点调试；
- 真正缺的是 MySQL / Redis（本机没装），把它们容器化就解决了核心问题；
- 全栈容器化留到 P1-5b，用于端到端验收、演示、以及上传服务器前的最后预演。

**否掉的方案**：一上来就全栈容器化。代价是每改一行代码要么 rebuild 要么配 bind mount，
调试体验明显变差；而这个「环境一致性」的收益，在本地开发阶段本来就用不上（本地根本没有服务器环境要一致）。

### 3.2 端口只绑 `127.0.0.1`

```yaml
ports:
  - "127.0.0.1:${MYSQL_PORT:-3306}:3306"
```

不写 `0.0.0.0` 是刻意的：这两个库只被宿主机上的应用访问，绑全地址等于把 3306 / 6379
暴露给同网段的任何机器。开发机常连公司网 / 咖啡厅网，这是最容易被扫到的默认配置。
将来上服务器时同理 —— 如果 Nginx 在本机，容器端口也不该往外暴露。

### 3.3 Redis 为什么是 `noeviction` 而不是 LRU 淘汰

```
--maxmemory 128mb --maxmemory-policy noeviction
```

直觉上「内存满了淘汰最旧的」更优雅，但这里不行：

- Redis 在本项目的定位是**队列 broker + 短期缓存**（见计划书 §4 数据分层），**不是真相源**；
- 如果开启淘汰，内存压力下 Redis 会**静默删掉队列里的任务**，表现是「某些文档永远停在 pending」，
  而且事后没有任何痕迹可查；
- `noeviction` 下写满会**直接报错**，入队失败能让用户看见、能重试 —— 静默丢数据比报错难查得多。

**代价**：极端情况下（队列积压到 128MB）入队会失败，上传接口会返回错误。
但队列消息只存 `doc_id`，128MB 能容纳的量级远超本项目实际吞吐，
且真到了那一步，说明解析能力已经严重跟不上上传速度 —— 这时候报错反而是正确的信号。

### 3.4 MySQL 的字符集与时区用 command 参数，不用 init 脚本

三个参数一拍即合：

```
--character-set-server=utf8mb4 --collation-server=utf8mb4_0900_ai_ci --default-time-zone=+08:00
```

- **utf8mb4 是硬要求**：中文正文之外，用户往对话里贴 emoji 时 utf8mb3 会直接写入失败；
- **时区必须统一**：不设的话容器默认 UTC，`create_time` 会整体偏移 8 小时，
  这种问题在页面上表现为「消息时间不对」，但排查要一路查到容器时区；
- 用 `command` 而不是 `docker-entrypoint-initdb.d/` 下的 init.sql，是因为 **init 脚本只在数据目录为空时执行一次**，
  改了不重跑，容易造成「配置文件里写了、实际没生效」的隐性不一致。command 参数每次启动都生效。

### 3.5 为什么不用 init 脚本建业务表

`docker-entrypoint-initdb.d/` 常被用来放建表 SQL，这里刻意不用：

- init 脚本**只在首次启动执行**，后续改表结构不会重跑 —— 而业务表一定会改；
- 表的真相必须只有一处：**Alembic 迁移**（P0-1）。两处建表逻辑必然漂移；
- 且第一版库名 `rag_qa` 与 `.env` 的 `MYSQL_DATABASE` 是两个地方，硬编码进 SQL 就等于埋一个脱钩点。

本版只依赖 `MYSQL_DATABASE` 环境变量建库（字符集继承 server 默认值，即上面的 utf8mb4）。

### 3.6 `MYSQL_HOST` / `REDIS_HOST` 做成变量

```bash
# 本地裸跑（本版）：应用在宿主机，连容器暴露的 127.0.0.1
MYSQL_HOST=localhost
# P1-5b 全栈容器化：服务间走容器网络
MYSQL_HOST=mysql
```

这是一个**必须现在就定下的约定**，理由：两种模式下主机名不同，如果代码里硬编码 `localhost`，
切到容器模式时必然漏改一处，而症状是「连不上数据库」这种低信息量报错 —— 排查成本远高于现在就多写一个变量。

### 3.7 踩到的坑：Docker Hub registry 端点在当前网络下不可达

**现象**：`docker compose up` 起不来，`docker images` 里一个字节都没有。

**排查过程**（值得记下来，因为一开始判断错了方向）：

1. 先怀疑代理。`scutil --proxy` 显示系统代理指向 `127.0.0.1:7890`，
   而 `lsof` 看不到 7890 在监听 → 一度以为「代理挂了」；
   **实际是沙箱看不到 Clash 的监听套接字**，用 socket 直连测试才发现 7890 是通的。
   教训：`lsof` 在受限环境下会给出假阴性，别据此下结论。
2. 用 curl 分段测：`google.com` 经 7890 → 302；`hub.docker.com` → 200；
   **`registry-1.docker.io` 无论走代理还是直连都是 `http=000` 超时**。
   → 结论：不是代理的问题，是这个 registry 端点在当前网络下被阻断。
3. 找到可达的镜像源：`docker.m.daocloud.io` → 401（未带 token 的正常响应）。

**处置**：备份 `~/.docker/daemon.json` → 加 `registry-mirrors` → `docker desktop restart` → `docker info` 确认生效。

**另一个把排查带偏的因素**：`docker pull` / `docker compose up` 的输出在**非 TTY 环境（管道、重定向）下会被缓冲**，
看起来「几十秒没有任何输出」，实际在正常下载。中途我因此两次误判为卡死并 kill 掉进程。
后来改成 `docker -D pull ... > 文件` 才看到真实进度。
**教训：判断「卡没卡」要看 `docker images` 的实际落地情况或落盘日志，不能看 stdout 是否安静。**

### 3.8 写自检脚本踩到的两个坑

都是同一类问题的两面：**命令在宿主机与容器之间交接时，参数不会自动跟过去**。

**坑一：变量后面紧跟全角标点，bash 会把它吃进变量名。**

```bash
bad "连不上库 $DB_NAME：$(...)"     # ← 报 DB_NAME?: unbound variable
```

`：` 是 U+FF1A（3 字节），bash 在 `set -u` 下把它的首字节当成了变量名的一部分，
于是去找一个叫 `DB_NAME\xef` 的变量。**报错信息指向变量未定义，实际是解析问题**，很容易查错方向。

修法：中文脚本里**所有变量一律写 `${VAR}` 花括号形式**。
这条已写进 `scripts/infra-check.sh` 的文件头注释，避免下次重犯。

**坑二：写在 docker CLI 前面的环境变量，进不了容器。**

```bash
MYSQL_PWD=xxx docker compose exec -T mysql mysql -urag ...   # ← 容器里拿不到
```

`MYSQL_PWD=xxx` 只留在**宿主机那个 docker 进程**的环境里；
容器内的 `mysql` 客户端是另一个进程，看不到。症状是 `Access denied ... (using password: NO)` ——
**注意 `using password: NO`，说明不是密码错，是密码根本没送到**，这个线索能省很多时间。

修法：`docker compose exec -e MYSQL_PWD=xxx ...`（用 `exec` 的 `-e` 显式注入）。
不用 `mysql -p` 是因为它会往 stderr 打「命令行传密码不安全」的警告，会污染脚本里的输出判断。

### 3.9 为什么自检脚本要检查「建表权限」

`infra-check.sh` 里有一项会真的建一张 `_perm_probe` 表再删掉。看起来多余（能连上不就行了），
但业务表由 **Alembic 迁移**创建（P0-1），如果应用账号只有 DML 权限没有 DDL 权限，
P0-1 一开工就会卡在 `CREATE TABLE` 上，而那时已经写了一堆迁移代码。
**把一个「早晚会撞上」的检查提到现在，成本是 3 行 SQL。**

### 5.2 决定性验证：容器移除重建后数据仍在

这一条才是本版的真正目的 —— 架构文档反复强调「容器销毁资产丢失」，所以要证明 volume 真的生效。
**注意用的是 `down` + `up`（容器被移除后重建），不是 `restart`** —— `restart` 只重启进程、不重建容器，
证明不了 volume 挂载。

```
=== 1. 写入探针 ===
mysql = survived-down
=== 2. down（移除容器，保留 volume）===
 Container rag-mysql Removed
 Network rag-qa-system_default Removed
剩余容器：0 个
剩余 volume：
rag-qa-system_mysql_data
rag-qa-system_redis_data
=== 3. up 重建容器 ===
 Container rag-mysql Started
 Container rag-redis Started
=== 4. 等待健康 ===
两个容器都 healthy（第 3 次轮询）
=== 5. 读回 ===
mysql 读回 = survived-down
redis 读回 = survived-down
```

两个库的数据都在 → **volume 挂载正确**，业务资产不在容器内部。

## 6. 已知边界与遗留项

1. **镜像源是第三方**（daocloud / 1ms.run）。用于本地开发加速可以，但**上服务器要换**：
   服务器（腾讯云）优先用内网镜像 `mirror.ccs.tencentyun.com`，或干脆先把镜像 `docker save`
   传上去再 `docker load`。理由：生产环境从第三方镜像源拉基础镜像是供应链风险。
2. **依赖本机 Docker Desktop 的代理设置**。当前 daemon 走系统代理（Clash 7890），
   而镜像源在国内本可直接访问 —— 多这一跳意味着「Clash 抽风 = Docker 拉不动」。
   如果后续频繁遇到拉取慢，可在 Docker Desktop → Settings → Resources → Proxies 里关掉代理。
3. **`MEMORY_BACKEND` 的取值仍是 `memory|redis`**（代码未动）。`.env` 注释已标记
   「Redis 作为会话真相源」的方案作废，但取值本身留到 P0-1 与代码一起改 ——
   只改注释不改代码会制造新的不一致。
4. **`mysql` 容器没做参数调优**（慢查询日志、连接数上限复核、备份），属于 P2-8 / P2-10 的范围。
   `innodb_buffer_pool_size` 已按 4C4G 预算压到 128M（计划书 §11.1），但**本地开发机上的实际占用没有核对** ——
   本机给 Docker 8G，不构成约束，服务器上要复核。
5. **本版动了一处仓库外的东西**：`~/.docker/daemon.json`（加镜像源）。
   换机器 / 重装 Docker Desktop 后需要重做，故记在此处。原文件已备份为 `daemon.json.bak-p1.5a`。
