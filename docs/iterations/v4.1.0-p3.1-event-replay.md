## 完成判据回填

**「给定 query_id 回放『路由→检索→重排→生成』全链路」→ 达成**：
- `qa_trace_repo.get_trace(query_id)`：按 id 取单行（一行=该轮全链路事实）；
- `replay_timeline(row)`：投影成**六阶段时间线**——route（意图/来源/终端）→
  rewrite（指代改写/改写句/HyDE）→ retrieve（候选清单/bm25/rrf）→ rerank
  （阈值/过滤前最高分/过滤数/返回数）→ generate（usage 归因三列/耗时）→
  verify（grounded/未支撑论断）；
- **只投影不编造**：未发生的阶段标 skipped 并给原因（闲聊/缓存命中轮不检索、
  未启用改写、零召回、校验未开）——不推断"应该发生过"的事件；
- **合规投影**：`GET /api/v1/admin/traces/{query_id}/replay`（require_admin），
  响应含 attribution（owner/session/usage）+ timeline + **audit_refs**（该提问者
  最近 5 条合规事件——登录/权限/额度变更，排查"当时是什么权限"的上下文）。

## 设计拍板

1. **对齐 office D1 的实际经验：不建新事件流表**——trace 单行摘要 + usage 镜像
  （p2.3）已含全链路信息，回放=投影重组（零新表零写入路径）。"audit 合一
  append-only"的原计划形态被 office D1 证明不必要（四源聚合+权限同口径即可）。
2. **audit 投影 = owner 最近合规事件**：audit_log 的动作是用户/KB 管理类，
   与单次问答无直接关联键——投影"这个人当时合规上下文"而非编造关联。
3. **端点挂 require_admin**：trace 是全员运营分析镜像（管理端既有页面的数据源）。
