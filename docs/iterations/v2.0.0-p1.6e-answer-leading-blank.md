# v2.0.0-p1.6e 答案首帧的前导空行

- **版本**：`2.0.0-p1.6e`
- **日期**：2026-10-06
- **对应计划书任务**：不占新的计划格。改的是已有的问答答案产出路径。
- **上游基线**：`2.0.0-p1.6d`
- **进度**：仍是 7/13（计划书第 3 版口径；本项不占格）。下一步仍是 P1-7 TLS。

一次真实使用中出现过「气泡第一行是空行」，之后再没复现。本轮的任务是先判断会不会复现，
会就修。结论：**会，而且是确定性的**，已修。

## 1. 问题与复现

模型偶尔以 `\n\n` 开头。链路里没有任何一处裁掉它：`_stream_answer` 原样吐出每一帧，
`api/routes/qa.py` 原样序列化，前端把增量拼进 `message.content`，气泡是
`white-space: pre-wrap` 的纯文本容器（`MessageBubble.vue` 的 `.content`）。
前导换行于是在渲染层变成空首行。

分两层取证，而不是只读代码下结论。

**后端层**：打桩 LLM 让首帧输出 `"\n\n你好，这是答案。"`，跑真实的 `stream()`：

```
帧序列： ['meta', 'chunk', 'chunk', 'done']
首帧 content repr： '\n\n你好，这是答案。'
首帧以换行开头？ True
落库答案 repr： '\n\n你好，这是答案。第二段。'
落库答案以换行开头？ True
```

注意第二行结论：**不只是当下显示错了，落库正文也带着它** —— 刷新后从历史读回来照样空一行。

**渲染层**：用气泡里真实生效的 CSS 渲染两段文本，数行盒（`Range.getClientRects()`）。
判据不是「长度对不对」而是**行盒数量**：

```
A 无前导换行    行盒=1  高度=26px
B 前导 \n\n     行盒=3  高度=77px    ← 多出两行空行
C 只有 \n\n     行盒=2  高度=51px    ← 一个只有空白的圆角气泡
```

C 就是现场症状：首帧恰好整包是 `\n\n` 时，前端把「正在思考」的占位换成了内容（`"\n\n"` 是真值），
于是占位消失、气泡里什么都没有。

## 2. 修法

在 `core/rag_chain.py` 加 `_strip_leading_blank()`，并让**答案变成结果的那几处**都过它：

- `_stream_answer()`：首帧前导空白裁掉；整包都是空白时**这一帧不发、也不算「已开始」**，
  等真正的内容到达。中间与结尾的换行一律不动。
- `_finish_cached()`：缓存回放路径（旧缓存条目里可能就存着带空白的答案）。
- `query()`：同步链路的两处 `answer`，与流式同口径。

只裁开头、不做全文 `strip()`。全文 `strip()` 会吃掉结尾换行与正文里的缩进，
而且它改的是「答案长什么样」，不是「首行是不是空的」。这里的边界要卡在最小：

```
模型输出 "\n\n你好"          →  "你好"
模型输出 "第一段\n\n第二段"   →  原样（中间的换行是内容的一部分）
```

## 3. 关键设计决策

**① 为什么在后端裁，不在前端裁。** 前端裁只能改「当下这一屏」；落库正文仍是脏的，
刷新后从历史读回来又会冒空行。而且答案有四个出口（流式增量 / 缓存回放 / 同步返回 / 落库正文），
前端最多管住一个。放在后端唯一入口，四个出口自动一致。

**② 为什么不用 CSS 解决。** `white-space: pre-wrap` 换来的是「模型怎么排版就怎么显示」，
这正是纯文本气泡想要的行为。为了一个前导换行把 `pre-wrap` 换成别的，等于为了治一个症状
改掉整条渲染契约，还赔上正文里的换行与缩进。否掉。

**③ 为什么「整包空白不发帧」比「发一个空帧」好。** 发空帧会让前端提前结束「正在思考」占位，
出现一个空气泡（就是上面 C 那一行测出来的东西）。不发帧则占位继续显示到真有文字。
代价：前端那段时间多转一会儿 —— 但它本来就在转。否掉的另一个做法是发一个空格，
那是把「看不见的空行」换成「看不见的空格」，问题还在。

**④ 用量统计不受影响。** 循环里 `_extract_usage()` 仍逐帧调用，包括被跳过的空帧 ——
末帧常带 `usage` 而 `content` 为空，跳过它就漏账。

## 6. 已知边界与遗留项

1. **历史脏数据不在本轮清理范围。** 修复只作用于新产生的答案。已经在库里的那一条（带前导换行）仍会
   在历史里显示空首行。要顺手洗掉的话：

   ```sql
   UPDATE chat_message SET content = REGEXP_REPLACE(content, '^[[:space:]]+', '')
   WHERE role = 'assistant' AND content REGEXP '^[[:space:]]';
   ```

   `LTRIM()` 只去空格不去换行，所以必须用 `REGEXP_REPLACE`。**本轮没有执行**：
   它改的是历史业务数据，应该由人确认过再跑。
2. **Redis 里的旧问答缓存条目**同样带脏答案。缓存有 LRU 上限（100 条），
   自然淘汰即可；要立刻干净就 `bump_kb_version()` 或清 `db0`。
3. **答案仍是纯文本展示，不渲染 Markdown**（承接 `p1.6c` 的结论）。所以本次不需要考虑
   「裁掉开头空白会不会破坏 Markdown 语义」—— 现在根本没有 Markdown 语义。
   将来真上 Markdown 渲染时，这里要重新看一眼。
4. 只在「答案整体」的开头裁。若模型在一句话中间吐了多余空行，**不动** ——
   那属于内容质量问题，不该由这条管线代劳。
