## 3. 关键设计决策

### 3.1 看板**自带对账行** —— 页面上「数字可信」的来源

15a 定的对账恒等式（全库 = 按人 + 未归属）不只活在测试里：
看板底部有一行「对账：全库 X input = 按人 Y + 未归属 Z  ✓」，
不等式不成立时 badge 变 ⚠。一个漏算自己站出来的看板，
比一个「每次都要人去跑测试才知道对不对」的看板可信得多。

### 3.2 `/quota/me` 的响应里**没有**「还能不能问」字段

15c 把 `OVER_ACTIONS` 锁死在 notify，但那只是判据层。
如果端点顺手返回一个 `can_ask: true`，前端早晚会拿它渲染一个禁用按钮。
所以端点层同样刻意缺席 —— 测试断言响应键里没有
`can_ask / allowed / blocked / remaining_ask`。
**要让「不会阻断」这件事稳定成立，每一层都不能给那扇门装把手。**

### 3.3 横幅 fail-open，鉴权 fail-closed —— 方向相反，各有理由

横幅拉不到（接口挂了/版本旧了）就静默不显示：它只是提醒，
为它在页面顶上摆一块「加载失败」的代价大于收益。
这与鉴权「拿不到就当没有权限」方向相反 —— 两条都是有意的选择。

### 3.4 前端零判定

看板的 `usage_percent / status / status_label` 全部后端算好；
横幅的 `banner` 是后端原文。15a「同一字段两个口径」的教训
在 15d 的两处 UI 上都以「前端只渲染」收口。

## 5. 已知边界

1. 横幅**登录时拉一次**，不做轮询 —— 月中额度被改小的人下次登录才看到
   （为一个提醒加轮询，代价大于收益）。
2. 管理员**只能主动打开看板**才知道谁超了 —— 没有邮件/企微/钉钉推送
   （§15d 明确不做；这是本项最大的缺口，计划书原文写明）。
3. 看板未做导出/分页 —— 当前 10 人规模不需要，人多时再加。
