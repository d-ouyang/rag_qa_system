## 1. 范围

**这一版只做一件事**：修 `add_exchange()` 里 `_normalize_meta()` 的调用位置错误，
让「每轮元数据」与「轮」严格一一对应。

顺带做的两件（都是被这次修复牵出来的，不做就等于留下新的雷）：

- 补一组回归断言（两个后端各跑一遍），并做了**反向验证**（把 bug 还原回来看测试红不红）；
- 修 `tests/test_module5_rag_chain_api.py` 依赖默认存储后端的问题 —— 它会在 `.env` 切成
  `mysql` 后连上**真实业务库**跑单元测试，既产生假失败，又会归档真实会话。

**明确不做**：

- **不写存量数据迁移脚本**。已经错位的历史会话读出来还是错的，本次不修数据、只修代码路径。
  理由：会话是可重建资产，用户已明确表示「不在乎那个会话，我可以重新生成测试」；
  而为了一批可重建的脏数据去写一次性迁移脚本，会把「数据修复」这件事变成长期维护负担。
- **不改 `chunk_id` 契约、不动检索链路、不动前端**（后端语义修复，前端零感知）。
- **不碰 module9**（用户指示本轮不跑；其全表清空仍是遗留项，见 §6）。

## 3. 关键设计决策

### 3.1 为什么这个 bug 能潜伏三个子版本（本节是这版最值钱的部分）

它从 `p0.1` 就在了。`p0.1` 的迭代文档 §6.1 和 CHANGELOG 修订表里都**明确登记过**，
写着「为保住『业务侧零改动』这条验收证据不修，修法已在文档中写明」。
然后 `p0.1b` / `p0.3a` / `p0.3b` / `p0.4a` / `p0.4b` 五个版本、上千条断言，没有一条抓到它。

原因是**它的现形条件极其刁钻**，三个条件必须同时成立：

1. **必须多轮**。单轮写入时 `expected = len(messages)//2` 恰好等于 1，补一个空占位再 append，
   最后被 `_trim()` 的防御分支砍掉头部 —— 结果**恰好是对的**。所以「写一轮、读一轮」的测试永远绿。
2. **中间必须有不带 meta 的轮**。如果每轮都带 meta，错位后的数组内容虽然错序，
   但「看起来每轮都有引用」，肉眼和粗粒度断言都发现不了。
3. **必须走「刷新」路径**。首屏渲染用的是流式响应里那一帧 meta（它是当轮直接给的，不经过存储），
   **所以用户当下看到的引用是对的**。只有刷新页面、走 `GET /sessions/{id}` 回填历史时，
   才会读到错位后的数组。

这三条凑齐，正好就是用户那句报障：

> 「我有个会话 #6cdde4e3，我发现只有第一次提问有数据引用，后面都没有。」

**教训（写给三个月后的自己）**：一个「按索引对齐两个数组」的不变量，
如果只在**单元素**和**全等长**两种极端下测过，那它基本等于没测。
这次的断言刻意写死轮号（`metas[0].get("intent") == "i1"`），
并且**复刻线上回填逻辑**（`metas[i // 2]`）而不是另写一套更"优雅"的取法 ——
测试里另写一套取法，等于给 bug 开了一扇后门。

### 3.2 根因推演（把每一次写轮都摊开看）

修复前，每轮写入都会做三件事，净效果是**把最老那轮的 meta 挤掉**：

```
写第 N 轮时：
  ① append 两条消息            → 轮数变成 N+1
  ② _normalize_meta()          → expected = N+1，于是补 1 个空占位（凭空多一个）
  ③ append 本轮 meta           → 数组长度 N+2，比轮数多 1
  ④ _trim() 末尾防御分支        → 从头部砍掉 1 条  ← 砍掉的是最老那轮的 meta
```

连写 3 轮（第 2 轮故意不带 meta）实测：

```
期望： [轮1meta, {}, 轮3meta]
实际： [{}, {}, 轮3meta]        ← 第 1 轮被顶掉
```

连写 5 轮实测（更直观）：

```
实际： [{'intent': 'i3'}, {}, {'intent': 'i4'}, {}, {'intent': 'i5'}]
                                                 ↑ 前两轮 meta 已蒸发，中间留空洞
```

修法是一行的位置调整：`_normalize_meta()` 移到 `append` **之前**。
这样它补的是「历史遗留的稀疏数组」，补完再 append 本轮，长度恰好等于新轮数。

**为什么选「移动调用位置」而不是「改 `_normalize_meta` 的语义」**：

- 否掉的方案 A：让 `_normalize_meta` 接受一个「目标轮数」参数，调用方算好再传。
  代价：把不变量的维护责任推给每个调用方，未来任何新调用点都可能算错。
- 否掉的方案 B：删掉 `_normalize_meta`，改成在**读取侧**（`get_exchange_meta` / 历史接口）
  每次动态补齐。代价：读路径变重，而且 v1.0.0 存量稀疏数据需要另一套兜底；
  更重要的是「写入即保证对齐」这个不变量一旦放弃，就要在每个读取点重复它。
- 选的方案：保持 `_normalize_meta` 语义不变（"补齐历史"），只纠正调用时机。
  代价是**这个约束只能靠注释和文档守住** —— 所以我在方法 docstring 里写了 ⚠️ 警示，
  并且补了能抓住它的断言。这是这类"顺序依赖"问题的通用代价，没有编译期解法。

`_trim()` 末尾那条防御分支（`len(exchange_meta) > turns` 就砍头部）**保留不动**：
修复后正常路径不会再触发它，但存量错位数据仍要靠它兜底，删掉会让老会话直接越界。

### 3.3 反向验证：先证明测试真的能抓住它

改完代码测试全绿，只能说明「代码和测试当下不矛盾」，说明不了「测试有效」。
所以我把 bug **临时还原**（把那一行挪回原位）再跑一遍：

```
修复前： 第 3B 组 8 条 FAIL（memory 4 + redis 4）   结果：119 通过 / 8 失败
修复后： 第 3B 组全绿                                结果：127 通过 / 0 失败
```

失败的正是「第 1 轮元数据还在」「回填后第 1 轮拿到自己的引用」「引用只落在它该在的轮上」
「续写 2 轮后前 3 轮原地不动」这四条 —— 也就是**真正描述这个不变量的那几条**，
而「元数据条数 == 轮数」这种粗粒度断言**在 bug 状态下依然是绿的**
（因为 `_trim()` 的防御分支把长度修回了正确值，只是内容错了）。

**这正是为什么不能只断言长度。** 那一条当时差点就只写长度了。

### 3.4 为什么必须再走一次 HTTP 端到端

单元测试跑的是 `MemoryManager`，跑不到「接口层按 `轮号 = 消息下标 // 2` 回填」这段代码。
而用户看到的症状恰恰发生在那里。所以补了 `scripts/e2e_p0_4c_meta.py`：
连问 3 轮 → 重取历史接口 → 逐轮打印引用。

实测结果（关键证据，三条引用各自对应自己的问题，没有串行）：

```
第 1 轮（问：入职申请具体怎么填写？） 引用 5 条 ['293:0', '293:1', '290:2', '290:1', '292:1']
第 2 轮（问：试用期转正申请怎么走？） 引用 5 条 ['292:0', '290:1', '290:2', '293:1', '292:1']
第 3 轮（问：离职手续需要办哪些？）   引用 5 条 ['291:1', '290:1', '290:2', '291:0', '293:1']
结论：每一轮刷新后都拿回了自己的引用 ✓
```

第 1 轮命中 293:*（入职文档）、第 3 轮命中 291:*（离职文档）——
**如果还在错位，这里会出现「离职问题挂着入职引用」**。

### 3.5 顺带修掉的：单元测试会连真实业务库

改完代码跑全量回归时，module5 冒出 2 条 FAIL：`会话计数正确` / `清空后计数减少`。
一开始以为是自己的改动引起的，用 `MEMORY_BACKEND=memory` 重跑 → 44/0 全绿，
确认**与本次修复无关**，根因是另一件事：

`tests/test_module5_rag_chain_api.py` 第 1 组写的是 `MemoryManager(max_turns=3, ttl_seconds=3600)`，
**不传 store → 按 `settings.MEMORY_BACKEND` 建**。本项目 `.env` 在本次排障中从 `memory` 改成了
`mysql`（这是为了让会话真正落库），于是这组单元测试就：

1. 连上了**真实业务库**，`session_count() == 2` 被库里既有的真实会话顶翻（假失败）；
2. 更糟的是后面 `cleanup_expired()` 会把真实会话**一并归档**（测试污染业务数据）。

修法：显式注入 `MemorySessionStore`，并把 TTL 同步下传（Manager 与 Store 各说各话是踩过的坑）。
**单元测试既不该碰业务库，也不该随 `.env` 漂移** —— 这两条是这次才真正吃到的。

> 排障顺序上有个值得一提的点：这 2 条 FAIL 出现在我刚改完核心代码之后，
> 第一反应自然会往「我改坏了」上想。判据是「把它和我的改动解耦」——
> 换个环境变量重跑，立刻就能区分「回归」和「环境基线漂移」。
> 这次省下的时间，比凭直觉在 `memory_manager.py` 里翻来覆去找要划算得多。

### 3.6 MySQL 后端为什么不需要跟着改

`MySQLSessionStore` 把 `exchange_meta[i]` 挂在该轮 assistant 行的 `turn_meta` 列上，
`load()` 用 `turn_meta IS NOT NULL` 还原。担心过一件事：空 dict 占位 `{}` 落库后
会不会被当成 NULL、导致 `load` 回来又变成稀疏数组？

不会 —— `sa.JSON(none_as_null=True)` 只对 Python `None` 生效，`{}` 是合法的空 JSON 对象，
落库是 `{}` 不是 `NULL`。所以「等长数组」这个不变量能穿透 MySQL 后端。
这一点在 module8（62 项）与本次端到端（后端就是 mysql）中都已被覆盖。

## 6. 已知边界与遗留项

1. **存量错位数据不修**。修复只保证「之后写入的会话正确」，历史会话读出来仍是旧的错位数组。
   用户已明确表示可重建，故**不写迁移脚本**（理由见 §1）。
   若将来要修，正确做法是一次性 SQL：按 `seq` 重排 `turn_meta`，而不是在代码里加兼容分支。
2. **`module9` 仍是全表清空**（`sa_delete(document_table)` 不带 `WHERE`），会抹掉开发机真实文档记录。
   本轮按用户指示未跑，也未改。跑完 `make test` 需 `make reindex-apply` 恢复演示数据。
   （module10 已在 `p0.4a` 收窄为前缀过滤，可照搬。）
3. **module8 同样连真实 MySQL**，是否有与 module5 相同的污染风险未排查。
   它的定位就是测 MySQL 后端，连真库是刻意的，但**是否做了数据隔离**尚未确认。
4. **`_normalize_meta()` 的调用时机约束只有注释和断言守着**，没有编译期保障。
   已被断言覆盖（还原即红），但未来若有人重写 `add_exchange`，需重新确认。
5. **后端进程与 Celery worker 共用同一 Chroma `persist_directory`** 的老问题依然存在
   （worker 写入不进后端 HNSW 索引，表现为「明明解析成功了却检索不到」，重启后端即恢复）。
   本次排障中它是导致「上传了知识库却答不知道」的**第二个独立原因**，
   与本次代码修复无关，根治要等 P1-5b 容器化后做进程隔离。

## 附：这次排障还原出的三个独立问题

用户一次报障里其实叠了三个问题，彼此无关，值得分开记 —— 因为它们各自的排查路径完全不同，
捆在一起看会互相误导（我当时就一度把「检索不到」当成「元数据错位」的后果）：

| # | 问题 | 性质 | 处置 |
|---|------|------|------|
| 1 | 数据库里看不到会话数据 | 配置：`.env` 是 `MEMORY_BACKEND=memory` | 改 `mysql` + 重启（本次已完成） |
| 2 | 同一会话只有第一次有引用 | **代码 bug**：`_normalize_meta()` 调用位置 | **本次修复** |
| 3 | 上传了知识库却回答「不知道」 | 运维/架构：后端进程 Chroma 索引陈旧 | 重启后端即恢复；根治在 P1-5b |

问题 3 的诊断过程值得一提：`total_chunks=18` 看起来完全正常，
**因为它是读元数据得到的，不走索引** —— 所以「库里有数据」这个数字证明不了「能检索到」。
真正的判据是拿一个**新进程**直接跑 `similarity_search_with_score()`：
新进程能召回（score 0.8267 / 0.8554），在线后端零召回 —— 差异只能来自进程内索引状态。
