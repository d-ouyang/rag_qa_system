## 3. 关键设计决策

### 3.1 为什么把存储拆出去，而不是在 MemoryManager 里 `if backend == "redis"`

v1.0.0 的 MemoryManager 同时干两件事：**会话语义**（轮数裁剪、元数据与消息按轮对齐、编辑重发的截断点取偶）和**存储实现**（dict + threading.Lock）。前者是经过测试、语义微妙的部分；后者是随时会换的部分。

拆开后换后端只改一行配置，逻辑层与所有调用方零改动。代价是多了一层间接（多一个 `load → 改 → save` 的往返），换来的是「换存储不碰语义代码」。

### 3.2 为什么存储接口是「整条会话快照」而不是「单条消息 CRUD」

读写模式天然是「一轮问答 = 读一次全部历史 + 写一次全部历史」，没有「单独改第 3 条消息」的场景。存整条快照的好处：

- 一次 `HSET`（Redis）或一次赋值（内存）写完，**天然原子**，不会出现「消息写进去了、元数据没写进去」的半截状态；
- 避免小 key 爆炸：10 轮对话按消息拆 key 要 21 次往返，整条只要 1 次。

代价是每次写要序列化整条，所以配了两个上限：`MEMORY_MAX_TURNS`（轮数）与 `MEMORY_MAX_SESSION_BYTES`（字节，默认 256KB，防「粘贴长文档」把单会话撑成大 key）。

### 3.3 Redis 数据结构：为什么是 HASH 而不是一条 STRING

```
rag:session:{id}   HASH   messages / exchange_meta / session_meta / usage / last_active
rag:sessions       ZSET   member=session_id, score=last_active（会话索引，按活跃排序）
rag:lock:{id}      STRING 会话级写锁（SET NX PX + token）
```

- 按 field 拆开，将来做「只取用量」「只改置顶」时不用反序列化整条；
- TTL 交给 Redis 自己（key 级别 `EXPIRE`），语义比应用层惰性判断更可靠：进程全挂了 key 照样准时消失；
- 索引 ZSET 解决了「列出全部会话」的需求，但**过期 key 不会自动从 ZSET 摘除**，所以读的时候惰性校验（`EXISTS` 批量）+ 顺手 `ZREM`，另给 `purge_expired()` 做批量清理。这是这套设计里唯一需要「补偿逻辑」的地方，写在代码注释里了。

### 3.4 分布式锁：为什么用 SET NX PX + Lua 释放，且拿不到锁不报错

- 临界区只有「读快照 → 改 → 写回」，毫秒级，单实例 `SET NX` 足够（多 master 才需要 Redlock 那套共识）；
- 释放必须用 Lua 比对 token：持锁进程若因 GC 停顿超过锁 TTL，锁会被别人拿走，此时它再 `DEL` 删的就是**别人的锁**，会出现两个进程同时持锁；
- **拿不到锁时降级为无锁执行 + WARN 日志**，而不是抛错。取舍是明确的：丢一轮记忆比让用户看到 500 可接受。这条写在文档里而不是藏着 —— 因为它是「有意的降级」，不是遗漏。

### 3.5 内存预警：分级、动作、以及为什么 fatal 不拒绝服务

Redis 是**共享资源**（同机其他服务也在用），但它满了之后的表现是**静默的**：会话写不进去，用户那边只是「模型失忆了」。所以必须在水位到顶之前就分级：

| 级别 | 阈值 | 动作 |
|------|------|------|
| ok | < 70% | 无 |
| warn | ≥ 70% | WARNING 日志（只在级别变化时打一次，防刷屏） |
| critical | ≥ 85% | ERROR 日志 + 主动清理过期会话索引 |
| fatal | ≥ 95% | CRITICAL 日志 + **写入降级为只读保护**：新会话不写记忆，问答照常返回 |

**fatal 选择「只读降级」而不是「拒绝服务」**，理由：会话记忆是增强项，不是核心链路 —— 没有历史上下文，RAG 问答照样能回答；反过来因为「存不下历史」给用户 500，那才是真故障。水位回落（< critical）自动解除保护，不需要人工重启。

水位基准的诚实之处：Redis 没设 `maxmemory`（=0，等于无上限）时用 `REDIS_MEMORY_ASSUMED_MAX_MB` 折算比例，并在返回值里标注 `ratio_basis: "assumed"` —— 不把估算值伪装成事实。

### 3.6 写入失败为什么不让问答 502（`MEMORY_DEGRADE_ON_ERROR`）

Redis 写失败（内存满 / 网络断）时默认**吞掉异常 + 记数告警**，这一轮记忆丢掉，问答正常返回。同时命中 OOM 时立刻进入只读保护，避免继续冲击已写满的 Redis（否则每个请求都要等一次写超时）。

### 3.7 顺手修掉的两个 v1.0.0 隐患

1. **读操作不再隐式创建会话**。v1.0.0 的 `get_messages("随便一个 id")` 会凭空创建一个空会话；换 Redis 后还会真的写一个空 key + 索引项，在前端会话列表里出现「点进去什么都没有」的幽灵条目。现在读就是读，不存在返回空。
2. **元数据与消息真正按轮对齐**。v1.0.0 只在「传了 meta」的轮 append 元数据，一旦中间某轮没带 meta，后面所有轮的元数据都会整体前移错配（引用资料显示到别的问题上）。现在 `_normalize_meta` 保证 `exchange_meta` 与轮等长（缺的补空占位）。

### 3.8 读会话列表不续命

`store.load(session_id, touch=...)` 区分两类读：看历史（touch=True，续 TTL，与 v1.0.0 一致）与翻会话列表/统计（touch=False）。否则有人反复刷新列表 = 给所有会话无限续命，「闲置过期」形同虚设。

### 新增接口：`GET /api/v1/system/memory`

返回 `backend / max_turns / ttl_seconds / max_session_bytes / degrade_on_error / store{...} / health{...}`；Redis 后端额外带 `redis_memory{ level, used_ratio, ratio_basis, used_memory_human, maxmemory_policy, thresholds, advice[] }`。

**为什么单开一个接口而不是塞进 `/health`**：`/health` 会被探活/负载均衡高频调用，必须保持轻量；本接口涉及 `INFO memory`、key 采样等相对昂贵的操作，适合分钟级抓取。混在一起会让探活变成压测。

监控接法：`redis_memory.level` 非 `ok` 即告警。

### 5.1b 补强：走真 socket 的「准真实」联调（43 项）

module6 用进程内 `fakeredis` 验「语义对不对」，但它有个**结构性盲区**：
数据活在测试进程的内存里，所以**永远验不出「进程重启后数据还在不在」**——
而这恰恰是 P0-1 存在的全部理由。语义一致不蕴含重启不丢数据。

所以补了 `tests/test_module7_redis_over_tcp.py`：用 `fakeredis.TcpFakeServer`
起一个**真的监听端口的服务**，再用**真的 redis-py 客户端**经 TCP 连上去。

```
$ .venv/bin/python tests/test_module7_redis_over_tcp.py
结果：43 通过 / 0 失败
```

| 组 | 验的是什么 | 代表断言 |
|----|-----------|----------|
| 0 | 真 TCP 往返 | 客户端 `PING` 通；服务端确认是 HASH 5 field / TTL / ZSET |
| 2 | **换客户端 = 换进程** | 新客户端 + 新连接池读到旧客户端写的数据 |
| 3 | **P0-1 验收**：换 Manager 实例 | 历史 4 条消息、置顶、标题、用量、token 明细全在 |
| 4 | Lua 锁在真连接下可用 | 5 线程并发读改写，5 条一条不丢 |
| 5 | 监控失效 ≠ 拒绝服务 | `INFO` 读不到时 `level=unknown` 且**不**进只读保护，写入照常 |
| 6 | 连接不可达降级 | 读返回 `None`、`save` 吞异常，问答链路不中断 |

**顺带修掉的两个坑**（都写进文件注释了）：

1. `ThreadingMixIn` 的 handler 线程默认**非守护**，而 redis-py 连接池一直攥着 socket 不放
   → 每个连接一个非守护线程 → 脚本跑完**退不出去**。修法：`server.daemon_threads = True`，
   收尾时显式 `close()` 连接池。
2. 我第一版断言把用量写在 `sessions[i]["requests"]`，实际在 `sessions[i]["usage"]["requests"]`——
   用量是 `add_usage()` 单独累加的，`add_exchange()` **不管 token 统计**（这是接口分层，不是 bug）。

**这轮还顺手改进了一处接口契约**：`RedisMemoryMonitor.inspect()` 原先在 Redis 不可达时
只返回 `{level, reason}`，字段形状随连通性变化——消费方（前端仪表盘 / 外部监控）每次都得写两套解析；
而且 Redis 挂掉正是最需要可执行建议的时刻，原来这一支一句建议都没有。现在约定：

> **`level` / `reason` / `thresholds` / `advice` / `checked_at` 恒在**；
> 只有比值与内存量这类「读不到就是读不到」的字段才允许缺失。

并加了反向断言：`unknown` 绝不套用 `ok` 的「水位正常，无需处理」话术 ——
`unknown` 是「没读到」，不是「读到了且正常」，混起来会掩盖故障。

## 6. 已知边界与遗留项

1. ~~**本机没有 Redis，未做真实 Redis 集成测试**~~ → **已部分补上**，见 5.1b：
   module7 用 `TcpFakeServer` + 真 redis-py 客户端走真 socket，已覆盖连接池、pipeline、
   Lua 锁、TTL、以及「换进程数据仍在」。
   **仍未覆盖**（必须有真实 Redis 实例）：
   · 真并发压力下连接池的表现（`max_connections=20` 够不够）；
   · `INFO memory` 的真实字段与数值（本机 fakeredis 不支持 `INFO`，所以 `level=unknown` 分支
     反而被充分验证了，但 `ok/warn/critical/fatal` 是拿 `_FakeInfoRedis` 注入验的）；
   · 真实 Redis 版本的 `MEMORY USAGE` 支持情况（已在 `stats()` 里单独兜底）。
   → P1-3 部署起 `redis:7-alpine` 后补一次真实联调。
2. **`MEMORY_BACKEND` 目前是「本地 memory、生产 redis」两套环境**，切换靠改 `.env`。
   切换后行为差异（TTL 由 Redis 兜底 vs 应用惰性回收）已在文档与代码注释中标注。
3. **索引 ZSET 的残留清理是补偿式而非事件式的**：没上 Redis keyspace notification（要额外订阅、
   且实例重启会丢通知），选择「读时惰性校验 + 定时清理」。会话量到十万级时这里会是第一个瓶颈。
4. **Redis 是多实例部署的必需项**：`MEMORY_BACKEND=memory` 下多 worker 会各存各的历史，
   表现为「聊着聊着模型失忆」。这条不是新问题，但现在有了明确开关与文档。
5. `models/` 软链在容器内会失效 —— 属于 P1-4 的范围，本版未动。

### 7.1 方案变更：会话真相源从 Redis 改为 MySQL

**这一条不是补漏，是架构级返工。** 记在这里而不是新开子版本号，是因为 `CHANGELOG.md` 约定
「子版本号 = 计划书任务编号，返工不新开号」—— P0-1 这项任务的目标变了，但编号不变。

#### 变更原因

第一轮把 Redis 当会话真相源，是**数据分层错位**：

1. **可靠性错位**：Redis 是内存库，实例重启、内存驱逐、容量保护都可能让数据消失；
   而会话与问答记录是永久业务资产，不该交给一个随时可能丢数据的组件；
2. **能力错位**：会话挪进 Redis 之后，SQL 能做的事全做不了 —— 按用户查、按时间聚合、
   用量对账、质检抽样、以及规划中的 Agent 审计留痕，全都没有落脚点；
3. **自相矛盾**：本轮自己实现了 Redis 三级水位预警 + fatal 只读降级（写不进去时降级但不 502），
   这等于承认「它可能写不进去」。让永久数据依赖它，逻辑上说不通。

调整后：**MySQL 存业务真相，Redis 只做队列 broker 与短期缓存，Chroma 存向量，原始文件落磁盘 volume。**

#### 保留了什么（这部分没白做）

| 保留项 | 为什么还能用 |
|---|---|
| `core/session_store.py` 的 `SessionStore` 抽象与工厂 | **当初拆这一层的直接目的就是「换后端不动业务」**，本次变更恰好验证了它：`memory_manager` / `rag_chain` / `qa.py` 依然一行不改 |
| module6 的契约测试（107 项） | 断言写的是接口语义，不是 Redis 实现细节；改为 `[memory, mysql]` 参数化即可复用 |
| `core/redis_monitor.py` 与三级水位机制 | Redis 现在只做队列，但**队列 broker 一样会被写爆**（积压任务体积不可控），水位预警与只读降级继续有效 |
| `core/redis_store.py` 的连接池 / 键前缀 / 超时配置 | 队列与将来缓存类场景复用同一套连接配置 |
| module7（`TcpFakeServer` 走真 socket，43 项） | 验证的是 Redis 客户端的真实语义，与「存什么」无关 |

#### 退役了什么

- **`RedisSessionStore` 不再作为生产会话存后端**，代码标注 deprecated 暂留（module7 仍依赖它做 Redis 语义验证），
  MySQL 版稳定后删除；
- `MEMORY_BACKEND` 的取值语义变更：`memory`（本地/测试）| `mysql`（生产真相源），
  `redis` 从中移除（再留着会误导后来者以为 Redis 能当真相源）。

#### 迁移安排

改由 `docs/PLAN-v2.0.0.md`（第 2 版）P0-1 承接，要点：

- 新增 `MySQLSessionStore`，实现同一套 `SessionStore` 接口，内部把整条快照 diff 成行级写入；
- 会话级锁从 Redis Lua 锁改为 `SELECT ... FOR UPDATE`（锁与被保护数据在同一事务边界内，比跨进程分布式锁简单且更可靠）；
- 表结构含 `user` / `folder` / `session` / `chat_message` / `document` 五张，一次到位避免二次迁移；
- 会话 TTL 改为**软过期**（超期 `load` 返回 None，但不物理删行）—— 永久业务资产不该被 TTL 抹掉，
  物理清理留到 P2-10 明确保留策略后再做。

#### 代价（诚实记下来）

- **一轮实现作废**：`core/redis_store.py` 的会话读写路径、HASH + ZSET 索引设计、Lua 锁、
  「读会话列表不续命」等设计不再用于生产，这部分工作量是沉没成本；
- **多一个组件要运维**：MySQL 比 Redis 重（内存、备份、迁移、连接数都要管）；
- **写入延迟变高**：整条会话快照 → 行级 diff 写库，比 Redis 一次 HSET 慢；
  量级上仍远小于 LLM 生成耗时，可接受；
- **必须重建向量库**：新方案要求 Chroma metadata 带 `doc_id`，现有向量数据缺这一项（计划书 P0-4）。
