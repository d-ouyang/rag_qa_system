## 3. 关键设计决策

### 3.1 「不可改不可删」做在表结构上，不是靠自觉

三道结构性约束，任何一道单独都不够：

1. **仓储层没有 `update_log` / `delete_log`**，也不导出任何以 `update`/`delete`/`purge`/`truncate` 开头的名字。
2. **表里没有 `update_time`、没有 `deleted_at`** —— 「顺手改一下」「先软删」在结构上无处落笔。
   这是最有效的一道：加列容易（迁移走流程会被人看见），但没人会为了改一条日志去写迁移。
3. **`assert_detail_is_safe()` 拒绝敏感内容**（下面 §3.2）。

代价：**应用层之外没有任何强制**。任何有 DB 写权限的人都能 `DELETE FROM audit_log` 或 `DROP TABLE`。
真正不可篡改要额外一套设施，本轮没做，理由见 §3.5。

### 3.2 密码永远进不来：`assert_detail_is_safe()`

审计表的读取权限通常比 `user` 表更宽（HR 能看审计，审计不该只给 admin）。
所以它一旦存了密码，就成了**第二个明文落点**。两道防线：

- **键名**：`password` / `passwd` / `pwd` / `password_hash` / `old_password` / `new_password` /
  `temp_password` / `token` / `access_token` / `authorization` / `secret` / `credential` …
  **深度遍历**（嵌套 dict、列表里的 dict 一样拦），命中抛 `AuditRefused`。
- **值**：`$2a$` / `$2b$` / `$2y$` —— bcrypt 哈希特征串，防止有人把哈希塞进 `note` 之类的键。

为什么值这一层要单独做：键名能拦住 `{password: xxx}`，拦不住 `{note: "密码是 $2b$12$..."}`。

`reset_password` 的 detail 里只有 `temporary_password_issued: true`。
测试断言方式是「**临时密码明文不在这行 detail 里**」而不是「detail 里没有 password 这个词」——
后者会因为写了 `temporary_password_issued` 而误判。

### 3.3 审计失败不阻断业务（fail-open）

`_audit()` 里的 `try/except` 吞掉异常并 `logger.error(exc_info=True)`。

**代价要说清**：一次用户操作成功了但审计没落库，页面上看不出来，只在日志里有一行 error。
**为什么仍然这么选**：业务与审计不在同一事务里。要么上分布式事务（复杂度与失败率都不可接受），
要么改成「审计失败则整个操作回滚」——后者意味着**审计表满了会导致没人能改员工资料**，
把一个只读的历史表变成业务可用性的单点。

选 fail-open 的真实理由：审计的价值在**事后追责**，「这次操作没记下来」是可接受的损失；
而「管理员改不了资料」是**当场**的、每次都发生的损失。

### 3.4 登录审计为什么留到 11c

`auth.login.success` / `auth.login.failure` / `auth.logout` 三个动作名已在白名单里，但**没有埋点**。
它们全都要落在网关/NestJS 侧，而网关现在只认 `.env` 的 `GATEWAY_USERS`（不查 MySQL）——
没有 `user` 表可查，也就无从判断「登录的人是不是一个已离职的员工」。

等 11c 落地、凭据真相源换成 MySQL，登录链路才有 `user_id` 可写进 `actor_user_id`。
**现在的失败登录在网关日志里，审计表里没有。** 这是当前形态下的已知缺口，不是遗漏。

### 3.5 不可篡改这件事，本轮明确没做

要真做到「有 DB 权限的人也改不了」，只有两条路：

- **独立审计库**：`audit_log` 放到另一个 MySQL 实例，应用账号只给 `INSERT`/`SELECT`，不给 `UPDATE`/`DELETE`。
  代价是应用层要处理「审计库挂了」这个新的失败模式（本轮选了 fail-open，所以其实是**两个库**各自失败）；
  开发环境要多起一个容器。
- **归档到不可写存储**：日志定期写到对象存储 / WORM 桶。代价是引入异步链路与延迟（分钟级），
  且「出事那天正好还没归档」这个窗口是新的风险。

本轮都不做，因为当前只有一个管理员、`user` 表本身就是唯一真相源，
**审计被改和业务数据被改的损失是同一个量级**。真正要上多角色、生产环境时再做 §3.5 的第一条。

### 3.6 `detail` 是 TEXT 不是 MySQL JSON 列

MySQL 的 JSON 列**不能有 DEFAULT 值**（5.7 至今都不行），而 `detail` 必须可空
（登录类动作没有变更明细）。于是只能 TEXT + 应用层 `json.dumps`。

代价：数据库层面查不了 JSON 内部（比如「找出所有把手机号改成 138 开头的」要全表扫 + 全文匹配）。
现在所有查询维度都有索引（时间/操作人/对象/动作），明细只做展示，够用。

### 3.7 `X-Forwarded-For` 敢信的理由与 identity 信任边界同源

`request.client.host` 在这里是 `127.0.0.1`（后端在网关后面），记下来的 IP 全是同一个，
审计就废了一半。所以优先取 `X-Forwarded-For` 第一段。

**这行的前提**：8000 端口不对外可达，XFF 只由 NestJS 网关写入。
哪天把 8000 映射出去或加了直连入口，`ip` 立刻变成一个任何人可伪造的字段。
这一点写在 `_client_ip()` 的注释里，不是写在文档里——因为改代码的人不一定读文档。

### 3.8 部门/职位删除前先取快照

`delete_department` / `delete_position` 删完之后行就没了，`target_label` 只能剩一个 id。
所以快照在 `DELETE` **之前**取。同理 `update_position` 的 before 快照必须在 `UPDATE` 之前
（第一版写成「改完再查」，于是 `changes` 永远是空的 —— 一个自造的 bug，靠 review 抓出来的）。

## 4. 过程中修掉的 bug

### 4.1 明细列整列显示「—」：detail 键名是前后端契约，没有类型检查

**症状**：浏览器里「变更系统角色」「变更员工状态」的明细列全是 `—`。
**根因**：后端对这两类动作统一写 `{"from":..., "to":...}`，前端第一版按
`detail.status` / `detail.role` 去读 —— `from` 永远是 `undefined`。
**为什么没被测出来**：后端全绿、接口 200、前端不报错。页面上看着完全像「这条日志没有明细」。

**修法不只是改前端**：加了一条**契约断言**（`test_module12_audit.py` 第 6 组末），
把 `action → detail 必需键` 钉成表，并**正扫 `AuditView.vue` 源码**确认前端引用的动作全在服务端白名单内。
这三条断言的价值是：以后谁改 detail 形状而忘了改前端，`check` 当场转红。
纯后端断言永远发现不了这类跨端契约问题（第 55 条坑的延长线）。

顺带把「建档类动作」也翻译了（原来只显示「—」），但**刻意不显示 `name`** ——
后端 detail 里没有 `name`（它在 `target_label` 那一列），编一个出来就是前端自己编的假数据。

### 4.2 13b 的静默数据污染：脱敏手机号被写回库

**症状**：管理员在员工页点「编辑」，不改手机号，只改姓名点保存 → 手机号变成 `138****0001`。
**根因**：列表接口脱敏（正确），但编辑弹窗直接用列表行的值填表 → 脱敏串是**合法字符串**，
写回库时任何校验都拦不住，当场不报任何错。
**修**：`GET /api/v1/admin/users/{id}` 返回原值（`to_dict(raw_phone=True)`），前端 `openEdit`
改成 async 先拉详情。列表仍然脱敏（**详情开特例不等于整体放开**，有回归断言守着）。

这是本轮唯一的真 bug，而且它是我**用浏览器脚本误改字段**才撞出来的——
curl 逐个接口验全是 200。

### 4.3 两个 13a 登录闭环 bug（在 13bc 已修，此处复验）

`LoginView` 登录后没有 `router.replace`（点登录什么都不发生）；`auth.ts` 里
`fetchProfile()` 写在 `setSession()` 之前（token 未落 → `/me` 裸请求 401 →
所有人报「账号已停用或不存在」）。**两个 curl 各自都验不出来**，只有浏览器串起来才现形。

## 5. 测试

`test_module12_audit.py`，11 组 64 断言，连跑两遍全绿。

判据偏「**不变量**」而不是「功能」：审计的价值全在出事那天能不能查出来，
而它缺东西的时候**不会报错**。所以不只断言「有日志」，还断言「没有明文」
「没有 update/delete 入口」「表里没有可改的列」「detail 键名与前端约定一致」。

包含 2 条**反向验证**（拆掉守卫，断言必须转红）：

1. 拆掉 `_audit` → 那两次状态变更一条审计都不落（证明留痕真的来自那行调用）；
2. 拆掉 `_FORBIDDEN_KEYS` → 明文真的能写进去（证明那道拦截是唯一防线，不是摆设）。

> ⚠️ 本模块自己在收尾时用 SQL 删掉造出来的审计行 —— **那就是删审计**。
> 这不是自相矛盾，是把边界写明白：不可删约束的是应用层，不是「任何人都不能删」。
> 测试文件头把这张张力明写出来了。
