# v2.0.0-p2.12b 身份与信任边界（P2-12b）

> 日期：2026-10-08 · tag：`v2.0.0-p2.12b` · 前置：`v2.0.0-p2.11c`（网关查库登录）
>
> **一句话**：把「谁能声称自己是谁」这件事从「谁先问到就听谁的」改成
> 「必须经过网关、而且网关证明过了才算」。这一格是 11c 打开多人登录口子之后
> **必须立刻封上的那道缝**（计划书 §0.7.2 红线）。

## 1. 范围

**做**：

- 网关**无条件剥离**入站身份头（8 个），之后才注入真实身份 + 网关证明；
- 网关**路径级授权**（`/api/v1/admin/*` 要 `admin|hr`；`/api/v1/internal/*` 对**所有身份**报 404）；
- 后端 `verify_gateway_proof()`：`IDENTITY_MODE=gateway` 下**验过网关证明才认身份头**；
- 探活 `/api/v1/system/health` 增`identity` 段（部署当天一眼看出信任边界有没有生效）；
- 新增 `tests/test_module14_trust_boundary.py`（9 组 47 断言）+
  `tests/test_module14_trust_boundary_reverse.py`（13 项反向验证）+
  `tests/acceptance_p2_12b.py`（真链路 25 断言）。

**不做**（对齐计划书，本格只做「身份」，不做「数据」）：

- **12c 会话隔离**（`session.user_id` 落库）—— **下一格**。所以此刻所有人看到的
  仍是同一份会话与同一个知识库，账号**仍然只能本机自用**；
- 12d文档与检索隔离（`project` 归属 + Chroma `where` 下推）、12e 越权回归；
- `X-Dept-Id` 的注入（11c 的 JWT 载荷里还没有 `dept_id`，12d 才需要它做数据范围过滤）。
  但**剥离清单里已经有它** —— 剥离可以提前，注入要等真值存在（§3.4）。

## 3. 关键设计决策

### 3.1 实测推翻了规格里的一条「选做」

设计规格 §5.1.3把「网关注入共享密钥 `X-Internal-Auth`」列为**选做（纵深）**，
理由是「只要 8000 不对外（compose 里 backend 不映射端口）就够」。

**12b 施工前先做了一次基线探测，结论是这条防线在本机裸跑形态下不成立**：

```
curl -H 'X-User-Id: 440' localhost:8000/api/v1/admin/users   → 200 + 完整员工名单
```

`440` 是种子里真管理员 `wu.jing` 的 `user.id`。两个原因叠加：

1. 本机 uvicorn 绑 `127.0.0.1`，**同机任何进程都能连**——「对外」这个说法在裸跑时不成立；
2. `.env` 默认 `IDENTITY_MODE=dev`，而无身份头会回落到 break-glass 超管。

所以「拓扑」是一道**依赖部署形态**的防线：哪天有人把端口映射出去、或者在容器里
多起一个同网段的服务，它就断了，而**代码里没有任何东西会察觉**。

据此把B 从「选做」升为**必做**，并**征询了用户拍板**（两个选项：只做网关剥离 /
加共享密钥校验），用户选「做纵深」。

> 这个例子值得留在文档里：规格写「选做」时 based on的假设是「compose 形态」。
> 假设变了（现在就是裸跑），结论就得跟着变 —— 而**只有实测能把假设暴露出来**。

### 3.2 代价不是白拿的：密钥要下发到两处

`INTERNAL_SHARED_SECRET` 与 11c 的 `/api/v1/internal/*` **共用同一个值** ——
它们本来就是同一个信任关系（「网关与后端之间」），分成两个只会让运维多记一个值、
少改一处而全站挂。代价写进 `core/identity.py` 的文件头：

- **漏配的表现**是「登录正常但所有数据接口 401」——症状与病因隔着一个进程；
  所以网关侧生产缺密钥直接启动失败，后端侧探活报 `gateway_proof_configured=false`。
- **轮换要同步改两处**，漏改的后果同上 —— 不是静默降级，是全站 401，
  **这点反而是好的**（失败得很响）。
- 它**防不了「已经拿到密钥的人」**：密钥进了环境变量就等于进了容器 env，
  `docker inspect` 看得到。所以它防的是「拓扑破了」与「顺手 curl 一下」，
  不是「攻陷了网关进程」。后者要靠 12d/P2-14 的对象级校验与审计。
- **dev 模式刻意不验证明** —— 否则 `make api` 裸跑时每条 curl 都要先造一个证明头，
  那不叫本地调试。它是**已知的本机后门**，所以只能是非生产默认值，
  而探活里的 `trust_enforced` 就是给部署当天看的那个指标。

### 3.3 内部接口对所有人报 404，不是 403

实测：`POST /api/v1/internal/auth/login` 经网关**是可达的**，带一个普通员工的合法
token 就能打到后端（后端回 401「内部接口鉴权失败」）—— 也就是说**唯一的防线是
11c 那道共享密钥**。一.dk密钥因任何配置失误而泄漏或为空，这条路立刻变成
「任意登录判定」。

所以加了一条路径级规则：内部接口**对所有身份都拒绝**（含 admin），且报 **404**：

- 为什么不能写「角色不够」：那会让一个 admin 看到「需要 admin 权限」这种自相矛盾的提示；
- 为什么报 404 而不是 403：403 等于确认「这条路径存在但你不许」，
  而内部接口**对任何调用者都不该存在** —— 不给枚举留线索。

### 3.4 剥离清单里有两个「没有对应注入」的头

`INBOUND_IDENTITY_HEADERS` 有 8 项，实际注入只有 5 个。多出来的三个各有理由：

| 头 | 为什么不注入但要剥 |
|---|---|
| `x-role` | **规格与实现不一致**（持续三个版本）：设计规格 §5.1.2 与复现脚本 `probe-header-strip.cjs` 写的都是 `X-Role`，而 11c 真正注入的是 `X-User-Role`。两个都剥，代价零，收益是**不管将来哪份文档/哪段代码读哪个名字，都读不到客户端填的值** |
| `x-dept-id` | 11c 的 JWT 载荷里还没有 `dept_id`，12d 才需要它做数据范围过滤。**剥离可以提前，注入要等真值存在** |
| `x-internal-auth` | 12b 新加的网关证明。同样不能让客户端自带 —— 否则任何人都能自己声明「我是网关」 |

⚠️ 这一条值得单拎出来说：`x-role` 的不一致是**规格自己漂了**，不是实现写错。
如果只剥其中一个，另一个就成后门 —— 而「后端将来会不会读这个头」是会变的
（12d 就会读 role）。**两份文档各写一份字符串字面量清单，没有任何东西会校验它们
还对不对得上**（13d 刚踩过这个形状：后端写 `{"from","to"}`、前端读 `detail.status`，
明细列整列 `—`，两边各自自洽、全绿、不报错）。

### 3.5 网关的粗筛必须比后端**更宽**，不是更严

`STAFF_ROLES = ['admin', 'hr']`（与后端 `core/identity.py` 对齐，D10）。
如果网关只放 `admin`，hr 会在网关上被拒，而后端那条 hr 分支**永远走不到**——
表现是**只有 hr 账号才现形**的「他为什么进不去管理端」。

判据写成：**网关答「你可能是管人事的，放进去让后端判」，后端答「你到底能不能改这个字段」**。
反向（网关比后端严）才是 bug。这条断言在 module14 第 4 组与真链路验收里各有一遍。

### 3.6 路径级授权为什么放在 Controller 路由而不是守卫

能放的地方只有三个，只有路由 handler 是正确的：

- **中间件** → 跑在守卫之前，未登录请求拿到 403 而不是 401，
  而前端对这两者处理不同（403 不跳登录页，用户会卡在页面上）；
- **守卫** → 也可以，但守卫只回答「你是谁」，让它顺带管路径会把两件事揉在一起，
  而且**白名单路径根本不经过它**；
- **这里** → 已经过了守卫（身份已知）、还没转发（请求不进后端）。

它**不是**后端 `require_staff` 的替代：那一层是本条规则失效时的兜底
（裸跑 8000、忘配路径规则）。

## 4. 过程中修掉的 bug / 挖出来的事实

### 4.1 规格把一条必做防线写成了「选做」（见 §3.1）

本轮最重要的一条，且是**实测挖出来的**，不是测试抓出来的。

### 4.2 module12_admin 的旧断言被新守卫打成 401 —— 修法不是改断言

12b 加了证明校验之后，`make test` 第一遍 module12_admin **74通过 / 1 失败**
（`gateway 模式下正常链路不受影响 | 401`）。

第一反应是把断言改成 `== 401`。**那是最坏的处理**：那条断言想验的是
「gateway 模式下合法链路仍然通」，而 401 说明证明校验把合法链路也挡了。
改成 401 它就绿了，但变成一条**恒真的假绿**（第 50 条：断言看着在跑，
实际什么也没验）。

正确处理是让 `act_as()` 默认**带正确的网关证明**（`_AUTO_PROOF` 哨兵 → 
按 `settings.INTERNAL_SHARED_SECRET` 取），要验 fail-closed 的地方显式传
`""`（不发）或错值，并补两条新断言：

- 身份头合法但**没有证明** → 401（12b 前是 200 + 员工名单）；
- 证明差一位 → 401。

顺带加了一条**前置断言**：`.env` 里必须配了 `INTERNAL_SHARED_SECRET`。
没有它，「正确证明 → 200」那条会因为拿不到密钥而变成 401，
而红的理由跟它想验的东西无关 —— 又是一次「假红」。

module12_admin 因此从 74 扩到 **79 / 0**。

### 4.3 `expect_401` 辅助函数自己恢复 settings → 后面 4 条全假绿

module14 第一版把「恢复 settings」放在 `expect_401` 的 `finally` 里，
于是第1 条检查通过后 `IDENTITY_MODE` 已经被还原成 `dev`，
后面 4 条全部因为「dev 模式不验证明」而**假绿**。

判据改成「不自己恢复、由调用方集中重设」，并在每条之前调 `as_gateway()`。
这个坑的形状值得记住：**辅助函数「顺手做好」的事，会让后面所有断言失去意义**。

### 4.4 反向验证自己先写错了一版

第一版反向验证断言的是「forgery works」（即**守卫拆掉后能伪造**），
而不是「拆掉后断言转红」。两者在**测试通过时长得一样**，但判据相反。

删掉重写成独立文件 `test_module14_trust_boundary_reverse.py`，
判据统一成「每条 `[RED]` 表示拆掉守卫后对应断言确实转红」。

### 4.5 反向验证自身的三个失效（与「崩掉 ≠ 失败」）

反向验证的价值全靠「拆掉之后必须红」，所以**它自己出错时也必须可辨**：

| 失效 | 症状 | 修法 |
|---|---|---|
| 断言只看前6 行 | 把剥离改成同行的 `if (x) for (...)` 后仍绿 | 改成看「剥离行 ±6 行」 |
| 锚点自相矛盾 | `inject_end` 的找法与 `inject_start` 冲突，定位到 -1 | 从剥离块起点一路找注入块起止 |
| 全文 `re.sub` | 顺手把 `GATEWAY_PROOF_HEADER = "x-internal-auth"` 也删了 → SyntaxError **崩在 import** | 只删清单字面量里那一行；并加一条「主测试没崩」的断言**区分崩与红** |

第3 条是最隐蔽的一种：**崩掉看起来也像「测出东西了」**。所以反向验证必须能区分
「崩了（改法错）」与「红了（守卫被拆）」。

### 4.6 `verify_p2_12b.sh` 的 kill 把调用方 shell 一起 SIGTERM

本轮的真链路验证最初写成一个 shell 脚本负责起服务，它 `kill` 8000/3000 时
**把发起调用的 shell 一起带走（exit 137）**。

改成：起服务走后台任务，验证逻辑拆成独立 Python 脚本。
最终固化时进一步收敛成一个正式验收脚本 `tests/acceptance_p2_12b.py`
（不杀任何进程，要求服务已起着），三个一次性脚本全部删除 ——
按11c 的惯例，一次性验证脚本不进仓。

## 5. 测试

### 5.1 `tests/test_module14_trust_boundary.py`（47 断言，9 组）

| 组 | 内容 |
|---|---|
| 1 | 前置（清理本模块残留） |
| 2 | 两侧身份头清单必须一致（跨端契约） |
| 3 | 先剥离、后注入（**顺序**不能反） |
| 4 | 路径级授权成对断言（该拒的拒、该放的放） |
| 5 | 后端网关证明 fail-closed（5 种情形） |
| 6 | 真链路等价 —— 剥离后白名单路径上还剩什么 |
| 7 | 探活要能看出信任边界有没有真生效 |
| 8 | 零残留 + 种子未被动 |
| 9 | 反向验证（拆守卫→ 断言必须红） |

**判据为什么全是「读源码」和「不变量」**：12b 要防的那几类失效**全部不报错** ——
剥离漏一个头 → 伪造头穿透、接口照样 200；两侧清单不一致 → 某个头静默不生效；
路径授权比后端严 → 只有 hr 账号现形。所以「跑一遍看结果对不对」在这里几乎没有
判别力，必须**把源码本身当被测对象**。

**TS 侧为什么用「读源码 + 等价重实现」**：本仓库测试统一是Python 脚本，
`make test` 里没有 tsc 环节，起 ts-node 也不划算（多一个运行时依赖，
还要 mock Express/Nest 的 req/res）。代价是等价重实现可能与真实 TS 漂移 ——
所以每组逻辑断言都附一条**正扫源码**的断言，两者互为交叉验证：
漂移了会表现为「逻辑组全绿但源码组红」，那是可读的失败。

**真链路那一层靠 `tests/acceptance_p2_12b.py`**（§5.3）。

### 5.2 两条不进 `make test`，理由不同（别混）

| 目标 | 不进的理由 |
|---|---|
| `accept-12b-reverse` | 它**临时改生产源码**再跑主测试看断言转红。混进 `make test` 意味着每次回归都在动源码 —— 主测试一旦失败，你分不清是「回归真失败」还是「反向验证把自己改坏了」。而且 `make test` 的契约是「全绿」，反向验证的契约是「必须红」，塞进同一条命令会让判据含混 |
| `accept-12b` | 它要求后端 + 网关两个进程**已经起着**（真 HTTP、真 token），而 `make test` 的契约是「离线可跑」 |

### 5.3 `tests/acceptance_p2_12b.py`（真链路 25 断言）

它补的是module14 结构上补不了的第三件事：**起真的后端 + 真的网关，
用真 token 打真 HTTP**。五条判据：路径级授权（员工 403 / 管理员 200 /
业务接口 200）/ 内部接口 404（两种身份都验）/ 白名单伪造头被剥离 /
生产形态缺证明 401（四种情形）/ 直连 8000 的本机边界（并明确标注为
**刻意保留的代价**而不是漏做）。

⚠️ 它会临时改 `wu.jing` / `chen.jie` 的密码（要拿真 token 只能真登录），
收尾换成**新的随机临时密码** + 强制改密标记。种子的原临时密码早已不可知，
所以「还原」不是假装还原成原值 —— 能还原的是「这个账号仍然可用、
仍处于强制改密状态」。

⚠️ 写第一版时踩了一个小坑：后端**没有** `/api/health`（那是网关自己的探活路由），
写成它会拿到 404，然后第 0 组判「后端没起来」—— 真实原因只是路径写错。
已改用 `/api/v1/system/health`，并在代码注释里写明这个坑。

5 个反向验证，**13 项符合预期 / 0 项不符合**：

| 3 | 调换剥离与注入的顺序 | 「剥离排在注入之前」 |
| 4 | 两侧清单都删掉 `x-internal-auth` | 「清单里含 x-internal-auth」 |
| 4′ | 只删 TS 侧 | 「TS 侧清单 = Python 侧清单」（跨端契约断言有效） |
