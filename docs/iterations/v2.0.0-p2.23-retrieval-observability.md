# v2.0.0-p2.23 检索可观测性：拒答轨迹 + NDJSON 调试事件

- 版本：`v2.0.0-p2.23` ｜ 日期：2026-10-09 ｜ 对应计划书任务：`docs/PLAN-v2.0.0.md` §13（P2-23）
- 上游基线：`v2.0.0-p2.22`（commit 2ef4b3a）

## 1. 范围

**做了什么**：

1. **检索轨迹日志增强**：`重排完成` 日志行补上【过滤前 top1 分数】与【被 score_threshold
   过滤的条数】；拒答分支新增结构化 INFO 日志
   `拒答 | 原因=检索为空 | 改写后查询=... | top1分数=... | 阈值=...`。
   消除 p2.22 验收时的观测盲点：被全过滤时 `分数区间` 退化为 `[0.0000, 0.0000]`，
   「差多少分」无从回答。
2. **NDJSON `retrieval` 调试事件**：`/ask/stream` 支持 `debug=true`（不传时 admin
   角色默认开启），在生成开始前推一个 `retrieval` 帧，携带改写后查询、意图分类结果、
   候选清单（chunk_id / 文件名 / 重排分 / 是否过阈值，**含被过滤掉的候选**）、阈值配置、
   过滤前 top1。
3. **前端「检索详情」折叠面板**：消息气泡「引用资料」旁新增；🔴 拒答的气泡（sources 为空）
   同样可见 —— 展开即能回答三个问题：改写后的查询是什么、检索到了哪些候选、
   top1 与阈值差多少。

**明确不做**：

- **不做调参**（§13 第 3 条）：调参决策必须用本版产出的真实「差分」数据支撑，
  数据还没积累，本版只交付观测手段；
- **不做检索详情的持久化**：retrieval 调试帧只在当轮流式过程中下发，
  刷新页面 / 会话历史接口不回填该面板（记忆里只存 sources/usage/耗时等既有字段，
  不为调试信息扩表）；拒绝原因见 §3；
- **不改同步 `/ask` 接口**：调试事件只进流式（拒答观测的主战场是前端气泡），
  同步链路的观测靠日志已够。

## 3. 关键设计决策

- **轨迹挂在重排器实例的 `last_trace` 字段（「最近一次」口径），而不是逐请求传递。**
  生产路径是 `ContextualCompressionRetriever → compressor.compress_documents → rerank()`，
  LangChain 压缩器接口没有为调用方回传诊断信息的口子；逐请求传递要改压缩器接口或包一层
  Runnable，改动面大。挂实例字段的代价是**并发请求会互相覆盖**（线程不安全）——
  当前部署形态是单团队低并发，「日志/调试事件看到的是最近一次检索」可接受，
  已在代码注释与本节明示。否掉的方案：① 改 `BaseDocumentCompressor` 接口加返回值 ——
  侵入第三方基类语义，升级 LangChain 时必炸；② contextvars 逐请求隔离 —— 正确但复杂度
  与收益不成比例，等真出现并发误读再上。

- **`_candidate_brief` 与 `rag_chain._resolve_chunk_id` 刻意不共用代码。**
  后者在前者之上（rag_chain import retriever），反向 import 成环。选择在 retriever.py
  本地实现同构逻辑（6 行），靠测试第 2 组的**同构断言**防两处漂移。
  否掉的方案：把 `_resolve_chunk_id` 下沉到 `core/vector_store.py` 共用 —— 搬动会牵连
  P0-4a 的引用契约测试与历史注释，为一行逻辑不值。

- **被过滤候选进清单的方式 = 重排器记录过滤前全量分数。**
  `_rerank_trace` 基于过滤前的降序全量构建候选（每条带 `passed_threshold`），
  而不是「返回 docs 标 true + 另查被过滤的标 false」—— 后者要求两次反查且顺序信息丢失。

- **debug 语义是「显式 > 默认」**：显式传 true/false 照传；不传（None）→ admin 默认开。
  这保证**不传 debug 的调用方事件序列与 P2-23 之前逐字节一致**（验收口径之一）。
  前端因此**不需要传 debug 字段**（登录态角色本来就不在前端手里，后端判定是唯一真相源）。

- **缓存命中与闲聊不下发 retrieval 帧**：两者没跑检索，硬造一个空事件只会误导
  （闲聊的意图在 meta 帧里已有）。

- **拒答日志里 top1 取不到时写「不可得」而不是 0.0**：0.0 会被误读成「模型真给了 0 分」；
  「不可得」逼着人去看轨迹为什么缺（重排关闭/轨迹被覆盖）。

- **检索详情不持久化**：调试数据进 `chat_message` 需要扩列/扩 JSON 结构，且历史轮次的
  轨迹在重排器实例上早已被覆盖，落库要在链路里多传一路数据 —— 为一个调试面板不值得。
  刷新后面板消失是**已声明的边界**（§6），不是缺陷。

- **模型选择**：任务书提示「环境支持则用 Hy4 preview」——检查 `.env` 与
  `config/settings.py`，本仓库的 LLM 配置只有 `LLM_PROVIDER/LLM_MODEL` 等固定项，
  没有「指定会话模型」的机制，故全部验证沿用默认模型（DeepSeek 生产配置 / 桩模型）。

## 4. 配置与接口变化

- **HTTP**：`POST /api/v1/qa/ask/stream` 请求体新增可选 `debug: bool`（缺省 null）。
  下发新帧类型 `retrieval`：

  ```json
  {"type":"retrieval","rewritten_query":"...","intent":"policy_consult","route":"rag_qa",
   "candidates":[{"chunk_id":"35:2","file_name":"员工手册.pdf","rerank_score":0.6123,
                  "vector_similarity":0.55,"passed_threshold":false}],
   "threshold":0.5,"top1_before_filter":0.4321,"filtered_count":2,"docs_returned":0}
  ```

  下发顺序：`session → meta → [retrieval] → chunk×N → done`。
- **无 env 变化**、无数据库 schema 变化、无迁移。
- 版本号：`.env` / `.env.example` `PROJECT_VERSION=2.0.0-p2.23`。

## 6. 已知边界与遗留项

- **检索详情面板不持久化**：刷新 / 会话历史回看时不显示（仅当轮流式过程可见）。
  要持久化得扩消息元数据并随链路传递轨迹，待有真实需求再立项。
- **轨迹「最近一次」口径**：并发请求下 `last_trace` 会被后完成的重排覆盖，
  日志与调试事件可能拿到「别人那次」的 top1。低并发部署可接受（§3）；
  出现误读案例再上 contextvars。
- **重排关闭（USE_RERANKER=False）时**：拒答日志 top1 恒为「不可得」（没有阈值也就
  没有差分问题）；retrieval 帧仍下发，候选从 sources 凑、全部标过阈值、threshold=null。
- **前端 auth store 不持有 role**：非 admin 用户将来若需要调试视图，要么前端拉 profile
  判角色传 `debug=true`，要么后端加配置项 —— 都留到有需求时再做。
- **浏览器人工验收（留给用户）**：见 §7。
- 调参闭环（PLAN §13 第 3 条）**未启动**：等本版积累真实差分数据后评估
  `score_threshold` 与改写提示词。
