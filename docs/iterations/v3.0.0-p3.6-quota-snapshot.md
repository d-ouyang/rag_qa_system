## 1. 背景（P3-1 改变了前提）

拦截（P3-1）上线后，「这个月用了多少」从看板上的一行数字变成了**执法依据** ——
被拦的员工与管理者之间可能就它发生争议。

争议需要证据，而当前的证据只有一份：`chat_message.usage_*` 明细。
明细的问题是它**寄居在聊天记录里**：将来做聊天记录清理 / 归档
（chat_message 是全库增长最快的表，几乎必然会发生），
用量历史跟着一起消失 —— 那时「他上个月到底超没超」死无对证。

所以把「每账期每人用了多少」定期抄进自己的表，只增不删。

---

## 2. 方案

```
Celery beat（worker 进程内嵌，每天 04:10）
        │  rag.snapshot_monthly_usage
        ▼
core/quota_snapshot.snapshot_period()
        │  数值来源 = usage_by_user() 本身（同一段 CTE）
        ▼
quota_usage_monthly  upsert 覆盖写当前账期（历史账期无写入路径）
```

- **口径同源**：快照的数值就是 `usage_by_user()` 的返回值，
  写入瞬间与实时聚合**逐位相等** —— 对账从「要证明」变成「恒成立」。
- **判定路径一行未改**：预检（P3-1）与看板（P2-15de）仍走 `quota_repo`
  实时聚合，明细在，实时算永远是准的。这张表只服务**归档对账**。

---

## 3. 被否掉的方案 / 要紧的取舍

### 3.1 快照模块自己写一段聚合 SQL — 否掉

「快照更简单，自己 SUM 一下」看起来省一次函数调用，实际是把
`usage_by_user` 里那段**两段聚合**CTE（2026-10-07 重复计数 bug 的验尸报告
就写在它的注释里）重新埋一遍，而且埋在「平时没人看」的归档表里 ——
炸得更晚、更难发现。module21 用 AST 扫字符串字面量钉住：
快照模块的 SQL 里**不许出现** SUM / GROUP BY / chat_message。

### 3.2 用 `bump_kb_version()` 式的 Redis 信号通知快照 — 否掉

快照是**定时**语义（每天一次），不是事件语义。塞进请求路径等于让
「最后一次提问的人」承担归档成本；挂在缓存版本号上则把归档与 Redis 可用性
绑死。beat + 任务队列是这两个语义的正解。

### 3.3 让 beat 接受「指定账期」参数 — 否掉

写入路径只存在「当前账期」一种：`snapshot_period()` 刻意**不带**账期参数，
「把历史账期覆盖掉」在函数签名上就不成立。要修正历史走人工 SQL 并留记录，
不该是例行定时任务的权限。module21 反向 3 钉住这个签名。

### 3.4 user_id 加外键（ON DELETE CASCADE）— 否掉

人可以被删（离职清理），但「他 10 月用了 8 万 token」是已发生的事实。
加外键 + 级联删除，删人会连带抹掉用量档案 —— 那正是这张表要防的事。
与 `audit_log` 同一个取舍（冗余可读性这里是次要的，id 本身够用）。

### 3.5 每天全量重算历史账期 — 否掉

beat 只算今天所在账期。历史账期的明细可能已被清理，
「重算历史」只会把档案改小甚至清零 —— 与「快照不回退」直接矛盾。

## 6. 风险与已知边界

1. **内嵌 beat 的多 worker 约束**：`-B` 只允许一个 worker 进程带。
   本项目由 4C4G 单实例部署兜着；若将来横向扩容，beat 要拆独立进程
   （`celery -A worker.app beat`），否则任务双跑 —— upsert 幂等不会写错，
   但日志与 `updated_at` 会互相踩。
2. **对账只对当前账期**：历史账期的明细可能已被清理，
   「快照 != 实时」在那里是预期。`verify_against_usage()` 刻意只比当前账期，
   防止把「归档生效了」误报成「数据不一致」。
3. **快照行不记用户名**：只存 `user_id`（PLAN 定的列）。人删了之后
   这行只剩 id —— 真需要可读档案时，join 不了就是 join 不了
   （这正是「归档」与「看板」的分工：看板有人、档案有数）。
   将来要做「按人查历史用量」的界面，届时再加 `username` 冗余列。
4. **当期无用量时不写行**：`snapshot_period()` 对空结果零写入
   （不造 0 行）—— 与 `usage_by_user` 的「没有用量就不出现」同一口径，
   表的行数 = 出现过量用人的历史并集，不会膨胀。
