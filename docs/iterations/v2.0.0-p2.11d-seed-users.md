## 3. 关键设计决策

### 3.1 修正迁移 0003：加一步 `LEGACY-<id>` 回填

这是本轮最重要的一件事，而且它**违反了「迁移是冻结的历史快照」这条约定**。

**触发**：11a 交付时我写下一条「已知限制」——`ADD COLUMN` 给所有存量行填空串，
而 `uk_user_employee_no` 不允许两行同为 `''`，所以 **0003 只在「user 表为空或至多 1 行」时能重放**。
当时验收脚本只灌 1 行，所以这条限制一直没被触发。

P2-11d 把 10 个员工灌进去之后，迁移往返验收第一次真的撞上：

```
sqlalchemy.exc.IntegrityError: (1062, "Duplicate entry '' for key 'user.uk_user_employee_no'")
```

**否掉的方案：让验收脚本绕开。** 比如「表里有数据就跳过往返验收」——
那等于把刚发现的 bug 藏起来，而且这个限制在**任何**有数据的库上都还在。

**采用的修法**（在 0003 的 `add_column` 之后、建唯一键之前）：

```sql
UPDATE `user` SET `employee_no` = CONCAT('LEGACY-', id) WHERE `employee_no` = ''
```

于是：任何行数的库都能重放；往返后工号是 `LEGACY-<id>`——确定、唯一（带主键）、
一眼看出是迁移补的占位值。**空串做不到后两条**：它既不唯一（所以建不了索引），也不可辨识。

**为这处改动付的代价，明写下来**：

- 与「老迁移不改」冲突。判断依据：改动**当天**发现、只有开发库跑过旧版、
  且不修就等于「任何有数据的库都无法重放」。这属于「迁移本身有 bug 时的例外」。
- 已跑过旧版 0003 的库**不会**自动获得这步回填，需要手工执行那条 UPDATE。
- 往返之后员工的工号会变成 `LEGACY-<id>`，需要人工/脚本换回真实工号
  （验收脚本已自带快照-还原，所以跑验收不会留下这个状态）。

**教训**：「只在空表上验证过」等价于「没验证过」。验收夹具必须覆盖真实数据量，
而不是刚好绕过边界。

### 3.2 重跑绝不重置密码，也绝不改 `status`

想象一下：种子跑完，某员工自己改了密码；一周后有人为了「刷新一下数据」重跑脚本。
如果脚本每次都重置密码，这个员工会被打回临时密码，**而且他自己不知道**。

所以重跑只补/ 修正资料（姓名、邮箱、手机号、部门、职位），并且：

| 字段 | 重跑时的行为 | 为什么 |
|---|---|---|
| `password_hash` | **不碰** | 员工自己改过的密码不该被打回 |
| `must_change_password` | **不碰** | 同上 |
| `status` | **不碰**（只在首次创建时写） | 管理员停用了某人，重跑不该把他悄悄恢复 |
| `display_name` / `phone` / `department_id` / `position_id` | 同步 | 这些是种子该负责的「事实」 |

换密码只有两条**显式**路径：`--reset-password`，或管理员在管理端重置（P2-13b）。

**实测验证过**：把陈杰停用后重跑 `--apply`，他仍然是 `disabled`。

### 3.3 幂等靠「按业务键 upsert」，不靠「先查再插」

朴素幂等（先 SELECT 看在不在，不在才 INSERT）在两个进程同时跑时会插出两条。
这里按业务键 upsert：部门按 `code`、职位按 `code`、员工按 `username`（唯一键）。
两边同时跑时第二次会撞唯一键，于是最坏结果是「一人一条」。

`--reset` 只删**种子自己的那些行**（按业务键），绝不全表清空——
全表清空会把真人建的东西抹掉且不报错，那是 module9 留下的教训。

### 3.4 凭据只显示一次，且不进日志

- 每人一个**随机**临时密码（`generate_temporary_password`），`must_change_password=1`；
- 同时写一条 `user_password_history` → 他首次改密时**不能用同一个密码**；
- **只显示一次**：打印到控制台，或显式 `--credentials-file`；
- 脚本一律用 `print` 而**不走 logging**，所以临时密码**不会进 `app.log`**
  （实测：在 4MB 的历史日志里搜三个临时密码，命中 **0** 次）；
- `--credentials-file` 会先 `git check-ignore` 判定路径，**被 git 跟踪就拒绝写**，
  并在 `.gitignore` 里加了 `*credentials*.csv`。

### 3.5 种子里的 `admin` 不是 break-glass 超管

两者都叫 `admin`，用途完全不同：吴静是**企业管理员**（管人事、重置员工密码）；
PLAN §11 D9 那个 break-glass 超管留在 `.env` 的 `GATEWAY_USERS` 里，
专门给「连不上数据库时进得去」用。脚本不造后者。

### 3.6 默认干跑

沿用 `scripts/reindex.py` 的规矩：**会写库的命令不该在敲错时直接生效**。默认只打印计划，`--apply` 才落库。

### 5.5 顺带修掉的两条「依赖空表」的判据

种子数据一进库，就有两处断言红了，**都是同一个毛病**——判据建立在「这张表本来是空的」上：

1. `module11` 的「按序列过滤为空时返回空列表」（职位表被灌了 6 个职位）；
2. `acceptance_p2_11a.py` 的「user 表总行数为 0」（user 表被灌了 10 个员工）。

两条都改成「**按业务键数自己造的那些行**」，再单独加一条「别人的行数没被改动」。
已记为踩坑清单第 51 条。

### 5.6 ⚠️ 发现并修掉的第三处往返数据损失

`downgrade` 会 `DROP TABLE department / position / user_password_history`，
**表里的数据跟着一起没了** —— 而员工的 `department_id` / `position_id` 还指着那些 id，
于是变成**悬空引用**（没有 FK 约束，不会有任何报错）。

修法：验收脚本往返前把这三张表连数据一起快照，往返后**按原 id 写回**
（保留 id 很重要：员工的引用靠它才继续有效）。`employee_no` 同理快照-还原。
现在往返验收跑完，库里的 10 员工 / 3 部门 / 6 职位 / 9 条历史 / 真实工号**一件不少**。

已记为踩坑清单第 52 条。
