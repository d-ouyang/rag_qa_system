# v3.1.0-p4.1 — site-mood：给个人站的心情表单一个落点

> P4 是计划外插入的模块：nianan.site（个人站，静态部署）底部有个
> 「Are you happy today」表单，提交 `{email, mood}`，此前前端
> `submitMoodNote()` 是空实现——数据没有去处。本任务在现有部署形态内
> 为它开出公开提交口 + token 保护的查看口，数据落在独立小表。

## 1. 背景

- nianan.site 与本系统同机部署（边缘 nginx 托管静态 + 反代 qa 子域）。
  个人站表单要落库，最自然的去处就是这台机器上现成的 MySQL/Redis——
  **但必须与 RAG 业务划清边界**：不外键、不进问答路径、不混用密钥。
- 前置决策（2026-10-14 用户拍板四条）：
  ① 表放现有 `rag_qa` 库（不新建库实例）；② 邮箱存明文；
  ③ 查看走浏览器 HTML 页面；④ 限流 = per-IP 每分钟 ≤3 次 + 邮箱去重。

## 2. 方案

链路：`浏览器(nianan.site) → 边缘 nginx(/api/mood/) → 网关 @Public 精确白名单
→ FastAPI /api/v1/mood/* → Redis 双闸 → MySQL site_mood_submission`。

- **表** `site_mood_submission`：email（明文，NOT NULL）/ mood DECIMAL(3,2)
  / mood_word（派生标签）/ page_url / ip / user_agent / is_read / created_at。
  迁移 `0010`，列注释与 `core/schema.py` 逐字对齐（compare_metadata 前提）。
- **POST /submit** 双闸，先外后内：per-IP 固定窗口（`INCR`+60s `EXPIRE`，
  3 次/分）→ 邮箱冷却（`SET NX EX` 600s，大小写不敏感，键存 sha256 不存明文）。
  业务拒绝 = **HTTP 200 + `{ok:false, reason}`**（与 internal.py 登录判定同一
  哲学：「业务没成」≠「接口失败」）；参数不合法才 400/422。
- **GET /admin**：独立 `MOOD_ADMIN_TOKEN` 常量时间比对（空 = 503 fail-closed，
  与 INTERNAL_SHARED_SECRET 运行期处理一致）；`include_in_schema=False`；
  返回体**不带 ip 列**（存它是为了限流，不是给人看的）。
- **网关** `PUBLIC_MOOD_PATHS = ['api/v1/mood/submit','api/v1/mood/admin']`
  精确路径 `@Public()`，handler 注册在通配 `api/v1/*` 之前（同健康检查的
  顺序要求）；不用 `api/v1/mood/*` 前缀通配——未来模块内新增接口默认仍要 token。
- **前端**（nianan-site 仓库）：`moodNote.ts` 真实现 fetch（同源路径
  `/api/mood/submit`，nginx 转发，零跨域）；四种结果各配提示文案；
  `public/mood-admin.html` 随站点构建发布，输入 token 渲染表格。

## 3. 被否掉的方案 / 要紧的取舍

### 3.1 单独起一个「站点服务」小进程 — 否掉
4C4G 内存预算按进程划死（backend 1.8~2.2G / worker 500~700M），为两个接口
多养一个 ~100MB 的进程不划算；复用现有进程则连接池 / 迁移 / 日志全部白嫖。

### 3.2 邮箱去重用 MySQL 唯一约束 — 否掉
去重语义是「冷却窗口」（10 分钟内算重复，过期可再交），不是「全库唯一」。
唯一约束把冷却语义锁死在 DDL 里，调窗口要改表；放 Redis 调 .env 即可。
代价：Redis 清空后冷却短暂失效——心情表单可接受（fail-open 见 3.3）。

### 3.3 Redis 异常时 fail-closed（拒绝提交）— 否掉
公开表单不是核心业务，宁可收下（极端情况多几行数据）也不让缓存层抖动
变成「用户看到发送失败」——与 MEMORY_DEGRADE_ON_ERROR 同源：可用性优先。
滥用风险主要由拓扑兜底（8000 不对外，只有网关能进来）。

### 3.4 admin 复用 RAG 的 JWT 或 INTERNAL_SHARED_SECRET — 否掉
这个模块的独立性是卖点：密钥互不牵连，泄露不殃及主系统。代价是多管一个
token（`.env` 一行），值得。

### 3.5 XFF 取「第一跳」就完事 — 不够，必须边缘覆盖写
客户端可自带 `X-Forwarded-For` 头伪造第一跳；若边缘 nginx 用
`$proxy_add_x_forwarded_for`（追加），伪造值会排最前。**部署必须用
`proxy_set_header X-Forwarded-For $remote_addr` 覆盖写**，否则限流可被
一行 curl 绕过。已写进部署步骤与 mood.py 注释。

## 6. 风险与已知边界

- **限流的前提是边缘 nginx 覆盖写 XFF**（见 §3.5）——不配，限流等于没做。
- NAT / 校园网共用出口 IP 会分摊 3 次/分额度；IPv6 下 per-IP 反而松——
  个人站量级下均可接受。
- email 明文 = PII：admin 口受 token 保护、返回不带 ip；**绝不**进任何公开返回。
- `make test` 全量仍不碰本模块（module22 只动自己的表）；sandbox 全量不含 22。
- 线上生效还需四步部署（.env token → db-upgrade → 重建 backend+gateway →
  edge nginx location），见发布说明。
