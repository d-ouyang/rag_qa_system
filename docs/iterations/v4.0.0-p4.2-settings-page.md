# v4.0.0-p4.2 — 设置页从「只能看」到「superadmin 可以调」

| **性质** | 计划内（PLAN-v4.0.0 P4-2，P4-1 ConfigService 的第一个消费者） |
|----------|--------------------------------------------------------------|
| **tag** | `v4.0.0-p4.2` |
| **默认行为** | **零变化**：所有开关的既有默认档原样生效；管理端不改，行为与 p4.1 逐字节一致 |
| **新增能力** | 设置页「运行时开关」卡片：superadmin 拨开关 + 「确认修改」→ **下一个请求即生效**，并落审计 |

---

## 1. 背景（结论先行）

P4-1 把业务开关的真相源搬进了 MySQL `system_config` 表，但改开关还只能 SQL/脚本。用户 2026-10-16 拍板的 P4-2 目标：现有只读「系统设置」页升级为**分层可操作面板**——热项可编辑 + 「确认修改」按钮 + 重启必需项徽标，权限 v1 从严（全部 superadmin）。

本版落地：**8 个注册标志**（检索 top_k / 重排开关 / 重排阈值 / 单轮改写 / HyDE / 问答缓存 / 记忆轮数 / 原件下载）全链路热化——管理端 UI → `PATCH /admin/config/{key}` → ConfigService 落库 → 各读取点下一次调用即用新值。

## 2. 方案（实现了什么）

**① 注册表 `core/config_flags.py`（新）**：`FLAG_REGISTRY` 是「能改什么」的**白名单**——每项登记 key/类型/卡片/中文名/描述/边界/默认档（惰性活读 settings）。没登记的 key 管理端一律 404；密钥/连接串**结构性**进不了热更新面（根本不在注册表里，不靠「记得别返回」）。读取点必须走 `flag_value(key)`，不许各自拼 `get_flag`（防注册表与读取点漂移）。

**② 读取点接线（老快照全部清掉）**：
- `qa_cache.py` 3 处、`documents.py` 2 处（capabilities + 路由闸门）——settings 读换 `flag_value`；
- `memory_manager.max_turns` 属性化：显式构造参数仍最高优先（测试契约不变），缺省时每次取值热读；
- `retriever` 三处热化：`top_k` 属性化（显式参数优先）；`_rerank_active()` 四层判定（开关关→关；重排器对象在→开，**module20「构造禁用后注入打桩器」的惯例靠这条保住**；显式禁用且无对象→不许热构建；无表态→siliconflow 懒构建，local 维持重启语义——内存预算不该被拨开关打爆）；阈值在 `_rank` 里每次检索下发到重排器（0 = 关闭过滤→None），重排器内部逻辑一行未动。

**③ 后端 `api/routes/admin_config.py`（新）**：`GET /api/v1/admin/config`（注册表+当前值，superadmin）、`PATCH /api/v1/admin/config/{key}`（类型/边界校验→ConfigService→**审计 `config.update`/`system`**，actor 记登录名）。门禁 `require_superadmin`（新增依赖，kb_role=superadmin，判据与 kb_acl 同源）——GET 也同门禁，前端拿 403 当「只读模式」信号。写路径 fail-closed：DB 挂了 500，管理端必须看见「没保存成功」。

**④ 审计扩容**：`audit_repo.ACTION_LABELS` 增 `config.update`（修改系统配置）、`TARGET_TYPES` 增 `system`（target_label 存配置键）——「谁在什么时候把哪个开关拨成了什么」能单独筛出来。

**⑤ 前端 `SettingsView.vue`**：顶部新增「运行时开关」卡片组（按注册表 card 分组）：bool 渲染拨杆、int/float 渲染数字输入（带 min/max），值变脏出现「确认修改」按钮，保存成功 toast「已保存，下一个请求即生效」；非 superadmin（403）整块不渲染。只读卡片补 note：LLM 卡注明「模型切换属 P4-3」、嵌入/切分卡注明「更改=重建索引，禁止随意切换」。`vue-tsc` 0 error。

## 4. 否掉的方案与代价

- **否掉「实例级锁死」（第一版 `_rerank_active` 的写法）**：显式 `use_reranker=False` 连同**事后注入的重排器对象**一起被拦——module20 的测试惯例（构造禁用 + 注入打桩器）直接 3 红。修正为「对象在就尊重（受开关热控）；锁死的只是热构建」。教训：**锁语义要锁「行为来源」而不是「实例命运」**。
- **否掉「给 rerank() 加阈值透传参数」**：两处签名变更 + None 语义歧义（「没传」与「传了 None=关闭」分不开），还得造 sentinel。改为检索前直接更新重排器的 `score_threshold` 属性——生产路径所有线程写同一个全局值，竞态无害，重排器内部零改动。
- **否掉「GET 登录即可看」**：注册表是运营参数真实值，收敛在超管视野内没有坏处，还省掉「GET 谁能看、PATCH 谁能改」的差异化门禁。
- **否掉「top_k/阈值也进热读但 rerank 模型名跟着热切」**：模型名切换是 P4-3（涉及缓存 key 带模型名），v1 不做；rerank 模型名保持构造期冻结。
- **已知代价**：`flag_value` 的默认档是惰性活读 settings——测试 patch `settings.XXX` 依旧生效，但若同进程里有人写过 config 行，**config 行压过 settings 补丁**（优先级是设计使然）；测试各自独立进程 + `_cleanup_flags()` 兜底，组间串味风险已covered（module25 每组后清理）。

## 5. 遗留与触发条件

- **P4-3 模型切换 / P4-4 会话三层存储 L1**（低优先级）：注册表/路由/审计基建已就绪，接入即用。模型切换硬约束不变：qa_cache key 必须带模型名。
- **CHUNK_MODE / 嵌入模型的「开关+重建」**：设置页已注明「禁止随意切换」，真正的「确认后触发异步重建索引任务」留待后续版本（需重建任务编排）。
- **会话 TTL（`MEMORY_SESSION_TTL_SECONDS`）热化**：值本身可加进注册表，但存储层对它的消费是构造期快照（SessionStore 构造参数），热化要动 store 生命周期——等真实需求。
- **Redis pub/sub 即时失效（P2）**：TTL 60s 兜底下多副本一致性窗口存在；触发条件不变（多副本部署）。
- **module4 偶发红**：全量偶发（同版后续两次全量绿），单跑不复现；下次若复现，按「先抓失败行再判断」处理。
