## 1. 这一版做了什么（一句话）

把计划书 §15c 设计的三档超额行为（仅提醒 / 提醒+降级 / 硬阻断）**收窄为一档**：
用户 2026-10-07 拍板「不要做真的阻断或者禁用，只做提醒和看板」，
所以本版交付的是**档位的唯一合法值 + 启动时校验**，而不是三档实现。

## 3. 关键设计决策

### 3.1 另两档**刻意不存在**，连空钩子都不留

一个返回 `True` 的 `can_ask()` 或一个空实现的 `degrade_model()`
比没有它们更坏：调用方以为有开关可拨，拨了才发现什么都不会发生。
真要做阻断时的判据要重新设计（降级到哪个模型、谁承担超额），
那是一张新表 + 一轮新决策，不是在这里补一个分支。

### 3.2 🔴 配错值**启动失败**，而不是「不认识的值就当 notify」

- 把 `"block"` 静默当 `"notify"`：管理员以为配了阻断，实际什么都没发生
  —— 这正是用户明确排除的行为，却以更坏的方式出现；
- 把 `"notify"` 静默当 `"block"`：直接违反拍板口径。

两种静默都不可接受，所以宁可启动失败。校验放在 `on_startup`
（每条真实启动路径都会走到），而**判定唯一处**在 `quota_policy`
（`api/main.py` 只调它 —— 报错文案里带口径出处，三个月后的人能查到为什么）。

### 3.3 结构断言：`quota_policy` 里不许长出「允许吗」形状的函数

第 6 组有一条**结构断言**：模块里不许存在 `can_*` / `allow_*` / `should_*` 前缀的函数。
理由：有了「是否允许继续提问」这个函数，配上前端就会自然长出「禁用」按钮
—— 那正是用户明确排除的行为。15a 文件头「刻意的缺席」从此有测试守着。

## 4. 验证证据

| 项 | 结果 |
|---|---|
| `tests/test_module16_quota.py`（含 `--reverse`） | **97/0**，连跑两遍 |
| 真实启动（notify） | 正常启动，日志打印「超额行为档位 = notify（仅提醒…）」 |
| 真实启动（`TOKEN_QUOTA_OVER_ACTION=block`） | `on_startup()` 抛 `ValueError`，报错含「只能是 ['notify']」与口径出处 |
| 库回基线 | 与 15b 相同（本版不碰库） |

### 反向验证新增两条

| # | 拆掉什么 | 必须转红的断言 |
|---|---|---|
| 12 | 档位清单放开成 `("notify", "block")` | 第 6 组「只含 notify」 |
| 13 | `validate_over_action` 改成恒放行 | 「非法档位被拒」（判据两半：恒放行时非法值真的被收下 + 恢复后重新被拒） |

⚠️ 反向 13 的实现踩了一脚：在**恢复原函数之后**又调了一次 `validate("block")`
想验证「会抛」，结果 `ValueError` 逃出 `check()` 直接炸掉整个脚本 ——
抛异常的验证要在 try/except 里做，别让异常逃出断言函数。
