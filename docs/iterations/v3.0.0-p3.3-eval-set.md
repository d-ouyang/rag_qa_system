## 1. 背景（此前检索质量是「我觉得还行」）

检索链路上有四个能改的数字：`SEARCH_TOP_K`、`RERANK_CANDIDATE_MULTIPLIER`、
`RERANK_SCORE_THRESHOLD`、以及 P3-4 要加的 `RETRIEVAL_HYBRID`。
改其中任何一个，此前唯一的验收方式是「我问两句，感觉一下」。

那不是判断，是掷骰子 —— 而且是最坏的一种掷骰子：

- **样本量是 2**：随手问的两句往往恰好是「锅圈是做什么的」这类
  头部问题，它们本来就排在向量空间的中心，怎么改都不会差；
- **没有对照组**：改完觉得「好像好了」，没有改之前的数字可对照；
- **结论不可传递**：你觉得好了，别人无法复现你的「两句话」。

P3-4 要把 BM25 + RRF 接进召回，**这类改动的收益本来就薄**（几十条候选里
多捞回一两条），薄收益配掷骰子式验收，结果必然是「为了做功能而开」。

所以本项只做一件事：**把「好」变成三个可复现的数字**。

---

## 2. 方案

```
data/eval/golden.jsonl        40 条人工标注（30 库内 + 10 库外）
        │
        ▼
scripts/eval_retrieval.py     每题按 k=5/10/20 各检索一次
        │                     （复用生产配置：top_k、候选池倍数、reranker、阈值）
        ▼
data/eval/results/<ts>-<tag>.json
        │                     recall@5/10/20 · MRR@10 · 拒答正确率
        ▼
--compare <baseline>          打印 A/B 差值 + P3-4 的三条达标判据
```

- **标注用真实 chunk_id**（`"<doc_id>:<chunk_index>"` 契约），
  逐条用 `get_chunk_by_position()` 反查确认正文真的相关，
  并可随时用 `--validate-only` 全量复核（知识库重建后 doc_id 会变，标注会整批失效）。
- **指标定义写在脚本文件头**，改定义必须先改那段注释 ——
  否则历史结果不可比，而「不可比的历史结果」比没有历史结果更危险。

## 3. 被否掉的方案 / 要紧的取舍

### 3.1 「一次取 20 条，再截前缀算 recall@5」— 否掉

这是最容易想到的省事写法（省 2/3 的远程重排调用）。但它测的不是线上：

| | 候选池 | recall@5 的含义 |
|---|---|---|
| 一次取 20 截前缀 | `20 × 4 = 80`（全库 90 片的一大半） | **在 80 条候选里重排后的前 5 条** |
| 线上真实 | `5 × 4 = 20` | 在 20 条候选里重排后的前 5 条 |

差别不是精度问题，是**偏差方向随改动而变**：候选池越大，recall@5 越乐观，
而「扩大候选池」恰好就是 P3-4 混合召回的卖点 —— 用它做 A/B 会系统性高估收益。
所以 k=5/10/20 **各跑一次**，远程调用 ×3（40 题 × 3 = 120 次，实测 93 秒）。
换来的结论是：**打印出来的 recall@5 就是线上那个 recall@5**。

### 3.2 recall 用「至少命中一条 = 1」的 hit 型 — 否掉

五条相关只找回一条，hit 型仍给满分 1.0。检索退化最常见的形态恰恰是
「找得回来但找不全」，hit 型对它完全不敏感。

本项两个都算、都打印，**主指标是比例型 recall**（命中数 ÷ 标注数），
hit 型降为辅助项（直觉更好读）。两者的差距在 §5 的 baseline 里已经看得见：
`recall@5 = 0.8944` 而 `hit@5 = 0.9667`。

### 3.3 拒答正确率的分母取全部 40 条 — 否掉

混成一个分数后，「该拒的拒了（+）」与「该答的也拒了（−）」会互相抵消：
一个涨一个跌，总分纹丝不动，看着没变化其实两个方向都变了。

- **拒答正确率** = 库外 10 条里被正确拒答的比例（PLAN 的达标判据写的是
  「10/10 保持」，分母就是库外题）；
- **库内误拒数** 单列（辅助项），不并进那个分数。

### 3.4 在评测脚本里再写一份 chunk_id 解析 — 否掉

`"<doc_id>:<chunk_index>"` 的解析在运行时已有两处同构实现
（`core/retriever._candidate_brief` 与 `rag_chain._resolve_chunk_id`），
由 `test_module5` 的同构断言守着。再加第三处，迟早漂移，
而漂移的症状是「recall 悄悄掉到 0」，不会报错。
本脚本直接 `from core.retriever import _candidate_brief`，
并由 module19 的源码级断言钉住「不许自己再写一遍」。

### 3.5 把评测跑进 `make test`（离线回归）— 否掉

真评测要联网（远程 embedding + 远程 rerank）且要真库（90 片），
跑一次 93 秒 —— 塞进离线回归，等于给每次回归挂一个「网络一抖就红」的定时炸弹，
而且会把「指标算错了」和「今天网不好」混成同一种红。

拆成两半：

- **`tests/test_module19_eval.py`（进沙箱回归，离线）**：用**假检索器**
  驱动 `evaluate_case`，只验「算得对不对」—— 指标定义、实验协议、
  拒答口径、落盘与对比、Makefile 目标，外加 4 条反向验证；
- **`make eval-retrieval`（手动，联网）**：真跑，数字落盘。

### 3.6 顺手评测「答案写得对不对」— 否掉（留作边界）

那是另一套东西：需要按答案质量的人工评分标准，且要区分「检索错了」
与「检索对了但 LLM 写坏了」。本项只回答**检索**的两个问题：
该找的找回来了吗、排得够靠前吗。

### 3.7 用 LLM 自动生成标注 — 否掉

让模型去问、再让模型去标，等于让考生自己出卷自己批。
标注里最有价值的部分恰恰是**人认定的「这条也应该被找到」**，
而模型只会标它自己找得到的那些 —— 那会把现有检索的盲区原样固化成「标准答案」。

## 4. 实现

### 4.0 前置：语料探底（一次性）

BM25 建索引的输入就是这批语料，P3-4 开工前必须知道它长什么样：

| 项 | 实测 |
|---|---|
| Chroma 全量切片 | **90 chunks** |
| 覆盖文件 | **35 份**，`doc_id` 范围 **588~622** |
| 正文非空 | **全部 90 条非空**（BM25 可直接用） |
| chunk_id 重复 | 无 |

⚠️ 与 PLAN §P3-3 正文里的「69 片」不一致 —— PLAN 写于早期，
期间知识库扩到 35 份 / 90 片。**以 90 为准**，PLAN 的数字是历史快照。

### 4.1 评测集 `data/eval/golden.jsonl`

40 条，配比按 PLAN 执行：

| 分类 | 条数 | 形态 | 举例 |
|---|---|---|---|
| `term` | 10 | 专有名词 / 制度名精确查询 | 「锅圈的股票代码是多少？」「华鼎冷链和锅圈是什么关系？」 |
| `numbered` | 8 | 编号 / 条款类 | 「GQ-HR-2026-005 是哪份文件？」「考勤制度第七条怎么规定的？」 |
| `paraphrase` | 7 | 口语化改写（答案在库里但问法不同） | 「我今天迟到了十几分钟，公司会怎么处理？」 |
| `cross` | 5 | 跨文档综合（标注 2~3 个不同文档的切片） | 「新人入职要办哪些手续、填哪些表？」 |
| `out_of_scope` | 10 | 库外（`should_answer=false`） | 天气、写诗、房价、Kubernetes 对比 |

标注方法：先 dump 出全量 `doc_id:chunk_index → 文件名 → 正文摘要` 映射，
逐题人工挑出相关切片，再用 `get_chunk_by_position()` 反查确认正文**真的**包含答案，
最后 `--validate-only` 全量复核 —— **50 个 chunk_id 全部命中库内真实切片**。

## 5. 验收证据

### 5.1 基线数字（纯向量召回 + bge-reranker-v2-m3，阈值 0.1）

`make eval-retrieval` → `data/eval/results/20261012-001334-baseline.json`

| 指标 | 基线 |
|---|---|
| `recall@5` | **0.8944** |
| `recall@10` | **0.9389** |
| `recall@20` | **0.9389** |
| `hit@5` / `hit@10` / `hit@20` | 0.9667 / 1.0000 / 1.0000 |
| `mrr@10` | **0.8889** |
| 拒答正确率 | **1.0000**（库外 10/10；辅助：库内误拒 0/30） |

分类下钻（recall@20 / mrr@10）：

| 分类 | n | recall@20 | mrr@10 |
|---|---|---|---|
| `term` | 10 | 1.0000 | 0.7833 |
| `numbered` | 8 | 1.0000 | 0.8542 |
| `paraphrase` | 7 | 0.9286 | 1.0000 |
| `cross` | 5 | **0.7333** | 1.0000 |
| `out_of_scope` | 10 | — | — |

**数字可复现**：同一份评测集连跑两遍（`00:11:38` 与 `00:13:34`），
六项指标逐位一致（93s 两遍），说明远程 rerank 在本规模下无抖动。

### 5.2 三条已经能读出来的结论

1. **`recall@10 == recall@20 == 0.9389`** —— 窗口从 10 拉到 20 一条都没多捞回来。
   加上 `hit@10` 已经是 1.0，说明当前瓶颈**不在召回面窄，在排序**：
   该找的切片基本都进了候选池，只是没排进前 5。
   👉 **对 P3-4 的直接含义**：BM25 的卖点是「扩召回面」，而这里缺的不是召回面。
   它要达标（recall@20 +5pp）得靠把 cross 类那 0.7333 顶上去，难度不小。
2. **最弱的是 `cross`（跨文档综合，0.7333）** —— 这类题标注了 3 个不同文档的切片，
   丢的那条通常是「沾边但表述不同的第二份文档」，正是向量召回最容易漏的形状。
   这是 BM25 理论上唯一有戏的地方。
3. **唯一完全未命中的是 `q017`（GQ-AD-2026-003 是哪份指引）** ——
   编号类查询里「编号字符串本身」在正文里只出现一次，向量化后与
   「行政制度」这类语义近邻拉不开距离。这是 BM25 的经典主场（词项精确匹配）。

### 5.3 回归

| 项 | 结果 |
|---|---|
| `tests/test_module19_eval.py` | **56 / 0**（连跑两遍） |
| 同上 `--reverse` | **60 / 0**（4 条反向：recall 退化成 hit 型 / 拒答分母改全量 / 协议改成截前缀 / 脚本里塞清库调用，均转红） |
| `scripts/eval_retrieval.py --validate-only` | **50 / 50** 个 chunk_id 全部命中库内真实切片 |
| `make kb-guard-count` | 35 / 35（本版只读，跑前跑后一致） |

覆盖的关键不变量：

- recall 是**比例型**（两条相关只中一条 = 0.5，不是 1.0），且随 k 单调不降；
- 每个 k **各检索一次**（源码级：`for k in k_values` + `retrieve(..., top_k=k)`）；
- 拒答判定用**最小档**（线上 top_k）的结果，分母只取库外题；
- 评测脚本**只读**（源码里不出现任何 `clear_all` / `delete_by_*` / `add_documents`）；
- 结果带**评测集指纹**，两份指纹不同时 `--compare` 显式警告「不可比」。

## 6. 风险与已知边界

1. **标注是单人一次性完成的**：40 条里「这条算不算相关」有主观成分。
   缓解方式是每条都写了 `note`（为什么它相关），事后可复核；
   但**它不足以支撑「recall 提升 1pp 也算赢」级别的结论** ——
   所以 P3-4 的门槛定在 5pp，正是为了跨过标注噪声。
2. **库只有 90 片，评测分辨率有限**：1 条题的变化 ≈ 2.5pp。
   小样本上的百分比容易大起大落，看数字时要连着「命中条数」一起看。
3. **知识库重建会让整批标注失效**（doc_id 变）。
   `--validate-only` 是兜底，但**没有自动化门禁**：
   建议以后把「跑评测前先 validate」写进 rechunk 的操作步骤。
4. **真评测要联网**：远程 embedding + 远程 rerank，40 题 93 秒。
   断网时 `make eval-retrieval` 会失败 —— 这是设计选择（§3.5），不是 bug。
5. **不覆盖生成质量**：检索全对而答案写坏，本评测看不出来。
