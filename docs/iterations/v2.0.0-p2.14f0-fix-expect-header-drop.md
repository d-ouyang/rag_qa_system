# v2.0.0-p2.14f0 —— 修一个静默失效的鉴权缺陷：`Expect: 100-continue` 让网关不注入身份头

> 本迭代是** unplanned 的**：它不在计划书里，是在做 14f（管理端下发知识库写权限）
> 的真链路探测时撞出来的。之所以单独拆一个版本号而不是并进 14f，是因为它的
> 影响面与性质完全不同 —— 它不是「加一个功能」，是「补一个所有人都能踩、
> 且踩了不报错」的洞。

|项 | 内容 |
|---|---|
| **修什么** | 网关在「客户端带 `Expect: 100-continue`」时**完全不注入身份头**，请求以 break-glass 超管身份到达后端 |

## 3. 关键设计决策（含否掉的方案）

### 3.1 根因：`http-proxy` 的 `proxyReq` 事件有一个 `expect` 条件门

`node_modules/http-proxy/lib/http-proxy/passes/web-incoming.js`：

```js
proxyReq.on('socket', function(socket) {
  if(server && !proxyReq.getHeader('expect')) {     // ← 客户端带 Expect，事件根本不触发
    server.emit('proxyReq', proxyReq, req, res, options);
  }
});
```

12b 把「无条件剥离客户端伪造的身份头」与「注入真实身份」**全都**放在了这个事件的
回调里。头一出现，回调一次都不跑。

### 3.2 实测证据（本机，2026-10-10）

复现脚本八个场景的原始输出：

```
身份头在   | A GET 无 Expect（基线） | 442,chen.jie,user,105
身份头在   | B POST multipart 无 Expect | 442,chen.jie,user,105
身份头丢失 | C POST multipart 带 Expect | ,,,
身份头丢失 | G 旧写法 + 伪造身份头 + 带 Expect | 440,wu.jing,admin,
身份头在   | D 入站盖头 + 带 Expect | 442,chen.jie,user,105
身份头在   | E 入站盖头 + 无 Expect | 442,chen.jie,user,105
身份头在   | H 入站盖头 + 伪造头 + 带 Expect | 442,chen.jie,user,105
身份头在   | F 只摘 expect + 带 Expect | 442,chen.jie,user,105
```

**G 行是本迭代存在的理由**：下游收到的是 `440 / wu.jing / admin` —— 客户端填的
伪造值原样穿透。12b 当年量化过的那条「`X-User-Id` 伪造可生效」，换了个入口。

### 3.3 修法：改**入站** `req.headers`，而不是 `proxyReq`

`http-proxy` 的 `common.setupOutgoing()` 第 43 行：

```js
outgoing.headers = extend({}, req.headers);   // 整个复制过去
```

所以在转发前改入接头，与改 `proxyReq` 的**最终效果完全一致**，但**不依赖那个
「可能不触发」的事件**。两个 handler 各加一行 `this.stampIdentityOnInbound(req)`。

### 3.4 顺带摘掉 `Expect`（不是顺便，是必要的）

摘掉之后 `proxyReq` 事件才会触发，`fixRequestBody` 与 `Accept-Encoding: identity`
才有地方执行 —— 否则这两件事在带 `Expect` 的请求上会一起失效（症状是「上传体是空的」
或「NDJSON 被 gzip 攒成一坨」）。

**代价**（已评估，可接受）：客户端的 `100-continue` 握手不再透传到后端。
- `Expect` 按 RFC 7231 §5.1.1 是**逐跳头**，代理剥掉它本就是合规的；
- 握手已经在「客户端 ↔ 网关」这一跳完成了（网关的 http server 自动回 `100 Continue`），
  后端直接收到完整请求体，不需要再问一次；
- 摘掉也不会让网关提前转发 body —— body 一直在流上 pipe，与 `Expect` 无关。

### 3.5 三条否掉的方案

| 否掉的方案 | 为什么否 |
|---|---|
| **在 `proxyReq` 里加个 `else` 分支，`expect` 存在时手动补一遍** | 补的时机在 socket 事件之后，客户端的 `100-continue` 已经握过手、头可能已发出（`ERR_HTTP_HEADERS_SENT`）。修法要成立就必须抢在 socket 事件之前，而那里唯一能改的是入站头 —— 也就是说方案③就是正解，多加一层只是把它复杂化。 |
| **给后端加「缺身份头时自己解析 JWT」** | 会造出**第二个认证入口**。现在「认证只有一个入口（网关）」是 `core/identity.py` 整份文件的地基，加第二条路等于把它抽掉。而且它治不了伪造头穿透（后端没有密钥可验）。 |
| **在 `INBOUND_IDENTITY_HEADERS` 里把 `expect` 也剥掉** | 语义错位。那个清单是「**身份**头」，`Expect` 是传输层逐跳头。混进去会让后来人以为「`Expect` 与身份安全有关」，而它与身份安全的关系是**间接的**（通过「事件不触发」）。混在一起反而掩盖了真正的机制。 |

### 3.6 一条被顺手改掉的旧断言（写在这儿是因为它本身是个教训）

`test_module14_trust_boundary.py` 原来断言「剥离走的是 `removeHeader`」。
14f 把剥离改成入站头的 `delete req.headers[h]` 之后它就红了。

改掉它**不是因为新写法不好**，而是**它验的是 API 名、不是意图**。意图是
「剥离后这个头是**缺失**，而不是空串」—— 空串会让后端读到 `''`，而按
`if user_id_header:` 判断的代码把 `''` 和缺失当同一件事，只有按
`header is not None` 判断的代码才区分。改成按意图断言（接受 `removeHeader`
或 `delete`，拒绝 `= ''`），并用反向验证确认判据有判别力。

## 6. 已知边界

1. **只验了 `http-proxy@1.18.1` / `http-proxy-middleware@3.0.7`。**
   换版本后 `web-incoming.js` 里那个 `expect` 条件门可能消失（那样修法依然成立，
   变成纵深），也可能变形。`probe-expect-header-drop.cjs` 就是为此存在的 ——
   它会在换版本后立刻给出结论，而不是让人以为「一直是对的」。

2. **`Expect` 之外的其他逐跳头没处理。**
   `Connection`、`Keep-Alive` 等由 Node 自己管，我们没碰。当前不需要碰，
   但如果将来发现「还有别的头也会让事件不触发」，修法是同一个（改入站头）。

3. **`/options` 的五档字典与 `core/kb_acl` 的一致性由 14f 的测试守着**
   （`tests/test_module12_kb_role.py` 第 6 组逐档比对），不靠人记。

4. **`Accept-Encoding: identity` 仍在 `on.proxyReq` 里。**
   它在 `Expect` 场景下不生效 —— 但我们已经在入站摘掉了 `Expect`，
   所以事件会照常触发，它也就照常生效。两处的关系写在 `stampIdentityOnInbound`
   的注释里了。

### 7.1 定位过程（值得原样留着当反面教材）

1. **症状**：14f 给 `chen.jie` 授权 `kb_role=superadmin` 后，重新登录拿到新token
   （JWT payload 实测 `ver=105 kbRole=superadmin role=user`），**经网关调四条写路径仍403**；
   但**直打后端 8000 带 `X-User-Id: 442` 却放行到业务层**（`400 上传的文件内容为空`）。
2. **第一个误判**：后端日志显示 `知识库写操作被拒 | actor=admin | uid=None | source=breakglass`
   —— 请求没带身份头到达后端。于是我判断「所有 multipart POST 的身份头都丢了」，
   并开始怀疑 `fixRequestBody`、`proxy.controller.ts` 的语句顺序、`JwtStrategy.validate`、
   `decidePath`（逐个排除，都没问题）。
3. **第二个误判**：加临时回显路由对比，发现 **GET 经网关五个身份头全在、
   POST multipart 经网关全部缺失**。看上去 multipart 就是原因。
   ⚠️ 但**浏览器实测（页面上下文 `fetch` 发 multipart）是正常的** ——
   这条矛盾本该立刻推翻 multipart 假设，我当时没重视。
4. **真相**：为了缩小范围，我加了一组「带/不带 Expect」的对照实验，
   显式加 `-H "Expect: 100-continue"` 时**身份头全丢**，不带孩子全在。
   而 multipart 从头到尾都是无辜的。
5. **我自己制造了那个现象**：最早那批探测脚本里，我为了「模拟真实客户端上传」
   显式写了 `Expect: 100-continue`（当时是随手加的，理由已经忘了），
   于是把「客户端行为」当成了「服务端缺陷」。

**教训**（已写进踩坑清单第 53条）：

> 当「某类请求必然失败、另一类必然成功」时，先怀疑**两组请求的共同差异**，
> 再怀疑它们的**语义差异**。我一路在想「multipart 有什么特别」，
> 而真正的差异是我自己在命令行里加的一个头。
>
> 更具体地说：**加对照实验时，一次只改一个变量。** 我当时
> 「带 Expect 的 multipart」和「不带 Expect 的 GET」对比 —— 改了两个变量，
> 所以得出的结论必然不可靠。
