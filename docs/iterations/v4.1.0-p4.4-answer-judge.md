# v4.1.0-p4.4 — 答案级语义评测：模型当裁判，给忠实度和可用性打分

> 一句话：检索指标答不了「检索对了但模型编了」，这一层补上。
> 首版数字难看（3.48 / 0.58），查下去发现是**裁判看不见片段全文**，不是产品变差——这个排查过程本身比脚本值钱。

---

## 1. 背景（结论先行）

现有三层评测，中间有洞：

| 层 | 脚本 | 答的问题 | 盲区 |
|---|---|---|---|
| 检索 | `eval_retrieval.py` + `check_golden_gate.py` | 对的 chunk 有没有进前 5 | 检索对了≠答对了 |
| 生成约束 | `eval_answer_guard.py` | 有没有踩**已知**禁语 | 只覆盖枚举过的 2 条 |
| 语义 | **本迭代 `eval_judge.py`** | 答案有没有编、够不够用 | — |

q041（病假扣薪）就是典型的洞：考勤制度只写"病假凭证明"，检索到了、也没踩禁语，模型却用常识补出了"扣薪比例"。这类问题只能靠读懂答案来判。

## 2. 方案（实现）

`scripts/eval_judge.py`，跑真实链路 + 模型裁判，两条判据：

- **faithful**：只判有没有编造。答案里的每条事实能否在片段找到依据，或明确说了"资料未涉及"。
- **score 0-5**：判能不能直接用。5 直接可用 / 3 漏关键细节要再问 / 2 有错 / 0 全编。

关键工程决策：

1. **每题跑 3 次取中位数**。`temperature=0` 在后端不等于确定性（浮点累加顺序、批处理分组都会变）。score 取中位数、faithful 取多数票（平票判不忠实，保守侧）。
2. **片段取 chunk 全文，不用接口的 200 字 snippet**。见 §3.2，这是本迭代最大的坑。
3. **`--replay` 复用历史答案只重跑裁判**。比 rubric、比裁判模型时必须控变量，否则分不清是"改判据"还是"模型这次心情不同"。
4. **判分失败不摊进平均分**。没拿到裁决的题单独计数并让门禁红——"没测"不能算"考得不错"。
5. **门槛只看下限**。avg 高但有一条编造仍然不过：用户看到的是一条具体答案，不是平均分。
6. **基线记 `judge_model` 与 `context_mode`**。换裁判就是换尺子，分数不可跨模型比较。

对外入口：

```bash
make eval-judge                                        # 跑全部内域题，每题 3 次
make eval-judge ARGS="--id q022 --repeat 1"            # 单题复现
make eval-judge ARGS="--init-baseline --tag <version>" # 首版/换尺子后重建基线
make eval-judge ARGS="--use-baseline"                  # 按基线阈值判定，不过即退出码 1
make eval-judge ARGS="--replay <result.json>"          # 复用答案，只重跑裁判
```

## 3. 验证

### 3.1 单测 22 项

`tests/test_module30_eval_judge.py`（编号 27/28/29 已被占用）。只测纯函数：裁判输出解析、片段拼装、中位数/多数票、分母口径、阈值判定、外域题筛选。

其中一条测出真 bug：`faithful` 是字符串时，原实现把**任何**无法识别的词都映射成 `False`——等于把"裁判没看懂"记成"答案不忠实"。已改为白名单 + 抛错。

### 3.2 首版数字难看，但错在评测本身

首版（snippet 模式 + 初版 rubric）：**均分 3.4839 / 忠实率 0.5806**，13 题判不忠实。而检索 recall@5 是 0.9086。

抽查发现裁判的 reason 明显不对：

- q030 答案如实列了 20 个登记表字段，裁判说"遗漏了最高学历、毕业院校……银行卡号"——**这些字段答案里全都有**。
- q013 答案已写"资料未涉及凭证类型"，裁判仍判不忠实——而 rubric 明确写了"说了资料没有不扣分"。

查片段：`sources[].snippet` 是接口侧 **200 字截断**。q030 的片段[1] 是表格，200 字正好停在"最高学历"，后面十几个字段被切掉。答案照着表格答，裁判看不到 → 判编造。

**这不是产品退化，是量具坏了。** 若直接把这个 0.58 写进基线，门禁从此红着，等于没有门禁（与 p4.3 记的教训同型）。

修两处：

1. **rubric 把"覆盖度"和"忠实度"解耦**：省略不是不忠实；"资料未涉及"是正确回答；只判说出口的内容对不对。
2. **片段改取 chunk 全文**（`fetch_chunk_contents`，1200 字上限），取不到才退回 snippet 并打日志。

### 3.3 第二个坑：全文换来了"一律满分"

改完全文后同样是 5 题：**5.0 / 1.0**。跳变太大，继续查 reason——变成"未添加或遗漏关键信息"这种笼统话。Qwen2.5-7B 面对 2000+ 字上下文开始偷懒，不逐条核对。

换 `deepseek-ai/DeepSeek-V3` 用 `--replay` 跑同一批答案：仍 5.0/1.0，但 reason 具体且准确。结论：这 5 条确实答得好，7B 的问题是"说不出为什么"。

### 3.4 阳性对照（这一步不能省）

裁判说"没问题"不等于没问题。造三条已知答案验证分辨力：

| 输入 | Qwen2.5-7B | DeepSeek-V3 |
|---|---|---|
| 编造（片段无扣薪规定，答"扣 30%"） | false / 2 ✅ | false / 2 ✅ |
| 诚实（"资料未提及计算方式"） | true / 3 ✅ | true / 5 ✅ |
| 答对（照抄片段要点） | true / 5 ✅ | true / 5 ✅ |

两个模型都能分辨编造与诚实。裁判有效。

### 3.5 全量首版结果

31 道内域题 × 每题 3 次裁决，裁判 DeepSeek-V3，chunk 全文：

```
有效裁决 31/31
均分 4.7742（最低 2）
忠实率 0.9677
低分/不忠实：q022
```

基线（留一档余地，不是为通过而放宽）：

```json
"judge": {
  "judge_model": "deepseek-ai/DeepSeek-V3",
  "context_mode": "chunk_full",
  "thresholds": {"judge_score_avg": 4.47, "faithful_rate": 0.92}

```

门禁正反验证：真实结果 `--use-baseline` → PASS；伪造一条链路异常 → FAIL（`1 题未取得有效裁决`）。

### 3.6 首跑抓到的真缺陷：q022

> 「离职之后我的企业微信和 OA 账号什么时候会被关掉？」
> 答：「资料中提到 IT 部于员工离职当日统一注销全部系统账号，但未具体说明企业微信和 OA 账号的注销时间。」

片段《劳动合同解除协议书》第三条写得很清楚：「乙方名下 IT 系统账号（OA、企业微信、UPMS、GitLab…）由 IT 部于离职当日统一注销」。

这是**幻觉式否定**——比编造更隐蔽，因为措辞非常谨慎（"未具体说明"听着像严谨）。已记入基线 `_known_failures`。

## 4. 否掉的方案

| 方案 | 否掉原因 |
|---|---|
| 接 RAGAS / DeepEval | 现有链路已经能跑真实问答，只差一个裁判。引框架要背依赖、背版本（RAGAS 0.4.3 后 9 个月未合 PR），收益接近零 |
| 人工打标 | 42 题 × 每次改动，不可持续；人工只该用来校准裁判（§3.4） |
| 只看均分 | 掩盖单条编造。q022 均分 4.77 里毫不起眼，但它就是最该拦的那条 |
| 裁判也用主模型（7B） | 能判对错但说不出理由，无法判断"判对了还是蒙对了"；固定用 DeepSeek-V3 |
| 把 judge 挂进 answer_guard | answer_guard 只有 2 条枚举特例，覆盖面太窄；judge 跑 golden 全量才有统计意义 |

## 5. 已知边界与遗留项

1. **判分成本**：31 题 × 3 次 ≈ 100 次调用/轮，约几分钱、5 分钟。不进每次 PR，只在改 prompt/切分/模型/换裁判时跑。
2. **只用 200 字 snippet 的模式不能用来建基线**：`--snippet-only` 只为复现历史结果，判据强度不同。
3. **表格类切片仍可能被 1200 字截断**：`MAX_SNIPPET_CHARS` 是权衡值，遇到超长表格要单独调。
4. **多轮题只判最后一轮**：沿用 answer_guard 的口径，中间轮次的忠实度未覆盖。
5. **既有失败（不是本迭代引入）**：`tests/test_golden_gate.py::test_stale_result_blocked` 红。该用例期望 `20261012-001334-baseline.json`（recall@5 0.8944 / hit@5 0.9667）被拦，但 p4.3 把阈值追平到 42 题口径后它已全部达标。已用 `git stash` 回退本迭代改动验证：**改动前同样红**。修法是把用例换成真正低于阈值的样本，而不是改期望值——留待单独处理。
