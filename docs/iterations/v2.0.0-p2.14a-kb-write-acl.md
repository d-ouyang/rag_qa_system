## 1. 范围

### 做了什么

1. **`user.kb_role` 权限维度**（迁移 `0006`）—— 谁能改全公司共用的那个知识库，
   五档 `none` / `ops` / `qa` / `dev` / `superadmin`，**默认 `none`**。
2. **`core/kb_acl.py`** —— 判定的**唯一出处**，纯函数、不起库。
3. **四条写路由逐条挂守卫**（14c）—— `upload` / `upload/batch` / `reparse` / `delete`。
4. **写操作落 `audit_log`** —— 三个新动作 `document.upload` / `document.delete` /
   `document.reparse`，`target_type="document"`。

### 明确不做什么（留给后续版本）

| 项 | 归属 | 原因 |
|---|---|---|
| 网关路径粗筛、`kb_role` 进 JWT | **14b** | 本轮判定在后端；网关那道门还没做 |
| 前端上传区 / 删除按钮显隐 | **14d** | 本轮只锁后端，界面还看不到 `kb_role` |
| 越权回归专项 + **结构断言** | **14e** | 本轮用真链路手工验证，尚未固化成回归 |
| 管理端下发授权（`PATCH .../kb-role`） | **14f** | 现在只能直接改库，界面上还没有入口 |
| `reindex` 的 HTTP 接口 | **不做** | 它是 `scripts/reindex.py`，不在 HTTP 面上。依赖 `require_kb_reindex` 已备好 |

### 为什么审计单独建 `kb_service` 而不是塞进 `admin_service`

13b 立过的规矩：**路由只收参，写操作全部收口在服务层**，理由是「审计只需在这一层加一行」。
知识库写操作与人事写操作是**两套 `audit_repo` 调用**，混在一个服务层里会让
「人事动作」与「知识库动作」的边界消失 —— 比如将来若要给知识库审计单独加保留期，
按 `target_type` 过滤比按「在哪个服务文件里」过滤可靠得多。

## 3. 关键设计决策

### 3.1 为什么不塞进 `user.role`（本轮最要紧的决定）

`user.role` 三档（`admin` / `hr` / `user`）管「**能不能进管理端**」，
判据在 `core/identity.py` 的 `STAFF_ROLES` / `is_admin()`。往里加第四个值会：

1. **让管理端权限一起漂** —— 任何一处 `role == "admin"` 的分支都要重新审。
   这是 P2-11b 踩过的「一处改处处受影响」，那次是 141 条断言才兜住的；
2. **表达不了真实存在的组合** —— `role=user`（进不了管理端）+ `kb_role=ops`
   （该维护知识库）完全合法。塞进一个字段只能靠加特例分支；
3. **让「改 role」的语义变含糊** —— `set_role()` 会 `token_version+1`，
   「改知识库权限」该不该踢人下线是另一个问题（D15 已定：要踢，但那是函数自己的决定）。

**代价**（写进迁移 0006 的文件头，因为它是真实的负担）：
「谁能改知识库」与「谁是管理员」不再有推导关系 —— 一个 `kb_role=superadmin`
但 `role=user` 的人能删知识库却进不了管理端。**必须靠 `audit_log` 才查得到谁干的**，
而审计不能防「有 DB 写权限的人直接改库」（13d §3.5 已写明这条边界）。

### 3.2 否掉的方案

| 方案 | 为什么否 |
|---|---|
| 建 `project` + `user_project` 按库授权（第 4 版 D13） | **库里从来没有 `project` 表**；且共用决策之后不存在「多个库」，这列权限无处安放。照它实现会去建一张不该建的表 |
| 默认值给 `ops` 或 `superadmin` | fail-closed 反了。**管理员改权限的频率远低于加人的频率** —— 默认值写错的那条路径会被走到多得多。新人默认 `none`，要授权必须有人明确动手 |
| 权限判定写在路由函数体里 | `Depends` 列表会变空，而**14e 的结构断言正是靠这张列表判断守卫有没有挂上**。判据不能同时被它保护的东西削弱 |
| `kb_role` 做成有序门槛（`min_kb_role`） | 五档**不是全序**：`qa` 与 `dev` 权限完全相同。排成一条线会让人以为「dev 比 qa 强」 |
| 把 `_purge_document` / `_accept_one_upload` 搬进 `kb_service` | 会让这个 diff 从「加权限」变成「搬代码 + 加权限」，更难审、更容易在 review 里被漏掉。真正的收口是**权限判定与审计**只在一处 |
| 审计与业务同事务（审计写不进就回滚） | 与 13d 同一取舍：会让只读的历史表变成业务单点（审计表满了就没人能改知识库） |

### 3.3 break-glass 超管的 `kb_role` 给 `none` 而不是 `superadmin`

`.env` 里那个不在 `user` 表里的内置超管，`kb_role=none`。

它能做的一切**管理端**操作靠的是 `role=ROLE_ADMIN`（`can_staff`），那些不依赖 `kb_role`。
真的需要它改知识库时（连不上库、库里那个超管被停用），正解是**往库里补一行并授权**，
而不是让一个不在库里的身份天然持有「删掉全公司知识库」的能力。

## 4. 配置与接口变化

### 数据结构

- `user` 表新增 `kb_role VARCHAR(16) NOT NULL DEFAULT 'none'` + `idx_user_kb_role`
- 迁移：`0006`（`down_revision = "0005"`，可 up/down 往返）

### 接口

**没有新增 HTTP 接口。** 四条写路由的行为变了：

| 路由 | 改前 | 改后 |
|---|---|---|
| `POST /api/v1/documents/upload` | 任何登录用户 → 202 | `kb_role` 不含 upload → **403** |
| `POST /api/v1/documents/upload/batch` | 同上 | 同上 |
| `POST /api/v1/documents/{doc_id}/reparse` | 同上 | 同上 |
| `DELETE /api/v1/documents/{doc_id}` | 同上 | `kb_role` 不含 delete → **403** |
| `GET` 系列（列表 / 统计 / 下载 / 切片） | 放行 | **不变**（共用决策：读不隔离） |

403 的响应体：`{"detail": "没有权限执行「上传知识库文档」，请联系管理员开通知识库维护权限"}`
（**不含**「你的 kb_role 是什么」—— 与 11b 的防枚举一致）

### `GET /api/v1/admin/me` 的响应新增三个键

```json
"permissions": {
  "staff": true, "reset_password": true, "manage_org": true,
  "kb_upload": true, "kb_delete": true, "kb_reindex": true     // ← 新增
}
```

### env

**无新增配置项。** 五档是硬编码的枚举，不是可配置项 ——
理由与 `user.role` / `user.status` 一样：取值集合要有单一出处（`core/kb_acl.py`），
而可配置会让人改出「有第三种状态」的局面。

### 5.1 真链路：普通员工的四条写路由全部 403

```
=== chen.jie (kb_role=none) 四条写路由 ===
POST   /upload        -> 403  {"detail":"没有权限执行「上传知识库文档」，请联系管理员开通知识库维护权限"}
POST   /upload/batch  -> 403  {"detail":"没有权限执行「上传知识库文档」，请联系管理员开通知识库维护权限"}
POST   /1/reparse     -> 403  {"detail":"没有权限执行「上传知识库文档」，请联系管理员开通知识库维护权限"}

GET    /（读，放行）    -> 200  total=35
```

```
(1483,'wu.jing','document.delete',717,'acl_ok_batch.txt','{"deleted_chunks":0,"file_removed":true,"reason":"主动删除","record_removed":true}','127.0.0.1')
```

### 5.3 迁移往返

```
alembic downgrade 0005 → downgrade 后还有 kb_role 吗: False
alembic upgrade head  → [('none', 11)]    ← 回来全是默认 none（fail-closed）
document: 35
```

⚠️ 往返会**丢授权数据**（列被 DROP 了）。这是DDL 的固有性质，不是缺陷 ——
但要知道：**生产上不要对已有授权的库做 downgrade**。

### 5.4 回归（连跑，护栏已确认知识库 35/35）

| 模块 | 结果 |
|---|---|
| `test_module11_account` | **141 / 0** |
| `test_module12_admin` | **79 / 0** |
| `test_module12_audit` | **64 / 0** |
| `test_module14_trust_boundary` | **47 / 0** |
| `test_module15_session_isolation` | **48 / 0** |

`compare_metadata` diff = 0（这一条在本轮真的抓到东西，见 §6.1）。

### 5.5 反向验证（拆掉守卫必须转红）

拆掉三条 upload/reparse 路由的 `Depends(require_kb_upload)` 后重启：

```
POST /upload -> 202  {"doc_id":718,...}    ← 拆掉后普通员工立刻能传
DELETE /718  -> 403  {"detail":"没有权限执行「删除知识库文档」..."}   ← delete 守卫仍在
```

**两个结论**：① 守卫确实在起作用（拆掉即穿透）；② **部分拆掉也能被检出** ——
delete 仍然 403 说明「拆一部分」不会让另一部分失效，反过来也说明
「三条 upload 一起失效」不是 `require_kb_upload` 这个对象的副作用。

## 6. 已知边界与遗留项

### 6.1 `compare_metadata` 当场抓到两处注释不一致（本轮的一个教训）

迁移 0006 里 `kb_role` 的列注释我写成「知识库写权限：…」，而 `core/schema.py` 里写成
「知识库写权限(P2-14a)：…」，差一个 `(P2-14a)`。于是 `test_module11_account` 报：

```
[FAIL] 七张表与 core/schema.py 完全一致  diff=[
  ('modify_comment', None, 'user', 'kb_role', ..., '知识库写权限：none(只读,默认)/…',
   '知识库写权限(P2-14a)：none(只读,默认)/…'),
  ('modify_comment', None, 'department', 'leader_user_id', ..., '按 P2-14 的 D13，默认是…writer',
   '知识库是全公司共用的，写权限改由 user.kb_role 授予…')]
```

**这正是那个守卫存在的意义** —— 两处各写一份注释（结构快照 vs 查询侧视图是两份文件，
本项目刻意不合并），漂了就自动抓到。修法是对齐两边 + 同步改库。

⚠️ **对齐已有库的注释需要手工 `ALTER TABLE ... MODIFY COLUMN`**（迁移已经跑过了，
再跑一次不会执行）。这是「迁移跑过之后改了迁移文件」的固有代价 ——
**所以迁移文件一旦 tag 就不要再改注释**。

### 6.2 拒权路径本身要能正常返回（本轮抓到的一个真 bug）

第一版 `kb_acl.describe()` 的参数名是 `kb_role`，函数体里用的是 `action`：

```python
def describe(kb_role: Any) -> str:
    ...
    }.get(action, "该操作")     # ← NameError
```

症状是：**判定生效了但响应是 500** —

```
WARNING - core.identity - 知识库写操作被拒 | action=upload | actor=chen.jie   ← 判定是对的
NameError: name 'action' is not defined
INFO: POST /api/v1/documents/upload HTTP/1.1" 500 Internal Server Error
```

若当时只看「普通员工的写操作没成功」就收工，会以为守卫已经做完 ——
实际上前端拿到 500 完全不知道是权限问题。

**教训**：「拒权路径本身要能正常返回 403」是一条**独立于**「权限判得对不对」的断言。
14e 必须包含它。

### 6.3 遗留项

| 项 | 说明 |
|---|---|
| **结构断言尚未固化** | 本轮靠人工枚举路由验的。14e 要写 `tests/test_module12_write_acl.py`，含「新增写路由未挂守卫必须转红」 |
| **`/api/v1/admin/me` 之外无处查档位** | 管理端拿不到别人的 `kb_role`（列表接口未透出）。14f 一并解决 |
| **`kb_role` 不进 JWT** | 本轮判定从库里实时读，所以**改完立刻生效**（实测）。14b 让 `kb_role` 进 JWT 后，网关也能读到，届时改授权会触发 `token_version+1` → 需要重登 |
| **dev 模式的 break-glass 超管不能传知识库** | 见 §3.3，是刻意的 |
| **`upload` 与 `upload/batch` 共用 `_accept_one_upload`** | 两者的守卫判定完全一样（同为 `require_kb_upload`），所以当前没有分歧。将来若想让批量走另一档，必须在**两个路由**分别改，光改共用函数会两边一起变 |
