# v4.0.0-p4.10 — 上下文滚动摘要（长会话跨轮记忆）

| **性质** | 计划内（PLAN-v4.0.0 P4-10） |
|----------|---------------------------|
| **tag** | `v4.0.0-p4.10` |
| **默认行为** | 有对话滑出记忆窗口时，自动增量压缩成摘要并随上下文带下去；无溢出时行为与旧版完全一致 |
| **新增能力** | `session_meta.summary` / `summary_upto`；热开关 `session_summary` |

## 补的是什么洞

历史全部存在库里（`_trim` 不删消息），但 `get_recent_messages` 只把最近 `MEMORY_MAX_TURNS` 轮送进模型和改写——**用户翻记录看得见，模型看不见**。第 6 轮问「第一轮说的那个流程呢」，模型没见过第一轮。

## 实现

**写入侧（增量）** `core/session_summary.summarize_overflow()`：

- 只压「上次摘要之后**新滑出窗口**的那部分 + 旧摘要」→ 一段新摘要（不每轮全量重压，省 token、也更稳）；
- 进度记在 `session_meta["summary_upto"]`（已压缩到第几条消息），下次从这里续；
- **存 `session_meta` 而不加迁移**：memory / redis / mysql 三套存储都原样往返这个 dict，加字段即全后端可用，不必动表结构（省一次迁移，也避免「表结构与 schema.py 不一致」的老问题）。

**读取侧** `MemoryManager.get_recent_messages()`：前置一条 `SystemMessage("【较早对话摘要】…")`，后面接窗口原文。**没有摘要时不多塞任何消息**（与旧版逐字一致）。

**触发**：`add_exchange` 成功后调可选钩子——**在会话锁外**（LLM 调用不该占着锁）。依赖方向是「`session_summary` 提供钩子 → `get_memory_manager()` 注入 `MemoryManager`」，这样 `memory_manager` 不需要反向依赖 `rag_chain`（否则成环）。

**姿态**：fail-open 双层（摘要函数内捕获 + 钩子外层再捕获）——摘要坏了的最坏结果是「没有摘要」，不是「会话不可用」。热开关 `session_summary` 可关。

## 真实链路验证

4 轮历史 / 窗口 2 轮 → 前两轮（品牌定位 + 愿景）滑出并被压缩为：

> 锅圈食汇定位为一站式在家吃饭餐食产品品牌、社区中央厨房，公司的愿景是在家吃就锅圈。

送进模型的上下文 = `[SystemMessage 摘要] + 最近两轮原文`；`get_messages()` 仍返回全部 **8 条**——一字未删。

## 测试

module29（新，15/0）：未溢出不调 LLM／溢出才压且 `upto` 前进／第二次只压新增且 prompt 含已有摘要／已压完幂等／LLM 异常与空返回均 fail-open／读取侧窗口条数与首条类型／无摘要时行为不变／全量历史仍在／开关关时不调 LLM。

## 明确不做

- 跨会话的用户级长期记忆 / 用户画像（另一件事，等摘要质量验证后再评估）。
- TTL 策略不变（6h 不活跃过期，运营向可调大）；「永远不忘」= TTL 调大 + 本摘要兜底窗口外。
