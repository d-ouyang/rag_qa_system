---

## 1. 背景（为什么现在要拦）

2026-10-09 系统对外上线（公网可达）。在那之前，「额度只提醒不阻断」是一个
**自洽**的决策：使用者都是内部员工，用超了无非是下个月看一眼看板。

上线之后这条推理链断了一环：**用超不再只是「多花一点」，而是「任何拿到账号的人
都可以无限量地花」**。提醒机制对一个决心刷量的人没有约束力 —— 他会看到那条
横幅，然后继续发第 1001 个问题。

所以 2026-10-11 用户拍板：加 `block` 档，超额提问直接拒绝（PLAN v3.0.0 §P3-1）。

本版同时明确**不做什么**：不降级到便宜模型、不做单轮 token 预估、不做并发精确
计量（理由见 §3）。

---

## 2. 方案（裁决 Q2：预检 + 宽限单）

```
提问 → 越权预检（403）→ 🔴 额度预检（429）→ RAG 链
```

- **判据**：`已用 >= 限量` → 拒；`已用 < 限量` → 放行。额度 ≤ 0（不限）永远放行。
- **预检点**：`/ask` 与 `/ask/stream` 各一处，共用一个 `_quota_precheck(actor)`。
  - `/ask`：在越权预检之后、`get_rag_chain().query()` 之前；
  - `/ask/stream`：**在 `return StreamingResponse` 之前**（200 头一旦发出，
    429 就只能沦为流里的一帧错误）。
- **宽限单**：判定通过后本轮不再复查。提问时没超就放行，这一轮照常答完照常计费，
  超出的部分体现在**下一问**被拦。
- **429 错误体**（结构化 dict，前端按 `code` 特化，不解析文案）：

  ```json
  {"detail": {"code": "quota_exceeded", "used": 100231, "quota": 100000,
              "period": "2026-10", "message": "本月 token 额度已用完，请联系管理员调整。"}}
  ```
- **notify 档一行不拦**：`_quota_precheck` 首行即 return，行为与 P3-1 之前完全一致。
- **默认仍是 notify**：`settings` 代码默认值不动，`.env` 显式配成 `block`。
  不配 `.env` 的人升级后行为不变。

---

## 3. 🔴 被否掉的方案（本版最值钱的部分）

### 3.1 推翻 P2-15c「只提醒不阻断」

这是本仓库**第一次推翻一个写进测试的结构性决策**，必须把代价记下来：

| | P2-15c（2026-10-07） | P3-1（2026-10-11） |
|---|---|---|
| 前提 | 内部系统，用超只是「多花一点」 | **对外**服务，用超 = 真实的钱与滥用面 |
| 有 `can_ask()` 的后果 | 会长出「禁用」按钮 → 误伤员工 | 长出「禁用」按钮 → **止血** |
| 因此 | 刻意不实现，连空钩子都不留 | 实现，并设为默认档 |

推翻的教训不是「当初拍错了」，而是：**那条决策的成立条件是隐式的**
（「内部系统」这四个字当时没有写进任何一处 docstring）。所以本版在
`core/quota_policy.py` 文件头把前提显式写出来，并注明哪天它被推翻、为什么。

⚠️ 旧测试里两条断言因此**应当**转红并改写（这是决策变更，不是回归）：
- 「OVER_ACTIONS 只含 notify」→ 改为 `("notify", "block")`，并补一条
  「仍然没有降级档」；
- 「quota_policy 里不许有 `can_*` 形状的函数」→ 删除，换成 `can_ask` 的
  边界行为断言（纯函数、>= 即拦、额度 0 永放行）。

反向 12 / 反向 13 同步改写（它们原本盯的是被删掉的那两条判据；盯一个
已不存在的判决等于没验）。

### 3.2 单轮 token 预估（否掉）

「还剩 200 token，这一轮问出去肯定超 —— 要不要提前拦？」不拦。
这一轮花多少取决于检索命中几条、历史带几轮、模型回多长，全是运行时才知道的。
硬估一个常数只会让「还差一点点」的人被拦，而那个人其实问得出。
**宽限单语义天然覆盖这个场景**：放他问完，超了体现在下一问。

### 3.3 降级到便宜模型（否掉）

PLAN §15c 设计的三档里原本有这一档。它要先回答「降级到哪个模型」，
那是一张模型映射表 + 一轮新决策，不是加个字符串。留白。

### 3.4 前端「禁用输入框」（否掉）

`/quota/me` **仍然不返回**「还能不能问」字段。理由与 15c 同构：
它若返回 `can_ask=false`，前端会长出禁用按钮，而禁用的判据在前端重写一遍
就是两份清单。拦截只发生在服务端预检；前端负责的是**被拒之后**怎么展示。

### 3.5 并发精确计量（否掉，接受竞态）

同用户并发两个提问可能双双过预检、实际略超限量。要精确就得在预检处加行锁或
分布式计数 —— 为一个内部系统的「略超一点」付这个复杂度不值。见 §6 风险。

## 6. 风险与已知边界

1. **并发竞态（接受）**：同用户并发提问可能双双过预检、实际略超限量。
   内部系统，不为它加分布式计数。
2. **break-glass 不设防**：`actor.id is None` 的身份（`.env` 里那个不在库里的超管）
   无法按人计量，预检跳过并记 WARNING。这是「没有数据可判」而不是「放行特权」。
3. **员工无自助出口**：被拦之后员工只能找管理员。所以 `BLOCK_MESSAGE` 里
   「请联系管理员调整」是功能的一部分，不是客套 —— 否则他只会反复重试。
4. **额度是实时查库的**：改额度**下一问即生效**，不需要重新登录
   （沿用 15b「不 bump token_version」的决策，本版未变）。
5. **横幅只在 over 档改口**：warn 档的人确实还能问，不能对他说「超出后无法提问」——
   那句话会立刻被他自己证伪，于是真到 over 那句他也不信了。
