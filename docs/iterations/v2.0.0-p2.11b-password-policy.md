### 2.2 `user_password_history` 表（迁移 0004）

```
id / user_id / password_hash / changed_at / changed_by_user_id
索引：idx_pwh_user_changed(user_id, changed_at)   ← 支撑「取最近 N 条」
```

`changed_by_user_id` 可空表示「本人自助改密」，**不用 0 占位**（与 0001 里 `folder.user_id` 不用伪 id 同一个理由：0 是能通过 FK 的假用户 id）。

### 2.3 `verify()` —— 本模块唯一的对外出口

| 顺序 | 情况 | `ok` | `code` | 对外文案 |
|---|---|---|---|---|
| 0 | 账号不存在 | False | `not_found` | **账号或密码错误** |
| 1 | 停用 / 离职 | False | `inactive` | 账号已停用或已离职，请联系管理员 |
| 2 | 锁定期内 | False | `locked` | **账号或密码错误** |
| 3 | bcrypt 不匹配 | False | `wrong_password` | **账号或密码错误** |
| 4 | 密码正确 + 强制改密 | **True** | `must_change` | 首次登录或密码已被重置，请先修改密码 |
| 5 | 密码正确 + 已过期 | False | `expired` | 密码已过期，请修改密码后继续使用 |
| 6 | 正常 | True | `ok` | （空） |

## 3. 关键设计决策

### 3.1 判定与存取分层：策略模块不做查询

**否掉的方案：把「是否命中历史」直接写成 `user_repo.check_password_reused(user_id, pwd)`。**

那样最省事，但代价是「判定逻辑只能连着数据库一起测」——单测会慢、会因为容器没起而假绿或假红。所以：

```
core/password_policy.py   纯判定，不做任何查询
core/user_repo.py         纯存取
```

调用方（未来的登录服务）把哈希列表取出来传进去。这也让 `verify()` 里的顺序、边界、文案都能在不起库的情况下钉死。

唯一的耦合是从 `user_repo` 导入 `STATUS_ACTIVE`（「在职状态」这个枚举的单一出处）。它不构成循环：`user_repo` 不 import 策略模块，且它的 Engine 是懒创建。

### 3.2 三种失败共用一句文案 + 四条路径耗时对齐

**否掉的方案 A：给「账号不存在」一句更友好的提示**（「该用户名不存在」）。这等于免费送一个用户名枚举器。

于是：`not_found` / `wrong_password` / `locked` 的**对外 message 逐字相同**，但**内部 code 仍然区分**（日志与监控需要）。

**否掉的方案 B：只在文案上对齐，耗时不管。** bcrypt 故意慢，慢到爆破不划算；但也慢到**能当侧信道**——「账号不存在」0.1ms 返回、「密码错」165ms，攻击者用响应时间就能数出哪些账号存在。

所以每条失败路径都会跑一次**真实的** bcrypt 比对（`_burn`），只是比的对象不同。实测四条路径耗时比稳定在 **1.00 ~ 1.11**。

### 3.3 `expired` 判成 `ok=False` 而不是 `True`

设计规格写「到期后除改密与登出一律 403」。所以密码过期是**凭据有效但被策略拦住**，处置方式（403 +引导改密）与「密码错了」（提示重试）完全不同。`ok` 的语义因此是「准不准继续」，不是「密码对不对」。

对比 `must_change`：那是**放行但打标**，因为管理员刚重置的临时密码得让人先进去改密。

### 3.4 `password_changed_at is None` → 按已过期处理（fail-closed）

无法证明它没过期，就不能放行。这与 §5.1「身份头必须由网关注入，否则 401」是同一个思路。发生概率极低（正常流程一定会写这一列），但万一发生了，`fail-closed` 的代价是「多改一次密码」，`fail-open` 的代价是「一个没到期的密码继续用90 天」。

### 3.5 死配置 `BCRYPT_LEGACY_COST` 被删掉

第一版加了它，想表达「存量 cost 10 的哈希不强制改密，登录成功后顺带升级」。写完 `needs_rehash()` 才发现：判据只有一条「存量 cost < 目标 cost 就重算」，**它能表达的这条规则已经被完全覆盖了**。

于是删掉。**配了但不生效的配置比没有配置更坏** —— 后人会以为它在起作用。

### 3.6 72 字节上限要单独校验，不能只数字符

bcrypt 只取密码**前 72 字节**，超出部分静默忽略 —— 意味着 `abc…(72字节)A` 和 `abc…(72字节)B` 在库里是同一个哈希。所以 `validate_strength` 把「UTF-8 编码后的字节数」列为独立一条：30 个中文字 = 90 字节，已经超了。

> 三处全部改成实测值。**数字写在文档里就要是被测过的数字。**

### 5.5 ⚠️ 抓到一个 15 遍漏 13遍的 bug

临时密码的「强制四位」里，我第一版只过滤了数字那一位，**小写位照样能抽到 `l`、大写位能抽到 `I`/`O`**。而测试断言是「抽一个 24 位样本看看有没有易混字符」——单次含易混字符的概率约 **28%**，于是 15 遍只红 2 次，很容易被当成偶发放过。

修法两条：
1. **断言不变量而不是断言样本**：改为断言「候选池不含易混字符」（确定性）+ 生成 200 个全查（概率上必然成立）；
2. **在生产代码里加兜底自检** `if set(out) & _TEMP_CONFUABLES: raise` ——让越界在结构上不可能，而不是指望每次改动都记得过滤。

修完连跑 20 遍，0 失败。已记入踩坑清单第 50 条。

## 6. 已知边界与遗留项

1. **本轮结束时 `user` 表仍是零行**，登录真相源还是 `.env`。11b 只是把规则准备好了，**一条规则都还没在真实链路上跑过**。
2. **`verify()` 还没被任何调用方使用**。它将在 P2-11c 被网关查库那侧接上；届时「四条路径耗时等长」这条验收（计划书 §11 P2-11）在真实 HTTP 口径上还要再验一遍。
3. **判重耗时 0.85s 只发生在改密动作上**。真嫌慢就调小 `PASSWORD_HISTORY_KEEP`，别调 `BCRYPT_COST`。
4. **`changed_by_user_id` 目前只被写入、没有被读取**（审计日志属 P2-13d）。
5. **到期的强制拦截（403）需要网关与后端都实现**。只在后端拦的话，前端绕过就失效了 —— 计划书 §4 已写这条，本轮只提供了判定。
6. **`make test` 全量仍未跑**：`module9` 全表清空 `document`、`module8` 的 `wipe()` 清 session/chat_message。本轮继续绕开，理由与 11a 相同。
