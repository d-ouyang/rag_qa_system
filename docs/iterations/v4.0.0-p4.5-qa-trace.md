# v4.0.0-p4.5 — 问答流程回溯（Q&A Trace）：检索轨迹落库，刷新后仍在

| **性质** | 计划内（PLAN-v4.0.0 P4-5 一期） |
|----------|--------------------------------|
| **tag** | `v4.0.0-p4.5` |
| **默认行为** | **零变化**：不传 `trace_out` 的检索调用逐字节不变；未开启 debug 的流式调用事件序列不变；老会话轮次无 `qa_trace`（前端不展示面板） |
| **新增能力** | 每轮问答的**完整链路轨迹**（终端状态 + 意图 + 改写 + 检索候选/阈值/top1/混合召回）随 `turn_meta` 落库，刷新 / 历史回看「检索详情」面板不再消失 |

---

## 1. 背景（结论先行）

排查问答时反复要回答「这一轮为什么这么答 / 为什么拒答」。p2.23 交付的「检索详情」面板**只在当轮流式过程中可见**——因为当时刻意没做持久化（v2.0.0-p2.23 §1/§6 原话：「待有真实需求再立项」）。本任务就是那个真实需求：把每轮的链路决策与检索细节**落库**。

一次问答有四个**终端状态**（隐式分支，此前无正式状态机）：

```
cache_hit（问答缓存命中）
chitchat（闲聊，不检索）
zero_recall（检索为空 → 固定拒答，不进 LLM）
rag_qa（正常检索 + 生成）
```

本版把这四个状态连同检索细节写进 `chat_message.turn_meta.qa_trace`，并让历史接口回吐。

## 2. 方案（实现了什么）

**① 轨迹按请求采集（`core/retriever.py`）**
- `RAGRetriever.retrieve()` 新增**可选出参** `trace_out: dict | None`：本次调用的轨迹写进它（`rerank` / `hybrid` 两段）。**不改返回值、不加位置参数**——测试注入的打桩重排器签名是 `rerank(query, documents, top_k=None)`，加参会直接打挂 module20，出参方案对它零影响。
- `_rank()` 在 `self.reranker.rerank(...)` **一返回就取走** `last_trace`，写进 `trace_out["rerank"]`。这把 P2-23「最近一次」口径的并发窗口从「整个请求」缩到「本次 rerank 调用刚结束」。重排关闭时写 `None`（没有阈值过滤就没有「差多少分」）。
- 混合轨迹同理，在 `_hybrid_merge` 后即时取走；开关关时写 `None`（「没开混合」≠「开了没命中」，与 P2-23 的 `bm25_hits` 口径一致）。

**② 组装 + 落库（`core/rag_chain.py`）**
- `_prepare_parallel` 生成一份 `trace = {}` 传给检索（投机检索先传；改写后重新检索时**换一份新的**，投机那次整体作废），收进 `prepared["retrieval_trace"]`。
- 新增 `_build_qa_trace()`：**复用 `_retrieval_debug_event`** 产出检索段（只剥掉流式用的 `type` 键）——保证「流式面板看到的」和「落库存的」是同一份数据，靠同构断言防两处漂移。新增 `_cache_qa_trace()` 处理缓存命中轮（无检索细节）。
- `query()` / `stream()` 计算 `decision`（四终端之一）后把 `qa_trace` 写进 `exchange_meta`；`_finish_cached()` 写 `cache_hit` 轨迹。**无需 alembic 迁移**（`turn_meta` 是 JSON 列）。
- 顺带：`_log_rejection` 与 debug 事件改用**本次调用**的轨迹，不再读实例级 `get_last_rerank_trace()`。

**③ 接口回吐（`api/routes/qa.py`）**：`GET /qa/sessions/{id}` 给 assistant 消息补 `qa_trace`（老轮次为 None）。

**④ 前端（`types.ts` / `MessageBubble.vue`）**：新增 `QaTrace` 类型（`RetrievalDebug` 超集）；「检索详情」面板数据源改为 `qa_trace ?? retrieval_debug`（**落库优先、流式回退**）——刷新 / 历史回看不再丢面板。

### 3.1 顺带修掉一个「验收会随机假红」的既有 flake

首轮全量回归出现**额外**红模块 `test_module4_llm_and_retriever`。查证后**不是断言失败**：

```
==== 汇总：通过 87 项，失败 0 项 ====
libc++abi: terminating due to uncaught exception of type std::__1::system_error:
recursive_mutex lock failed: Invalid argument
scripts/test_sandbox.sh: line 227: 24560 Abort trap: 6
```

即**所有断言跑完之后**、解释器**退出阶段**崩在原生库，退出码 134（SIGABRT）。
单跑三次得到 **134 / 0 / 0**，三轮断言均 87/0 —— 环境级 flake（macOS 上
torch/MPS + ollama HTTP 客户端在 `finalization` 时的遗留线程），与断言、与本次改动无关。
module4 **完全不涉及** trace 代码路径；`p4.2` 的 CHANGELOG 里其实已记过「module4 曾一次全量偶发红，
单跑不复现」，当时只记录未定性。

**处理**：`scripts/test_sandbox.sh` 加窄判据 `_run_test()`（只摘 134，其他非零码照常算失败）——
退出码 **134 且** 输出含「…失败 0 项」汇总行 → 计入已知 flake 并打印警告；只满足一半
（真崩、没跑到汇总）仍判红。脚本头部「已知局限」补 ④。

**四种情形定向验证**（合成用例，见坑 98）：

| 用例 | 期望 | 实测 |
|------|------|------|
| 正常退出 0 + 汇总行 | 绿 | ✅ 绿 |
| SIGABRT + 汇总行（伪造 flake） | 绿 + 警告 | ✅ 绿 + 警告并登记 |
| SIGABRT + **无**汇总行（真崩） | **红** | ✅ 红 |
| exit 1 + 「失败 7 项」 | **红** | ✅ 红 |

→ 教训入坑 98：「验收脚本连跑两遍才算过」的前提是**跑出来的红必须是真红**；
一个把好代码判红的 flake 比漏网 bug 更能拖垮验收纪律（它训练人忽略红色）。

## 4. 否掉的方案与代价

- **否掉「给 `rerank()` 加 `trace_out` 参数做真·按请求隔离」**：最彻底，但两处重排器签名变更 + 测试打桩器签名不匹配 → module20 直接红；收益（并发下彻底不串）与破坏面不成比例。改为「实例级字段即时取走」——窗口从整个请求缩到一次 rerank 调用，且**不碰任何既有签名**。已知边界见 §5。
- **否掉「扩 `chat_message` 加独立列 / 建 qa_trace 表（一期）」**：JSON 列 `turn_meta` 已承载同轮的 sources/intent/usage，加子键**零迁移**；独立表是二期跨会话分析才需要（届时再上 alembic + 索引）。
- **否掉「把 `_extract_sources` 与 `_retrieval_debug_event` 合并」**：方向相反（前者在 rag_chain，后者依赖 retriever 轨迹），合并成环；保持两函数、靠 module26 的同构断言防漂移（与 P2-23 对 `_candidate_brief`/`_resolve_chunk_id` 的处理同款）。
- **否掉「缓存命中/闲聊也硬造一份空检索事件」**：会误导（「没跑检索」和「跑了没捞到」排查方向相反）。统一用 `None`/空候选表达「没跑检索」。

## 5. 已知边界与遗留项

- **轨迹仍是「实例级即时取走」而非真·按请求隔离**：高并发下两次 rerank 交错，仍可能取到别人的 `last_trace`。触发条件 = 出现并发误读案例；届时改 `rerank()` 返回值 + 同步改 module20 打桩器。
- **`turn_meta` 体积增大**：多存候选清单，单轮约 1~3KB（20 候选量级），可接受；若知识库候选池显著变大需复核。
- **二期未做**：跨会话分析（`qa_trace` 表 + `GET /admin/qa-traces`）、溯源可视化页、`QaFlowMachine` 状态机收口。触发条件 = 需要「按拒答/意图跨会话筛选」或专门的链路回放页。
- **老轮次无 `qa_trace`**：P4-5 之前的会话历史不含该字段，前端不展示面板（非缺陷）。
