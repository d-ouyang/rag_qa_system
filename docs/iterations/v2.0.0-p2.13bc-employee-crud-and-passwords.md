## 3. 关键设计决策

### 3.1 为什么 13b 和 13c 合并成一个版本号（否掉的方案）

按计划书它们是两个任务，理想形态是 `p2.13b`、`p2.13c` 两个 tag。**否掉**，原因是物理拆不开：

- `core/admin_service.py` 一个新文件同时装着 CRUD（13b）与密码（13c），拆分要按行 staging 一个 624 行的新文件；
- `test_module12_admin.py` 的 73 条断言一个文件盖两块，拆开必然出现「中间 commit 的测试测的是还没写的代码」。

硬拆的产物是两个**都不能独立验收**的假提交 —— 违背「每个 tag 都能独立验收」这条更根本的规矩。
代价：`PROJECT_VERSION` 只有一个值（`2.0.0-p2.13bc`），PLAN 上两个格子指向同一个 tag。

### 3.2 写操作全部收口在 `admin_service` —— 给 13d 留的口子

所有路由只做「收参 → 调服务 → 转 `AdminError`」，业务动作只存在于服务层。
13d 审计日志要落「谁 / 何时 / 对谁 / 做了什么」，只需要在服务层函数里加一行，
**不用动任何路由**。反过来说：这次若让路由直接摸 `user_repo`，13d 就得改 13 处。

### 3.3 一次性临时密码：明文只出现一次

`create_user` / `reset_password` 返回 `(记录, 明文)`，明文**只在这一次 HTTP 响应里**：
不写日志、不落库明文、没有「再看看」的接口（单向哈希，丢了只能再重置）。
前端在两个页面（员工页、密码页）复用同一个弹窗，顶部都写「关掉就再也看不到」。
**不做「设一个我指定的密码」**：存在这个接口就会被拿来「统一改成一个口令方便调试」，
管理员不该知道员工的密码。

### 3.4 看板五桶互斥，判定顺序是契约

```
锁定 → 待改密 → 已过期 → 即将到期 → 长期未登录（90 天）
```

一个人只落一个桶，`counts` 加总 ≤ 在职人数。**前端不重新计算**，只展示后端给的桶 ——
两边算法一旦分叉，「数字对不上人数」这种 bug 最难发现。测试第 9 组拿 SQL `CASE WHEN` 逐桶对账。

只统计**在职**的人：离职/停用本来就登不进来，把他们的「密码过期」放进看板，
管理员每看一次都要先想一遍「这些人为什么还在」。

### 3.5 强制改密开关 ≠ 改密码：`set_must_change_password()` 的由来

这条是**测试先红、代码后修**的真实案例：`set_must_change` 第一版复用了 `update_password`，
结果断言「开关不给密码续期」抓到 `password_changed_at` 被写成了 now ——
等于给旧密码**续了 90 天**，还顺手 `token_version +1` 把人踢下线。
新增只改一列的仓储函数，注释里写明「这个开关绝不能走 `update_password`」。

### 3.6 部门防环是双层的

后端 `update_department` 用 `_descendant_ids` 拒绝「上级 = 自己或子孙」（否则整条环
会从部门树里静默消失）。前端编辑弹窗的下拉**直接不渲染**这些选项 —— 不是替代后端校验，
是别让人提交一个必然 400 的表单再对着报错发呆。

### 3.7 唯一键冲突翻译成人话

MySQL `IntegrityError` 按唯一键名映射：`uk_user_username→登录名`、`uk_user_employee_no→工号`、
`uk_user_email→邮箱`、`uk_dept_code→部门编码`、`uk_position_code→职位编码`。
报错形如「登录名 `chen.jie` 已被使用」，而不是让用户看 `Duplicate entry ... for key ...`。
未识别的键走 fallback 原文，**绝不吞掉**。

### 3.8 前端三处小决定

- **删部门/职位失败用 `warn` 不用 `error`**：「还有 3 人挂着这个职位」是**预期中的业务结果**，
  弹红色错误会让人以为系统坏了。
- **看板卡片即筛选器**：五个数字是给人扫读的，但「有 7 个待改密」要能变成动作 —— 点卡片落到名单。
- **重置/角色按钮对「自己」隐藏**：改自己的角色/重置自己的密码在服务层本来就被拒
  （防「最后一个管理员把自己降级」这类死锁），界面别摆一个必然失败的按钮。

## 4. 顺带修掉的 13a 两个登录闭环 bug（浏览器验收抓的）

> 这两条的共同教训：**curl 验接口全 200 ≠ 页面能用**。接口各自正确，串起来死在半路。
> 13a 的验证只到 curl（§5.1），浏览器只确认了「5174 返回 200」，没真登录过。

### 4.1 登录成功后不跳转

`LoginView.submit` 调完 `auth.login()` 就结束了 —— store 只管换凭据，路由不会因为
「token 有了」而自动离开登录页。表现：填完账号密码点登录，**什么都不发生**。
修法：登录成功 `router.replace(redirect)`，`redirect` 取自路由守卫附带的 `?redirect=` 参数
（守卫同步补上：被拦到登录页时记住来访者要去哪，登录后回到原目标，深链接不用走两遍）。

### 4.2 `/me` 二次确认是裸请求（顺序反了）

`auth.login()` 的意图是「先换 token，再问 `/me` 确认权限」，代码却把 `fetchProfile()`
写在 `setSession()` **之前** —— 发请求时 token 还没落库，`getToken()` 返回空串，
`/me` 401，于是**所有人**登录都报「账号已停用或不存在」。
一条把人指向完全错误方向的提示，而 curl 各自验两个接口都是通的。

### 4.3 环境坑：后端旧进程没有热重载，404 会误判成「路由没写上」

手工用 `uvicorn api.main:app --port 8000`（**无 `--reload`**）起的进程在改完路由后
`/password/board` 一直 404，第一反应是「路由注册漏了」。判据别猜进程：
`curl /openapi.json` 数一数运行中的路由 —— 实际只有 13a 的两条，是进程旧了不是代码错了。
**规矩**：本地手起后端一律带 `--reload`（`make api` 本来就带）。

## 7. 已知边界与遗留项

### 7.1 本轮在测试里发现并修掉的第三类「断言骗人」

收尾断言原来是「`SELECT COUNT(*) FROM user` == 10」。与 module11 **并行**跑时红了 ——
因为对方正在造自己的账号，全表总数是**共享状态**。
改为「种子名单逐个还在」（按业务键 `username IN (...)`）：
既不受别人新增影响，也更严格（认名字不认数量）。**两条测试脚本不要并行跑**；
`make test` 是串行的，没事。

### 7.2 浏览器还验不了的事

- **hr 视角**：种子里的 `zhou.yan` 在网关眼里还不存在（登录源还是 `.env`，那是 11c 的活），
  所以「人事看不到重置按钮」只在 TestClient 层验证过（403），真浏览器里没点过。
- **看板分桶的丰富状态**：种子全员 `must_change=1`，另外四桶当前都是空的 ——
  「已过期 / 即将到期」要等时间流逝或改数据才看得到，SQL 对账断言已覆盖。

### 7.3 遗留

- 13d 审计日志（服务层收口已就绪，见 §3.2）。
- `password/board` 的 `stale_days=90` 是函数参数默认值，没进 `settings`；
  等有「账号回收策略」需求时再提配置。
- 看板名单无分页 —— 在职人数少时不值得做，人多了先看 `GET /users` 的分页参数是否够用。
