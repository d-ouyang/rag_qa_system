## 2. 方案（实现了什么）

```
                    ┌─ 向量召回 candidate_k（不变）
用户问题 ──┤
                    └─ BM25 召回 candidate_k（jieba 分词，进程内索引）
                            │
                            ▼
                    RRF 融合：score(d) = Σ 1/(k + rank_i(d))，k=60
                            │  取融合 top candidate_k
                            ▼
                    bge-reranker-v2-m3 精排 + 0.1 阈值   ← 一行未改
                            │
                            ▼
                        返回 / 零召回拒答
```

- **融合只动候选池，不动裁决**：reranker 与阈值对混合毫无感知（module20 源码级断言钉住）。
- **开关每次检索时读**：`RETRIEVAL_HYBRID` 在 `retrieve()` 里取值而非构造时锁死 ——
  它是 A/B 的被测变量，锁死会让对比多出一个「重启冷启动」变量。
- **BM25 进程内单例 + 惰性构建**：首次 search 才从 Chroma 拉全量切片建索引
  （实测 90 片 317ms）；`invalidate()` 只置脏，下次检索前全量重建。

## 3. 被否掉的方案 / 要紧的取舍

### 3.1 把 RRF 换成「向量分 + BM25 分归一化加权」— 否掉

BM25 分数是无上界的正数，向量分数是 [-1,1] 的余弦。归一化要先定上下界，
而 BM25 的上下界**随语料变化**，定不出来。RRF 只看名次，对量纲与分布完全不敏感，
是融合异构检索器的标准做法。module20 反向 2 用一个构造性语料钉死了这个取舍：
两篇正文词项完全相同、只差文档长度 —— RRF 维持名次序，直接加分会被 BM25 翻盘。

### 3.2 BM25 索引增量维护 — 否掉

全库 90 片，jieba 分词 + 建索引毫秒级。为省这点时间做增量，要背三件事：
增量与全量的边界条件、「增量算错了但不报错」、验证增量 == 全量的测试。
**只做全量重建 + invalidate() 置脏。**

### 3.3 「search() 直接返回 Document」— 否掉，保持 PLAN 的 `[(chunk_id, 分数)]`

BM25 命中的切片要变成 Document 才能进 reranker。把物化塞进 search() 会让
「检索」和「构造 LangChain 对象」两个职责粘在一起；拆出 `materialize(chunk_ids)`
（索引里存着正文与元数据，不必回查向量库），search 保持纯「给查询吐键和分」。

### 3.4 用 `bump_kb_version()`（Redis 计数器）当索引失效信号 — 否掉

它要 Redis 可用且 `QA_CACHE_ENABLED=true`，把这两个前提带进检索路径，
等于给「Redis 挂了」新增一种「检索悄悄变差」的死法。失效信号只用
**进程内的 invalidate 钩子**；跨进程改动（维护脚本）的代价是「重启后端」，
见 §6.3。

### 3.5 混合层自己做阈值过滤 — 否掉

阈值 0.1 是 reranker 分数的属性，不是候选池的属性。混合层只决定
「谁有资格被重排」。module20 断言 `_hybrid_merge` 里不出现 `score_threshold`。

## 5. 验收证据

### 5.1 回归

| 项 | 结果 |
|---|---|
| `tests/test_module20_hybrid.py` | **60 / 0**（连跑两遍） |
| 同上 `--reverse` | **64 / 0**（不分词 → 编号查询崩塌；RRF 换加分 → 顺序变；删 invalidate → 源码断言红；默认值翻 true → 红） |
| `make test-sandbox` 全量 | 仅 `test_module12_audit` 红 —— 沙箱无种子数据的**已知局限**（P3-2 已记录），与本版无关 |
| `tests/test_module3/4/5` + 观测性 | 102/0 · 85/0 · 55/0 · **59/0**（观测性含新字段契约） |
| `frontend` `vue-tsc --noEmit` | 0 error |
| `make kb-guard-count` | 35 / 35 |

覆盖的关键不变量：

- **关 = 一行不多**：混合分支只有一行入口；主路径不出现 `get_bm25_index`；
  轨迹恒 None；
- **裁决不变**：`_rank` 无 BM25/RRF 字样、`rerank(query, docs, top_k=target_k)` 原样、
  融合层不读阈值；打桩 reranker 端到端验证「融合候选 → 重排 → 阈值」整链；
- **RRF 可手算**：融合顺序与测试内按公式重算的期望完全一致；
- **invalidate 钩子**：源码级断言钩子必须挨着写库点；行为级验证置脏后新内容可命中；
  worker 无实例时 invalidate 是无害空操作。

### 5.2 A/B 实测（`make eval-retrieval TAG=hybrid CMP=baseline`）

| 指标 | 基线 | hybrid | 差值 |
|---|---|---|---|
| recall@5 | 0.8944 | **0.9389** | **+4.45pp** |
| recall@10 / @20 | 0.9389 | 0.9389 | +0.0 |
| hit@5 | 0.9667 | **1.0000** | +3.3pp |
| mrr@10 | 0.8889 | 0.8889 | +0.0 |
| 拒答正确率 | 10/10 | 10/10 | 0 |

分类下钻完全不动（cross 0.7333 / paraphrase 0.9286 / term、numbered 满分）。
基线唯一未命中的 `q017`（编号 GQ-AD-2026-003）在 hybrid 下**进前 5**
（BM25 第一名就是 `599:0`）—— 但它本来就命中于 recall@10/20，
所以上限指标纹丝不动。

### 5.3 数字背后值得留下来的三句话

1. **判据 `recall@20 ≥ +5pp` 在这个库上结构性不可能通过**：
   基线 recall@20 = 0.9389、hit@20 = 1.0，缺口只剩 cross 类那 0.7333 的 1.3 片，
   上限就 ~6pp，而它们是「沾边的第二份文档」，不是「词面精确」——
   BM25 的主场根本不在这里。**这个判据是 P3-3 基线出来之前写的**，
   当时不知道基线会在 k=20 摸到天花板。
2. **线上真实档位（recall@5）实打实 +4.45pp、hit@5 拉满**，
   且拒答零退化 —— 混合检索在「字面精确查询」上确实有效，
   P3-3 里那句「BM25 是编号查询的主场」被实测验证了。
3. **结论仍然是不开**：判据是判据。但把「recall@5 +4.45pp / 拒答不降 /
   已有 60 条回归与源码级护栏」记录在案 —— 若将来出现
   「员工按编号查制度查不到」的真实反馈，把它翻 true 的全部证据已经齐了，
   补一条人工验收即可，不需要重做本项目。

## 6. 风险与已知边界

1. **索引是进程内的**：只与 backend 同生命周期，重启即重建，无落盘 →
   不存在「磁盘索引与库不一致」的问题；代价是 backend 重启后第一次检索
   多 ~0.3s 建索引（90 片；库大了之后这个数字会涨，涨到秒级就该重新审视本节）。
2. **backend 必须**单进程**：多 worker 会各自持一份索引且互相不知情。
   Dockerfile 本就禁多 worker（内存约束），这条约定由部署形态兜着，
   没有代码级守卫 —— 若将来横向扩容，BM25 要换家（Redis / 独立服务），
   届时应先重做 P3-3 评测再动。
3. **跨进程改动后索引会短暂脏**：维护脚本（rechunk / reset / clean_orphan / reindex）
   在独立进程里改库，backend 的进程内索引感知不到。缓解：
   ① 这类操作本就要求停后端或操作后重启；② 任何**在线**改动（路由 / 解析）
   都在同进程内 invalidate。已知的脏窗口 = 「脚本改库 + 后端不重启」的组合，
   目前没有自动化守卫。
4. **BM25 对「全库都出现的词」给 0 分**（rank_bm25 的 idf 数学性质）：
   这正是我们想要的（全员共现 = 无区分度），但迷你语料上会让检索返回空 ——
   module20 的反向组因此专门构造了带填充文档的语料，防止后人写测试时踩进去。
5. **`bm25_hits=20`（满命中）是常态**：90 片的库里，多数查询的 BM25 都能凑满
   candidate_k。RRF 只看名次，所以这不影响融合质量；
   真正有信息量的是 `bm25_only`（向量没捞到、BM25 补进来的条数）。
