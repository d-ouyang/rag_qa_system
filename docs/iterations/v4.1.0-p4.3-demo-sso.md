# v4.1.0-p4.3 · 演示 SSO 收尾（2026-11-23）

## 为什么这一期必须做

nianan.site 改版后，项目卡片上的「在线演示」入口（`src/lib/sso.ts`，v0.9.5 已上线）
会现场签一张 HMAC ticket，然后整页跳 `https://qa.nianan.site/?sso=<ticket>`。

而 qa 侧处理 `?sso=` 的代码（网关 `POST /api/auth/sso` + 登录页自动登录）从 11-19
起只躺在 `hotfix/keyword-fallback-recall` 分支上，**没进 main、没上线**。结果就是：
访客从主页点「在线演示」→ 落到 qa 登录页 → ticket 白带 → 演示在这条路上直接断掉。

这是「对方已经上线在等你」的断链，比一个待办功能严重得多，所以单独收尾。

## 上线前的现状核查（都是查过的，不是假设）

| 检查项 | 结果 |
|--------|------|
| 生产 `.env` 的 `SSO_SHARED_SECRET` | 有，前缀 `5f0bfcdb07e3`，与 nianan-site 里硬编码的一致 |
| 生产 `user` 表 demo1~demo6 | 全部 `active`，`role=user` |
| 它们 `token_version` | 全为 `0` —— 与 SSO 签发的 `ver=0` 一致（不一致会被后端判「登录态已失效」）|
| 月度额度 | 各 100000，且 `TOKEN_QUOTA_OVER_ACTION=notify`（只提醒不阻断）|
| `kb_role` | `none` = 只读：能检索、能看引用，不能改任何东西（演示正好）|
| 网关是否校验 `ver` | 不查库，原样传下游；后端 `identity.py` 按 `sub`（登录名）补查，SSO 的 `sub=demo1` 能命中 |

结论：账号、额度、权限、密钥全部就绪，**唯一缺的就是服务端代码和那两个 bug**。

## 修掉的三个缺陷

1. **验签恒失败**（上线即死）：`expected` 是 64 字符 hex 字符串、`given` 是 32 字节
   Buffer，代码直接比 `.length`，永远不相等 → 所有 ticket 都 `bad signature`。
   改为两边转 Buffer 再 `timingSafeEqual`。
2. **缺 `exp` 的票永不过期**：`Number(undefined)` 是 `NaN`，而 `now > NaN` 恒 false，
   删掉 `exp` 字段的票照样换到 token。**这不是纸上风险**：SSO 密钥本来就随
   nianan-site 的构建产物公开，任何人拿到就能自签一张无限期 demo 票，而 `exp`
   是这条链路上唯一会自己失效的东西。现在 `exp` 必须是有限数字，且不得超过
   `now + 300s`（签票方只给 60s，留 5 分钟吸收时钟偏差）。
3. **编译期作用域问题**：`payloadB64/sig/expected` 在 `try` 内声明、`catch` 里引用
   → 生产 build 直接报错。提到 `try` 外。

## 安全边界（写清楚，别让后来者误以为很牢）

- 密钥是公开的（跟着 nianan-site 的 JS 一起下发）。所以**防的不是「能不能签票」，
  而是「签出来能换成谁」**：服务端硬白名单 `^demo\d{1,2}$`，只能换 demo 账号；
  签发的 token 固定 `role=user / kbRole=none`，即使有人绕过也拿不到 admin。
- **ticket 可重放**（无状态 HMAC，60 秒窗口内可重复兑换）。演示场景接受这个代价；
  真要一次性消费需要一个短期存储（Redis SETNX + TTL），当前刻意不做——多一个
  依赖就多一个「Redis 挂了演示登不进去」的失败面。
- **`ver=0` 与 demo 账号的 `token_version=0` 是耦合的**：哪天有人给演示账号改密码，
  `token_version` 会 +1，SSO 立刻 401。演示账号不应当走改密流程，或在改密后把
  `token_version` 归零。
- 限流与 login 同档（8 次/分钟/IP），压测时先看到 429 属正常防护。

## 验证（本地真链路，非单测打桩）

本地起网关（3010，真实 `SSO_SHARED_SECRET`）+ 真实后端（8000）+ 真实 MySQL/Chroma，
用与 nianan-site 相同的算法自签 ticket 逐用例打：

| 用例 | 结果 |
|------|------|
| demo1 / demo6 合法票 | 200，拿到 token |
| 过期票（exp = now-10） | 401 `SSO_TICKET_EXPIRED` |
| `admin` 用户 | 401 `SSO_FORBIDDEN_USER` |
| `demo1x`（前缀绕过尝试） | 401 `SSO_FORBIDDEN_USER` |
| 错密钥签名 | 401 `SSO_BAD_TICKET` |
| **缺 exp** | 401 `SSO_BAD_TICKET`（修复前是 200）|
| **exp = now+1d** | 401 `SSO_BAD_TICKET`（修复前是 200）|
| 格式错（无 `.`） | 401（连打 9 次后转 429，限流生效）|

拿 SSO token 继续往下打：`/api/auth/me` 返回 `source=sso`、`tokenVersion=0`、
`kbRole=none`；经网关转发 `/api/v1/system/health` → 200（下游身份补查通过）。

## 顺带的三件工程卫生

1. **golden-gate 取错文件 + 基线口径过期**：`_latest_result()` 按「最新 json」取，
   必然抓到每日 04:10 的 `timing-stats-*.json`（无 metrics）→ 报「5 项指标缺失」。
   改为只认 `eval_retrieval.py` 的 `YYYYMMDD-HHMMSS-tag.json`。同时发现基线还按
   40 题（30+10）算阈值，而 p4.15 扩题后是 42 题（31+11）：旧阈值 `hit@5 0.97`
   高于新实测 `0.9677`，真跑必红。已追平到 42 题实测（0.9086/0.9677/0.8559/0.9091），
   并把两道刻意留的锚题写进 `_known_failures`：q041（病假扣薪幻觉，靠答案级守卫兜）、
   q042（复合问句重排分稀释）。现在 `make golden-gate` 不带参数即可自证。
2. **`admin-console/components.d.ts` 移出版本控制**：unplugin-vue-components 的自动产物，
   每次 dev/build 重写，进仓库后表现为「跑一次构建就多一个无关改动」。
3. **部署超时 40→60 分钟**：11-23 那次部署在 buildkit 依赖层缓存被 GC 回收后要全量
   重下 torch 等依赖，吃满 40 分钟被 cancelled（前端/网关镜像已好、后端未出、
   迁移与起容器都没跑）。

## 部署与验收

- 版本 `v4.1.0-p4.3`，登录逻辑只动网关，**数据库无迁移**。
- 生产验收三条：① `https://qa.nianan.site/?sso=<现签 ticket>` 能直接进主界面；
  ② 侧栏显示 demo 账号；③ 问一句知识库问题能正常检索作答。
- 回滚：`git revert` 本条 commit + 重新部署即可；`SSO_SHARED_SECRET` 置空也是
  一个即时开关（返回 `SSO_DISABLED`，登录页会提示失败但账密登录不受影响）。
