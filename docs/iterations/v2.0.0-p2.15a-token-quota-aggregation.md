## 1. 这一版做了什么（一句话）

把「谁这个月用了多少 token」这件事的**口径定死**，并让它可核对：
按人 × 自然月，来源是 `chat_message` 明细 join `session` 取 `user_id`，
三个数（input / output / cache_read）分开报，其中 `cache_read` **不计入计费总额**。

本版**只有取数与判定**，没有写路径（15b）、没有触达（15d）——
但口径一旦定错，后面三格全部要跟着改，所以它排在最前面。

## 3. 口径（本版存在的全部理由）

### 3.1 按人 × 自然月，来源是**明细**而不是汇总列

`chat_message` 明细 join `session` 取 `user_id`，按 `m.create_time` 落自然月。

**否掉的方案**：直接查 `session` 的四个汇总列（`usage_input_token` 等）。

**为什么否**：会话被删 → 汇总行一起没了 → 「他这个月用得少」。
`chat_message` 是**历史真相**。计划书 §15a 原文也是这个意思。

⚠️ **代价，说清楚**：`chat_message` **没有** `usage_cache_read_token` 列
（实测：只有 `usage_input_token` / `usage_output_token` 两列），
cache_read 只能从 `session` 汇总列拿。
所以返回值里显式带 `cache_read_source` 标记 ——
将来若有人改成从 `turn_meta` JSON 提取，那个标记会变，
而「这个数从哪来」必须是看板上看得见的事实：**两个口径的数字不一样，而它们都叫 cache_read**。

### 3.2 计数用 `m.create_time` 而不是 `s.create_time`

一个上个月开的会话、这个月聊了 10 次，那 10 次属于**这个月**。
用 session 的时间会把它们全算到上个月。

### 3.3 `cache_read` **不计入**计费总额

它的单价与普通输入不同（通常更便宜），混进总额会算错钱 ——
而「算错钱」比「算得粗」严重得多：它会让「谁超了」这个判断本身失真。

**也没有「价格 → 金额」的换算**：不同模型单价不同，换算表会随服务商调价而失效，
而**额度本身就是 token 数**，不需要折成钱才能判断「谁超了」。
真要算钱时应当另开一张 `TOKEN_MODEL_PRICING` 表（§15c 提到过），
而不是在这个函数里硬编码系数。

### 3.4 `usage_percent` 无额度时返回 `None` 而不是 `0.0`

「无额度」与「额度是 0」是两件不同的事 —— 前者是「不管他」，后者是「他一个 token 都不能用」。
混成一个0 会让「不限额度的人」显示成「用量 0%」，而看板上「0%」与「不限」应该长得不一样。

### 3.5 `0` 而不是 `NULL` 表示「用全局默认」

`user.token_quota_monthly` 是 `BIGINT NOT NULL DEFAULT 0`，`.env` 的默认也是 0。
两边同一套编码 → `effective_quota` 只需要一条判据（≤ 0）。
如果一边 `NULL` 一边 0，就得写 `if x is None or x <= 0` ——
而那种双判据的函数总有一边会漏（14f 的 `set_role` vs `set_kb_role`）。

### 3.6 🔴 本模块**没有**「是否允许继续提问」这个函数 —— 这是刻意的缺席

用户2026-10-07 拍板：

> 「超出 token 预警，不要做真的阻断或者禁用，只做提醒和看板。」

所以 `quota_policy` 里没有那个函数。一旦有了它，配上前端就会自然长出「禁用」按钮，
而那正是用户明确排除的行为。将来若真要阻断，判据得重新设计
（要回答「降级到哪个模型」「谁承担超额」），**不能靠在本模块加一个 bool 了事**。

### 3.7 「查不到归属」有**两种**，分别计数

`session.user_id` 允许为 NULL，而实测发现第三种情况才是真正的坑：

```
session.user_id = 657，6894 个 input token，
而 `user` 表里已经没有 657 这一行
```

只查 `user_id IS NULL` 的「未归属」返回 **0**，而对账恒等式**不成立**（11926 ≠ 5032 + 0）。

**我的第一反应是「聚合 SQL 写错了」** —— 去查了半天的 JOIN。
真相是聚合没错、**是「未归属」的定义漏了一种**。

所以 `unattributed_total()` 的口径是「`user_id` 为空**或**指向一个不存在的用户」，
并且分别计数 `null_owner_input` / `orphan_input`。两者的运维含义不同：
`orphan` 正常情况下应为 0（`user` 表刻意不删行、只置 `resigned`），
它出现就说明有人**手工SQL 删过**。

这个函数存在的意义始终是**让漏算变得可见**：
一个不允许被发现的漏算，比一个会报警的漏算危险得多 —— 后者会有人去查，前者不会。

## 4. 🔴 本轮抓到的三个 bug（都不是断言写错，是代码/口径错）

### 4.1 `usage_by_session` 的 cache_read 取值 `KeyError: 0`

`_query` 返回的是 **dict 列表**，而代码写 `r2[0][0]`。
且 `SELECT COALESCE(...)` 不取别名时，返回的 dict 用的是**整段表达式**当键。

**这条路径在真实调用下从来没跑通过** —— 当时测试没跑到它。

### 4.2 🔴 cache_read 被乘上消息条数（777 → 2331 = 777×3）

第一版写成「子查询按 `s2.id` 分组再 join 进来」：

```sql
LEFT JOIN (SELECT s2.id sid, SUM(s2.usage_cache_read_token) ...
           FROM session s2 GROUP BY s2.id) su ON su.sid = s.id
... COALESCE(SUM(su.cache_read), 0)
```

看起来「已经先聚合了」，但 **`session.id` 是主键**，按它分组 = 每会话一行 =
**跟没聚合一样**。外层 `SUM(su.cache_read)` 仍在**消息粒度**上把该会话的
cache_read 加了「消息条数」次。

**❌ 否掉的方案**：`SUM(DISTINCT s.usage_cache_read_token)`。
「不重复」看起来成立，但**两个会话恰好同值时会漏掉一个**（A=777、B=777 → DISTINCT 只剩 777）。
而「两人用量相同」在0 用量、小用量这些场景里非常常见 ——
用「看起来对」换「一定错」，不划算。

**✅ 采用**：CTE 先把**消息按会话收敛成一行**，外层再 `SUM`。
收敛之后每会话只出现一次，既不重复、也不受同值影响。

### 4.3 `requests` 一个字段两个口径

聚合用 `COUNT(*)`（含 user 消息）给 3，`usage_by_session` 用 `role='assistant'` 给 2。
已统一为 **assistant 消息数**（= 一次模型调用 = 一次请求），
三个函数全部照它，并在测试里断言一致性。

⚠️ 它与 `session.usage_requests` 汇总列**未必相等** —— 那个列是应用层写的。
这正是 `usage_by_session` 存在的意义：两处不一样时能看出来。

## 5. 🔴 判据「在当前数据下无从验起」比 bug 更危险

第 4.2 条那个 bug 之所以能活下来，是因为它**在当前数据下验不到**：

库里唯一 cache_read 非零的会话（256 tokens）**恰好是那条 orphan**
（`session.user_id=657`，主人已被手工删），而 orphan 按定义**不在看板里**
（看板左连接 `user`）。于是「看板里这个人的 cache_read = 真值」这条断言无从验起。

- 写成 `PASS` 是自欺（断言什么都没验）；
- 写成 `FAIL` 会让人以为代码坏了，去改**对的东西**。

**正解**：造临时样本 —— 一个挂在职员工名下、3 条消息、`cache_read=777` 的会话，
验完在 `finally` 里连消息带会话删干净。

⚠️ 两条必须遵守的细节：

1. **样本的 `create_time` 显式写在本月内**，不用 `NOW()`。
   聚合按自然月筛，用 `NOW()` 的话**跨月运行那天这条断言会恒红** ——
   而「测试在某天跑会红」是最难查的一类问题。
2. **断言一律用增量**（先量基线，再插探针）。直接断言绝对值时，
   探针挂的那个员工自己的真实用量会让777 变成 2331 —— **探针是对的，断言错了**。

## 6. 反向验证：上一版写错了，重写

第 4 组上一版写的是「改了函数值会不会变」：

```python
qp.billable = lambda i, o, c=0: i + o + c
check("反向：...", qp.billable(100, 50, 999) != 150)
```

**那不是反向验证。** 它验的是「我改的那行代码被执行了」，
而反向验证要验的是「这行代码被这组断言真的守着」。

举例说明差别：如果上面那条断言写成 `per["requests"] > 0`
（而不是等于 assistant 条数），那么拆掉 `role` 过滤后它**仍然绿** ——
护栏形同虚设，而「值会变」这个反向验证**抓不到**。

所以「断言够不够狠」和「反向验证能不能发现」是同一件事的两面。

**改法**：统一为「临时替换实现 → 重算受影响的判据 → 断言它已变 → 换回来」，
5 条扩到 **9 条**，全部 monkeypatch 内存对象，不落盘、不改库。

## 8. 顺带修掉的注释假论据

`period_bounds` 原注释写「`<= 本期最后一秒` 会漏掉带微秒的那一刹那」。

**实测**：本库所有时间列都是秒级 `datetime`
（`information_schema.COLUMNS.COLUMN_TYPE` 全是 `datetime`，没有 `datetime(6)`），
所以该论据在**今天**并不成立。

已改成真实理由：左闭右开让「本月」与「下月」首尾相接、无缝无重叠，
于是「按任意月份区间求和」永远等于「逐月求和之和」；
而 `<= 最后一秒` 这种写法每个区间都要自己算一遍「最后一刻」，
一旦某张表精度是 `DATETIME(6)`，就得写 `23:59:59.999999`，少写一位就是静默漏掉。

⚠️ **写进注释的理由也必须是实测的**（同「性能数字必须是实测的」那条）：
一个听起来合理但不成立的论据，会让后来人以为这条约束有别的历史原因，
于是「反正有别的原因撑着」就把它改了。

## 9. 已知边界（本版不解决，登记在此）

1. **cache_read 只能从 `session` 汇总列拿**（明细没有独立列）。
   若将来应用层不再更新那个汇总列，这个数会偏小 —— 标记 `cache_read_source` 就是为了让这件事看得见。
2. **`orphan_input` 当前不为 0**（6894，主人 657 已被手工删）。
   本版**不清理**它（按铁律「不清全表」），
   但它会在看板上可见 —— 这正是 `unattributed_total` 存在的意义。
3. **额度调整历史不在本版**：靠 `audit_log` 承担（15b 落审计时写）。
4. `period_bounds` 的 `start_day` 是预留参数（按结算周期），默认 1 = 当月 1 号。
