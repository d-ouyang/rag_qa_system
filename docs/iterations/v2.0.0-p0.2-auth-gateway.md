# v2.0.0-p0.2 鉴权网关：NestJS JWT 登录 + 全局守卫 + 限流 + 反代（NDJSON 透传）

- **版本**：`2.0.0-p0.2`
- **日期**：2026-09-23
- **对应计划**：`docs/PLAN-v2.0.0.md` → P0-2（鉴权网关）+ 用户补充要求（请求头放 token、每次网关校验、统一底层报错、登录界面、token 联动）
- **上游基线**：`v2.0.0-p0.1`
- **一句话**：在浏览器与 FastAPI 之间加了一个只有 3000 端口的 NestJS 网关，它负责「登录发 token → 每个请求校验 → 按用户限流 → 原样转发（含 NDJSON 逐字流式）→ 统一错误体」；前端补了登录页、token 存储与 401 自动登出。

## 3. 关键设计决策

### 3.1 为什么代理要注册成 Controller 通配路由，而不是 `app.use(createProxyMiddleware(...))`

**Express 中间件跑在 Nest 守卫之前**。代理若挂在中间件层，请求会先被转发到后端、之后守卫才判断有没有 token —— 等于鉴权完全失效，而且日志一切正常、极难发现（实测症状就是「没带 token 也能问答」）。

正确顺序：

```
中间件(requestId) → 守卫(JWT + 限流) → 拦截器 → 路由 handler(代理转发)
```

只有走到 handler 才转发，鉴权一定是已经过了的。

### 3.2 转发请求体：body-parser 与 fixRequestBody（以及踩过的坑）

Nest 启动时默认挂 `express.json()`，请求体已被解析成 `req.body`、原始流已消费完，直接代理会转发一个**空 body**（后端报 422 参数校验失败，且只在 POST 上出现）。解法是用官方 `fixRequestBody` 把 `req.body` 重新写进 `proxyReq`。上传接口的 multipart 不走 body-parser，流没被动过，照常 pipe。

**踩的坑（已修，且值得记下来）**：`fixRequestBody` 在重写完 body 后会调用 `proxyReq.end()`，那一刻请求头已经发出。此时再 `proxyReq.setHeader(...)` 会抛 `ERR_HTTP_HEADERS_SENT`，而这个异常发生在 EventEmitter 回调里、**没有任何地方 catch** —— 结果是一个普通 POST 请求就把整个 Node 进程带走了（日志：`Cannot set headers after they are sent to the client`）。

修法两层：

1. **顺序**：所有 `setHeader` 必须在 `fixRequestBody` 之前；
2. **兜底**：整个 `proxyReq` 回调包 try/catch，且 `main.ts` 加了 `uncaughtException` / `unhandledRejection` 处理器 —— 网关是无状态转发服务，宁可「这次转发少带一个头」也不要「整个进程消失」。这个取舍连同它的代价（将来若网关开始持有状态，兜底就变成帮凶）写在代码注释里。

### 3.3 流式（NDJSON）为什么不会被缓冲

三处共同保证：网关用 `selfHandleResponse: false`（代理自己 pipe）、转发时显式带 `Accept-Encoding: identity`（不要中间多一层 gzip）、vite 代理侧同样带该头。实测 28 帧（1 session + 1 meta + 25 chunk + 1 done）逐帧到达。

### 3.4 「统一底层报错」的边界

统一错误体：

```json
{ "error": { "code": "TOKEN_EXPIRED", "message": "登录已过期，请重新登录",
             "detail": "...", "requestId": "uuid",
             "timestamp": "...", "path": "/api/v1/qa/ask" } }
```

`code` 给机器（前端分支），`message` 给人（可直接弹提示），`requestId` 用于把用户截图和服务器日志对上（同时回写 `X-Request-Id` 响应头）。

**但只统一网关自己产生的错误**。后端 FastAPI 已经写好响应体的（如 4xx/5xx 的 `{"detail": "..."}`）由代理原样透传 —— 要改写它们就得缓冲整个响应体，会把 NDJSON 流式一起搞坏。所以前端 `http.ts` 同时兼容两种错误体，这层适配是「统一报错」在客户端的落点。

两个具体优化（都是实测发现的）：

- `ThrottlerException` 的 message 是英文类名（`ThrottlerException: Too Many Requests`），会直接透给用户 → 用「形如 `XxxException:` 前缀」判定并换中文；
- 字段校验失败时 class-validator 会一次报多条（「密码不能超过 128 个字符；密码不能为空；密码格式不正确」），而对「没填密码」的人只有「不能为空」有意义 → 按**可操作性**取一条，其余挪进 `detail`。

### 3.5 鉴权：为什么默认拒绝 + 只接受 bcrypt 哈希 + 恒定时间比对

- **默认拒绝（fail-closed）**：全局守卫拦截一切，只有 `@Public()` 标记的少数路由放行。反过来做（默认放行、逐个标记需登录）的话，新增接口忘了标记就是直接裸奔。
- **只接受 bcrypt 哈希**：环境变量会被 `docker inspect`、进程列表、监控采集看到，明文口令放进去等于公开。配成非哈希直接**启动失败**并提示生成命令（`npm run hash -- <密码>`）。开发环境不配则用 `admin/admin123` 并打 WARN，生产不配直接启动失败。
- **恒定时间比对**：用户不存在时也跑一次 bcrypt 比对（喂哑 hash）。bcrypt 是故意慢的（约 100ms），若不存在的用户立刻返回，攻击者能用响应时间枚举出有效用户名。
- **失败文案统一**：「用户名或密码错误」，不区分是哪个错（不给撞库的人提供反馈信号）。

### 3.6 限流为什么按用户而不是按 IP

家庭/公司/校园网出口 IP 共享（NAT），按 IP 会误伤同网段用户，而且「谁在被限流」无从解释。登录后按 `userId` 计数，语义明确、用户可解释。登录接口单独写死 8 次/分钟（不提供配置项）：它唯一的用途就是防爆破，做成可配置只会被调松。

### 3.7 JWT 无状态与登出语义（明确写下取舍）

token 有效期 12h，服务端不存会话，登出由前端丢弃 token 实现。**代价是「签发后无法立刻吊销」**，对单/少数账号的系统可接受；等真需要吊销（改密码、踢设备）时引入 token 版本号或黑名单，`POST /api/auth/logout` 这个接口就是那时要改的地方 —— 所以现在虽然什么都不做也留着它。

### 3.8 前端为什么把 token 放 localStorage（项目里唯一的例外）

会话数据、UI 状态都刻意不落 localStorage，但登录 token 必须落：刷新不该重新登录（排除 sessionStorage）、新标签页应继承登录态（localStorage 跨标签共享）、它本来就是身份凭证而非业务数据。

**风险写在代码注释里**：localStorage 对 XSS 不设防。当前输入都经后端处理且前端全程文本插值（无 `v-html`），风险可控；彻底解决要换 HttpOnly Cookie + CSRF 防护，那是后续迭代的事，不是遗漏。

### 3.9 401 统一登出放在 http 层，且不 import store

token 失效可能发生在任意请求上，所以处理只能放 http 层。但 http 层 import auth store 会形成循环依赖（store 的 action 又要调 http），所以用「注册回调」把 `getToken` / `onUnauthorized` 注入进来，依赖方向单向。

主动登出与被动登出都会清空本地会话数据（`sessions.resetAll()`）。**不清的话下一个登录的人会直接看到上一个人的对话历史** —— 而且因为前端读的是内存里的旧数据，看起来像「后端串号了」。这一步在 App.vue 的 `watch(isAuthenticated)` 里统一收口，避免「从某个入口登录进来少了初始化」。

登录接口的 401 单独走 `postJsonNoAuthRedirect`：账号密码错也是 401，但不该触发「清凭据 + 跳登录页」（用户本来就在登录页），而应把「用户名或密码错误」显示在表单上。

### 3.10 健康检查白名单：为什么是两条**精确路径**，且必须声明在通配路由之前

计划书 P0-2 写的是「`@Public()` 白名单放行 login 与两个健康检查（`/api/v1/system/health`、`/api/v1/qa/health`）」。首轮实现只放行了 login 与网关自己的 `/api/health`，把这两个上游探活漏成了「需 token」——功能上不影响前端（前端带 token 调得通），但上线后 Uptime 类监控拿不到 token，探活会一直红。

于是补一个 `@Public() + @All([...PUBLIC_HEALTH_PATHS])` 的 handler，**与通配路由共用同一个 `this.proxy`**，两处唯一差别就是那一个装饰器——转发逻辑（流式 pipe / 超时 / 错误体）不复制第二份。

两个必须写下来的约束：

1. **路径必须精确，不能用前缀通配。** 写成 `api/v1/system/*` 会把 `/api/v1/system/memory`（含会话数、存储后端、Redis 水位）一起放开。`smoke-test.sh` 里加了一条**反向断言**专门守这件事：`/api/v1/system/memory` 必须返回 401，一旦哪天有人图省事放大白名单，测试立刻变红。
2. **必须声明在 `@All('api/v1/*')` 之前。** Express 按注册顺序匹配，Nest 按方法声明顺序注册 —— 具体路径先注册才能抢在通配路由前面命中。顺序反了不会造成安全漏洞（回落成 401，fail-closed），但白名单会**静默失效**，肉眼看不出来，所以同样用冒烟断言盯着。

否掉的方案：把这俩路径从 `PUBLIC_HEALTH_PATHS` 里删掉、只保留网关自己的 `/api/health`。代价是监控区分不出「网关活着但后端挂了」——而后者才是最常发生的故障，等于把探活的意义削掉一半。

## 5. 验证证据

### 5.1 网关端到端冒烟（`gateway/scripts/smoke-test.sh`，25 项）

```
$ ./scripts/smoke-test.sh
== 0. 网关自身健康检查（公开路由，不需要 token） ==
  [PASS] GET /api/health 返回 200      [PASS] 健康体里带 service 标识
== 0b. 上游健康检查白名单（P0-2：免 token 放行） ==
  [PASS] GET /api/v1/system/health 免 token 可访问
  [PASS] GET /api/v1/qa/health 免 token 可访问
  [PASS] 同前缀的 /api/v1/system/memory 仍需 token（白名单没被放大）
== 1. 未带 token 访问受保护接口 ==
  [PASS] 无 token 返回 401             [PASS] 错误体含 error.code（TOKEN_MISSING）
  [PASS] 错误体含 requestId            [PASS] 伪造 token 返回 401
== 2. 登录接口 ==
  [PASS] 错误密码返回 401              [PASS] 错误码为 INVALID_CREDENTIALS
  [PASS] 用户名不存在也是 401          [PASS] 正确凭据返回 200
  [PASS] 拿到 access_token             [PASS] GET /api/auth/me 返回 200
== 3. 代理转发（带 token 打后端） ==
  [PASS] GET /api/v1/qa/sessions 返回 200
  [PASS] GET /api/v1/system/memory 返回 200
  [PASS] POST /api/v1/qa/ask 返回 200（body 转发正常）
== 4. 流式问答（NDJSON 逐帧透传） ==
  [PASS] 有 session 首帧 / chunk 增量帧 / done 结束帧
  [PASS] 无 token 的流式请求被挡在 401（不是 200 带错误帧）
== 5. 登录限流 ==
  [PASS] 连续错误登录会触发 429 限流
==================================================
结果：25 通过 / 0 失败
```

补充实测数据：

- 流式回答 **28 帧**（`session 1 + meta 1 + chunk 25 + done 1`），逐字到达；
- 登录返回 `expires_in=43200s`（12h）；
- 下游不可达时（把后端指向未监听端口）返回 `502 UPSTREAM_UNAVAILABLE` + 统一错误体 +
  `detail: connect ECONNREFUSED 127.0.0.1:9999`；
- 连续错误登录第 5 次起返回 `429 TOO_MANY_REQUESTS / 操作太频繁，请稍后再试`；
- 参数校验返回 `400 BAD_REQUEST / 密码不能为空`（中文、单条、可操作）；
- 白名单四条独立复核（见 3.10）：

  ```
  /api/v1/system/health   HTTP=200   ← 公开
  /api/v1/qa/health       HTTP=200   ← 公开
  /api/v1/system/memory   HTTP=401   ← 仍需 token（白名单未放大）
  /api/health             HTTP=200   ← 网关自身
  ```

## 6. 已知边界与遗留项

1. **限流存储是进程内存**。多实例部署时每个副本各算各的，实际限额被放大 N 倍。
   → 上多副本时必须换 `@nestjs/throttler` 的 Redis storage（同时说明 Redis 也已为 p0.1 引入，成本很低）。
2. **JWT 无状态 ⇒ 无法即时吊销**（见 §3.7）。当前通过「短有效期 + 服务端重启换密钥」缓解。
3. **后端 8000 必须只在内网可达**（转发时注入的 `X-User-Id` 是信任头，谁能直连 8000 谁就能伪造身份）。
   本地开发无此风险，但**部署时必须确保 compose 里 backend 不对外暴露端口**。
   若需要纵深防御，可给后端加「内部令牌校验」（`INTERNAL_API_TOKEN`），本版未做。
4. **`trust proxy` 默认关闭**：网关直接暴露时开启会让攻击者用伪造 `X-Forwarded-For` 绕过按 IP 的登录限流；
   只有在 Nginx 用 `$remote_addr` **覆盖**该头时才应开启（已写入 `.env.example` 注释）。
5. **尚无 TLS / HTTPS**（P1-5，卡 ICP 备案）。当前浏览器与网关之间是明文 HTTP，
   在公网使用前必须补上，否则 token 在链路上可被读取。
6. **登录页没有「忘记密码」**：账号来自环境变量配置，改密码的流程是「跑 `npm run hash` → 改 `.env` → 重启网关」，
   尚未产品化。
7. **本机存在 HTTP_PROXY 环境变量**，会让 `curl http://127.0.0.1:...` 走到代理并得到来源不明的 502。
   冒烟脚本里所有 curl 已带 `--noproxy '*'`，这个坑也写进了脚本头部注释。
