## 2. 变更清单

### 2.1 `user` 表：从 6 列到 23 列

新增 18 列，分四组：

| 组 | 列 |
|---|---|
| 组织 | `employee_no`(UK) / `email`(UK) / `phone` / `gender` / `department_id` / `position_id` |
| 权限 | `role`（默认 `user`）/ `status`（默认 `active`） |
| 密码策略 | `password_changed_at` / `must_change_password` / `failed_login_count` / `locked_until` |
| 吊销与审计 | `token_version` / `last_login_at` / `created_by` / `updated_by` / `update_time` / `deleted_at` |

新增索引与唯一键：`uk_user_employee_no`、`uk_user_email`、`idx_user_dept_status(department_id, status)`、`idx_user_role(role)`。

**下线 `is_active`**（详见 §3.1）。

### 2.2 `department` / `position`

```
department: id / code(UK) / name / parent_id / leader_user_id / sort_order / create_time
position:   id / code(UK) / name / level / sequence / create_time
```

`department.parent_id` 自关联表达「中心 → 部门 → 组」，不建闭包表。
`position.level`（职级 P4~P8）挂在职位上而不是 user 上 —— 同岗位的人职级一般一致，改一次动一处。

### 2.3 `core/user_repo.py` 的职责边界

**只做存储原语，不做判定规则。** 这是本模块最重要的一个取舍：

| 函数族 | 本轮做的 | 留给谁 |
|---|---|---|
| `create_user` / `get*` / `list_users` / `update_profile` | ✅ 存储 | — |
| `set_status` / `set_role` / `bump_token_version` | ✅ 存储 + 连带 `token_version + 1` | 谁能调 → 13b |
| `update_password` | ✅ 落哈希 + 记时间 + 清失败计数 + 吊销旧 token | **bcrypt cost / 强度 / 历史不可复用 → 11b** |
| `record_login_failure` | ✅ 原子 +1 并返回新计数 | **连错几次锁多久 → 11b** |
| `mask_phone` / `to_dict` | ✅ 脱敏 | — |
| `create_department` / `build_department_tree` / `create_position` | ✅ | — |

理由：同一个「是否锁定」「密码是否到期」的判断，如果散落在 `api/routes/admin/*`、网关查询、种子脚本里各写一遍，三处必然漂移。所以规则由 11b 注入一次。

## 3. 关键设计决策

### 3.1 下线 `is_active`，而不是留着它

**否掉的方案：保留 `is_active` 并与 `status` 并存。**

设计规格 §3.1 原本写的是「不 DROP 旧列，老迁移要能在新代码下原样重放」。执行时判断这条在这里不成立：

1. 「老迁移能重放」这个理由只要求 **0001 不被修改**（它确实没被改），**并不要求 0003 保留 0001 建出来的列**。
2. 留着的代价是两个列表达同一件事，且必然不一致 —— 一个说 `is_active=0`，另一个说 `status='resigned'`，应用层该信谁？**两份真相源在权限场景下的表现就是「离职的人还能登录」。**
3. 而且布尔**表达不了三态**。企业场景里「停用」（账号被冻结，待处理，可恢复）与「离职」（不可恢复）性质完全不同，但 `is_active` 只能表示「不在」。
4. 数据代价为零：`user` 表**零行**，且 `grep is_active` 全仓库只命中 0001 与 schema.py 两处**定义本身**，没有任何代码读过它。

**代价**：回退方向会丢失信息 —— downgrade 已按 `status` 回填 `is_active`，但 `resigned` 会映射成 `1`（布尔表达不了三态）。这是**主动接受**的损失，写在迁移文件头里。

### 3.2 不建外键约束

沿用 0001 的决定。具体的现实理由：`session.user_id` 现在是 **NULL**，而 `user` 表零行 —— 一旦加 FK，两表之间立刻出现孤儿行，而孤儿行只能靠「先补 user 行、再改 session.user_id」这种手工数据修复解开，**比没有 FK 更难处理**。

完整性继续靠应用层：删部门前先查有没有在职员工（P2-13b 的职责）。

### 3.3 `employee_no` 的 `server_default=""` 与它带来的限制

> ⚠️ **本节已被 P2-11d 修订**（2026-10-07）：下面写的「只能重放在空表上」这条限制**不成立了**，
> 因为迁移里补了一步回填。原限制保留在下面「修订记录」里，说明它是怎么被发现的。

**决策**：NOT NULL + 空串默认值，理由是让 `ADD COLUMN` 在**非空表**上不报 1364。

**当时的代价（两条，都成立过）**：

1. 重放 0003 时若 `user` 表已有 **2 行或更多**，建 `uk_user_employee_no` 会因两行同为 `''` 而失败。
2. 往返之后旧行的工号会变成空串 ——「工号唯一且有值」这条业务约束在往返后不成立。

**P2-11d 交付后这条限制真的被撞上了**：种子数据把 10 个员工放进表里，迁移往返验收第一次
在 `user` 表有 ≥2 行的情况下执行，立刻报 `1062 Duplicate entry ''`。

**修法不是绕开，而是把迁移改对**（`0003` 在 `add_column` 之后、建唯一键之前加一步）：

```sql
UPDATE `user` SET `employee_no` = CONCAT('LEGACY-', id) WHERE `employee_no` = ''
```

于是：任何行数的库都能重放；往返后工号是 `LEGACY-<id>` —— 确定、唯一、一眼看出是迁移补的占位值。

> ⚠️ **这改动了已tag 的迁移 `0003`**，与「迁移是冻结的历史快照」冲突。判断：改动当天发现、
> 尚未有任何非开发环境跑过它、不修就等于「任何有数据的库都无法重放」。
> 代价是：已跑过旧版 0003 的库不会自动获得这步回填 —— 需要手工执行那条 UPDATE。
> **这属于「迁移本身有 bug 时的例外」，不是「可以随意改历史迁移」的通行证。**

### 3.4 `token_version` 的联动：四处 +1

无状态 JWT 签发后无法收回（PLAN §11 D4 已定「不做 token 白名单」）。所以：

| 动作 | 效果 |
|---|---|
| `set_status(停用/离职)` | `token_version + 1` |
| `set_status(恢复 active)` | **也 +1** —— 不让「离职前签发、还在宽限期的 token」在恢复后复活 |
| `set_role` | +1 —— 提权/降权都要立刻生效 |
| `update_password` | +1 —— 其他设备上的旧 token 全部失效 |

漏掉任何一处，「停用了人还能用半天」就会回来。这是 P2-11c 的地基，本轮已用断言钉住。

### 3.5 `update_time` 由应用显式写，不用 `ON UPDATE CURRENT_TIMESTAMP`

`ON UPDATE` 无法用 SQLAlchemy Core 的列属性表达，只能整段写成 DDL 文本，那样 `core/schema.py`（结构视图）与迁移（DDL 快照）之间会出现一段无法逐字对照的片段，`compare_metadata` 也读不懂。

代价：应用层负责维护 —— `user_repo` 里每个 UPDATE 都带 `update_time`。**漏写就会留下「时间戳停在旧值」的历史记录，那比时间戳不准更麻烦，因为它看起来是对的。**

### 5.3 存量数据零损失

```
文档 35 个 / 切片 90 个   迁移前后一致
会话 1 个 / 消息 12 条    迁移前后一致
```

**实测撞出来的一条真问题**：往返之后 `employee_no` 被填成空串，于是按 `employee_no` 前缀做的清理**漏掉了那一行**；而我「验证清理干净」用的条件**与清理条件完全相同** —— 那个断言永远为真，测试全绿而库里有残留。

修法两条：① 清理锚点换成不受迁移影响的 `username`；② **验证条件必须独立于清理条件**，并额外加一条「`user` 表总行数为 0」兜底。已写进踩坑清单。

### 5.4 反向验证（两条，都确认断言会红）

## 6. 已知边界与遗留项

1. **本轮结束时系统仍处于「假隔离」中间态**，且比之前更明显：`user` 表有了结构但**一行数据都没有**，登录仍走 `.env`。**不要把「用户表建好了」理解成「多用户能用」** —— 能登录的是 11c，能隔离的是 12c。
2. **`user` 表没有任何 HTTP 入口**。它是给 11c / 13b 用的地基，本轮只能从 Python 直接调 `user_repo` 验证。
3. **工号在迁移往返后需要回填**（§3.3 第 2 条）。
4. **`session.user_id` 仍是 NULL**，现有那个会话依然不属于任何人 —— 要等 12c。
5. **`update_time` 依赖应用层维护**（§3.5）。
6. **`user_repo` 没有并发保护**：建号时两个请求同时用同一个工号，会靠唯一键报错而不是静默产生两条 —— 这是有意为之（错误响亮），但调用方需要把 `IntegrityError` 转成可读提示（P2-13b 的职责）。
7. **`module9` 的全表清空仍未修**（遗留项）。本轮为保护演示数据绕开了它，但这不是一个可以长期绕开的理由。

## 7. 修订记录

### 7.1 2026-10-07（P2-11d 期间）：修正 §3.3 的限制 —— 迁移 0003 增加 LEGACY- 回填

P2-11d 把种子员工灌进 `user` 表之后，迁移 0003 的往返验收报`1062 Duplicate entry ''`。
根因是 §3.3 记的那条限制（ADD COLUMN 给所有存量行填空串 → 唯一键建不出来）。

修法在迁移里加一步回填（见 §3.3），而不是在验收脚本里绕开。
影响：任何行数的库都能重放 0003；往返后的工号是 `LEGACY-<id>` 而非空串。
本节与 §3.3 同时被 `2.0.0-p2.11d` 引用。
