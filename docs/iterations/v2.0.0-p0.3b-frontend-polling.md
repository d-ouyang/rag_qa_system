# v2.0.0-p0.3b 前端轮询改造：从「等它做完」到「看着它做」

- **版本**：`2.0.0-p0.3b`（`PROJECT_VERSION` 同步）
- **日期**：2026-09-23
- **对应计划书任务**：`docs/PLAN-v2.0.0.md` → P0-3 异步解析链路（**3b 前端**）
- **上游基线**：`v2.0.0-p0.3a`（后端异步交付，tag 已打）
- **本轮范围**：只动前端 4 个文件 + 1 个验收脚本 + Makefile；**后端一行未改**

## 1. 范围

### 做了什么

P0-3a 把上传改成了异步（202 受理 + 队列 + Worker），但前端还停在旧契约上 ——
它读的是响应里的 `chunks_added`，而异步之后**这个数在响应那一刻根本不存在**。
所以从 `p0.3a` 起知识库管理页是坏的（P0-3a 迭代文档 §3.8 里写明了这是刻意选的短期断点）。

这一版就是把这个断点接上：**让页面从「等它做完」变成「看着它做」**。

具体四件事：

1. 上传后按 `status` 轮询，状态列走完 `排队中 → 解析中 → 已完成 / 失败`；
2. 终态时弹一次提示（成功给出片段数，失败给出可读原因）；
3. 「片段 / 下载 / 重试 / 删除」四个按钮按状态置灰，**且置灰时说明原因**；
4. 失败原因整行展示 + 「重试」入口真的把文档送回队列。

外加一个不在计划书里、但不做就不完整的：**解析链路的可观测提示** ——
「有文档在排队但没有 Worker 在跑」时给出告警，因为这是用户唯一能自己修的一类故障。

### 明确不做什么

- **不动后端**。P0-3a 已经把 7 个接口的形状用 module9 锁死了，前端改造有一个稳定的靶子；
  一旦这边也顺手改接口，「哪边错」就要同时怀疑两边。
- **不动 `App.vue` 的视图渲染方式**（见 §3.1，把轮询放 store 里去规避，而不是改成 `v-show`）。
- **不做前端单测**。项目至今没有前端测试框架，本轮用 Playwright 浏览器端到端验收覆盖。
  取舍与代价见 §6。
- **不做上传进度条**。当前上限 50MB、提交阶段通常不到 1 秒，进度条没有信息量。
- **不做列表分页**。接口默认 `limit=200`，超出后表格截断但顶部计数仍是全库 —— 记在 §6。

## 3. 关键设计决策

> 这一节记的是「当时还考虑过什么」，因为三个月后回看代码能看懂「为什么」，
> 但看不懂「否掉了什么、代价是什么」。

### 3.1 轮询放 store，不放视图的生命周期

**否掉的方案**：在 `KnowledgeView.vue` 的 `onMounted` 起轮询、`onUnmounted` 停。

**为什么否掉**：`App.vue` 用 `v-if` 渲染三个视图，切到会话页会**卸载** `KnowledgeView`。
轮询挂在组件上就会跟着断，于是「关掉页面对后台任务没影响」这条后端能力，
到前端变成「切走页面对后台任务没影响，但你也永远不会知道它什么时候跑完」。
用户在等一个几十秒的 PDF，顺手去聊天页看一眼，回来才发现早解析完了 —— 或者更糟，
回来看到的还是切走前那一瞬的快照。

**另一条路也否掉了**：把 `v-if` 改成 `v-show` 或套 `<KeepAlive>`。
那确实能让组件活着，但代价是三个视图同时常驻内存、状态互相残留，
而收益只有一个「文档轮询」—— 用一个全局改动换一个局部需求，不划算。

**选 store 的代价**：Pinia store 是单例，它的生命周期绑定到「登录态」而不是「视图」。
所以必须显式回答「什么时候停」，否则会变成永动轮询器。答案见 §3.3 与 §3.4。

### 3.2 递归 `setTimeout`，不用 `setInterval`

**否掉 `setInterval` 的原因**：请求比间隔还慢时会**叠发**（上一发没回来就发下一发），
把「慢」放大成「越来越慢」；而且想改间隔必须 `clear` + 重建。

**代价**：每一轮都要重新排一个定时器，多了一次 `clearTimeout` 的心智负担 ——
而这正好引出下面这个坑。

### 3.3 `clearTimer()` 与 `stopPolling()` 必须分开

`syncNow()` 的开头要清掉旧句柄（否则会和新句柄叠成两个轮询），
但它紧接着又会重新排一个。最初的写法是在开头调 `stopPolling()`，而 `stopPolling()`
顺手把 `polling` 置了 `false` —— 于是界面上那个「正在自动刷新」的小圆点
**以轮询周期为频率闪烁**（2 秒一次）。

**修法**：拆成两个函数 —— `clearTimer()` 只清句柄，`stopPolling()` = 清句柄 + 灭指示灯。
**「停掉这个定时器」和「停止轮询这件事」是两回事**，混在一起就会到处闪。
这一处是交付前自己读代码发现的，没进验收脚本（闪烁很难断言，但不该留着）。

### 3.4 三条自我限制：一个不做限制的轮询器就是一台持续烧服务的机器

| 闸 | 规则 | 不做会怎样 |
|----|------|-----------|
| 1 | `inFlightCount === 0` 时直接停 | 知识库全部解析完成后，页面仍然每 2 秒问一次「有没有变化」 |
| 2 | `document.hidden` 时跳过这一轮（回到前台立刻补一次） | 后台标签页每 2 秒发一次请求，纯浪费 |
| 3 | 连续失败时指数退避（2s → 4s → … → 30s 封顶） | 后端挂了的时候，前端以 2 秒一次的频率去敲一扇已经锁了的门 |

**第 1 条的代价（要想清楚）**：判据「有没有非终态文档」本身来自一次请求，
所以「知识库全终态时，页面不会自动更新」。
这在业务上是自洽的：文档状态会自己变，只可能是因为有任务在跑；
而任务在跑，就意味着列表里一定有非终态。**所以不做「空转探测」**——
如果将来出现「别人在别的浏览器里改了知识库、我这边要实时看到」的需求，
这条限制就是第一个要推翻的地方。

### 3.5 队列状态按 1/6 频次拉，不跟文档列表同频

**原因不是省流量，是省服务端时间**：`GET /api/v1/system/queue` 在服务端要**阻塞约 1 秒**
（worker 存活探测走 `inspect().ping()`，必须等满一个超时窗口 —— 见 P0-3a 迭代文档 §3.12）。
如果跟文档列表同频（每 2 秒一次），服务端就有一半时间在等 Worker 应答。
而这些信息本来也不需要秒级新鲜度：Worker 掉线不会在两秒内自己恢复。

**否掉的方案 A**：拆成两个接口（文档列表 / Worker 心跳分开）。
代价是要动 P0-3a 已锁死的接口形状，而这次改动唯一的好处只是「前端少一次判断」。

**否掉的方案 B**：干脆不拉，只在用户手动刷新时查。
代价是用户看不到「其实没有 Worker 在跑」—— 而这恰恰是他唯一能自己修的故障。

**代价**：用户打开页面的**最初几秒**可能看不到 Worker 状态（第 1 轮会拉，之后每 6 轮一次）。
可接受：它不是业务信息，晚几秒知道不影响任何操作。

### 3.6 终态提示只发给「进过 `watched` 的文档」

**否掉的方案**：只要看到终态就弹 —— 第一次打开知识库时，
历史里所有已成功的文档会各弹一条 toast，**十几条同时糊在屏幕上**。

**规则**：还在动的文档 → 纳入 `watched`；已经是终态的 → 只有观察过它才提示。
发出提示后立刻从 `watched` 移出，保证只提示一次。

**这条规则顺带解决了另一半**：刷新页面时正好有文档在解析 → 第一次拉取就把它纳入 `watched`
→ 完成时照样提示。这正是「关掉浏览器再打开，状态和进度都还在」在前端的落点。

**代价**：如果这份文档是在**别的浏览器 / 别的标签页**里提交并完成的，
这个页面不会提示 —— 因为它从没见过它处于非终态。
这是刻意接受的：「提示」的语义是「**你**提交的东西好了」，不是「知识库里的东西变了」。

### 3.7 抽屉存 `doc_id`，不存对象快照

抽屉打开期间文档状态会变（每 2 秒一次轮询）。若存对象快照，抽屉会一直显示旧状态。
所以 `activeDocId` 存 id、`activeDoc` 用 `computed` 从列表里取。

配套还有一个 `chunksStale`：记下「片段是哪一刻取的」。若之后状态变了，
抽屉顶部给一条「状态已更新，片段可能已变化 / 重新加载」——
而不是让用户对着空列表猜「是不是坏了」。

### 3.8 `重试` 置灰必须给理由

三种不可用状态各给一句能解释原因的 `title`：

- `fail` → 可用（「重新排队解析」）
- `success` → 「已解析成功，不支持重解析；如需重跑请先删除再重新上传」
- `pending` / `parsing` → 「正在排队或解析中，无需重试」

**否掉的方案**：置灰但不说为什么。代价是用户只会以为页面坏了 ——
「按钮点不动」在用户那里的第一解释永远是「系统出错了」，而不是「这个操作对我当前状态无意义」。

### 3.9 下载必须走 `fetch` → `blob` → 临时 object URL

`<a href="/api/v1/documents/download?doc_id=1">` 带不上 `Authorization` 头，
直链会 401。所以只能 `fetch` 拿 blob，再 `URL.createObjectURL` 触发保存。

**代价**：文件要过一遍内存。当前上限 50MB，可接受；
若之后放开上限，这是第一个要重新算的地方。

**顺手处理的**：`revokeObjectURL` 放在 `finally`。不 revoke 的话，
每个下载过的文件都会被浏览器一直持有到页面关闭 —— 是那种「单次无感、整场会话累积」的泄漏。

### 3.10 删除确认框对「在飞」的文档加一句警告

`parsing` → 「注意：该文档正在解析中，删除会中断本次解析。」
`pending` → 「注意：该文档还在排队，删除后不会再被解析。」

**不这么做会怎样**：用户点完删除、稍后再传一次，看到又跑了一遍解析，
会以为「系统重复解析了」—— 而实际情况是他自己删掉的那次被中断了。**不说清，就是制造一个假 bug 报告。**

### 3.11 链路告警的判据是「有在飞 + 没有 Worker」，不是单看任一个

- 「积压 30 条」本身不是故障（Worker 正在追）；
- 「Worker 空闲」也不是故障（就是没活）。

**两个同时成立才是真故障**，而且**用户能自己修**（启动 Worker）。
没有这条提示，用户看到的只是「一直转圈」，无从下手。
所以告警文案必须给出下一步（`make worker`），而不是只报一个状态。

### 3.12 「片段」按钮按 `chunk_count > 0` 置灰，而不是按 `status === 'success'`

看起来等价，但不完全：`chunk_count` 才是「有没有东西可看」的直接事实。
用 `status` 推是间接的，一旦将来出现「解析成功但零切片」的边界（比如全是空白页的 PDF），
用 `status` 判断会打开一个必然为空的抽屉。

### 3.13 验收脚本按**元素**记账，不按**文案**去重

首轮实测踩到：同一份文档重复失败两次，两次提示的文案**一模一样**
（同一个文件名、同一个原因）。脚本最初按文案去重 → 第二次被吞掉 →
「重试真的又跑了一遍」这条断言**假失败**（`1 → 1`）。

**修法**：用 `WeakSet` 认 DOM 元素，同一节点只记一次，文案重复则如实记两条。
另存一份去重文案给「有没有出现过某句话」用。

### 3.14 断言要**等条件成立**再数，不能在动作后立刻数

第二轮实测踩到：点开抽屉 → 立刻 `count('.chunk-card')` → 数到 0。
原因不是渲染坏了，而是抽屉里正在异步取片段（显示「读取片段中…」），
而首轮碰巧在响应回来之后才数、通过了。

**修法**：`tryWait(n >= chunkN)`。顺手把断言加强成「抽屉列出了**全部**片段」
（接口返回全文不截断，这条也一起验了）。

**真正的教训不是这两行代码，是**：**一次通过不算通过**。
首轮 57 项里只有 1 项失败，很容易顺手改掉那 1 项就收工；
但那个「通过」的抽屉断言其实一直在赌时序。所以本轮验收**连跑两遍**才算数。

### 3.15 前端验收不并入 `make test`，单独一个 `make accept-ui`

`make test` 的契约是「**离线、无外部依赖、必须永远全绿**」（队列/Worker/向量库都打桩或换临时目录）。
浏览器验收需要中间件 + 四端全在，塞进去会把 `make test` 变成「不准备好环境就跑不了」。

所以维持本项目已有的二分法，并**变成三分**：

| 命令 | 是什么 | 环境要求 |
|------|--------|----------|
| `make test` | **回归**：打桩、离线、秒级全绿 | 无 |
| `make accept` | **后端验收**：不打桩，走 HTTP（P0-3a） | 中间件 + 后端 |
| `make accept-ui` | **前端验收**：不打桩，走真浏览器（本轮新增） | 中间件 + 四端 |

### 3.16 验收脚本里的两处桩，以及为什么用桩

`tests/acceptance_p0_3b_ui.mjs` 号称「不打桩」，但**有两处**是 `page.route` 伪造的：

1. `/api/v1/system/queue` 的 `worker.ok=false`；
2. 文档列表里注入一条 `pending` 记录。

**为什么不用真的**：验「有文档在排队但 Worker 不在」需要 Worker 真的停着。
脚本**不该去杀用户的 Worker**（杀完还得负责起回来，一旦脚本中断就把环境留成半死状态）；
而且用真 Worker 时这两个条件会**互相抵消**（Worker 在，它就把任务领走了）。

**所以这两处只验前端渲染分支**。后端「没 Worker 时确实报 ok=false」由 P0-3a 的验收脚本
与 module9 第 9 组覆盖 —— **两边合起来才是完整证据**，这一点在脚本头注释里也写明了。

### 3.17 全角标点紧跟变量名会吃掉变量（脚本内也踩了）

脚本输出里出现过 `${VAR}` 之类的写法是刻意的。这条坑在项目记忆里已有记录
（bash 的 `${DB_NAME}：` 被解析成变量名带全角冒号），本轮在 Node 脚本里没有复现，
但写带中文的 shell 片段时继续沿用花括号形式。

## 4. 配置与接口变化

### 环境变量

**无新增、无删除**。只有一处版本号同步：

| 文件 | 变化 |
|------|------|
| `.env` / `.env.example` | `PROJECT_VERSION=2.0.0-p0.3a` → `2.0.0-p0.3b` |

> `frontend/.env.development` 的注释改了（说明 proxy 目标是网关 3000），但**值没变**。

### HTTP 接口

**零变化**。P0-3a 定的 7 个接口原样消费：

| 接口 | 前端怎么用 |
|------|-----------|
| `GET /api/v1/documents/` | 轮询主接口（顺带拿 `counts`，它是全库口径、不受 `limit` 影响） |
| `GET /api/v1/documents/stats` | 统计卡片（与列表并行拉） |
| `POST /api/v1/documents/upload` | 提交；按 `queued` 决定提示「正在后台解析」还是「排队失败」 |
| `POST /api/v1/documents/{id}/reparse` | 「重试」。**空 body 必须显式发 `{}`**（见下） |
| `GET /api/v1/documents/{id}/chunks` | 片段抽屉 |
| `GET /api/v1/documents/download?doc_id=` | 下载（fetch + blob） |
| `DELETE /api/v1/documents/{id}` | 删除；按 `file_removed` 单独提示磁盘残留 |
| `GET /api/v1/system/queue` | 链路状态条 + 告警（按 1/6 频次拉） |

**`reparse` 为什么发 `{}`**（读源码确认的）：网关的 `http-proxy-middleware`
的 `fixRequestBody` 对**空 body 直接 return**（`if (!requestBody) return`），
不会补 `Content-Length`；那样 FastAPI 会收到 `Content-Length: 0`。
显式发 `{}` + `Content-Type: application/json` 是走那条已经被验证过的 JSON 路径，更稳。

### Makefile

```
make accept-ui    NODE_PATH="$(npm root -g)" node tests/acceptance_p0_3b_ui.mjs
```

顺带新增 `NODE ?= node`（窄 PATH 环境可覆盖）。
脚本内部用 `createRequire` 借道 CJS 才拿得到全局装的 playwright ——
**ESM 的 `import` 不认 `NODE_PATH`**。

### 前端内部契约

`types.ts` 按 P0-3a 的形状重写，关键差异：

| 字段 | 旧（坏的） | 新 |
|------|-----------|-----|
| `chunks_added` | 上传响应里有 | **不存在**（异步之后那一刻还没有这个数） |
| `status` | 无 | `'pending' \| 'parsing' \| 'success' \| 'fail'` |
| `attempt_count` / `fail_reason` / `parse_started_at` | 无 | 有 |
| 列表响应 | `documents` | `documents` + `counts`（pending/parsing/success/fail/total）+ `total_chunks` |
| 上传响应 | `chunks_added` | `doc_id` / `status` / `queued` / `detail?` |

> `upload_time` 是 `"YYYY-MM-DD HH:mm:ss"`（**不是 ISO-T**），因为它是 MySQL 原样返回的字符串。

## 6. 已知边界与遗留项

1. **toast 会盖住页头文案**（截图 `07-retry-then-fail-again.png` 最明显）：
   `ToastStack` 固定在顶部居中，知识库页在这个位置正好是标题与说明文字。
   本轮之前这里最多同时出现 1 条 toast，现在「提交 + 完成」或「失败 + 重试」可能同时 3 条，
   遮挡就显眼了。**本轮没改**：`ToastStack` 是全局组件，动它会影响会话页与设置页的观感，
   属于超出本次范围；且它与异步解析这条契约无关。建议作为一次独立的界面打磨
   （候选：移到右下角，或给 toast 一个不透明底色 + 更大偏移）。**已截图留证**。
2. **「片段总数」里含 P0-4 之前的遗留向量**：`document` 表 0 行时 `片段总数` 显示 15 ——
   那是 P0-4 之前写入的、metadata 里没有 `doc_id` 的旧切片（`upload/test.docx` 与
   `upload/离职流程与注意事项.pdf`）。这不是本轮的缺陷，正是 **P0-4 要重建的对象**；
   重建后这个不一致会消失。
3. **列表不分页**：接口默认 `limit=200`，超出后表格只显示前 200 条，但顶部计数仍是全库。
   当前规模下无影响；等知识库到几百份文档再处理（属于 P2-9 那一带）。
4. **轮询间隔与退避参数写死在前端源码里**（`POLL_INTERVAL_MS` / `POLL_MAX_INTERVAL_MS` /
   `QUEUE_EVERY_N_TICKS`），没有做成可配。理由：它们属于「前端怎么刷新」，改一次就要重新构建发布，
   做成 `.env` 反而会给人「改了就生效」的错觉。若之后要做慢速网络调优，这里是入口。
5. **片段数在解析期间不增长**：`chunk_count` 只在 `success` 时才有值，
   所以解析中那一列显示 `—`。如果以后要做「边解析边看到切片增长」，前后端都要改。
6. **没有前端单测**：本轮所有前端保证都来自端到端验收。代价是验收慢（约 21 秒）且需要完整环境；
   好处是它验的是真行为。若前端逻辑继续变厚（比如再引入几个 store 间的联动），
   值得补一层 `vitest` 单测覆盖纯函数与 store 状态机 —— 现在还不值。
7. **`watched` 集合只在登出时清空**（`reset()`）。单次会话内它最多与「本会话见过非终态的文档数」同阶，
   不是泄漏；但若将来做「长时间不登出」的公开试用，这是第一个要加超时清理的地方。
8. **两处 `page.route` 桩的局限**（§3.16）：`accept-ui` 不覆盖「真 Worker 下线时后端是否如实上报」，
   那部分证据在 `accept` 与 module9 里。两个脚本要一起跑才算完整。
9. **`upload/` 里可能残留上一次崩溃的夹具**：脚本 `finally` 里走 HTTP 善后
   （不依赖浏览器还活着），并在开头用随机 `RUN` 后缀隔离；但若进程被 `kill -9`，
   `upload/` 与 `/tmp/p03b_*` 夹具会留下 —— 名字里都带 `p03b_`，便于手工清理。
