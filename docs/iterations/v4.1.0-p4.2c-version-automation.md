# v4.1.0-p4.2c · 版本号自动化 + 线上四小修（2026-11-16）

## 背景与问题（全部线上实测）

1. **UI 版本号停在 4.0.0-p4.16**（生产已 4.1.0-p4.2）：真相源是 `config/version.py`
   的常量，靠「迭代五件事」纪律 bump——纪律一松就漂。**解法：版本号改为自动解析**，
   解析顺序 `config/_runtime_version.txt`（deploy.sh 在 reset 后用 `git describe
   --tags --always` 生成、build 烧进镜像）> 本地 `git describe` > 兜底常量。
   语义变化：常量从「真相源」降级为「最后防线」，**不再要求每次迭代手动 bump**。
2. **test 账号 display_name 乱码**（截图反馈）：2026-11-11 建体验账号时 mysql 客户端
   未带 `--default-character-set=utf8mb4`，中文以 latin1/cp1252 逐字节再编码入库
   （双重编码）。全表排查只有 id 61（office-service）/62（test）中招，已用
   `CONVERT(CAST(CONVERT(display_name USING latin1) AS BINARY) USING utf8mb4)` 反转码修复
   （test→「体验账号」，office-service→「办公智能体服务账号」）。
   **防坑**：手工 SQL / seed 含中文一律带 `--default-character-set=utf8mb4`。
3. **/api/v1/system/health 触发方梳理**：前端 p4.12 已去轮询（挂载+visibilitychange
   事件驱动）；现存周期触发只有 **docker healthcheck（15s→30s）**。该接口纯静态
   （版本+identity 配置位，无向量库/LLM 调用），不构成内存泄漏风险。
4. 系统设置页文案去掉 `（kb_role=superadmin）`。

## 排查 SQL（同款乱码通用）

先 SELECT 确认 recovered 可读再 UPDATE（只改命中行，不要全表跑）：

```sql
SELECT id, username, display_name,
       CONVERT(CAST(CONVERT(display_name USING latin1) AS BINARY) USING utf8mb4) AS recovered
FROM user;
UPDATE user SET display_name = CONVERT(CAST(CONVERT(display_name USING latin1) AS BINARY) USING utf8mb4)
WHERE id IN (61, 62);
```
