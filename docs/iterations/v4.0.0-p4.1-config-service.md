# v4.0.0-p4.1 — 运行时配置服务：业务开关不用重启就能改

| **性质** | 计划内 · 基础设施改造（PLAN-v4.0.0 P4-1，用户 2026-10-16 讨论拍板） |
|----------|----------------------------------------------------------------------|
| **tag** | `v4.0.0-p4.1` |
| **默认行为** | **零变化**：所有开关的既有取值路径（.env → 代码默认）原样保留；DB 无配置行时与旧版逐字节一致 |
| **新增能力** | MySQL `system_config` 为业务开关真相源，管理端（P4-2）改了**即时生效，无需 recreate 容器** |

## 1. 背景（结论先行）

两个问题在 2026-10-16 的讨论里被摆到桌面上：

1. **改任何开关都要重启**。`.env` 经 compose `env_file` 在容器创建时注入成环境变量，pydantic-settings 在进程启动那一刻冻结——拨一个 `QUERY_REWRITE` 也得 `docker compose up -d --force-recreate`。对基础设施配置（连接串/密钥/端口）这是应得的代价，对业务开关是纯运维摩擦。用户后续还要做模型切换、会话三层存储，都需要一个「运行时可变」的配置层。
2. **版本号与代码不同步**。`PROJECT_VERSION` 写在 `.env`（gitignore），`deploy.sh` 的 `git reset --hard` 不带它上服务器——服务器的 `.env` 长期停在部署那天的旧值（真实事故：代码已是 3.1.0-p3.7d，UI 设置页与 health 还显示 3.0.0-p3.6）。

**结论**：P4-1 落地 ConfigService 底座——MySQL `system_config` 表做业务开关的真相源，进程内缓存 + TTL 回源读，管理端写；`QUERY_REWRITE` / `QUERY_HYDE` 作为试点从 settings 迁入。同时把版本真相源移到**入库的 `config/version.py`**，版本号随代码/tag 同步，`.env` 降级为本地覆盖。

## 2. 方案（实现了什么）

**① 版本真相源入库（`config/version.py`，新）**
`PROJECT_VERSION = "4.0.0-p4.1"`；`settings.py` 以它为默认 + `field_validator` 兜底空串（防 `.env` 写 `PROJECT_VERSION=` 把 UI 版本显示成空）。`.env.example` 版本行改为「本地覆盖示例」并注明服务器删行即跟随代码。铁律的版本 bump 从「只改 .env」改为「`config/version.py` + `.env.example`」。

**② `system_config` 表（迁移 0011 + `core/schema.py` 同步）**
`config_key`(PK) / `config_value`(JSON 文本) / `value_type` / `description` / `updated_at` / `updated_by`。列注释与迁移逐字相同——`compare_metadata()`（module8）diff 必须为 0，已实测通过。

**③ `core/config_service.py`（新，核心）**
- `ConfigStore` ABC + `MemoryConfigStore`（测试/开发）+ `MySQLConfigStore`（生产真相源），与 `SessionStore` 同构；
- `ConfigService`：`get_flag(key, default)` / `set_flag` / `unset_flag` / `reload` / `all_flags` / `list_entries`；进程内缓存 + `CONFIG_TTL_SECONDS`（默认 60s）TTL 回源，双检锁；
- **取值优先级：DB 值 > `.env` 值 > 代码默认值**——调用方传的 default 就是 `.env`/代码档（`get_flag("query_rewrite", settings.QUERY_REWRITE)`）；
- **类型守卫**：`_type_of` 判别顺序 bool 先于 int（`isinstance(True, int)` 为真）；库里值类型与期望不符 → 告警 + 回落默认（防 `"yes"` 这种 truthy 字符串静默放行）；`set_flag` 拒绝 None/list/dict 与跨类型改写；
- **故障姿态**：读 fail-open（DB 挂了回落默认值，服务不炸）；写 fail-closed（落库失败必须抛，管理端看得见「没保存成功」）；
- 单例 `config_service` 按 `CONFIG_BACKEND`（memory|mysql，默认 memory 保离线测试可跑）装配；P2 的 Redis pub/sub 失效广播预留了 `reload()` 钩子。

**④ 试点迁移 `core/rag_chain.py`**
`_prepare_parallel` 的三处 `settings.QUERY_REWRITE/QUERY_HYDE` 改为 `config_service.get_flag(...)`，settings 值降为默认档。module23 十四项断言**原样通过**——证明默认档链路零破坏。

**⑤ `api/main.py` 启动预热**：`on_startup` 里 `config_service.reload()` 并打日志（backend + 生效项数）；DB 故障不阻启动（读 fail-open）。

**⑥ `.env.example`**：新增 `CONFIG_BACKEND` / `CONFIG_TTL_SECONDS` 段，版本行改新规则注释。

## 4. 否掉的方案与代价

- **否掉「配置真相源放 Redis」**：违反项目铁律（Redis 仅缓存/队列，不存真相），且 Redis 一挂配置全丢。Redis 在 P2 只做变更广播 + 热缓存。
- **否掉「按类型分列」**（bool_value/int_value/...）：每加一种开关类型就改一次表。JSON 文本 + `value_type` 标注让「加类型」只是应用侧的事；类型校验在应用层集中做，与「判定逻辑集中在 core/*.py」的既有约定一致。
- **否掉「启动时强校验配置表/DB 可达」**：DB 挂了服务该起还是得起（读 fail-open），与安全判定（kb_acl/身份）的 fail-closed 刻意区分——「查不了配置就拒绝服务」比「用默认值多跑一次改写」严重得多。
- **否掉「P1 就上 Redis pub/sub」**：单实例下 TTL 60s 已满足最终一致；pub/sub 留给 P2，与会话缓存失效共用同一套基建（一次搭建两处受益）。
- **已知代价**：`CONFIG_BACKEND` 默认 `memory`——生产若忘记配 `mysql`，症状是「以为配了热更新、其实只存在进程内存里」（重启即忘）。缓解：启动日志明确打 `backend=`，settings 注释写明「生产要在 .env 显式配 mysql」。

## 5. 遗留与触发条件

- **P4-2 设置页改造**（本计划下一高优任务）：现有只读「系统设置」页升级为分层可操作面板 + `api/routes/admin/config`（superadmin 门禁）。ConfigService 的 `list_entries()`/`set_flag` 已为其备好。
- **P4-3 模型切换 / P4-4 会话三层存储 L1**（低优先级，依赖 P4-1）：见 PLAN-v4.0.0.md。
- **P2：Redis pub/sub 即时失效**。触发条件：多副本部署，或 60s TTL 不可接受。
- **per-user 模型切换**。触发条件：出现「不同角色/个体确需不同模型」的真实需求（届时 user 表加 `default_model`，优先级 用户 > 全局）。
- **服务器待办（部署本版后执行）**：删除 `/opt/qa/.env` 的 `PROJECT_VERSION` 行并 recreate backend——否则它会继续覆盖成旧版本号，UI 仍显示老版本（这正是本次要根治的问题）。命令：`sudo sed -i '/^PROJECT_VERSION=/d' /opt/qa/.env && cd /opt/qa && docker compose --profile full up -d --force-recreate backend`。
- **生产 `.env` 需加 `CONFIG_BACKEND=mysql`**（当前服务器未配，部署后热更新才真正生效；不配则维持「重启才生效」的旧行为，不会更坏）。
