## 3. 关键设计决策

### 3.1 否掉「网关直连 MySQL」（设计规格 §8 D11 的字面表述）

D11 写的是「网关直连 MySQL 读 `user` 表」。**落地时否掉**，改成后端出内部接口、网关调它。

**理由：判定规则会变成两份。** `core/password_policy.verify()` 是 11b 立的
「判定规则唯一出处」，带 141 条断言，其中三条在 TypeScript 里重做特别危险：

1. 「账号不存在 / 密码错 / 已锁定」对外文案必须**逐字相同**（防用户名枚举）；
2. 四条失败路径的**耗时**必须等长（响应时间就是枚举器）；
3. 到期判据是 `>` 不是 `>=`（差一秒，口径就变了）。

重写一遍 = 三份没有测试的副本。半年后有人改 Python 侧口径，TS 侧静默漂移，
症状是「有人能登录、有人不能，而没人知道为什么」。

**代价（认下来）**：登录多一次内网 HTTP；
多一个必须保护好的内部接口（§3.3）。这是拿「多一跳」换「规则只有一份」。

> ⚠️ **收尾时补测的延迟口径**（初版这里写的是「实测 < 5ms」，**那句话是错的**，已改）：
> 「一跳 HTTP 本身」与「整个登录请求」是两个量，混起来写就会得出一个漂亮但没意义的数字。
> - 纯 HTTP 开销（同一路由、故意传错密钥 → 401，不跑 bcrypt）：**0.7~1.1ms**（5 次采样）
> - 整个内部登录判定（跑完 bcrypt cost 12）：**172~179ms**（5 次采样，首次 371ms 是冷启动）
> - 本机 bcrypt cost 12 单次：**167ms**
>
> 所以真实结论是：**多一跳 HTTP 的成本 ≈ 1ms，可以忽略；而登录慢是因为 bcrypt 慢（防爆破的刻意设计）**，
> 那 167ms 无论判定放在 Python 还是 TS 都一样存在，**不是这个方案引入的**。
> 写成「< 5ms」会让人误以为登录很快，而实际用户能感觉到的是 170ms 级的等待 ——
> 而它来自安全设计，不该被当成性能问题去优化掉。

**落地前先实测过**：`bcryptjs` 能否验 passlib 生成的 `$2b$12$` 哈希 —— 这是
「网关自己判」的前提，验不通整个方案要换。实测通过（205ms / 200ms，耗时比 1.02），
但仍然选了否掉方案 —— 因为「能验」不等于「该验」。

### 3.2 网关用 `node:http` 而不是全局 `fetch`（踩出来的，别改回去）

Node 的全局 `fetch`（undici）**会读 `HTTP_PROXY` / `http_proxy` 环境变量**，
且默认**不尊重** `NO_PROXY`。本项目对后端的调用是**同机内网**（本机 `127.0.0.1`、
compose 里的 `backend`），于是：

- 开发机常年挂着 ClashX / 机场客户端（`export http_proxy=...`）→ **必踩**；
- 很多服务器默认也 export 了代理变量 → **生产同样会踩**；
- 症状 = `fetch failed` + `cause: ECONNREFUSED`，**没有状态码、没有响应体**，
  而那个 `ECONNREFUSED` 指的是**代理端口** —— 排查时极易往「后端没起」上想，
  其实后端活得好好的（本轮就真的绕了一圈，先怀疑是 8000 挂了）。

**否掉的方案**：给 fetch 传 `dispatcher`（undici 的 `Agent`）。实测 `undici`
在 Node 22 里既不能 `require('undici')` 也不能 `import 'node:undici'`，
而 `setGlobalDispatcher` 在 Node 22 上不是全局（实测 `undefined`）——
**没有一条能稳定绕过代理的路**。改用 `node:http`（完全不读代理环境变量，已实测）。

代价：API 啰嗦（自己拼 JSON、自己收分块）。值，换来的是本机 / 测试机 / 生产机
行为**完全一致**。

### 3.3 内部接口的信任边界：共享密钥 + 严格白名单

`/api/v1/internal/*` 能验证密码、能改 `failed_login_count`、能写 `last_login_at`、能落审计。
拿到它 ≈ 半个登录系统。三道边界：

1. **`X-Internal-Token` 用 `hmac.compare_digest` 比对**（不是 `==`）——
   字符串相等比较会在第一个不一样的字节上返回，能被用来逐字节试出密钥。
   缺密钥时 **503 fail-closed**（不是「不校验」也不是「给个默认值」）。
2. **`include_in_schema=False`** —— 免得 `/docs` 变成「如何绕过网关登录」的说明书。
3. **不参与 `X-Forwarded-For` 之外的任何信任**。

⚠️ 这三条**不解决「8000 被映射出去」**。那件事的答案是拓扑：
`docker-compose.yml` 里 backend 不映射端口。密钥是第二道防线，不是第一道。

### 3.4 「判定没跑成」与「判定为不通过」必须可区分

`InternalAuthClient.verify()` 的返回类型是 `InternalAuthResult | null`：

- 非 null = 判定**跑完了**（成或不成都是跑完了）
- null = 判定**没跑成**（后端不可达 / 缺密钥 / 5xx / 解析失败）

混起来的后果很具体：后端挂一小时，所有人收到「用户名或密码错误」。
用户会去问「我密码没改啊」，排查的人会去查密码策略与 bcrypt cost ——
而真因是网关连不上后端。**错误信息把排查引向反方向**，代价远大于多写一个类型。

判定不通过时**也返回 HTTP 200**（语义：请求处理成功，业务上没过）——
网关要靠 body 里的 `code` 区分「回 401 通用文案」还是「把他导到改密页」。

### 3.5 对外 code 与后端内部 code 必须分开（防枚举器的第二道）

后端的 code 是给后端日志看的（`wrong_password` / `not_found` / `locked`）。
**直接透传出去等于在响应体里附送一个用户名枚举器** —— 前端不显示它，
但它在 network 面板里，谁都能看。

所以网关做一次翻译：`not_found` / `wrong_password` / `locked` → **同一个**
`INVALID_CREDENTIALS`；`expired` → `PASSWORD_EXPIRED`（密码**是对的**，
只是到期了，前端要导去改密而不是让他重新输）；`inactive` → `ACCOUNT_INACTIVE`。

11b 已实测：④「密码错」与⑤「账号不存在」的响应体**逐字相同**。

### 3.6 回落默认关闭（含生产）

`GATEWAY_INTERNAL_FALLBACK` 默认 `false`。判定的后端不可用时，
网关**明确报「认证服务暂时不可用」**，不静默改用 `.env` 那份数据。

回落看着「提高可用性」，实际是开了一条绕过 MySQL 的登录通道：内部接口配错时，
**所有**账号都改用陈旧数据判定，只有一行 warn 日志。
真正需要它的是本机断网调试 —— 那时外部进不来，设 true 是安全的。

### 3.7 `update_password_hash_only()`：升 cost 不是换密码

bcrypt cost 迟早要涨（涨得越慢越好，CPU 越贵）。涨的那一刻库里所有存量哈希
都弱一档，11b 定了「登录成功时顺带升级」。

**不能走 `update_password()`**：那个函数是「换密码」语义，会连带
`token_version + 1`（改密后其他设备全部失效）、`password_changed_at = now`
（给密码续 90 天）。做成「只是把 cost 补上去」等于**用户每次登录都被踢下线、
每次登录都续一次有效期** —— 90 天到期策略就永远不会触发了。

新函数只动 `password_hash` 一列。有断言守着这两条（token_version 与
password_changed_at 都不变）。

### 3.8 `create_user` 的 `password_changed_at` 兜底（本轮唯一的产品侧改动）

11b 定了「`password_changed_at` 为 NULL 时按已过期处理」（fail-closed）——
那是对迁移前老行的正确处置。但 `create_user` 传了哈希、**不传时间**时，
语义上显然是「这个人刚建、密码刚定」，落成 NULL 等于建出一个
**一登录就报「密码已过期」**的账号。

两条真实路径（`admin_service` 建号、`seed_users` 种子）都显式传了时间，
所以没出过事 —— 是本轮测试写漏了才发现。留着的风险是：将来第三个调用方
忘了传，就是一个静默的「所有人都登不进去」。兜底放在仓储层，
因为那是唯一能让「漏传」不可能出错的地方。

**代价**：无法表达「导入一个只知哈希、不知何时设的外部账号」。
要造过期账号请用 `update_password()` 传一个过去的时间 —— 那才是明确的表达。

### 3.9 `X-Token-Version` 缺了不拦（不制造无收益的登出）

`status` 校验挡得住「停用/离职」，但**挡不住「改密后旧 token 仍有效」**——
改密时人还是 active，新旧两个 token 都指向同一个 active 的人。
所以要靠 `token_version`（改密 / 停用 / 改角色都会让它 +1）。

但**头缺了不拦**，刻意：

- dev 裸跑 / 手写 curl 时没有这个头，拦住的话本地一切 401；
- 11c 之前签发的 token 里没有 `ver`（最长 12h 窗口），拦住的话升级瞬间所有人
  被踢下线 —— 而那次踢下线**毫无安全收益**（那些 token 签发时确实有效）。

真要收紧（生产强制 `ver` 存在）是「破坏性变更」级别的决定，该在 12b 收口时做，
不该偷偷夹在 11c 里。

⚠️ 顺带一个已知后果：`jwt.strategy.ts` 里 `sub` 的**语义变了** ——
11c 之前是登录名，之后是 `user.id` 的十进制串。旧 token（最长 12h）仍能通过校验
（`uid` 为 null → 走兼容分支）。要立刻失效就把 `GATEWAY_JWT_EXPIRES_IN` 临时调短。

## 4. 过程中修掉的 bug

### 4.1 Node fetch 走代理 → 登录全挂（最难查的一个）

症状 `fetch failed` / `cause: ECONNREFUSED`，**没有状态码**。
第一反应是「后端没起」，但后端健康检查明明 200。
真因：`HTTP_PROXY` 被本机代理软件 export 了，Node 的 fetch 照样读它。
详见 §3.2。修法是换 `node:http`。

### 4.2 `create_user` 漏传时间 → 新号一登录就报过期

见 §3.8。测试发现的（不是生产事故），但风险是真的。

### 4.3 一个「发现即修」的判据漏洞

第一版测试里，`svc.login()` 直调时断言「IP 取 XFF 第一段」。写完意识到：
那要求 `svc.login` 也去解析 XFF 头，而 `api/routes/internal._client_ip()`
已经在做了 —— **两处实现同一份解析**，正是本轮花大力气避免的那类重复。
改成断言「IP 如实落库」，XFF 那一段由真链路 curl 验（实测落库 `203.0.113.55`）。
