## 1. 范围

### 做了什么

1. **`kb_role` 进 JWT** —— 网关得以知道「这个人能不能改知识库」。
2. **网关路径粗筛** —— 四条知识库写路径，`kb_role=none` 直接 403，**请求不进后端**。

| 项 | 归属 | 原因 |

| 前端入口收敛 | **14d** | 本轮只锁链路两端 |
| 管理端下发授权 | **14f** | 改授权仍要直接改库 |

## 3. 关键设计决策

### 3.1 为什么**不注入** `X-User-Kb-Role`（本轮最要紧的一条）

剥离清单里加了它，注入列表里**刻意不加**。

后端的 `kb_role` 从 **MySQL 实时读**（`core/identity.py::_make_actor`），所以 14a 实测里
「管理员改授权 → 立刻生效，不用重登」。若网关再注入一个来自 JWT 的 `kb_role`，
同一个字段就有两个来源：JWT 里是**签发时的快照**、库里是**当前值**。

**权限系统里「两个真相源」意味着「在某些时刻它就是错的，且不报错」。**
必须回答「谁说了算」，而那个答案会随部署形态变化。

代价（写进代码注释，因为它是真实的）：**网关的粗筛用的是 JWT 快照**，
所以「降级某人的 `kb_role`」之后，他手里的旧 token 仍能过网关这道门，
直到 token 过期（最长 12h）。但**后端会拒**（它读的是库里当前值）——
两层都在，粗筛那道只是「省一次后端往返」，不是唯一防线。
要让网关立刻知道，改授权时 `token_version+1` 强制重登即可
（`set_kb_role()` 已经这么做了，14f接上管理端即生效）。

### 3.2 网关的粗筛必须**比后端更宽**

判据是 `kbRole !== 'none'` 就放行，**不是**精确匹配五档。

12b 已经踩过一次反面教材：网关只放 `admin` 会让 `hr` 在网关被拒，
而后端那条 hr 分支永远走不到，症状是「只有 admin 账号能进管理端」——
一个**只在特定账号下才现形**的 bug。

具体到本轮：`ops` 能上传/删除但**不能重灌**，而网关会放 `ops` 去打后端，
然后被后端以 `reindex` 拒掉。这是**误拒一次**；
而漏放的代价是全公司知识库被改。两害相权取轻。

### 3.3 `decidePath()` 的签名改造

从 `decidePath(path, role: string | undefined)` 改成
`decidePath(path, user: {role?, kbRole?} | undefined, method?)`。

**理由**：传两个字符串参数的话，加第三个维度时**少传一个不会编译报错**，
只表现为「那道门忘了看这个字段」，且不报错 —— 与13d 的
「后端写 `{"from","to"}`、前端读 `detail.status`」是同一类失效。
传对象的话调用点必须把整个 user 交出来。

同时把「新增的第三个参数 `method` 设为可选」：漏传时`isKbWriteRequest()`
返回 `false` → 放行给后端判。**粗筛漏了不致命，后端还在**；
反过来若它默认 `true`，任何一个漏传 method 的调用点都会把**所有**请求拒掉。

### 3.4 方法必须参与判定

`GET /documents/{id}` 与 `DELETE /documents/{id}` 共用路径形状。
只看路径的话，一个 `kb_role=none` 的人连**看**单篇文档都不行——
而共用知识库是刻意的业务决策。所以四条规则都写全了「方法 + 正则」。

正则里 `{doc_id}` 用 `\d+` 限定：将来出现 `/documents/import` 这种路径时，
不会被误判成「带 id 的文档」而拒掉（那条路径现在不存在，放行给后端是对的）。

### 3.5 否掉的方案

| 方案 | 为什么否 |
|---|---|
| 注入 `X-User-Kb-Role` | §3.1，两个真相源 |
| 网关精确匹配五档（`ops` 不许过upload） | §3.2，网关比后端严是 bug |
| 网关查库拿 `kb_role` | 每个请求多一次 DB 往返；且后端本来就要查库，D11 §8.1 选的就是「`ver` 进 JWT、后端比对」 |
| 粗筛按路径前缀 `/api/v1/documents/` | 会**误伤所有读接口**，等于把「共用知识库」这个业务决策推翻了 |

## 4. 配置与接口变化

### 环境变量

**无新增。** 网关没有连MySQL，也不新增连接配置。

### 接口

**行为变化**（同一个接口，同一个 403，只是拒绝发生在更前面）：

| 路由 | 改前（14a） | 改后（14b） |
|---|---|---|
| `POST /api/v1/documents/upload`（`kb_role=none`） | 后端 **403**，`{"detail":"没有权限执行「上传知识库文档」…"}` | 网关 **403**，`{"error":{"code":"FORBIDDEN_KB_WRITE","message":"没有权限修改知识库，请联系管理员开通"}}` |
| 同上（`kb_role=ops`） | 后端 202 | 网关放行 → 后端 202 |

⚠️ **响应体格式变了**（网关统一错误体 vs 后端 `detail`）。这是既有约定
（`CHANGELOG` 里有「统一错误体只包网关自身错误」），不是本轮引入的。

### 登录响应新增字段

```json
"user": {
  "username": "chen.jie",
  "role": "user",
  "kb_role": "none",          ← 新增
  "employee_no": "G0002"
}
```

**前端要读它**做 14d 的入口收敛，而前端除了这个响应拿不到该值
（后端 `/api/v1/admin/me` 只给自己的）。

### JWT 载荷新增

```
kbRole: 'none' | 'ops' | 'qa' | 'dev' | 'superadmin' | 'unknown'
```

`unknown` **不是一档权限**，而是「值不认识」的降级目标。
14b 之前签发的 token 没有这个字段 → `validate()` 填`none`。

## 6. 已知边界与遗留项

### 6.1 本轮写断言时自己踩了一次「夹具坏了却像实现有 bug」

第 4b 组第一版用 `re.sub(r"\d+", "123", pattern)` 从正则生成真实路径，
结果把 `/api/v1` 里的 `1` 也换掉 → `/api/v123/documents/upload` → **四条断言全部假红**。

症状看起来像「网关实现有 bug」，实际是夹具自己坏了。
修法：**正则负责判定、真实路径单独枚举**（`KB_WRITE_ROUTES` 与 `KB_WRITE_PATHS`
分成两个列表）。

还有一处：`PATH_AUTH_SRC.count("pattern:")` 数出来是 5 而不是 4 ——
因为**我自己写的注释里提到了 `pattern:`**。改成数 `{ method: ..., pattern: }`
这个整体形状。与第 78 条坑（静态检查把自己判成违规）同一类。

### 6.2 `kb_role` 不进身份头，所以「降级授权」后网关有最长 12h 的滞后

见 §3.1。**不影响安全性**（后端拒），只影响「粗筛那道门什么时候知道」。

### 6.3 遗留项

| 项 | 说明 |
|---|---|
| **结构断言在 14e** | 第 4b 组断言的是「网关规则与本组的 Python 等价实现一致」+「正扫 TS 源码」。但**后端 `documents.py` 的四条路由**与 `KB_WRITE_ROUTES` 的一致性还没有机械断言 —— 现在两者是各写一份、靠人keep 它们同步。14e 要加「后端新增写路由时网关粗筛必须跟着加」 |
| **老 token 无 `kbRole`** | 最长 12h 窗口内按 `none` 处理（fail-closed），即「改了授权但要等重登才生效」 |
| **break-glass 超管 `kbRole='none'`** | 他 `role='admin'` 所以能进管理端，但不能改知识库。要改得往库里补一行并授权 |
| **登录响应体变了** | 前端若读 `user` 对象做类型判断，TS 会因新增 `kb_role` 而需要适配（实测前端无破坏，但 14d 会正式读它） |
