## 1. 对话 hover 复制没有成功提示

**问题**：用户消息悬停后点复制，剪贴板其实写上了，但界面只有按钮 title 闪一下「已复制」，没有全局提示。

**改法**：`MessageBubble.vue` 的 `copyText()` 走已有的 `useUiStore().toast`。
成功：`已复制到剪贴板`；失败（非 HTTPS / 权限拒绝）：如实说「浏览器拒绝了剪贴板访问」，不再只 `console.error`。

`App.vue` 里本来就挂了 `ToastStack`（知识库上传完成用的就是它），这次只是把同一条通道接到复制上。

## 2. Token 明细：整行 hover 都弹，且会顶高最后一条

**问题有两层**：

1. hover 绑在整条 `turn-meta` 上，鼠标扫过「耗时」徽章也会弹出 Token 明细。
2. 浮层用 `position: absolute` 挂在徽章里，朝下展开时仍是滚动容器的子孙 ——
   会抬高 `scrollHeight`，最后一条回答被顶上去，看起来像整窗抖一下；
   `overflow-y: auto` 还会把弹窗裁掉，底部信息看不全。

**改法**：

- hover 只绑在 Tokens 徽章上（`token-badge`），耗时徽章不再触发。
- 浮层仍是徽章的 DOM 子节点（鼠标从徽章滑进弹窗不会断），但定位改成 **`position: fixed` + 视口坐标**。
- hover 时量一次视口余量：下方不足约 280px 就朝上（典型是最后一条回答）。
- 滚动时关掉浮层（徽章走了、浮层还钉在视口会对不齐）。
- 徽章与弹窗之间 6px 空隙用 `::before` 桥接，避免一闪就关。

## 3. 滚动条时有时无，挤占宽度导致换行抖动

**原因**：浮层或流式追加一旦让内容刚好越过一屏，滚动条出现/消失会吃掉约 15px 宽度，消息文本跟着换行。

**改法**：`.message-scroll` 加 `scrollbar-gutter: stable`，槽位恒定预留。
这条和「浮层改 fixed」是配套的：fixed 避免 hover 本身制造滚动条，gutter 兜住流式追加等其它溢出。

## 4. 上传后要重启后端才能检索到 —— 启用 Chroma server

**根因**（p1.5b §6 第 2 条已经写过）：backend 与 worker 各自用嵌入式 `PersistentClient` 打开同一份 `vector_db/`，
HNSW 索引在各自进程内存里。worker 落盘后，backend 还拿着启动时那份索引 → 新文档「库里有、答不知道」。

**改法**：向量索引改由 **chroma 容器单点持有**，应用经 `HttpClient` 共享。

| 位置 | 行为 |
|------|------|
| `settings.CHROMA_HOST` 为空 | 仍走嵌入式（单测 / 兜底） |
| `CHROMA_HOST` 非空 | `chromadb.HttpClient` |
| 显式传了 `persist_dir`、没传 `chroma_host` | **强制嵌入式**（防单测随 `.env` 去连真实服务，p0.4c 同类事故） |

编排与运维：

- compose 增加 `chroma`（`chromadb/chroma:0.5.23`，与 lock 客户端对齐），默认 profile。
- 宿主机映射 `127.0.0.1:8001`（8000 给裸跑 backend）；容器内仍是 8000，全栈模式 compose 覆盖为 `chroma:8000`。
- 数据挂 **`./chroma_data`**，**不要**再挂 `./vector_db`。
  曾经试过复用 `vector_db`：单测若再以嵌入式打开同一目录，HNSW 会坏，问答直接 502
  （`ef or M is too small`）。服务端目录和应用测试目录必须分开。
- 心跳用 `/api/v1/heartbeat`（0.5.23 稳定有；v2 在部分 0.5.x 镜像上没有）。
- `make infra` 现在起 `mysql + redis + chroma`；`infra-check` 从 14 项扩到 17 项。
- 裸跑 `.env`：`CHROMA_HOST=127.0.0.1`、`CHROMA_PORT=8001`。
- `reindex --apply` 在 server 模式下不再因「后端在线」拒绝（索引在服务端，重灌即刻可见）。worker 在线仍拒绝（会和重灌抢同一批 doc_id）。

**实测（不重启 backend）**：

1. 上传 `p15c_live_1790231608.txt` → worker 2 秒内 `success`。
2. 立刻 `POST /api/v1/qa/ask`，引用命中 `324:0`（`HIT_NEW_DOC True`）。
3. 测完已删除 324 与另一份验证文档 318。

当前运行态：`GET /api/v1/system/settings` → `type=chroma(server)`，`persist_directory=server://127.0.0.1:8001`。

## 5. 单文件上传扩展为多文件 / 选文件夹

后端 `load_directory` 是「磁盘上已经有一棵目录，再递归解析」。
浏览器上传到不了那一步：用户选的是 `FileList`。选文件夹时，浏览器（`webkitdirectory`）
已经把子目录展开成文件列表，每个 `File` 带 `webkitRelativePath`。
所以前端要做的不是再写一套递归，而是 **一次把多份 File 交出去**。

| 层 | 改动 |
|----|------|
| 后端 | `POST /api/v1/documents/upload/batch`，逐份走原来的 `_accept_one_upload`；单份失败不拖垮整批；单批最多 50 份 |
| 前端 store | 单个 / 多个统一走批量接口，一个口径 |
| 知识库页 | 文件框 `multiple`；「或选择整个文件夹上传」；拖拽多文件（拖文件夹请用按钮，本轮没做 `webkitGetAsEntry`） |
| nginx | `client_max_body_size 120m`（默认 1m 会把 >1MB 的文档拦在网关前，报错不带上下文） |

网关的 json/urlencoded 限制 4mb **不挡** multipart：上传流不进 body-parser，原样 pipe 到后端。

## 7. 本轮踩到的坑（必须记）

1. **module9 仍会清空整张 `document` 表**（`_cleanup_documents` 不带 WHERE，p0.4a 就登记过）。
   本轮为了补批量用例跑了一次 module9，原 doc_id 289–293 被抹掉。
   已从旧 `vector_db` 元数据找回原始文件名，重灌后现为 319–323，展示名已改回
   `01_员工录用通知书.md` 等。**旧会话里的引用编号（如 `289:0`）对不上新 id**，
   点开会走「引用内容已随文档删除」那条分支。内容还在，编号变了。
2. **Chroma server 的数据目录不能和应用嵌入式目录是同一个。**
   挂 `./vector_db` 时，单测用 `PersistentClient` 打开它，服务端 HNSW 立刻坏，
   问答 502。现已改为 `./chroma_data`。
3. 重灌时「补登记」按磁盘 uuid 文件名建记录，会把展示名变成 uuid。
   已手工改回原始名。以后若再跑 `reindex-apply`，先确认 MySQL 里是否已有对应 `storage_path`。

## 8. 怎么用（本机当前形态）

```bash
make infra          # mysql + redis + chroma
# .env 里 CHROMA_HOST=127.0.0.1  CHROMA_PORT=8001

make worker         # 解析
make gateway        # 鉴权
```
