## 3. 关键设计决策（含**否掉的方案**）

### 3.1 🔴 改额度**不 bump `token_version`** —— 与四条既有写路径都相反

`set_role` / `set_status` / `set_kb_role` / `update_password` 都 `+1`，
理由统一是「权限字段变了，旧 token 里的旧值必须立刻失效」。

而额度**不是权限**：它**不进 JWT**（D15 只放 `role` 与 `kb_role`）；
本项**只提醒不阻断** —— 额度在生效路径上**根本不被读**，不存在「旧额度还在拦他」。
所以 `+1` 是**纯粹的成本**：管理员改一个数字，那个员工正在写的对话当场 401，
而「额度」这件事他甚至看不到界面（15d 才有横幅）。

**为了一个只改提醒文案的事把人踢下线，是按错的代价做对的防护。**
`user_repo.set_token_quota` 的 docstring 里留了话：将来若真做阻断，这一行必须改，
且要连同「额度进 JWT 还是每次查库」一起决定。

### 3.2 **允许改自己的额度** —— 与 `set_kb_role` 相反

`set_kb_role` 禁止降自己的权，理由是「降权让 token 立刻失效，恢复要找别人改，
一个人把自己锁在外面时那个『另一个人』未必存在」。

而额度不 bump token_version（§3.1），把额度改小**不会让任何人掉线、不会锁死任何功能**
—— 最坏结果只是他自己接下来看到一条横幅。用一个不成立的危害去禁止一个无害的操作，
只会逼出荒唐的后果（「唯一想给自己设额度的人恰好是管理员，于是他必须找同事」）。
只加一条提示：审计 detail 里标 `self=True`。

### 3.3 🔴 布尔必须在**请求体层**拦 —— Pydantic 会替你转，服务层的拦截是死代码

第一版把 `isinstance(raw, bool)` 拦截写在服务层 —— 实测 HTTP 打过去
`{"quota_monthly": true}` **成功写入了 1**。

原因：Pydantic 的 `int` 字段在 JSON 反序列化时就把 `true` 转成 `1`、`false` 转成 `0`，
**根本到不了服务层**。也就是说「把额度设成 1 token」这个荒谬操作
会因为前端传了个布尔而悄悄发生，界面还显示「1」。

修法：`TokenQuotaBody` 上加 `field_validator(mode="before")`，在转换**之前**看一眼。
同时删掉服务层那个分支 —— 死代码比没有代码更坏：它看起来在防什么。

**❌ 否掉的方案一**：`StrictInt`。能拒布尔但**连字符串一起拒** ——
而字符串恰恰是最该收下的（前端表单、curl、其它语言客户端都传 `"5000"`）。
**❌ 否掉的方案二**：`NonNegativeInt`。负数的判断留在服务层，那里能给出
「0 表示不限」这个上下文，而 Pydantic 只有英文 422。

### 3.4 审计记**生效额度**而不只是个人值

审计要能回答「当时他到底被限制在多少」。而 0 的含义是「用全局默认」，
只记 0 的话，三个月后没人知道全局默认当时是多少 ——
所以 detail 里同时记 `effective_from / effective_to / default_quota`。
刻意**不记** token_version：额度不改它，记一个永不变的值进审计只会让人误以为它会变。

### 3.5 管理端输入框显示**个人值**而不是生效值

把生效值放进输入框会让「全局默认 50000 的人」输入框里也显示 50000，
他一确认就把全局默认**固化成个人值** —— 以后改全局默认对他就不再生效，
而没有人知道为什么。所以输入框只放个人值（0 = 不限/用全局默认），
生效值显示在旁边的灰字里（`.quota-eff`，弱化色：它是上下文，不是可编辑值）。

### 3.6 测试发现的两个坑

1. **`audit_repo.ACTION_LABELS` 白名单**：`_audit` 设计成「失败不阻断业务」，
   于是动作名没登记时业务照常完成、审计静默丢失 ——
   表现为测试里 ERROR 日志 + 「审计行查不到」。**fail-open 的组合让漏登记不报错**。
   登记表是新写路径的必经点，顺序应当是「先登记动作名，再写业务」。
2. **测试的清理要按动作删、不按 target_id 删**：第 5 组动了两个人
   （目标员工 + 管理员自己），只删一个 target_id 的审计会留下另一个 ——
   「测试跑完库要回到原样」说的是**整库**。反向组跑在第 5 组 `finally` **之后**，
   所以每个反向验证**自己收尾**；浏览器脚本同理（PATCH 落的审计也清掉）。
   —— 终检（「全库额度为 0」「无审计残留」两条）就是为此而加，它当场抓到了
   浏览器脚本留下的 8 条审计。
