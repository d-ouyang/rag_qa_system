### 2.3 顺手修的真 bug：一条说反了的日志

真链路探测时从后端日志里看出来的：

```
token_version 不匹配（token 已失效）| uid=wu.jing 持有=3 库里=3
```

两边都是 `3`、请求照常200/404 通过，却打了一句「已失效」。

**原因**：那条 `logger.warning` 写在 `raise HTTPException(...)` 的**下一行**。Python 先抛异常，那行是**死代码，永远执行不到**。而它上面的 `if` 分支（不匹配）里已经先抛过一次了 —— 于是「不匹配被拒」和「匹配但正常放行」打的是同一句话，而后者才是实际发生的。

**为什么危险**：一条与事实相反的日志比没有日志更糟 —— 排障时会先信它，于是往「token 版本对不上」这个方向查半天，而真问题在别处。而且它是**静默**的：功能测试全绿、接口 200、没有任何报错。

**修法**：warn 挪到 `raise` 之前。并加断言 **2h** 看住它（判据是源码里 warn 与 raise 的**行号顺序**，不是「日志内容对不对」—— 后者跑一百遍也测不出来）。

## 3. 关键设计决策

### 3.1 为什么用「构造内存Actor + 直接调依赖」而不是打真 HTTP 上传

守卫是纯函数式的（`actor.kb_role` → 判定），不碰库。所以「守卫判得对不对」**不需要真库就能验**。

而真上传会在 `upload/` 留文件、在 `document` 表留行 —— 14a 已经栽过两次（PLAN §4.8）。测试不该再往真知识库里造数据。

**代价**：验不到「守卫依赖与 FastAPI 的 `Depends` 解析确实接上了」。这一层由 2a/2b 的结构断言 + 14a/14b 的真链路实测覆盖。

### 3.2 为什么期望值要**手写**而不是从 `kb_acl` 派生

`EXPECTED` 那张表是手写的。若从 `MIN_KB_ROLE_BY_ACTION` 派生，这条断言就成了「实现等于它自己」—— 恒真、零判别力（这正是 module15 记的「验收脚本自己会骗人」的同一种病）。

代价是改档位时要改两处；收益是改错档位时测试会红。

### 3.3 结构断言为什么要扫「装饰器块」而不是逐行正则

FastAPI 的装饰器可以跨行写。逐行正则会在参数换行时**漏掉半个路由** —— 而漏掉就等于没检查，是这类结构断言最坏的失败方式（看起来通过了）。

所以用「装饰器块」切分：`@router.xxx(` 到下一个装饰器为止，整块拿去做 `Depends` 提取。

### 3.4 2b 的「不在枚举内的写路由」为什么要设计成转红

将来有人加第五条写路由：

- **2a**（依赖里有没有 `require_kb_*`）会红 —— 如果他忘了挂；
- **2b**（这条路由在不在 14a 的枚举里）**也会红** —— 哪怕他挂对了。

第二条是有意的：它要求**有人来判断「它该挂哪个守卫」并更新枚举**。挂对了但没更新枚举时，那条路由的守卫档位没有人审过 —— 而「reparse 与 upload 同档、delete 单独一档」这种判断不该由提交者随手做。

### 3.5 2g 为什么同时断「含每一条」和「两侧条数相等」

- 只查「网关有的后端也有」不够；
- 只查「后端有的网关也有」也不够（那正是 14b 的隐患方向）。

**双向都查**，且额外断「条数相等」—— 这三条一起，才能在任一侧增减时都抓到。

### 3.6 否掉的四个方案

| 方案 | 为什么否 |
|------|---------|
| **把结构断言写成「数一下有几个 `Depends(require_kb_`」** | 数不出「挂在哪条路由上」。挂错路由（把 delete 的守卫挂到 upload 上）照样通过。 |
| **在 `documents.py` 里用一个 `KB_WRITE_ROUTES` 常量，让守卫与路由共用** | 那样结构断言就成了「实现等于它自己」。而且路由表与守卫表合一后，路由表就成了权限配置 —— 一旦有人为了少写一条而删表里的条目，权限跟着消失。 |
| **用 `pytest` 的 fixture + 参数化写矩阵** | 项目现有 17 个测试模块全是手写 `check()` 计数器（无 pytest 依赖，`make test` 逐个 `python` 跑）。为一个模块引pytest 会让 `make test` 的执行方式分叉。 |
| **真上传一个临时文件验「该放的放」** | 会留文件与表行。14a 已因此栽过两次。「该放的放」改成对 `capabilities()` 与 `Actor.can_*` 断言 —— 纯函数、零副作用、判别力更强（它同时验了三处派生是否一致）。 |

## 6. 已知边界

### 6.1 14d 的基线已经量到了，但本版不做

浏览器实测（`chen.jie`，`kb_role=none`，知识库页）：

```
file input=1 | 含「删除」按钮 10 个 | 文档 35 份全部可见
```

即**上传区与每行的删除/重试按钮对所有人完全一样**。这正是 14d 要按 `kb_role` 收掉的。

⚠️ 截图存于 `/tmp/ui14e_kb_none.png`（不入仓）。

### 6.2 结构断言的判据是**源码文本**，不是运行时

- 改法：如果有人把守卫挪进函数体（2e 会红），或者换个写法挂依赖（比如包一层新的 `Depends`），**2a 可能认不出来**。
- 代价：结构断言是「约定级」的检查，不是语义级的。
- 缓解：2e + 真链路实测兜底。语义级的最终保证仍是「真打一次 HTTP」。

### 6.3 `2b` 的枚举会「过时」—— 这是有意的

14a 认定四条。将来加第五条时 2b 会红，要求有人审过守卫档位后更新枚举。**这条「红」不是误报，是设计。**

### 6.4 遗留：撞到过一次「尺子坏了」

第一版 2g 硬编码了 `method: 'post'`（小写）与未转义的正则，而网关源码写的是**大写方法名 + `\/` 转义** → 四条全假红。

更糟的是我第一版的 `backend_to_gw` 键写成元组，`for method, pattern in d` 解包出两个字符串，`method[0]` 取到首字母 —— 断言名印出「D」而不是「DELETE」。

两次都是同一个病：**尺子坏了，看起来像被测物坏了**。修法是解析出四元组再比对，而不是硬编码字符串。

### 6.5 遗留：登录响应字段是 `access_token`（蛇形）

写浏览器脚本时先按 `accessToken` 取，两次探测里一次碰巧成功（有 fallback）、一次拿到空串导致全401，浪费了一轮。

**已在脚本注释里记**（`/tmp/ui14e.mjs`，不入仓）。前端用 `ragqa.auth.token` 这个键名，也不是 `token`。

### 6.6 撞到过限流

连续登录 + 反复验收会吃到 429（登录接口有throttler）。等 65 秒后重跑即可，不是 bug。
