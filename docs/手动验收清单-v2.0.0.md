## 0. 先回答你问到的三个点

### 0.1 创建会话后，MySQL 里能看到什么？

**⚠️ 关键前提：只「新建会话」不落库，发第一条消息才落库。**

这是 v2.0.0 刻意改掉的行为：读操作不再隐式创建会话。以前 `GET /sessions/{任意 id}`
都会凭空造出一条空会话记录（列表里出现「点进去什么都没有」的幽灵条目）。
现在只有真实写入（一轮问答）才会创建。

所以验证顺序是：**在前端新建会话 → 发一条消息 → 再看库**。

```bash
docker compose exec -T -e MYSQL_PWD=rag_root_pwd mysql mysql -uroot rag_qa \
  -e "SELECT id, project_id, title, is_pinned, usage_requests, last_active_at, is_archived FROM session ORDER BY last_active_at DESC LIMIT 5;"

docker compose exec -T -e MYSQL_PWD=rag_root_pwd mysql mysql -uroot rag_qa \
  -e "SELECT session_id, seq, role, LEFT(content,30) AS content, ref_ids FROM chat_message ORDER BY id DESC LIMIT 6;"
```

**`session` 表（每个会话一行）**

| 字段 | 含义 |
|---|---|
| `id` | 会话 ID（前端 URL 里那个 32 位十六进制串） |
| `project_id` | 知识库归属，当前固定 `default` |
| `folder_id` | 所属文件夹（可为空，前端文件夹功能未用） |
| `title` | 会话标题 |
| `is_pinned` | 是否置顶 |
| `usage_input_token` / `usage_output_token` / `usage_cache_read_token` / `usage_requests` | 该会话累计 token 用量与请求次数 |
| `last_active_at` | 最后活跃时间（判软过期用） |
| `is_archived` | 归档标记（软过期后由清理任务置 1，**不物理删行**） |
| `create_time` | 创建时间 |

**`chat_message` 表（每条消息一行）**

| 字段 | 含义 |
|---|---|
| `session_id` / `seq` | 所属会话 + 消息序号（**偶数 = 用户问，奇数 = AI 答**） |
| `role` | `user` / `assistant` |
| `content` | 正文 |
| `usage_input_token` / `usage_output_token` | 本轮用量 |
| `is_cache_hit` | 是否命中问答缓存 —— **当前恒为 0**，见 §0.3 |
| `ref_ids` | JSON 数组，本轮引用的切片编号，如 `["293:0","290:2"]` |
| `turn_meta` | JSON，本轮展示元数据（意图 / 耗时 / 时间戳 / 用量明细） |
| `create_time` | 写入时间 |

> `user` 与 `folder` 两张表已建好，但当前没有链路在用（账号仍在 `.env`，决策 D2：本版不迁）。

### 0.2 文档解析完成后，怎么验证？切片 id 在哪？

**先纠正一个预期：MySQL 里没有切片 id 列表。**

- `document` 表只存 **`chunk_count`（切片数量）**，不存每一片的 id；
- 切片 id 是**规则拼出来的**：`chunk_id = "<doc_id>:<chunk_index>"`，
  即「293 号文档的第 1 片」= `293:0`。它写在 Chroma 的 metadata 里；
- 只有**被引用过的**切片 id 会落到 MySQL —— 存在 `chat_message.ref_ids` 里。

这么设计的原因：切片列表随切分参数变化，存一份在 MySQL 就要维护两份事实，
改切分参数时必然漂移。数量（`chunk_count`）是事实，id 是派生值。

**① 看文档记录与解析状态**

```bash
docker compose exec -T -e MYSQL_PWD=rag_root_pwd mysql mysql -uroot rag_qa \
  -e "SELECT id, file_name, status, chunk_count, attempt_count, fail_reason, upload_time FROM document ORDER BY id DESC;"
```

| 字段 | 含义 |
|---|---|
| `id` | 文档 ID（`chunk_id` 冒号前的那个数字） |
| `project_id` | 归属项目 |
| `file_name` | **原始文件名**（用户看到的） |
| `storage_path` | 磁盘存储路径（哈希名，防撞名） |
| `file_size` | 字节数 |
| `status` | `pending` / `parsing` / `success` / `fail` |
| `chunk_count` | 切了几片 |
| `fail_reason` | 失败原因（可读，前端整行展示） |
| `attempt_count` | 被解析过几次（重试会 +1） |
| `upload_time` / `parse_started_at` | 上传时间 / 本次解析开始时间（回收僵尸任务用） |

**② 验证切片真的进了 Chroma（两种方式）**

方式 A —— 走接口（推荐，不碰向量库文件）：

```bash
curl -s --noproxy '*' "http://127.0.0.1:8000/api/v1/chunks/293:0" | head -c 600
```
预期返回 `chunk_id` / `doc_id` / `chunk_index` / `content`（切片全文）以及源文档信息
（文件名、页数、大小、上传时间）。把 `293` 换成你刚上传的文档 id、`0` 换成第几片。

方式 B —— 直接查 Chroma 的 metadata（想看原始字段时用）：

```bash
ANONYMIZED_TELEMETRY=False .venv/bin/python -c "
import chromadb
col = chromadb.PersistentClient(path='vector_db').get_collection('rag_qa_knowledge')
print('切片总数:', col.count())
r = col.get(where={'doc_id': 293})          # ← 换成你的 doc_id
for i, m in zip(r['ids'], r['metadatas']):
    print(' ', i, '|', {k: m.get(k) for k in ('doc_id','chunk_index','chunk_id','page','source')})
"
```
预期：列出该文档的每一片，`chunk_id` 形如 `293:0` `293:1`，`chunk_index` 连续。
> ⚠️ 这是只读查询。但后端正在跑时，多个进程同时打开同一个 `persist_directory`
> 有损坏索引的风险（详见 §7 遗留项），**不要**用它做写入操作。

**③ 看整体统计**

```bash
curl -s --noproxy '*' "http://127.0.0.1:8000/api/v1/documents/" | head -c 400
```
预期：`total_documents` / `total_chunks` / 各状态计数。
⚠️ 注意：`total_chunks` 读的是元数据、**不走索引**，所以「数字对」不代表「能检索到」（见 §7 第 1 条）。

### 0.3 Redis 缓存为什么没触发？每轮对话不做临时缓存吗？

**因为问答缓存根本没做 —— 它不是没触发，是不存在。**

三个证据：

```bash
docker compose exec -T redis redis-cli -n 0 DBSIZE     # → 0，缓存库一个键都没有
docker compose exec -T redis redis-cli -n 1 KEYS '*'   # → 只有 Celery 的 3 个 binding 键
```
代码侧：`chat_message.is_cache_hit` 字段建好了，但存储层注释写明
「**目前没有任何链路会设置 cache_hit**（问答字符串缓存是 P3 的事）」。

**为什么回答还那么像？** 因为链路本身就是确定性的：检索 + 重排没有随机性，
LLM 温度设的是 `0.1`（很低）。同样的问题走两遍，答案本就该高度一致 ——
**相似不代表命中了缓存**。

**那 `cache_read_tokens` 是什么？** 那是**大模型服务商那侧**的 prompt 缓存
（硅基流动返回的），不是我们自己的 Redis 缓存。两者别混。

**每轮对话的临时缓存**：没做，且是刻意不做。决策记录里列了原因 ——
会话与问答记录是永久业务资产，存 Redis（内存库）属于数据分层错误（会因重启、
内存驱逐、容量保护丢数据）。**会话的真相源是 MySQL，不是 Redis**。
问答字符串缓存被排到 **P3-11**（2.0.x 的可选增强），当前 2.0.0 范围内不做。

**Redis 现在实际只干一件事**：Celery 的任务队列 broker（db1）。见 §8。

## 3. P0-3 异步解析（队列 + Worker）

**做了什么**：上传立即返回（HTTP 202），解析交给独立 Worker；
文档状态机在 MySQL；原子抢任务保证多 Worker 不重复解析；僵尸任务 15 分钟后可回收；
前端轮询看进度、失败能重试。

**怎么验**：

1. `make worker` 起 Worker（不起的话文档会一直停在 `pending`）；
2. 前端上传一个文档 → **立刻**出现一条 `pending` 记录（不再转圈等解析）；
3. 几秒后变 `success`：
   ```bash
   curl -s --noproxy '*' "http://127.0.0.1:8000/api/v1/system/queue"
   docker compose exec -T -e MYSQL_PWD=rag_root_pwd mysql mysql -uroot rag_qa \
     -e "SELECT id,status,chunk_count,attempt_count FROM document ORDER BY id DESC LIMIT 3;"
   ```
4. **关掉浏览器**，上传第二个文档 → 解析照样完成（这是异步最直观的证明）。

## 7. 已知边界（测到这些别当成 bug）

1. **「库里有但答不知道」= 后端进程的索引陈旧**（最常见的一条）。
   Worker 与后端是两个进程，共用同一个 `persist_directory`：Worker 写完落盘，
   但后端内存里的索引还是启动时那份 → **新上传的文档要重启后端才能检索到**。
   立即可解：重启后端。根治要等向量库换成服务模式（或把写入收敛到单进程）。
   判据：`total_chunks` 数字是对的（它不走索引），但检索召回 0。
2. **旧会话的引用可能仍是错的**：`p0.4c` 的修复只管修复**之后**新写的会话，
   历史错位数据没有自动纠正（会话可重建，没写一次性迁移脚本）。
3. **引用只存编号不存快照**：文档删除后，历史回答里那条引用的正文查不到，
   前端会显示「引用内容已随文档删除」—— 这是刻意取舍（决策 D3），不是缺失。
4. **`make test` 的 module9 会清空 `document` 表**（遗留项），跑完需要
   `make reindex-apply` 恢复演示数据。**建议手动验收期间不要跑 `make test`**。
5. **token 不能即时吊销**：无状态 JWT，只能等过期（决策 D4：不做白名单）。

## 8. Redis 现在到底在做什么

**只有一件事：Celery 的任务队列 broker（db1）。**

```bash
docker compose exec -T redis redis-cli -n 0 DBSIZE     # 缓存库：0（没有业务在写）
docker compose exec -T redis redis-cli -n 1 KEYS '*'   # 队列：Celery 的 binding 键
docker compose exec -T redis redis-cli INFO keyspace   # 只有 db1 有键
```

| 库 | 原设计用途 | 当前实际 |
|---|---|---|
| db0 | 短期缓存（会话、问答缓存、SSE 碎片） | **空** —— 会话已迁 MySQL；问答缓存与 SSE 碎片属 P3，未做 |
| db1 | 解析任务队列 broker | **在用** —— 唯一的实际用途 |

所以「Redis 没触发缓存」是预期内的：它现在只是个队列。
什么时候会看到 db0 有键？等 P3-11（问答字符串缓存）落地。

## 10. 一键自检

```bash
# 全链路活着吗
curl -s --noproxy '*' http://127.0.0.1:8000/api/v1/system/health   # 后端（含版本号）
curl -s --noproxy '*' http://127.0.0.1:3000/api/health             # 网关
curl -s --noproxy '*' http://127.0.0.1:8000/api/v1/system/memory   # 记忆后端（应为 mysql）
curl -s --noproxy '*' http://127.0.0.1:8000/api/v1/system/queue    # 队列积压

# 数据落库了吗
docker compose exec -T -e MYSQL_PWD=rag_root_pwd mysql mysql -uroot rag_qa -e "
  SELECT (SELECT COUNT(*) FROM session)       AS sessions,
         (SELECT COUNT(*) FROM chat_message)  AS messages,
         (SELECT COUNT(*) FROM document)      AS documents,
         (SELECT SUM(chunk_count) FROM document WHERE status='success') AS chunks;"
```
> ⚠️ SQL 的**列别名别用中文**：`docker compose exec` 传参时中文别名会编码错乱，
> 报的是 `You have an error in your SQL syntax`，看着像 SQL 写错了，实际是编码问题。
> 列名本身（数据里的中文）不受影响。

> 上面 `切片数` 来自 MySQL 的数量字段；要和 Chroma 实际条数对一下的话，
> 用 §0.2 方式 B 的 `col.count()`（两边应当一致，不一致说明有孤儿切片）。
