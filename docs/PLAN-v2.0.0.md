## 0. 计划修订说明（第 1 版 → 第 2 版；第 2 版 → 第 3 版见 §0.6；第 3 版 → 第 4 版见 §0.7）

### 0.1 为什么改

第 1 版把「会话持久化」的落脚点定在 Redis。重新论证后确认这是**数据分层错位**，三条理由：

1. Redis 是内存数据库，实例重启、内存驱逐、容量保护都可能让数据消失。会话与问答记录是**永久业务资产**，不该交给一个随时可能丢数据的组件；
2. 会话在 Redis 后，SQL 能做的事全做不了：按用户查、按时间聚合、用量对账、质检抽样、后续 Agent 审计留痕；
3. 本项目自己实现了 Redis 三级水位预警 + fatal 只读降级 —— 这等于承认「它可能写不进去」。让永久数据依赖它，是自相矛盾。

调整后的分层一句话：**MySQL 存业务真相，Redis 只做队列与短期缓存，Chroma 存向量，原始文件落磁盘 volume，解析交给独立 Worker。**

### 0.2 变了什么

| 项         | 第 1 版                    | 第 2 版                                   |

### 0.6 计划修订说明（第 2 版 → 第 3 版，2026-10-06）

### 0.6.1 为什么改

第 2 版把系统推到「一个 `admin` 账号 + 一个公共知识库」的生产形态，够上线，但**不像一家公司**：  
所有登录的人看到的是同一份会话和同一份知识库。这一版要把「用户」当成真东西来做：  
人事能分部门/职位建员工，员工各看各的，管理员在独立的管理端做增删改查与密码管理。

**这是需求驱动的增补，不是返工**：第 2 版已完成的部分（P0 四项、P1-5、P1-6）一格都不动。

### 0.6.6 决策已定 + 新增 D12（同日第二轮）

2026-10-06 同日，用户拍板：**D6 = 90 天 / D7 = 管理端独立服务 / D8 = 部门共享 + 个人库 /  
D9 = 保留 break-glass 超管 1 个 / D10 = `hr` 不能重置密码 / D11 = 网关直连 MySQL**。

同时用户提出「能否把多租户隔离校验放到网关层直接拦截」。结论落为 **D12**：

- **网关**：认证 + 身份归一（解 token → 注入头）+ **剥离客户端伪造的身份头** + 粗粒度路径授权 + 限流；
- **后端**：数据范围过滤（会话归属、文档归属、**Chroma `where` 下推**、对象级鉴权）。

理由是隔离判据的**物理位置**在数据库里 —— 列表类要解析响应体、检索类要下推向量过滤  
（等后端查完再过滤，泄漏已经发生）、流式响应中间层无解。详见设计规格 §5.1。

**这一轮顺带实测到网关的一个真实缺口**：`proxy.controller.ts` 的身份注入写成条件式  
（`if (incoming.user)`），白名单路径（守卫不跑）上客户端自带的 `X-User-Id: 999` / `X-Role: admin`  
**会原样转发给后端**。今天无害（后端没人读这两个头），但 12b 一旦实现 `current_user`，  
任何被误标 `@Public()` 的数据接口都会变成身份伪造通道，且不报错。  
**所以 12b 的第一件事是「无条件剥离」，第二步才是「注入」。**

## 4. 数据分层（本项目最终口径）

> 这张表是后续所有实现的裁决依据。任何「这个数据放哪」的分歧，以本表为准。

| 数据                                   | 归属                              | 生命周期   | 严禁                                          |
| ------------------------------------ | ------------------------------- | ------ | ------------------------------------------- |
| 用户 / 文件夹 / 会话 / 消息 / 文档元数据           | **MySQL**                       | 永久业务资产 | 不放 Redis（会丢）、不放 Chroma（不是 KV）               |
| 解析任务（队列消息）                           | **Redis 队列**（Celery broker，db1） | 消费即删   | **不当可靠任务源**；任务真相是 MySQL `document.status`   |

| chunk 切片正文 + 向量 + metadata(`doc_id`) | **Chroma**                      | 随文档删除  | 不放原始文件；**不拿它统计业务文档数**（它数的是切片数）              |

**本期不启用的 Redis 场景**（架构文档里有，我们暂不用，理由写清避免后人疑惑）：

| 场景                                  | 不启用理由                                                         |
| ----------------------------------- | ------------------------------------------------------------- |
| 登录 token 白名单                        | 本项目 token 是无状态 JWT（网关签发），天然不需要服务端存储；代价是无法即时吊销，只能等过期（见 §11 D4） |
| 问答字符串缓存（`rag:qa:{project}:hash(q)`） | 收益不确定、且知识库更新必须清对应缓存，否则答旧内容；放 P3 再评估                           |
| SSE 流式碎片断点补发                        | 只能补「已生成未推送」的碎片，不能恢复模型计算；当前流式未出现明显断点痛点；放 P3                    |
| 语义缓存（Chroma `qa_cache`）             | 副作用最大：知识库变更不清缓存 = 旧答案幻觉；**默认不做**                              |

- **现状问题**：`api/routes/documents.py` 的上传是**同步**的 —— HTTP 请求里直接 `load_file` → `add_documents`（解析 + 切分 + 嵌入 + 入库）。大文件会把请求挂住几十秒，且无法批量上传。
- **改造后的链路**：
  1. 浏览器提交文件二进制；
  2. 后端生成 **uuid 文件名**落盘（不用原始文件名，防重名覆盖）；
  3. MySQL `document` 写入记录，`status=pending`；
  4. **每个 `doc_id` 推一条独立任务进 Redis 队列，HTTP 立即返回**（不阻塞）；
  5. Worker 消费：`status=parsing` → 读盘 → 解析 → 切分 → 写 Chroma → `status=success` + `chunk_count`；异常则 `status=fail` + `fail_reason`；
  6. 前端**轮询** `GET /api/v1/documents` 读 `status` 显示进度。**网页关闭不影响后台任务**，下次打开从 MySQL 读状态。
- **队列技术选型**：Celery + Redis broker。
  - broker 用 **db1**（`redis://redis:6379/1`），缓存类将来用 db0，逻辑隔离；
  - **不配 result backend** —— 状态真相是 MySQL `document.status`，再存一份 Redis 只会带来一致性麻烦和白耗内存；
  - `--concurrency=1`（解析是 CPU 密集 + 模型内存占用大，并发只会互相抢 CPU）；
  - `--max-tasks-per-child=20`：解析会反复吃内存，定期回收子进程防泄漏；
  - `task_time_limit` 设上限，防坏文件把 worker 卡死。
- **幂等（多 worker 抢同一任务）**：用 **MySQL 原子 UPDATE 抢任务**，不用 Redis 锁 ——  
  `UPDATE document SET status='parsing', attempt_count=attempt_count+1 WHERE id=? AND status IN ('pending','fail')`，  
  影响行数为 0 说明已被别人拿走，直接返回。抢到后先 `delete_by_doc_id` 再写 Chroma，重复消费也不会重复插切片。
- **失败兜底**：Redis 重启会丢未消费任务 —— 靠「MySQL `status` 为真相 + 手动重解析接口」兜底，不指望 Redis 持久化。

### P2-14 知识库写权限分发（第 5 版重写，2026-10-08）

> ⚠️ **本段已在2026-10-08 重写。** 第 4 版原文依赖 `12a` 的 `project` 表与
> `user_project.role`，而**那个方向已被用户决策推翻**（知识库全公司共用、不隔离读，
> 见 §8.1），且**库里从来就没有 `project` 表**（实测：只有 alembic_version / audit_log /

> user_password_history）。若照第 4 版实现，会去建一张不该建的表。
> 保留在下面的只有「为什么要做」这个判断，方案本身全部重写。

**为什么要做**：知识库共用之后，**写权限就是唯一的防线**。一个普通员工能把整库重灌，
全公司都答错，而且**不报错**（不像删文件会报错，重灌后问答照样返回结果，只是结果是错的）。

#### 14.0 施工前实测的基线（2026-10-08）

⚠️ **这一节是本项最重要的部分 —— 它推翻了「加一层校验」的假设。**

第 4 版以为问题是「有个只读账号能重灌」。**实测发现现在根本没有门槛**：

```
POST   /api/v1/documents/upload        → 202 + {"doc_id":587, ...}   # 普通员工 chen.jie 能上传
DELETE /api/v1/documents/587           → {"deleted_chunks":0,"record_removed":true, ...}
```

根因：`api/routes/documents.py` 的**四条写路由都没挂任何身份依赖**
（无 `Depends(current_actor)`、无 `require_staff` / `require_admin`）。
对照：12c 给 `qa.py` 的 7 个路由**都**挂了 `Depends(current_actor)`。

全量枚举（`grep -nE "@router\.(post|put|patch|delete)" api/routes/documents.py`）：

| # | 路由 | 行号 | 现状 |
|---|------|------|------|
| 1 | `POST /documents/upload` | 73 | 任何登录用户 |
| 2 | `POST /documents/upload/batch` | 106 | 任何登录用户 |
| 3 | `POST /documents/{doc_id}/reparse` | 372 | 任何登录用户 |
| 4 | `DELETE /documents/{doc_id}` | 418 | 任何登录用户 |

（**无 put / patch** —— 文档没有「编辑」接口。）

⚠️ **所以本项不是「加一层校验」，而是「从零补上整个守卫」** ——
失败模式完全不同：**漏一个路由就完全没有防护**，而且不会有任何报错提示。
因此 14e 的测试里必须含**结构断言**（见下）。

#### 14a 权限模型：`user.kb_role` 五档

迁移 `0007` 加一列 `user.kb_role`，默认 `none`：

| 档 | 含义 | 上传 | 删除 | **重灌索引** |
|----|------|------|------|------------|
| `none` | 默认，什么都不给 | ❌ | ❌ | ❌ |
| `ops` | 运营人员 | ✅ | ✅ | **❌** |
| `qa` | 测试 | ✅ | ✅ | ✅ |
| `dev` | 开发 | ✅ | ✅ | ✅ |
| `superadmin` | 超管 | ✅ | ✅ | ✅ |

**用户拍板**（2026-10-08）：「知识库的写权限一般有运营人员、测试、开发、超管，
**目前我这个项目只给 admin 的超级管理员**。」
→ **只有 `wu.jing`（role=admin）会被授予 `superadmin`**，其余四档**只建判定逻辑、不发给任何人**。
理由：判定逻辑不写，将来第二个人上岗时要重新想一遍；现在发，等于把权限白送出去。

**为什么「重灌索引」单独一档、且 `ops` 刻意不给**：
它是**唯一会让全公司答错**的操作 —— 改切分参数 = 整库重建（§4 的 `chunk_id` 契约
`"<doc_id>:<chunk_index>"` 依赖切分参数，参数变了全库引用失效）。
上传/删错了能改回来，重灌错了要等所有人重新积累问答。

⚠️ **绝不塞进 `user.role`**：`role` 三档（`admin/hr/user`）管的是「能不能进管理端」，
判据来自 `core/identity.py` 的 `STAFF_ROLES` / `is_admin()`。加值会让管理端权限**一起漂**
（`superadmin` 与 `admin` 的 `startswith` 判断、任何 `role == "admin"` 的分支都要重审）。
**正交维度才能避免这种连坐。**

#### 14b 网关路径门槛

四条写路径在网关先粗筛：`role=user` 且 `kb_role=none` → 直接 403，**不打后端**。

⚠️ **网关要比后端更宽，不能更窄**：网关是粗筛（可能因为没读到某个字段而误拒），
后端是判定唯一处。粗筛宁可多拒—— 误拒的代价是用户重试一次，
漏放的代价是全公司知识库被改。

- `kb_role` **必须进 JWT**（否则网关看不见它）
- **老 token兼容**：11c 之前签发的 token 里没有这个字段 → **按 `none` 处理（fail-closed）**。
  代价是最长 12h 窗口内已登录的人要重新登录一次；反过来（按 `superadmin` 处理）
  才是真正的漏洞。

#### 14c 后端对象级校验（四条路由逐条挂）

判定逻辑**唯一处**：`core/kb_acl.py`（纯函数，与 `core/password_policy.py` 同构）。
**为什么必须是唯一处**：11c 已经吃过「登录判定在网关和后端各写一份」的亏 ——
两份没测试的副本半年内必然静默漂移。

- 四条写路由**逐条**挂 `Depends(require_kb_write)` / `require_kb_reindex`
- 每次写操作落 `audit_log`（谁 / 什么动作 / 哪个文档 / IP）
- ⚠️ **解析 Worker 没有身份**（它消费队列，不经过网关）→ **绝不能读请求头**；
  重灌的权限判定必须在**接口层做完再入队**。

#### 14d 前端入口收敛 ✅（`2.0.0-p2.14df`）

主应用的上传区 / 删除按钮按当前用户的 `kb_role` 显示或禁用。
⚠️ **这只是防误操作，不是防线**（绕过 UI 直接调接口仍会被 14b/14c 拦）。
理由与12d 相同：前端藏入口能防「手滑」，防不了「故意」。

**实际交付（与计划的两处偏差，都有理由）**：

### P2-15 Token 额度与预警（2026-10-08 用户新增）

> **用户原话**：「需要知道每个人对话用的token 用量，每个人有默认用量，需要做 token 预警。」  
> **定位**：这是**成本控制**，不是权限隔离 —— 与 P2-12 无关，排在 ④ 之后独立交付。

#### 15.0 现状盘点（已落地的部分可直接复用，不要重写）

| 已有     | 位置                                                                                               | 说明                                                               |
| ------ | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 会话级汇总  | `session.usage_input_token` / `usage_output_token` / `usage_cache_read_token` / `usage_requests` | **P0-1b 就建好了**，已在 `add_usage()` 落库                               |
| 消息级明细  | `chat_message.usage_input_token` / `usage_output_token` / `is_cache_hit`                         | 每条助手消息一行，可对账                                                     |
| 单次用量捕获 | `core/rag_chain.py:205` `_normalize_usage()`                                                     | 已从服务商响应里抽 `input_tokens` / `output_tokens` / `cache_read_tokens` |
| 缓存回放用量 | `p1.6b` 的精确问答缓存                                                                                  | 命中时**不重复计费**，`cache_read_tokens` 是服务商侧 prompt 缓存，**与本地命中不是一回事**  |

⚠️ **所以本项不是「从零做统计」，而是「加聚合 + 加额度 + 加预警」**。  
`session` 表**已有 `user_id`**（12c 刚落的），所以「按人聚合」的数据链路**已经通了**。

#### 15a 聚合口径（**先定死这个，否则后面全是来回改**）

- **按人 × 自然月**：`SUM(chat_message.usage_*)` join `session` 取 `user_id`。  
  ⚠️ **不能只查 `session` 汇总列**：会话被删就丢了，而明细是历史真相。
- **成本口径**：`cache_read_token` **单独一列，不计入 `total`** —— 它是服务商侧的 prompt 缓存命中，  
  单价与普通输入不同，混进总额会算错钱。三个数分开报：`input` / `output` / `cache_read`。
- **「本轮花费」与「累计花费」分开**：明细表给单轮（可追「哪一问最贵」），  
  聚合表给人（可判「谁超了」）。**混在一起就没法做预警** —— 预警需要的是期间累计值。

#### 15b 额度模型（配置放哪、默认多少）

- **额度定义在 `user` 表**（迁移 `0007`）：`token_quota_monthly`（`NULL` = 用全局默认）+ `token_quota_override`。
- **全局默认放 `.env`**（`TOKEN_QUOTA_DEFAULT_MONTHLY`），**不在库里**——  
  理由与 `.env` 里的 `MEMORY_BACKEND` 同源：改一次全站生效，不必迁移。  
  ⚠️ **代价**：改额度要重启后端（与 `MEMORY_BACKEND` 一致，可接受）。
- **判定规则的唯一出处**：新增 `core/quota_policy.py`，与 `core/password_policy.py` **同构**  
  （纯函数、不做数据库查询、规则有独立测试文件）。⚠️ **不要在两处各写一遍百分比算法** ——  
  11c 已经因为「登录判定在网关和后端各写一份」吃过亏（`bcryptjs` vs `passlib`），教训还热着。

#### 15c 超额行为（三档，**必须先问清楚再写**）

| 档           | 行为                    | 谁看得到     |
| ----------- | --------------------- | -------- |
| **仅提醒**（默认） | 照常问答，只在界面顶部横幅 + 管理端标红 | 本人 + 管理员 |
| **提醒 + 降级** | 超过阈值后只允许「用过的模型」，禁用更贵的 | 本人 + 管理员 |
| **硬阻断**     | 超过额度直接拒绝新提问           | 本人 + 管理员 |

⚠️ **默认必须是「仅提醒」**：硬阻断在共享知识库场景下会让人**完全没法工作**，  
而预警的本来目的是「让人早点知道」，不是「罚人」。  
⚠️ **降级档的模型清单不要硬编码** —— 与其写死「哪些贵」，不如给 `token_quota_policy` 一张  
可配的价格表（`TOKEN_MODEL_PRICING`），否则加一个新模型就要改代码。

#### 15d 预警触达（**先做最便宜的那一路**）

- **管理端加一页「用量看板」**：按人 × 本月的 `input` / `output` / `cache_read` / 合计 / 额度 / 使用率，  
  超过 80% 标黄、超 100% 标红，支持按部门筛选。
- **主应用顶部横幅**：本人用量接近上限时提示「你已用 92%，还有 X tokens」。
- **不做邮件 / 企微 / 钉钉推送**（本轮明确不做）：需要外部凭证与出网配置，  
  而4C4G 的生产形态还在等备案。⚠️ **代价**：管理员只能**主动打开看板**才知道谁超了 ——  
  这是本项最大的缺口，交付时要写明。

#### 15e 越权回归

`tests/test_module16_quota.py`：跨用户改额度 403（**只有 admin/hr 能改额度**）；  
改别人的额度落 `audit_log`；用量聚合**只统计自己的**（`admin` 看全量也要走单独接口）。

**验收**：管理端看板上每个月的数与 `SUM()` 手工核对一致；  
超 80% 有横幅、超 100% 按选定档位生效；跨用户改额度 403 且留审计；  
**每条都能反向验证**（把阈值判定去掉，对应用例必须转红）。

**依赖**：**无** —— `session.user_id`（12c）已落，用量列P0-1b 已有。可与 ④ 并行。

## 11. 风险与注意

### 11.1 4C4G 内存预算（**最大的硬约束，先算清再动手**）

| 服务                         | 常驻估算           | 备注                                |
| -------------------------- | -------------- | --------------------------------- |
| MySQL 8                    | 350~450 MB     | `innodb_buffer_pool_size` 压到 128M |
| Redis                      | ≤ 128 MB       | `maxmemory 128mb` + `noeviction`  |
| gateway (Node)             | 120~180 MB     |                                   |
| nginx                      | ~20 MB         |                                   |
| backend（嵌入 + 重排 + uvicorn） | 1.8~2.2 GB     | **reranker-base 是内存大头**           |
| worker（仅嵌入 + Celery）       | 500~700 MB     | `concurrency=1`，**不加载 reranker**  |
| OS + Docker 自身             | 300~400 MB     |                                   |
| **合计**                     | **3.4~3.9 GB** | 4G 很紧，必须有对策                       |

**对策**（按优先级）：① worker 不加载 reranker；② `--max-tasks-per-child` 定期回收；③ MySQL buffer pool 降 128M；④ Redis 128MB noeviction；⑤ 加 2G swap 兜底；⑥ 若仍不够，reranker 换小模型或延迟加载（问答首请求才加载）。

### 11.2 其他风险

- **队列不可靠**：Redis 重启丢未消费任务。**不修**，靠 MySQL `status` + 重解析接口兜底（修它要引入 Redis Streams + 消费者组，复杂度不划算）；
- **多 Worker 幂等**：所有解析入口必须先做 MySQL 原子抢任务，否则重复插切片；
- **Chroma 无原生 TTL**，且统计的只是切片数、不是业务文档数 —— 业务计数一律以 MySQL 为准；
- **本次调整的一次性成本**：现有向量库 metadata 缺 `doc_id`，必须重建；
- **备案时序**：P1-7 依赖 ICP 备案通过（1~2 周），期间走 IP:端口 自测，勿对外解析域名；
- **密钥**：`.env` 全程不入库、不进镜像；
- **本地 LLM 不上云**：云端 LLM 走 API，无 GPU 机器本地推理太慢。

**D1 结论与落地方式**（这一条会直接影响 `.env` 结构与 compose 写法，先说清）：

- **日常开发**：`docker compose up -d mysql redis` 起中间件，`make api` / `make gateway` / `make frontend` 裸跑；  
  应用通过 `localhost:3306` / `localhost:6379` 连容器，热重载与断点调试体验不变；
- **`MYSQL_HOST` / `REDIS_HOST` 必须做成变量**：本地裸跑要 `localhost`，P1-5b 全栈模式下服务间走容器网络得是  
  `mysql` / `redis`。用两个变量表达主机名，切模式只改这两个值 ——  
  **不要在两处硬编码主机名**，否则切换模式必然漏改一处，且症状是「连不上数据库」这种低信息量报错；
- **全栈 compose 的用途**：本地端到端验收、演示、以及上传服务器前的最后预演。
