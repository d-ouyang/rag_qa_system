## v2.0.0-p0.2 · 给系统装上一道门

**这一版解决了什么问题**：v1.0.0 上线即裸奔——任何人都能上传文档、提问，直接消耗大模型额度。
这一版在业务后端前面加了一个独立的鉴权网关，所有请求必须先登录才放行。

### 新增

- **独立鉴权网关**（NestJS，`:3000`）：JWT 登录、全局默认拒绝的守卫、按用户限流（防止别人白嫖
  大模型额度）、请求白名单机制。
- **请求转发**：网关校验通过后把请求转给后端。**关键要求是流式输出不能被破坏**——
  问答接口是逐字返回的，中间多一层缓冲就会把「打字机效果」变成「等 30 秒一次性吐出来」。
- **统一错误格式**：无论鉴权失败、请求过频、参数不合法还是后端不可达，前端拿到的错误结构都一致，
  不必写四套解析。
- **身份透传**：网关验完 token 后把用户身份放进请求头传给后端，**后端一行代码没改**，不用自己解析 JWT。
- **前端登录页与登录态联动**：token 失效自动回登录页；主动/被动登出都会清空本地会话数据
  （不清的话下一个登录的人会看到上一个人的聊天记录）。
- **网关自身探活接口**（免登录），用于监控判断「网关进程是否活着」——它有意识地和「后端是否活着」分开，
  否则后端挂掉会把网关一起判死。

### 修复

- **★ 一个 POST 请求就能把整个网关进程打挂。** 最严重的一个 bug，值得完整记一笔：
  为了让被框架提前消费掉的请求体能重新转发，用了官方的 `fixRequestBody`。
  但它内部会**结束掉请求**——此后任何「往请求上加一个头」的操作都会抛异常。
  真正致命的是：这个异常发生在一个事件回调里，**没有任何地方捕获它**，
  于是整个 Node 进程直接退出。症状极具迷惑性——只要有人提交一次表单，网关就凭空消失，
  而日志里只有一行看不出严重性的提示。

  修法是两层的：先调整语句顺序（所有加头的操作都提到结束请求之前），
  再给回调整体加上异常捕获，最后在进程级也加一道兜底。
  **这个 bug 的教训是：异常发生在回调里时，「有没有人捕获」比「异常本身」更要命。**
- **参数校验提示答非所问**：漏填密码时提示的是「密码不能超过 128 个字符」——
  框架遍历校验规则的顺序不确定，取到了最后一条。改为优先取「不能为空」这类更贴切的提示。
- **限流提示透出英文类名**：只显示 `ThrottlerException: Too Many Requests`，用户看不懂，
  已换成中文文案。
- **前端登出提示语病**：出现过「登录状态已失效（登录状态无效，请重新登录），请重新登录」
  这种同义反复嵌套，已收口成两种固定文案。
- **（修订）漏放行两个上游健康检查**：计划书明确要求放行，首轮实现只放了登录和网关自身探活。
  功能上不影响前端，但上线后监控探活会一直是红的。
  **这次的意外收获是暴露了测试的盲区**：原来的断言只检查「无 token 要被拒绝」，
  从没反过来问「该放行的放行了吗」——只测「该拒的拒了」不够。
  而且一旦引入白名单，就同时引入了「白名单被放得太大」的反向风险，两者必须成对断言。
  已补上双向断言（该放的放行 + 同前缀的受保护接口仍然拦得住）。

### 优化

- **防止用户名枚举**：即使账号不存在也照样做一次密码哈希比对，耗时一致，
  攻击者无法通过响应快慢判断某个用户名是否真实存在；密码错误统一提示「用户名或密码错误」。
- **生产环境不静默降级**：缺少 JWT 密钥或账号配置时直接启动失败，而不是悄悄用默认值把服务跑起来。
- **不让监控失效变成拒绝服务**：Redis 内存信息读不到时只告警、不阻断写入，
  业务按「没有历史」降级继续，不会因此报错。

### 验证

- 网关端到端冒烟 **25 项全绿**（含伪造 token、无 token 打流式接口、限流触发、白名单双向断言）。
- 浏览器实测全流程：登录 → 提问 → 退出 → 失效 token 自动登出 → 错误密码提示。
- 后端全量回归 **497 项全绿**。

## v2.0.0-p0.1 · 会话不再「重启即丢」

**这一版解决了什么问题**：v1.0.0 的会话历史、置顶、标题、用量全都存在**进程内存**里，
后端一重启就全没了；而且将来部署成多副本时，每个副本各存各的，
用户会感觉「聊着聊着模型失忆」。这一版把存储抽出来，可切换到 Redis。

### 新增

- **可插拔的存储抽象层**：把「会话怎么存」从业务逻辑里切出来，
  一行配置就能在「内存」和「Redis」之间切换（本地开发不必为了跑测试先装 Redis）。
- **Redis 存储实现**：会话用一个 Hash 存、另用一个有序集合维护索引，配一把分布式锁；
  锁的释放用 Lua 脚本保证「只释放自己加的锁」。
- **Redis 内存预警（重点新增）**：问题的背景是「数据量和访问量上来之后 Redis 会满」。
  做法是三级水位 + 自动止损：
  - 达到警戒 → 提示确认驱逐策略、缩短会话过期时间；
  - 达到严重 → 自动清理索引残留；
  - **达到致命 → 写入降级为只读保护**（宁可这一轮记不住对话，也不让整个问答返回 502），
    水位回落自动解除。
  - 每条预警都给**可直接执行的处置建议**，而不是只报一个百分比。
- **新接口 `GET /api/v1/system/memory`**：对外暴露存储后端、会话数、内存水位与建议，供监控抓取。
- **20 项新配置**：Redis 连接、锁参数、预警阈值全部可配。

### 修复

- **过期会话被「复活」**：会话过期时间在两处各存了一份，两处不一致导致已经过期的会话
  被读回来时又被当成新的存了一遍。已改为单一下传。
- **元数据与消息错位**：元数据是按轮记录的，但「没有元数据的那一轮」不占位，
  于是裁剪历史之后意图标注就整体错位了。已改为空占位保证一一对应。

### 优化

- **读操作不再隐式创建会话**：以前读取一个不存在的会话会凭空造出一条空会话，
  查询会话列表时越查越多。已改为「不存在就是不存在」。
- **翻会话列表不会让冷会话永生**：只有真正「续聊」才刷新过期时间，浏览列表不刷新。
- **业务侧零改动**：`rag_chain.py` 与问答接口一行都没改，这是抽象层设计到位的直接证据。
- **顺手解决「换后端 = 换了个 bug」的风险**：两个存储后端跑**同一套语义断言**，
  保证行为完全一致。

### 验证

- 新增 `module6`（107 项）：两个后端同套语义断言 + Redis 专有行为 + 内存预警分级与降级。
- 新增 `module7`（43 项）：**走真实 socket** 的联调。
  为什么单独做这个：`module6` 用的假 Redis 数据活在测试进程里，
  **永远验不出「进程重启后数据还在不在」**——而这恰恰是本次改造的全部目的。
  `module7` 起一个真实监听端口的服务，再用真实客户端连上去，
 于是能硬断言「换一个客户端（等价换一个进程）后，历史对话、置顶、标题、用量全都还在」。
- 既有测试回归 347 项全绿（含直接受影响的问答接口）。

## v1.0.0 · 从零到能跑

**这一版解决了什么问题**：把一个 RAG 问答系统从零搭到可以本地完整跑通——
能上传文档、能检索、能流式回答、有能用的前端界面。**还没有做任何上线加固**。

### 新增

- **后端 FastAPI（`:8000`）** 三组接口：问答（逐字流式返回）、知识库文档管理、系统配置。
- **核心链路八个模块**：文档加载与切分（多格式）、向量化、向量库
  （Chroma / FAISS 双实现，默认 Chroma 落盘）、大模型客户端
  （支持 ollama / siliconflow / openai 三种）、检索、重排、意图路由、会话记忆。
- **前端工作台**（Vue 3 + TypeScript + Pinia + Vite）：左侧边栏（项目信息 / 会话列表）
  \+ 右侧对话 / 知识库 / 设置三个视图。
- **统一配置层**：所有开关与参数由 `.env` 驱动，一处集中管理。

### 已知边界（这一版故意不做的）

这三条直接决定了后面 2.0.0 要做什么：

1. **会话全在内存**：重启即丢，也无法多副本部署 → 催生 `p0.1`。
2. **没有任何鉴权**：谁能访问谁就能用，直接消耗大模型额度 → 催生 `p0.2`。
3. **只有本地联调形态**：没有容器化、没有 TLS、没有备份 → 属于 2.0.0 的 P1/P2。

### 验证

- `module1` ~ `module5` 测试全绿（配置 / 文档加载 / 向量库 / 检索与大模型 / 记忆与问答链路）。
