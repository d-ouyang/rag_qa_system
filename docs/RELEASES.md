## v2.0.0-p2.14f0 · 一个「所有人都以为不可能」的漏洞：请求可以不带身份进后门

这一版不在计划书里。它是在给知识库做权限下发的功能时，顺手用真实客户端探了一遍
系统，然后撞出来的。

### 现在的行为（修复前 → 修复后）

网关的职责是把「你是谁」告诉后端——因为后端自己不认令牌，它只相信网关加上去的
那个身份字段。**只要这个字段没加上，后端就会把请求当成「没登录的人」处理。**

问题是：这个字段以前写在了一个「不一定每次都会执行到」的位置上。所以：

| 客户端怎么发请求 | 修复前 | 修复后 |
|---|---|---|
| 浏览器打开页面点上传 | 身份正常带上 | 一样 |
| 命令行工具上传大文件 | **身份字段整个消失** | 正常带上 |
| 命令行工具上传小文件 | 正常带上 | 一样 |

### 为什么说它是个漏洞，而不只是「有个 bug」

因为**伪造的身份也会跟着一起通过**。

早先有一版专门处理过这件事：不管客户端怎么自称，网关都会先把那些身份字段
**擦掉**，再写上真实的那个。实测过——有人自称管理员，请求真的就按管理员处理了。
从那以后这条路被堵住了。

但这次发现：**擦除动作和写入动作放在了同一个「有时会执行有时不会」的位置上**。
一旦它不执行，就变成「既没擦掉、也没写入」——于是伪造的身份字段原样通过，
回到堵住之前的状态。

换句话说：**这不是新漏洞，是同一个老漏洞被找到了第二个入口。**

### 为什么这么久都没人发现

因为要踩中它需要同时满足两个条件，而这两个条件在正常使用时**永远不会同时出现**：

1. 客户端要发一个特定的头（浏览器的网页代码默认不发）；
2. 请求要被上传这类操作触发（而从网页上传本来就不发那个头）。

12b 当年验证「伪造身份」用的是不带那个头的请求，验证「正常身份」用的是网页上传
——**两件事各自都验过，唯独没人去试它们交叉的那一格。**

而它触发时的表现也足够隐蔽：请求**不会报错**，接口正常返回，功能测试全绿。
唯一的痕迹是后端日志里一句「用户=admin」（本地调试用的那个万能账号），
而那句话平时就经常出现，没人会觉得不对。

### 这一版做的四件事

1. **把「擦除 + 写入身份」挪到了一个「一定执行」的位置**——放在转发之前，
   而不是放在那个由库决定要不要触发的回调里。
2. **顺手摘掉那个特定的头**（它按协议本来就是逐跳的、网关该剥的），
   这样回调才能正常触发，请求体改写和「不要压缩」这两件事也才能正常工作。
3. **新增一个可重复运行的复现脚本**：用真实版本的转发库起服务，
   八个场景对照「修复前写法 / 修复后写法」×「带/不带那个头」×「带/不带伪造身份」，
   其中有一组专门证明「修复前伪造身份确实能通过」。
4. **新增 34 项自动检查**，其中一层是真链路（把复现脚本跑一遍，逐条读它的结论），
   一层是源码结构（「身份注入不许被挪回那个不可靠的回调」）。
   并用四条反向验证确认这些检查真的有鉴别力——**把修复拆掉，测试必须变红**。

### 已知边界

只验过当前版本的转发库（网关与后端之间那层）。将来升级时，
复现脚本会立刻给出结论，而不是让人误以为「一直都没问题」。

## v2.0.0-p2.14df · 门装上了，但按钮还摆在外面

**这一版解决了什么问题**：`p2.14a` 之后知识库已经有锁了 ——
后端会拒绝没权限的人、网关上越权请求连后端都到不了。
但打开界面上看一眼就知道：**那些会出错的按钮还摆在每个人的桌面上**。

一个只读员工进知识库页，看到的和管理员看到的一模一样：
一个虚线框（点它可以上传）、每一行四个按钮（其中一个是红色的「删除」）。
区别只在于他点完之后会收到一句「没有权限」。

这不是「权限在生效」，这是「权限在事后惩罚人」——
而是把整页东西摆出来让人试，试完再告诉他不行。

**这一版做了什么**：

1. **没有权限的人，上传区和「删除」「重试」按钮直接不显示**，
   换成一段说明：「你当前是只读的，可以查看、搜索与下载；
   如需修改，请联系系统管理员为你开通」。
2. **管理员在管理端一行就能开通或收回**，
   确认弹窗会**当面说清「改完他将能干什么」**，并提醒「知识库是全公司共用的，
   改的是所有人都会搜到的东西」。收回时的措辞更重 —— 因为它不会通知到对方。
3. 每次开通与收回都**落进审计**：「谁、何时、对谁、从哪档改到哪档」，
   改不了也删不掉。

**顺带修掉两个真缺陷**（都与权限有关，但不是这一版的主要目标）：

- 此前机械检查「每条写接口都挂了守卫」的实现**会扫描注释** ——
  于是一句写在文档里的 `Depends(require_kb_*)` 被当成了真依赖，
  报出「有个查询接口挂了写权限守卫」的假警报。检查本身现在更准了，
  而且补了四条自检，保证它不会因为「剥注释剥过头」而变成**漏检**
  （在这类检查里，漏检比误报更坏）。
- 这次开发自己的验收脚本**往知识库里塞了一份垃圾文件**
  （拖拽探针的对照组是真发请求的）。已改为中途拦截 ——
  我们要验的是「界面有没有发起请求」，而请求在浏览器里就被掐断，根本到不了服务器。

**一个容易被忽略的地方**：文件拖拽的落点挂在**整个页面**上，不是挂在上传框上。
所以「把上传框藏起来」并不妨碍「把文件拖到页面任意空白处照样上传」。
这一条界面验收看不出来 —— 界面上确实什么都看不见。
只有盯着网络请求看，才知道那次拖拽其实发出了请求。

**至此 `P2-14` 六格全部就绪**：模型（14a）、网关（14b）、守卫（14c）、
回归（14e）、缺陷修复（14f0）、界面（14df）。
剩下的是 token 额度与预警（`p2.15`）—— 那一样只提醒、不阻断。

## v2.0.0-p2.14a · 知识库终于有了门：不是所有人都能改它

**这一版解决了什么问题**：上一版把「每个人的问答记录归他自己」做实了，
但同一件事里还有另一半没解决 —— **知识库是全公司共用的，可是改动它的入口一直是敞着的**。

实测的结果是这样的：拿一个普通员工的账号，**能上传文档，也能删文档**。

不是「可能会出问题」，是当场就能删掉一份正被别人的回答引用的文档。
整个过程没有任何报错，也没有任何人收到通知。

### 现在的行为

| 你做的事 | 结果 |
|---------|------|
| 用没被授权的账号上传文档（含批量上传） | **403 拒绝** |
| 用没被授权的账号重新解析文档 | **403 拒绝** |
| 用没被授权的账号删除文档 | **403 拒绝** |
| 用没被授权的账号**查看**文档 / 下载 / 看引用 | ✅ 照常（知识库本来就该共享） |
| 管理员给某个同事开通权限后，他再上传 | ✅ 立刻生效，不用等 |
| 任何一次上传 / 解析 / 删除 | 都会在审计日志里留下「谁、什么时候、对哪份文档做了什么」 |

### 为什么「查看」和「修改」要分开

这一条值得单独说：**共享的是知识，不是改动权**。

十几个人用同一份知识库回答问题是合理需求（不然部门内的知识就没法沉淀），
但「谁能往里加东西、谁能删东西」是另一回事。前者影响的是效率，
后者影响的是**所有人第二天早上还能不能问出正确答案**。

所以这次的取舍是：**读一律放开，写一律看授权**。

### 这版做的三件事

**一、权限是独立的一维，不塞进「管理员 / 人事 / 员工」那三档里。**

原来只有三档角色，管的是「能不能进管理后台」。如果把「能不能改知识库」也塞进去，
想给一个运营同事开通上传权限，就得顺手给他管理员身份 —— 而这两件事本来毫无关系。

拆成两个独立字段之后，「进不了后台但能维护知识库」是个正常配置，
15 种组合全部合法。代价是「谁是管理员」不再能推出「谁能改知识库」，
所以**这次特别把写操作全部记进审计日志**。

**二、默认是不给权限，而不是默认给。**

新同事进来时不会自动获得改知识库的能力。要开通，必须有人明确操作一次。

反过来的默认值（默认能改）看着方便，但**开权限的次数远少于加人的次数** ——
那条写错的路径会被反复走到。

**三、「重建整个知识库」这件事，单独设了一档，不给日常维护的人。**

上传错了、删错了，都能改回来。但「重建索引」不一样：
它会让全公司已有的问答引用指向错的地方，而且**不报错** ——
用户照样能问出答案，只是那个答案是错的。

所以日常维护知识库的同事能上传能删除，但**不能重建**。

### 已知边界（这一版故意不做的）

- **界面上还没变**：上传入口对所有人依然可见，只是点了会被拒绝。这是刻意的顺序 ——
  先把后端锁住（那才是真正的防线），界面下一版收。
- **授权只能靠管理员在后台改数据库**：管理端的「下发授权」界面下一版做。
- ~~**网关那道门还没加**~~：已在 `p2.14b` 补上（粗筛比后端**更宽**，见下一段）。

### 验证

- 没授权账号：四条写接口全部 403，读接口全部 200
- 授权后：上传 / 批量上传 / 重新解析 202，删除 200，审计日志有 5 条对应记录
- **反向验证**：把守卫临时拆掉 → 没授权账号立刻能上传（证明这道门真的在起作用）；
  而没拆的删除接口仍然 403（证明「只拆一部分」不会导致另一部分失效）
- 数据库结构一致性检查通过；知识库 35 份文档 / 35 个文件 / 90 个片段**零损失**

## v2.0.0-p2.14b · 越权请求连后端都到不了

**这一版解决了什么问题**：上一版给知识库加了门 —— 未授权的账号调写接口会拿到 403。
但那道门装在**后端**上，请求得先穿过网关、转发到后端，才知道要拒。

对一个每天被全公司共用的知识库来说，这意味着：**任何人绕过界面直接调接口，
系统都会老老实实地替他把请求转进去、跑一遍完整流程，最后才告诉他不行。**

### 现在的行为

| 你做的事 | 结果 |
|---------|------|
| 未授权账号调四条知识库写接口 | **网关直接 403**（错误码 `FORBIDDEN_KB_WRITE`），**后端日志里查无此请求** |
| 未授权账号看文档 / 下载 / 看引用 | ✅ 照常（读永远共享） |
| 已授权账号（运营 / 测试 / 开发 / 超管）调同样四条 | ✅ 放行给后端，行为与之前一致 |
| 用**改权限之前**签发的旧令牌 | 按「无写权限」处理 —— 宁可多拒一次 |
| 绕过网关、直接打到后端 | 仍然被后端那道门拦住（两道门互不依赖） |

### 怎么证明请求真的没进后端

只看「返回了403」是不够的 —— 后端也可能先处理完、再返回 403。
所以这次抓的是**后端的访问日志**：同一个令牌、同一秒钟，
`GET /`（读）在后端日志里有记录，那四条写操作**一条都没有**。

这才是「请求根本没走到后端」的证据。

### 这版做的三件事

**一、给令牌也加上了这个字段，改权限即刻生效，不用等令牌过期。**
权限现在是令牌的一部分。所以管理员改了某人的写权限，
那人手上的旧令牌就作废了 —— 这是**故意**的：否则「已授予 / 已收回」在
12 小时之内会不一致，「收回」这件事会显得像没生效。

**二、老令牌一律按「无写权限」处理，而不是按「有写权限」。**
发布这一版之前签发的令牌里没有这个字段。两种默认各有诱惑：
默认「有」能让老用户不掉功能，默认「无」会让人以为自己被莫名拒了。
选后者 —— 权限系统的默认值必须是保守的那一端。

**三、网关这道门，刻意比后端更宽，不是更严。**
网关只认一种情况：「这个人的写权限明确是『无』」。
剩下四档（运营 / 测试 / 开发 / 超管）全部放行去问后端。

这么设计的原因是**各层守卫的职责不同**。后端是唯一的判定出处，
它的五档矩阵永远是对的；网关如果照抄一份五档，两份规则就会开始各自漂移 ——
改了一边忘了另一边，就是一个真实的漏洞。所以网关只当一道**提前拒绝**的粗筛，
宁可多拒一次（那一档会落到后端拿准确答案），不可漏放一次。

### 已知边界（这一版故意不做的）

- **界面和授权入口还没变**：上传按钮对所有人依然可见（管理端授权在 `p2.14f`）。
- **这道粗筛和后端的四条写路由是各写一份、靠人同步**。
  以后如果新增一条写接口而忘了加进网关清单，那条接口在网关上就是敞开的 ——
  后端仍会拦住，但粗筛形同虚设。下一版补一条**结构断言**：
  新增写路由而没同步清单，测试必须转红。
- **两套规则会短暂不一致**：网关热重载生效、新后端镜像还没替换的这段时间，
  放行的请求以后端的判定为准（因为网关只会更宽）。这是选「更宽」换来的确定代价。

### 验证

- 未授权账号经网关：四条写路径全部 403，且**后端日志无对应记录**（同一时刻读接口有记录）
- 已授权账号经网关：上传 202 / 删除 200，与绕过网关时行为一致
- 信任边界测试 **47 → 103 项全绿**；反向模式下 107 项全绿
- 用户体系、管理端、审计、会话隔离四组回归全绿
- 知识库 35 份文档 / 35 个文件**零损失**；测试探针零残留

## v2.0.0-p2.12c · 「登 A 看 A 的、登 B 看 B 的」这次真的成立了

**这一版解决了什么问题**：前两版把「你是谁」这件事做实了 —— 账号是真的、身份不能伪造。
但只要打开界面就会发现一件事：**不管你登的是谁，左边那份问答记录都是同一份**。
谁的对话都能看、都能改、都能删。上一版封的是「冒充别人」，这一版封的是「看到别人的」。

**为什么这两件事不能互相替代**：身份不可伪造，只保证了你**是**你自己；
它不保证你**看不到**别人。就像进小区要刷门禁，但楼道里的信箱还没分户 ——
进得去不等于只看得见自己那一格。

### 现在的行为

| 你做的事 | 结果 |
|---------|------|
| 用 A 的账号登录，看到 A 自己的问答记录 | ✅ |
| 在**同一个浏览器**里登出，换 B 的账号登录 | ✅ 界面上一条 A 的记录都没有 |
| 拿 A 的会话 ID 去读 A 的问答 | **403 拒绝** |
| 拿 A 的会话 ID 去改标题 / 清空 / 删除 / 接着聊 | **403 拒绝，且一个字都不改** |
| 登 12c 之前建的旧会话 | 归到第一个打开它的人名下（不丢数据） |
| 用系统内置的应急管理员登录 | 问答里看不到任何人的会话（它不区分人） |

### 这版做的三件事

**一、把「这条会话归谁」这件事，钉在数据存取的那一层。**
不是每个接口各写一遍过滤条件，而是**存取的时候必须问一句「你要谁的」**——
不传就直接报错。这是为了防「以后新加的接口忘了加过滤」：
漏传会是立刻报错，而不是安静地把所有人的数据都返回出去。

**二、拿别人的会话 ID 一律明确报 403，而不是含糊的「不存在」。**
如果报「不存在」，用户会以为自己的记录弄丢了，反而去建新的，攒下更多没人认领的数据；
而且这样就看不出有人在试探别人的数据了。**返回 403 会在日志里留下痕迹。**

**三、越权的判断放在模型回答之前。**
如果放在最后，会出现这种情况：模型已经完整答完一遍、检索也跑完了，
才告诉用户「这个会话不是你的」—— 白花一次检索和一次大模型的钱。
所以开口之前就拦下来。

### 验证（形态就是你要亲手复现的那件事）

用两个**平级**普通员工的账号（刻意不用管理员 —— 用了管理员，
「他权限更高所以能看到」就成了一个合理解释，而要证明的恰恰是**权限再高也看不到别人的问答**）：

1. 第一个账号登录 → 提问 → 直接查数据库确认那条会话真的记在他名下；
2. **不刷新页面**、在同一个浏览器里点「退出登录」，换成第二个账号登录；
3. 第二个账号的会话列表是空的，界面上搜不到第一个账号那句提问的任何片段；
4. 第二个账号自己提问 → 数据库里记在他名下，与第一个账号的是两条不同会话；
5. 第二个账号退出，第一个账号再登回来 → 只有自己那条。

第 2 步刻意不刷新页面：只有这样才能验「上一个用户的对话有没有留在浏览器内存里」。
用两个浏览器窗口等于两个浏览器，第一个用户的内存与第二个毫无关系，验不到任何东西。

这套验证**连跑两遍都是 28 项全过**，脚本本身也被修过两轮
（一处是它把「这次提问新开了哪条会话」当成必然，而实际上界面已有当前会话时是**接着聊**；
另一处是它在收尾时崩在第一步，导致**两个账号的密码没还原**——留在了库里）。

### 这一版**没有**解决的问题（重要）

**知识库是全公司共用的。** A 上传的文档，B 搜得到，**也能删**。
会话隔离挡住了「看到别人的对话」，但挡不住「改这个库」。

⚠️ **2026-10-08 决策：知识库不隔离读，是业务需求不是疏漏** —— 企业知识库的价值恰恰在于
所有人问同一套资料，按部门切开会导致「问的人找不到答案」，而这比「看到别人的东西」更严重。
所以**跨部门检索隔离（`p2.12d`）整格取消**，12a / 12e 随之缩范围。

把系统交给第二个人之前只剩一件事：**知识库写权限（`p2.14`）**。

### 已知的一处未解事项

全量回归跑两遍，其中一遍 module15 是 48 项、另一遍是 47 项。
已排查未复现（单独跑 6 次、按批次条件跑 2 次都是 48 项，数据库也无残留）。
**不下结论**，如实记在迭代文档里，留作下次遇到时的线索 ——
一次没复现的红点，和一次没跑过的测试，区别只在于后者是已知的。

## v2.0.0-p2.12b · 封上一个真实存在的漏洞：此前谁都能自称管理员

**这一版解决了什么问题**：上一版让员工账号真的能登录了，也留了一句警告 —— 「网关目前会无条件相信请求里带过来的『我是谁』」。这一版就是去兑现那句话。

**它不是理论隐患，是当时就能用的**。12b 施工前实测：在本机直接调后端接口，头里写上 `X-User-Id: 440`（这是种子里真管理员的数字 id），返回 **200 和完整的员工名单** —— 工号、部门、职位、手机号、角色，一个不少。想知道「谁是管理员」不需要密码，猜一个数字就行。

为什么会这样：设计文档里写的是「后端端口不对外，只让网关访问」，而这句话在**当前的运行方式下不成立** —— 本机后端绑的是回环地址，同一台机器上的任何程序都能连上它（包括浏览器里的任何脚本、任何本地开发工具）。而程序里还有一条调试用的后门：没带身份信息时，会落到一个内置的应急管理员账号身上。**两条凑在一起，就成了「谁都能当管理员」。**

**这一版做了三件事**：

**一、进来的身份信息一律先扔掉，再写上真的。** 之前是「如果确实是登录用户，才覆盖掉请求里带的身份信息」—— 而两个健康检查接口不需要登录，于是那段覆盖逻辑整个跳过，**请求里带的身份信息原样传到了后端**。现在改成无条件先删掉那 8 个头（不只是常用的两个，是全部 —— 包括那个「网关证明」头，否则任何人都能自己声明「我就是网关」），再写上真的。这两件事的顺序不能反：反了会把真的身份一起删掉，全站登录后立刻被踢。

**二、证明「你确实是网关发来的」。** 光「先删再写」还不够 —— 它假设了「后端只有网关能访问」。所以再加一道：网关转发时带一个只有它和后端知道的密钥，后端**验过之后**才认那些身份头。缺了或错了，一律拒绝。攻击者要冒充管理员，现在不光得猜对一个数字，还得知道一个 64 位密钥。

**三、给「内部接口」上锁。** 上一版新增了一批只给网关调用的内部接口（登录判定就走它们）。实测发现它们**从网关上是可以直接访问到的** —— 也就是说当时唯一的防线就是上面那个密钥。密钥一旦因为任何配置失误而泄漏或为空，这条路立刻变成「任何登录都能过」。现在这条路径从网关上**彻底封掉，而且对所有人（包括管理员）都回答「找不到这个接口」** —— 回答「没权限」等于告诉探测者「它在这儿」，那本身就是线索。

**这一版还修掉一处「以为修好了其实没修」**：新加的密钥校验让管理端一批旧测试红了。红的理由是「测试自己没带密钥」，而最省事的修法是把断言改成「应该被拒绝」—— **那是最坏的处理**：那条断言本来要验的是「合法请求仍然通」，改成拒绝之后它就变成一条「无论代码对错都会绿」的假断言。正确做法是让测试默认带上正确的密钥，另加专门验「不带 / 带错就拒绝」的用例。

**为什么路径权限要「宁可松一点」**：网关这一层的规则是粗筛（能不能进管理端），后端那一层才是精确判据（能不能改某个字段）。如果粗筛卡得比精确判据还严，人事岗（hr）会「打不开管理端」—— 而这个 bug **只在用人事账号登录时才现形**，用管理员账号测是测不出来的。所以粗筛放行「管理员和人事」，具体权限让后端判。反过来才是 bug。

**用一句话说这一版**：现在**伪造身份**这条路是堵死的 —— 改一个请求头就能当管理员的漏洞，已经变成必须知道一个只有内部才知道的密钥才会发生。

⚠️ **这一版堵的是「冒充」，不是「串数据」**：12b 做完之后，每个人都能确认「我就是我」，但**所有人看到的仍然是同一份会话和同一个知识库** —— 那是下一格（`12c` 会话隔离）要解决的事。**在它做完之前，账号仍然只能本机自用，不要发给第二个人**（计划书 §0.7.2）。

## v2.0.0-p2.11c · 员工账号真正上岗：管理端建的人能登录问答系统了

**这一版解决了什么问题**：前面三版把「员工」这件事在数据库里、在管理界面上都做实了 —— 10 个有工号、有部门、有职位的人躺在表里，管理员能在页面上建人、重置密码、办离职。**但这些人谁也登录不了系统。** 登录这件事一直读的是配置文件里手写的两三个账号：新建员工、停用员工、给员工改角色，在登录这一侧全都不生效。

这一版把两端接上了。现在管理员在管理端建的员工，用管理员发给他的临时密码就能登录问答系统；离职或停用的员工立刻登不进去；密码到期的人登录后会被要求先改密。登录这件事从此以数据库为准，配置文件里那个账号降级成「数据库整个连不上时的应急入口」。

**这一版做的两个决定，都不是「哪个方案更优雅」，而是「哪个方案不会悄悄坏掉」**：

**一、密码判断只写一份。** 系统里判断「这个人能不能登录」的规则已经有 140 多个测试守着：错 5 次锁 15 分钟、密码 90 天到期、不能复用最近 5 个、为防猜用户名故意让「账号不存在」和「密码错了」返回**一模一样**的提示、连失败几次的响应时间都刻意做成一样长（否则攻击者能用响应快慢区分账号存不存在）。这套规则如果让登录入口**再写一份**（哪怕是在另一种语言里），两边迟早漂移 —— 而漂移的直接后果就是防枚举那层保护失效。所以改成：登录入口去问真正做判断的那一方。代价是登录多一次内网往返 —— 实测**这一跳本身只花约 1 毫秒**（登录要等的那 170 多毫秒来自故意设计得很慢的加密算法，那是防爆破的成本，无论判定放在哪都一样）。

**二、登录入口本身不能被伪造。** 上面那个「问一句」的接口，如果谁都能调，等于多了一条绕过数据库的登录通道。所以它带一道只有内网知道的共享密钥，用**恒定时间比较**（防「逐字符猜密钥」那种时序攻击），且不出现在接口文档里。密钥没配就直接拒绝服务，不会悄悄退回到「随便谁都能进」。

**顺手修掉三件会让「以为上线了其实没上线」的事**：

- 员工的密码如果因为系统升级参数被重新加密，**重置登录凭证的版本号而不是重置密码本身** —— 第一版写成了重置密码，结果顺带把「90 天到期」重新计时、还把这个人正在用的会话踢下线，而这两件事跟加密参数升级毫无关系。
- 「改完密码，旧的手里的登录凭证立刻失效」这条规则，之前只有管理端改密时生效，**员工自己在管理端改的密码不生效**，因为后端压根没比对这件事。现在补上了。
- 「密码过期判定用的是什么标准」这种细节，写在了代码注释里而不是文档里 —— 因为三个月后回来改代码的人不会去翻文档，但一定会读到那段注释。

**登录这件事从这一版开始有记录了**：谁登录成功、谁失败、什么时候、从哪个 IP，都进审计日志。上一版审计日志就位时特意给登录类动作留了三个名字（成功 / 失败 / 登出），一直没人用 —— 这一版是它们第一次真被用到。

**用一句话说这一版**：管理端不再只是个花架子，建出来的员工真的能上班干活了 —— 而且密码规则只有一份、登录通道只有一条、登录行为有据可查。

⚠️ **这一版解锁了一件被刻意按住的事**：从 11c 起，系统第一次可以同时有多个人正常登录使用。计划书里排的下一格（`12b`）正是为此准备 —— 网关目前会**无条件相信**请求里带过来的「我是谁」，任何能直接访问后端端口的人都可以自称管理员。`12b` 就是封这个口子。**在那之前，这套账号只能本机自用，不要发给第二个人**（计划书 §0.7.2）。

## v2.0.0-p2.13d · 每次管理操作都留下记录，而且改不了也删不掉

**这一版解决了什么问题**：上一版管理端能干活了，但干了什么只有当时的操作日志（会滚动、会被清、混在几百行报错里）。出了事只能靠回忆和翻日志——「上周是不是有人把陈杰的密码重置过」「赵敏的权限是不是被人改过」，查不出来。这一版加了一个专门的「审计日志」页，回答「谁、何时、对谁、做了什么、从哪个 IP」。

**审计日志与操作日志的区别值得说一句**：操作日志是机器写的、给人排障用的，会轮转、会丢；审计日志是给人追责用的，只写不改。页面上可以按操作人、动作、对象、关键词筛，也可以按时间倒着翻。

**这一版特意做的三件事**：

- **密码永远进不来。** 审计的读取权限通常比员工表更宽（人事能看审计），它一旦存了密码就成了第二个明文落点。所以除了拦「`password`」「token」这类字段名，还拦密码哈希的形状（`$2b$`）——因为字段名拦得住「密码：xxx」，拦不住「备注：密码是 $2b$12$...」。
- **「改不了删不掉」做在结构上，不是靠自觉。** 记录表里没有「修改时间」也没有「已删除」两列，所以「顺手改一下」和「先软删」在结构上就无处落笔。**但要说清边界**：这约束的是程序，不是拥有数据库密码的人——真要做到连数据库管理员都改不了，得另起一个独立审计库，代价是开发和部署都复杂一档，这一版没做。什么时候该做、代价是什么，写在迭代文档里。
- **一个字段都没改就不记。** 打开编辑框又直接点保存，什么都没变却留下一条「修改了 6 个字段」的记录，几天后就没 人信这些记录了，审计会整体失效。

**同时修掉一个上一版埋下的数据问题**：编辑员工信息时，手机号框里显示的是打码的（`138****0001`），如果管理员只是改姓名、手机号没动直接保存，**打码后的这串字符会被写回数据库**。它是个格式合法的字符串，任何校验都拦不住，当场也不会报任何错——直到某天核对号码才发现。修法是编辑时单独取一次原始值，但列表页继续打码（查看权限放开就等于没有打码了）。

**用一句话说这一版**：管理端做的每一件事都留了底，事后查得到是谁做的、什么时候、从哪儿做的；而且这些记录是只写的——程序里没有任何一条路径能改它或删它。

## v2.0.0-p2.13bc · 管理端能干活了：员工、组织、密码三件事都能在界面上办

**这一版解决了什么问题**：上一版管理端只有个空壳 —— 侧边栏四个入口里三个是占位符。这一版把三个内容页填实了，从「有界面」变成「能干活」：

- **员工**：新建员工会自动签发一个一次性临时密码（只在弹窗里出现一次，关掉就永远看不到，丢了只能再重置）；改资料、停用、复职、办离职都在列表上完成。离职是「改状态」而不是「删掉这个人」—— 他名下的问答记录和文档还在，删行会让它们全部变成悬空引用。

**用一句话说这一版**：管理员不用再写 SQL 了 —— 建员工、发密码、停账号、看谁的密码快过期，都是点几下的事。

## v2.0.0-p2.13a · 管理端开张：独立后台界面，「你是不是管理员」由后端判定

**这一版解决了什么问题**：上一批版本把「员工」这件事做实了 —— 数据库里有了部门树、职位职级、10 个带工号的员工。但这些人只存在于数据里：**没有任何界面能看到、能维护他们**。要改一个人的手机号，得写 SQL；要给新员工发临时密码，得跑脚本而且要自己想办法把密码告诉他。

现在有了一个独立的后台：`make admin` 起来就是一个管理端界面，侧边栏分「概览 / 员工 / 部门与职位 / 密码管理」，登录走的是和主应用**同一个网关**（不多一道认证），进去之后由后端判定这个人有没有管理端权限。

顺带做了一件容易被跳过、但缺了就等于没有权限体系的事：**后端终于知道「这次请求是谁」了**。以前网关会把用户名塞进请求头转发给后端，但后端一行代码都没读过它 —— 这意味着任何权限判断都无处安放。现在身份解析收敛到一个出口，管理员 / 人事 / 普通员工三档权限在这里判定，和将来做数据隔离用的是同一套东西。

顺手修了一个已经发生过的数据事故：迁移的往返测试会把员工表新加的那些列**连同数据一起删掉再按默认值补回来** —— 结果是管理员被冲成普通员工、离职的人变回在职，而当时的断言一条都没红（它只检查列还在不在、行数变没变）。

**用一句话说这一版**：界面才刚立起来，三个内容页还是空的 —— 下一版开始往里填。

## v2.0.0-p2.11a · 组织与账号表就位

**这一版解决了什么问题**：从 P0-2 鉴权网关上线到现在，「用户」这三个字一直只存在于 `.env` 的一行配置里。数据库里确实建了 `user` 表，但它有六个月——从建表那天起一行都没有，全仓库也没有任何一行代码读过它。登录是谁在做？网关查 `.env` 里的 bcrypt 串。后端连「来的是谁」都不知道。

现在这张表终于是真的了：23 列的账号表，加上部门树和职位职级两张表。员工有工号、有姓名、有手机号、有部门和职位、有系统角色;离职和停用是两种不同的状态，不再是一个布尔开关。

顺带修掉一个从 P0-1 留下的隐患：原来那个 `is_active` 布尔列**下线了**。布尔只有「在/不在」两种状态，而真实的企业里「账号被暂时冻结」和「人已经离职」性质完全不同——前者要能恢复，后者不该再出现在任何选择列表里，但**两者都必须保留历史行**，因为他名下还有会话和文档。一个布尔表达不了这件事，两个列表达同一件事则必然漂移，漂移的后果是「离职的人还能登录」。

还有两件看不见但重要的事：

- **手机号默认脱敏**。`to_dict()` 输出的是 `138****5678`，要拿原值必须显式说一声。让「忘记脱敏」变成一个需要解释的选择，而不是一次疏忽。
- **停用、离职、改角色、改密码，都会让已经发出去的登录令牌立刻失效**。这是无状态 JWT 的固有短板（不能收回已签发的令牌），所以每一次这类变更都会让令牌版本号加一，版本对不上就当没登录过。这四种动作一个都没漏，包括「恢复在职」——否则一个离职前签发、还在宽限期的令牌会在恢复后复活。

### 已知边界

**这一版之后，系统仍然只能用 `admin` 一个账号登录。** 用户表建好了，但里面一行数据也没有，登录的真相源还是 `.env`。让它变成「多人能登录」是下一次的事（网关改查数据库），而「每个人的会话互相看不见」是再下一次。

迁移能安全地来回跑，存量数据一行不少（35 个文档、90 个切片、那个会话和它的 12 条消息都原样在）。往返之后有一点要知道：老员工的工号会变成空值，需要人工回填——加列只能填默认值，造不出真实工号。这条已写成断言钉在验收脚本里，不会悄悄发生。

## v2.0.0-p1.6e · 回答不再顶着一行空白开头

**这一版解决了什么问题**：回答气泡偶尔会以一行空白开头 —— 看起来像气泡顶部凭空多出一块留白，气人但说不出哪里不对。模型极少这么做，出现过一次之后就再没复现。

查下来是确定性的：模型偶尔会以两个换行符开头，而整条链路里没有任何一处把它裁掉。气泡是按原样排版的纯文本容器，换行就是空行。更糟的是这一行空白**同时被写进了历史记录**，所以刷新页面后它还在。如果那一帧整包就是两个换行符（刚开始生成的那一刻），页面上会出现一个空的气泡。

现在答案开头不会再带着空白进入气泡，也不会带着它进历史记录。只裁开头，正文里正常的换行与段落间距照旧。如果模型第一包只吐了空白，页面会继续显示「正在思考」，而不是先出现一个空气泡。

### 已知边界

已经存在数据库里的那一条历史记录不会自动变干净（这是对业务数据的批量修改，交给人工确认后再执行）。缓存里可能也留着旧回答，它有容量上限，会自然淘汰。

答案仍然是纯文本展示，不渲染 Markdown —— 所以这次不需要考虑「裁掉开头空白会不会影响排版语法」。

## v2.0.0-p1.6c · 回答生成到一半，可以停下

**这一版解决了什么问题**：回答一旦开始，就只能等它写完。想换个问法，也停不掉。同时，往上翻去看引用或更早的对话时，新写出来的字会把画面硬拉回底部。

现在生成过程中，发送按钮变成「停止」。点下去这一轮就中断，已经出现的文字留下，并标明已停止。后面不再继续向模型要字。停在半截的内容不会写进会话记录，避免残缺回答影响下一轮。

人还停在最新内容附近时，页面继续跟着往下走。上滑超过一小段之后，新内容不再抢滚动位置。滚回底部附近后，跟随恢复。

长回答里的小片段会合并到同一帧再显示，减少文字不断跳动。答案仍是纯文本，标题和表格不会排成富文本。

### 已知边界

- 停掉的那一轮刷新后不在历史里。
- 断开发生在模型正在吐一个片段时，这个片段可能还会到达，随后停止。
- 富文本展示这一版不做。

## v2.0.0-p1.6b · 会话留得住，相同问题不用再问一遍模型

**这一版解决了什么问题**：闲置 6 小时后，左侧就找不到那条会话；在同一条会话里接着问，还可能把上面的记录盖掉。同一句问题每次都重新检索、重新生成，开销重复。

现在会话一直留在列表里。多久没打开、没再问，仍然记着，但不再因此隐藏。库里的问答全部保留。模型每次只看最近 5 轮，用来理解「它」「上面那条」。

同一句完整问题会把上一次的回答存进缓存。再问同一句时直接返回，不再调用大模型。缓存最多 100 条，最久没被问到的会被挤掉；刚被问到的排到最前。知识库文档有增删或重新灌入时，缓存清空，避免答旧内容。

「如何办理居住证」和「居住证的流程是什么」不会当成同一题。这种相近问法先不做。

另外：知识库列表在表格里翻页，底栏一直看得见；引用显示文件名，悬停可以看到存放路径；上传说明里不再出现「选择整个文件夹」。

### 已知边界

- 同一句的第一次仍会走模型，第二次才用缓存。
- 界面上 Token 明细里的「缓存命中」是模型服务商的提示词缓存，和这次的问答缓存不是一件事。
- 指代很短的追问（例如「它呢」）不会写进公共缓存。

## v2.0.0-p1.6 · 模型不再装在本机

**这一版解决了什么问题**：原来嵌入和重排要在本机（以及以后的服务器）放一份模型文件，进程启动时读进内存。换机器就要准备目录、占磁盘、占内存。

- 解析和问答会多一次公网请求，也会计入接口用量。

## v2.0.0-p1.5c · 用起来顺一点，上传完立刻能搜到

**这一版解决了什么问题**：全栈跑通之后，日常使用里还有几处别扭。

复制对话没有成功提示；鼠标扫过回答底部整行都会弹出 Token 明细，而且最后一条会被弹窗顶上去、滚动条忽隐忽现把文字挤换行；新上传的文档要重启后端才检索得到；知识库一次只能传一个文件。

### 优化

- **复制有提示**：点复制后会出现「已复制到剪贴板」。浏览器不允许写剪贴板时，会说明失败原因。
- **Token 明细只认那一枚徽章**：耗时旁边不再误弹。下面放得下就朝下展开，最后一条会被挡住就朝上。弹窗不再把整段对话顶高。
- **滚动条槽位一直留着**：消息区宽度不再因为滚动条出现/消失而变，正文不会跟着抖一下换行。
- **上传后不用重启**：向量库改成独立服务，解析进程写进去，问答进程马上能搜到。
- **可以多文件、也可以选整个文件夹**：一次最多 50 份，其中某一份不合规不会让整批失败。

### 验证

- 新文档解析完成后不重启后端，问答引用直接命中这份新文档。
- 回归测试：向量库模块 102 项、文档解析模块 173 项，均 0 失败。中间件自检 17 项通过。

### 已知边界

- 选文件夹可以递归带上子目录里的文件；把文件夹拖进上传区还不会展开，请用按钮。
- 跑全量测试时，其中一组用例仍会清空文档表。跑完后文档编号可能变化，旧对话里的引用编号会对不上。

## v2.0.0-p1.5b · 整套系统可以一条命令起来了（已联调通过）

> ✅ **联调已于 2026-09-24 完成并通过**：六容器协同、登录、同步/流式问答、
> 上传解析、引用反查、删除闭环全部实测。联调抓到并修复了 3 个真问题
> （见下「修复 / 消掉的隐患」末尾），修复后复测通过。
> P1-5 的阶段标记 `v2.0.0-p1.5` 已补打。

**这一版解决了什么问题**：在此之前，「把系统跑起来」是一件需要开四个终端的事 ——
起数据库容器、起后端、起网关、起前端、再起一个解析进程，端口和启动顺序全靠人记。
换一台机器（比如服务器）就得把这套动作重新做一遍，漏一步的表现通常是
「页面能开但一问就 500」这种不带上下文的失败。

这一版把这四件事写进同一份编排文件：**一条命令起整套，一条命令停整套。**

### 新增

- **四个应用服务进容器**：后端、解析进程、网关、前端各一个容器，
  加上此前的数据库与缓存，整套共六个服务，依赖关系与健康检查都写死在文件里
  （数据库没就绪就不会去启动后端，避免"启动顺序靠运气"）。
- **前端由 nginx 托管**：构建产物只有一堆静态文件，运行只需要一个极小的 web 服务器，
  不再需要 node 进程常驻。
- **两条命令管全栈**：起、停、看状态、看日志、重建单个服务，都有对应入口。

### 修复 / 消掉的隐患

- **端口冲突**：应用服务默认不随日常命令启动。日常开发仍然只起数据库与缓存，
  应用继续在宿主机上跑（有热重载、能断点调试）；要起全栈是另一个明确的命令。
  否则"起个数据库"会顺手把四个应用也拉起来，和正在调试的进程抢端口。
- **容器里的 localhost 不是宿主机的 localhost**：如果将来要用本机的大模型服务，
  容器里写 localhost 连不到宿主机 —— 已预留好固定的访问通道。
- **一个改了不生效的配置项**：环境文件里有个 Redis 地址变量，代码其实并不读它
  （真正生效的是另一条完整地址）。已明确标注，避免以后有人改它然后困惑。
- **联调抓出的三个真问题**（均已修复并复测通过）：
  ① 网关在生产模式下需要两个环境变量，但它们只存在于开发用的配置里，
  全栈模式下网关**启动即崩** —— 已补齐；
  ② 编排工具会把登录密码哈希里的 `$` 当变量展开，哈希被**静默改坏**，
  表现是登录永远失败、日志里没有任何配置错误 —— 已转义；
  ③ 依赖清单在 Linux 上构建时会临时补拉数 GB 的显卡驱动库，镜像膨胀 ——
  已改为显式安装 CPU 版本。

### 关键取舍（这几个坑不写就一定会踩）

- **流式输出靠一行配置保住**：web 服务器默认会把响应攒起来再发，
  后端逐字吐出的回答会被攒成一整坨，前端变成"转圈半天然后一次性出现"。
  特点是**不报错，只是慢**，极容易被当成模型慢而去查错方向。
- **反向代理的启动顺序**：web 服务器启动时会去解析上游服务名，
  上游还没起来它就会**直接退出**，配上自动重启就是刷一片日志，
  看起来像"网关挂了"，实际是它自己起不来。已改成请求时再解析。
- **后端只能是单进程**：多个进程同时写同一个向量库目录会损坏索引，
  表现是问答接口直接报 500。这条限制已写进启动命令的注释里。
- **解析进程不加载重排模型**：解析用不到它，关掉约省 1.1GB 内存 ——
  这是 4G 内存的服务器上"跑不跑得动"的关键一条，且不影响解析结果。

### 验证

- **静态校验**：编排文件解析通过（含变量替换、挂载路径、依赖关系逐项核对）；
  三个镜像构建脚本静态检查零告警；命令入口展开正确。
- **全栈联调（2026-09-24 实测）**：六个容器全部健康；前端入口正常；
  登录下发令牌；同步问答 10.8s 且引用与裸跑一致；流式回答 248 帧逐帧到达
  （缓冲关闭那行配置在真实链路兑现）；上传 0.27s 入队、解析进程 5.2s 完成；
  引用反查穿透反向代理正常；不带令牌的访问被 401 拦下；
  删除文档后数据库、向量库、磁盘三件事零残留。

### 已知边界

- 向量库仍由后端与解析进程**共享同一份目录**，这个结构在容器里没变，
  所以"刚上传的文档要重启后端才检索得到"这个现象**依旧存在**，根治方案另记。
- 模型目录仍走宿主机挂载；本机它是个软链，联调中已验证容器内可正常跟随，
  上服务器前要换成真实目录。
- 容器以 root 运行、日志写在容器内部、跨域白名单还是本地地址 —— 都属于后续打磨项。

## v2.0.0-p0.4c · 刷新之后，每一轮的引用都还在

**这一版解决了什么问题**：一个很具体、也很影响信任感的毛病 ——

> 同一个对话里连着问几个问题，**只有第一个问题的回答带着引用资料**，
> 后面几轮的引用不见了；重新打开页面（刷新）之后尤其明显。

引用资料是这个系统最重要的东西：它告诉用户「这句回答是从哪份文档的哪一段来的」。
引用不见了，回答就退化成一句没有根据的话。

### 这个毛病为什么难查

它有三个特点，凑在一起非常容易误判：

1. **当场看是对的。** 提问的那一刻，引用直接跟着回答一起返回，一切正常。
   只有**刷新页面、重新加载历史**之后，引用才消失。
   —— 所以「点一下就好了」这种验证方式永远试不出来。
2. **只有第一个问题有引用**，看起来像「后面的问题没检索到」，
   很容易被当成检索或知识库的问题去查，而它其实是**记录引用时的位置错位**。
3. **只问一轮时完全正常。** 问题要连着问三轮以上才现形 ——
   而之前的测试基本都是「写一轮、读一轮」。

### 根因

每一次问答，系统都要记两样东西：对话内容，以及这一轮的引用资料。
两样都按「第几轮」对齐存放，取的时候按编号取。

问题出在记的顺序上：**本轮内容先写进去，然后才去补引用资料的空位** ——
于是每写一轮，就凭空多出一个空位，紧接着又被清理逻辑砍掉一个；
砍掉的恰恰是**最早那一轮的引用**。

净效果：每问一轮，就把最老一轮的引用挤掉。问到第三轮时，
第一轮和第二轮的引用已经蒸发，中间还留下空洞。

修法本身只有一行（调整记的顺序），难的是定位它。

### 修复

- **调整记录顺序**：先补齐历史，再写本轮 —— 引用资料与轮次严格一一对应。
- **补上能抓住它的测试**：刻意「连写三轮、中间一轮不带引用」，并逐条写死「第几轮应该有什么」。
  只断言「条数对不对」抓不住它 —— 条数在出错时反而是对的，错的只是内容。
- **反向验证过**：把这一行改回错误位置再跑一遍测试，14 条断言里 8 条立刻变红，
  证明这组断言真的守得住，不是摆设。
- **走真实接口验证了完整操作序列**：连问三轮 → 刷新 → 检查每一轮的引用。
  三轮各自拿回自己的引用（入职问题挂着入职文档的片段、离职问题挂着离职文档的片段，没有串台）。

### 顺带修掉的

- **单元测试不再连真实数据库**：有一组测试没指定存储后端，于是跟着配置走 ——
  配置改成用数据库后，这组「单元测试」就连上了真实业务库，
  既产生假失败，还差点把真实会话归档掉。已改为固定使用进程内存储。
  单元测试不该碰业务数据，也不该随配置漂移。

### 验证

- 回归测试（9 个模块，666 项）全绿；新增 14 条专门守这个不变量的断言。
- 端到端：连问三轮后刷新，每轮引用都在。

### 已知边界

- **修复只管之后新写的对话**。修复前已经错乱的历史对话不会自动纠正 ——
  这类数据属于可重建资产，不值得为它写一个一次性脚本（脚本本身会成为长期负担）。
  将来真要修，应该是一次性的数据订正，而不是在代码里加兼容分支。

## v2.0.0-p0.4b · 引用真的能点了

**这一版解决了什么问题**：上一版给每条引用发了一张身份证（编号），
数据、接口、清理能力都齐了 —— 但**界面上那条引用还是一段死文本**，
点它没有反应。用户看到的仍然只有 200 字摘要：想知道这句话在原文里是怎么说的、
前后文是什么、出自哪份文档，一概查不到。

一句话说就是：**能力已经在后端了，界面还没接上。**

这一版把它接上：**点引用 → 展开切片全文 + 源文档信息。**

### 新增

- **引用条变成可点的按钮**。点文件名展开，再点收起。
- **点开看到的是切片全文，不是那 200 字摘要**。摘要只是全文的开头一小段，
  而真正回答「这句话在原文里是怎么说的」的是全文。
- **同时告诉你它出自哪儿**：文件名、第几页、第几片、多少字、什么时候上传的 ——
  这些信息来自数据库里的文档记录，不是从文件路径猜出来的。
- **一次只展开一条**。引用条本身很窄，同时展开几条会把对话挤得读不下去。

### 修复

- **没有编号的引用不再假装可点**。有一批早期入库的切片压根没有编号，
  本来就查不到。以前它们和能查的引用长得一模一样，点了必然失败。
  现在它们渲染成普通文本，鼠标悬停会说明「这条引用没有可反查的编号」——
  **一个点了就报错的按钮，比没有按钮更让人恼火**。
- **展开过的不会再反复取**。包括「取失败」的结果也记下来：
  否则关掉再点开，会看到一次假的「正在取回…」然后又弹同一个错，像网络在抽风。

### 优化

- **后端说「查不到」时，界面显示的是后端那句原话**，前端不自己重写一遍。
  后端已经把情况分清楚了（「引用内容已随文档删除」是永久的、
  「引用片段已失效，请刷新后重试」是暂时的），前端重写一次就多一处对不上的风险。
- **正文还在、但数据库记录没了的情况下，照常显示正文**，只额外标一个「文档记录缺失」。
  内容确实还在，不该给用户报错 —— 那个标记是给运维看的：该跑一次重建了。
- **顺手消掉一处重复定义**：问答接口返回类型里把「引用长什么样」又抄了一遍，
  抄一份就多一处漂移点（后端加字段时只有一处会记得改）。改成共用同一份定义。

### 验证

- **浏览器端到端验收 18 项、0 失败，连跑两遍**：真实浏览器登录 → 真问一个问题
  （真检索 + 真重排 + 真大模型）→ 点引用 → 读展开出来的 DOM。
  它验的是接口测试看不见的东西：按钮到底能不能点、展开的是全文还是摘要、
  再点会不会收起、点开第二条时第一条有没有自动收起。
- **类型检查 + 生产构建 0 错误**：类型检查是开着严格模式跑的，
  这一条同时覆盖了「可能为 null 的字段没判空」这类问题。
- **后端全套测试没有重跑**：这一版**后端一行未改**，Python 侧不存在受影响的代码路径。
  上一版的 812 项基线不变 —— 「项数不变」本身就是「这次改动对后端零影响」的证据。

### 已知边界

- **刷新页面后同一条引用会重新取一次**。缓存挂在界面组件上，没做全局缓存：
  全局缓存要额外处理「文档被删了缓存要不要失效」，收益不抵复杂度。
- **没编号的老引用仍然点不开**，跑一次知识库重建之后它们就有编号了。
- **不做「打开源文档原文」**：前端没有 PDF/Word 的渲染能力；
  真要核对原件，走知识库页的「下载原文件」。

### 复盘 · 验收脚本差点又骗了我一次

这一轮第一版跑出来是 16 通过 / 1 失败，失败项是「文档已删除」那个分支。
查下来不是功能坏了，是**验收脚本自己挑错了对象**：它点的是一条**已经被展开过**的引用，
而展开过的结果已经进了缓存，再点不会发请求 —— 于是那个「假装接口返回 404」的桩
永远拦不到，那一组实际上是在验缓存，不是在验错误分支。

改法是显式挑一条没展开过的引用，并在代码注释里写明为什么。
**一个看起来在验 A、实际在验 B 的断言，比直接失败更危险** —— 它会一直绿着。

（另有一处小坑：验收脚本里侧边栏选择器写错了，表现是「登录失败」而不是
「找不到元素」，很容易往鉴权方向查。）

## v2.0.0-p0.4a · 引用有了身份证：点得开、溯得到源、删得干净

**这一版解决了什么问题**：系统回答问题时会在下面附几条「引用资料」。
但那些引用实际上是**死的**——它们只是 200 字的摘要片段，点不开、看不到完整原文，
也查不出它出自哪份文档的哪一页。更要命的是，向量库里那些片段只记了一个磁盘文件路径，
**没记它属于哪份文档、是第几片**。于是：

- 文档删掉之后，它留下的片段可能还躺在库里，**能被引擎检索到、却溯不回源**；
- 想按文档删除切片，只能拿文件路径去字符串匹配——文件一改名、一挪位置就对不上了；
- 历史回答里的引用，删档之后到底该显示什么，没有依据可判断。

一句话说就是：**引用只有样子，没有身份。**

这一版给每个切片发一张身份证，叫 `chunk_id`，长成 `284:7`（284 号文档的第 8 片）。
有了它，引用才第一次变成一条**可点击、可溯源、可清理**的数据。

### 新增

- **每条引用都能点开看全文**。新增反查接口：拿 `chunk_id` 就能取回这个切片的完整正文，
  以及它出自哪份文档、什么时候上传的、属于哪个项目 —— 文件信息来自数据库，不是猜的。
- **四种情况各说清楚，不再笼统报错**：

  | 点开一条引用时 | 系统怎么说 |
  |------|------|
  | 链接本身不合法 | 明确是请求的问题 |
  | 那份文档已经被删了 | 「引用内容已随文档删除」（这是预期内的终态） |
  | 文档还在、但这一片刚被重新解析过 | 「引用片段已失效，请刷新后重试」（暂时的，刷新就好） |
  | 正文还在、但数据库记录没了 | 照常显示正文，同时**如实标记「记录缺失」**——这是给运维的信号，不是给用户添堵 |

  把「永久失效」和「暂时不一致」分开说，是为了让用户知道**下一步该干什么**，而不是干瞪眼。
- **能查出并清理「无主切片」**。识别出两类：一类是早期写入、压根没记文档编号的；
  另一类是文档记录没了、片段却还在的。都能列出来、能清掉。
- **`make reindex` 知识库重建**：扫描已上传的文件重新灌一遍向量库。默认**只报告不动手**
  （先告诉你它打算做什么），确认后加 `--apply` 才执行；中途失败可以接着跑，不会把库清空了跑一半。

### 修复

- **引用键在接口里被静默丢掉了**（本版最贵的修复，实际改动只有一行）。
  现象是：后端日志里明明带着引用键，浏览器拿到的响应里却一个都没有，而且**不报任何错**。
  根因是接口层会按预先声明的字段清单过滤返回值，没声明的键直接丢弃。
  顺手加了一道通用守卫：以后再往引用里加字段却忘了登记，测试会立刻红——不管新字段叫什么。
- **跑一次回归测试会把真实文档记录抹掉**。这是测试脚本自己的毛病：
  它的清理动作写成了「清空整张表」，于是在开发机上跑一遍测试，知识库记录就没了，
  而切片还留在库里，变成一堆查得到正文、溯不到源的「幽灵引用」，且没有任何提示说是谁干的。
  已改成只清理测试自己创建的数据。

### 优化

- **老切片不用为了一个派生字段整库重建**。文档编号和序号都在，引用键可以在读取时现拼。
  代价是「为一个字段重灌整个库」这种不划算的事不用做了。
- **重建脚本自带两道闸门**：后台解析进程在跑、或者后端服务在跑，它都拒绝执行并说明原因。
  这不是保守——多个进程同时改写同一个向量库目录会让索引损坏，
  表现是问答接口直接报 500。**重建这种一次性动作，停服是值得的。**
- **重建可中断、可重跑**：不是「先清空再重灌」（那样中途失败就什么都没了），
  而是「补登记 → 逐份重灌 → 最后清无主切片」，最坏情况也只是多跑了一遍。

### 验证

- **新增 87 项离线测试、0 失败**：覆盖身份证的格式拼装与解析（含全角数字这类会让程序
  「校验通过但转换崩溃」的边界）、写入后自洽、无主切片识别与清理、引用键三级取值、
  历史引用的落库、反查接口的四种返回。
- **新增 41 项验收、一处不打桩**（真实数据库、真实向量库、真实检索），
  计划书 4 条标准逐条实测全部成立：删除文档后磁盘/向量库/数据库三处均无残留；
  点引用能拿到切片正文与源文档信息；重建后同一问题检索到的内容与重建前**逐字一致**；
  向量库里不存在缺文档编号的切片。
- **后端全套 812 项、0 失败**（上一版 725 项，本版新增 87 项，项数差正好等于新增测试）。
- **上一版的验收标准全部重跑，5 条依然成立**，与上一版基线一字不差。
- **真实浏览器链路留证**（三件套全部跑起来、全程走登录网关）：版本号、登录、问答（9.5 秒出答案）、
  引用带键、点开拿到 380 字全文并溯源到《离职流程与注意事项.pdf》、非法链接正确报错。

### 已知边界

- **界面上引用还是点不了**。这一版只做后端：数据、接口、清理能力都齐了，
  但页面上那条引用仍然只是一段文本。把它变成可点的按钮是下一版（`p0.4b`）的全部内容，
  交接物已经备好，不需要再回头改后端。
- **文档删掉之后，历史回答里那条引用的正文查不到**。这是刻意的选择：
  不保留引用内容的副本，换来的是**删得干净**——敏感文档不会以副本形式残留在历史记录里。
- **重建必须停服**（后台进程与后端服务都要停）。这是向量库的硬限制，不是脚本偷懒。

### 复盘 · 两个「测试全绿但功能其实是断的」

这一轮最有价值的东西不是加了什么，而是**两个差点带着上线的问题**，
它们的共同点是：测试全绿、日志正常、功能却是坏的。

第一个是上面「修复」里的引用键丢失。接口层按字段清单过滤返回值，
我加了字段却忘了登记，于是**后端有、接口没有**。单元测试测的是内部函数（有），
接口测试没覆盖这个字段（所以也没红）。教训是：断言不能只测「代码里产出了什么」，
要测「接口真的带出去了什么」——现在这条守卫是通用的，不绑定具体字段名。

第二个是测试脚本清空了真实数据表。它照抄了另一个测试模块的清理写法，
而那个写法是「清空整张表」。在开发机上这等于跑一次测试就删一次业务数据，
而且**没有任何报错**，只会表现为「引用突然溯不到源了」这种离真相很远的症状。
教训是：测试脚本的清理动作必须和它的创建动作**用同一把尺子**（同样的前缀），
三处清理口径一致才不会误伤。

## v2.0.0-p0.3b · 后台在做什么，页面上看得见

**这一版解决了什么问题**：上一版把上传改成了「提交立刻返回、解析交给后台慢慢做」。
这条路是对的，但它把一个问题推到了前台：**界面上看不出后台在干什么**。

上一版的界面还在问「这一次入库了多少片段」——而这个数字在提交那一刻根本不存在，
要等后台解析完才知道。于是上一版上线之后，知识库管理页实际上是**坏的**：
点了上传，页面不给任何反馈，用户不知道文件到底进去了没有，只能反复点、
或者关掉重试。**能力做对了，界面还在按旧节奏说话。**

这一版把界面接到新的节奏上，核心就一句话：**后台在做什么，页面上要看得见。**

### 新增

- **状态列：排队中 / 解析中 / 已完成 / 失败**。提交之后不用猜，看着它从「排队中」
  走到「解析中」再到「已完成」；一段时间没动静也不会误以为卡死——状态自己会更新。
- **完成时弹一次提示**，写明这份文档被切成了多少片段。片段数不是装饰：
  检索、引用、喂给模型的都是片段，不是原文档整体，所以这个数是用户判断
  「这份文档有没有被好好处理」的唯一依据。
- **失败可以一键重试**。以前失败就是失败，用户只能把文件删掉重传；
  现在失败那一行直接给一个「重试」按钮，点一下重新排队。
- **「解析进程是不是在跑」会显示出来**（重点新增）。这是异步化带来的新故障类型：
  后台那个常驻进程如果没启动，提交上去的任务会**静静地躺在队列里**，
  页面看起来就是「一直在转圈」，而且**转多久都不会好**。
  这一版会明确告诉用户「有几份文档在等待解析，但没有检测到解析进程在运行」，
  并给出该执行哪条命令 —— 这是用户唯一能自己修的一类故障，不告诉他等于让他干等。
- **可以下载原文件**。排查「我上传的到底是不是那份」时不用再去服务器上找。

### 修复

- **上传后不会再因为「没反应」而重复上传**。这是上一版最直接的副作用：
  用户点上传、页面没反馈，于是再点一次，于是又提交一份。
  这一版提交后立刻给一句「已提交，正在后台解析」，并且**刻意不说「成功」**——
  受理不等于完成，这时候说成功就是在骗人。

### 优化

- **轮询只在有必要的时候才转**。三道限制：全部文档都处理完了就不转；
  页面切到后台（切走标签页）就不转，切回来立刻补一次；请求连续失败就逐步拉长间隔
  （最多拉长到 30 秒一次）。一个不做限制的轮询器，就是一台持续消耗服务器的机器。
- **切走页面、关掉标签页，回来照样能看到结果**。这一点是刻意设计的：
  解析要几十秒甚至更久，用户在等的时候一定会去干别的。如果进度和完成提示
  「一离开页面就没了」，那用户就只能在知识库页干等——那等于没做成异步。
  做法是把「盯着进度」这件事放在页面之外的地方，而不是挂在某个具体的页面上。
  验收里专门验了这条：切到别的页面之后，完成提示照样弹出来。
- **失败原因整行展开，写成人话**。它要回答的是「我下一步该干什么」，
  所以必须完整可见、指明是哪个文件；塞进一个小格子里被截断，等于没给。
- **按钮置灰时必须说明原因**。比如「已成功解析的文档不支持重试」——
  置灰而不解释，用户只会以为页面坏了。
- **下载按钮带上了登录凭据**。下载链接如果直接点，浏览器不会带上登录信息，
  结果就是一个「未授权」的错误页；改成一键保存，并且文件名保持中文原样不乱码。

### 验证

- **浏览器端到端验收 56 项、0 失败，连跑两遍**。专门写了一个用真实浏览器跑的验收脚本：
  用真实账号登录 → 真实上传 → 等真实的后台进程解析 → 读页面上的状态与提示 → 真实下载 → 真实删除，
  全程零控制台报错。它验的是那些用接口测试**看不见**的东西：
  状态列到底有没有在动、按钮到底有没有灰、失败原因到底能不能读懂。
- **连跑两遍才算数**：第一遍 57 项里挂了 1 项、第二遍挂了 2 项，
  查下来都是**验收脚本自己的毛病**（一次是把两条一模一样的提示当成一条、少算了一次；
  一次是在片段还没加载完就去数，结果数到 0 —— 而第一遍那次「通过」其实是在赌时间）。
  修完连续两轮全绿。**同一次绿不算数**，这是这一轮最有价值的教训。
- **上一版的验收标准全部重跑一遍，5 条依然成立**：50MB 上传响应立即返回（实测 0.60 秒）、
  关掉浏览器任务照常跑完、同一任务入队两次不会产生重复内容、损坏文件标记失败且原因可读、
  杀掉后台进程再重启任务继续被消费。
- **后端全套 725 项、0 失败，项数与上一版一字不差**。本轮是纯界面改造，
  没加任何后端测试，也不该改变任何既有行为——「项数不变且全绿」本身就是
  「这次改动对后端零影响」的证据。

### 已知边界

- **提示条会盖住页面顶部的一段说明文字**。同时出现两三条提示时比较明显。
  之所以这一版没动它：这个提示条是所有页面共用的，改位置会影响问答页和设置页的观感，
  超出了这次「把知识库页接上后台节奏」的范围。已截图留证，留作一次独立的界面打磨。
  （顺带说明：这一版之前这里最多同时出现一条提示，所以看不太出来。）
- **侧边栏的「片段总数」里含一批旧数据**。知识库列表为空时它显示 15，
  那是早期（切片还没带文档编号时）写入的遗留内容，列表里看不到、也管不了。
  这不是本版的缺陷，而正是**下一步要做的「知识库重建」**要清理的对象。

### 复盘 · 一次「假通过」的验收

这一版一共在验收脚本上栽了两次。第二次特别值得记：

| | |
|---|---|
| **发现方式** | 第一次跑全绿了。为了确认不是运气，又跑了一遍 —— 第二遍挂了 2 项。 |

## v2.0.0-p0.3a · 上传大文件不再「转圈等到超时」

**这一版解决了什么问题**：在这之前，用户点「上传」之后，浏览器要**一直等到文档解析完**才能收到响应。
解析包括读取文件、切分、把每一段转成向量、写进向量库 —— 一本几十 MB 的 PDF 要几十秒甚至几分钟。

这段时间里发生的事很难看：浏览器等不及会超时，用户以为上传失败于是再传一次（于是又挂一次），
而服务器那边其实一直在干活。更糟的是**换个页面、关掉浏览器，这次上传就白做了** ——
因为「正在解析」这个状态只存在于那个请求里。

这一版把上传拆成两步：**浏览器只负责把文件交出去，解析交给一个常驻的后台进程慢慢做**。
上传接口在一秒内返回，用户提交完就可以关掉页面；下次打开，页面从数据库读到的就是最新的处理进度。

### 新增

- **上传秒回**：上传接口不再等解析，收到文件就返回「已受理」。
  实测 50MB 文件与 1KB 文件的响应耗时几乎一样（0.575 秒 vs 0.495 秒）——
  这说明耗时只取决于往硬盘写文件，和文件内容、大小基本无关。
- **解析交给独立后台进程**：不再是「在上传请求里顺手做」，而是有一个常驻工作进程专门消费待解析的任务。
  这么做不只是为了快：解析要加载模型、吃 CPU 和内存，跟网站进程放在一起会把网站一起拖慢；
  分开之后，两台角色可以按各自需要分配资源。
- **关掉浏览器，任务照常跑完**：提交后关掉页面，解析继续；重新打开时状态从数据库读回来。
  实测就是这样做的：提交 → 断开连接 → 三秒后重新连上读状态，显示已完成、切片数正确。
- **一次提交只会被解析一次**：即使同一条任务被投递两次（用户连点、队列重投），
  也只会有一个进程真正抢到它。实测推两条消息，最终只解析了一次、切片数与单次完全一致。
- **失败原因写成人话**：上传损坏的文件不再是一个沉默的失败。数据库里会记一句
  「解析失败或没有可提取文本（文件可能已损坏）：报销单.docx」——
  **指明是哪个文件**、没有一行看不懂的报错堆栈，用户可以据此重新上传或用「重解析」按钮再试一次。
- **多了一个「队列体检」接口**：能一眼看到「还有几个任务在排队」「工作进程活着没有」「待解析/解析中/成功/失败各几个」。
  工作进程没启动时它也不会报错，而是如实显示「没有进程应答」。
- **50MB 上限与超限提示**：超过 50MB 的文件直接被挡回并说明上限，不会先写盘再失败。

### 修复

- **工作进程被强制杀掉后，任务永远卡住的问题**：这是异步化必然带来的新问题 ——
  进程被杀的那一刻，文档状态停在「解析中」，而「解析中」既不是「待解析」也不是「失败」，
  于是**没有人会再去捡起它**，表现是「一篇文档永远在转圈，点多少次重试都不动」。
  这一版给文档加了一个「本次解析开始时间」字段：解析中但开始时间已经过去太久的，视为上一次的残留，
  允许重新被抢走。判定依据是**数据本身**，不是「某个进程什么时候启动的」——
  后者在多进程场景下会误伤正在干活的进程。
- **被拒绝的路径不再有可乘之机**：下载接口按编号取文件，所以文件路径全部由数据库记录推导。
  这一版把路径校验写得更严：先把 `..` 这类相对路径**展开**再判断，
  而不是比较字符串开头 —— 比较字符串开头的话，`upload/../../某个系统文件` 是能蒙过去的。

### 优化

- **删文档变成「一次都不能少的三件事」**：硬盘上的原文件、向量库里的所有切片、数据库里的记录。
  顺序也是刻意定的：**先删可以重新生成的（切片、文件），最后删那条「指向它们」的记录**。
  反过来的话，中途失败就再也没有东西能告诉我们「该清哪些切片」，库里会留下永远查不到也删不掉的残留。
- **切片的写入顺序改成「先解析、后删、再写」**：直觉上「先删旧的再解析」更整齐，
  但那样一个大文件会造成几分钟的空档 —— 这段时间里这篇文档检索不到、引用也查不到正文。
  改到解析之后删，空档缩短到毫秒级；附带好处是解析失败时**旧切片原封不动**，
  文档仍然可被检索到，而不是「越重试越查不到」。
- **「重解析」这个动作被收紧了**：已经解析成功的文档不允许重解析（会明确拒绝并说明原因），
  必须先删除再重新上传。否则「重解析」的含义就模糊了：是删掉旧的重新生成，还是在旧的上面再叠一份？
- **依赖锁定只增不改**：加一个新库时，锁定文件里应当**只多出这个库和它自己的依赖**。
  这一版做到了 —— 没有出现任何与本次改动无关的版本漂移。这件事听起来像常识，

**这一版解决了什么问题**：在这之前，要让项目跑起来，得先在电脑上单独装好数据库和缓存两个服务，
再手工调字符集、时区、内存上限；换一台机器就要重来一遍，而且很容易漏掉某一项而查不出原因。
这一版把它们装进容器：一条命令起停，参数全部写死在配置文件里，
并且增加了「一条命令做 14 项体检」的自检脚本。

### 新增

- **一条命令起停的两个基础服务**：数据库（MySQL）与缓存（Redis）改用容器运行，
  起来、看日志、停掉、彻底移除各对应一条命令。容器只是**运行方式**，
  里面的数据存在容器之外的独立空间里 —— 所以删掉容器重建，数据依然在。
- **端口只对本机开放**：两个服务的端口只绑定本机地址，同一网络下的其他机器连不上。
  开发机经常连公司网或公共 Wi-Fi，这个默认值比顺手写一个「对所有地址开放」安全得多。
- **启动自检脚本（14 项）**：一条命令检查服务是否健康、账号能不能连上、
  中文和 emoji 会不会存坏、时间会不会差 8 小时、缓存的内存上限是否真的生效、
  本机端口是否通。以前这些要挨个手动验，且「验过没有」无法追溯。
- **建表权限的提前检查**：自检里会真的建一张临时表再删掉。
  下一步要用迁移工具创建业务表，如果账号只有读写权限没有建表权限，
  到那时才会卡住 —— 而那时代码已经写了一堆。提前 3 行 SQL 就能避免。

### 修复

- **（环境问题）镜像下载不下来**：本机网络下 Docker 官方镜像仓库不可达，
  容器因此一直起不来。排查确认**不是代理故障** —— 代理正常工作、能访问其他站点 ——
  而是那个仓库地址在当前网络下被阻断。改用国内加速源解决。完整排查过程见下方复盘。

### 优化

- **中文与时区一次性配好**：字符集、排序规则、时区都写在服务的启动参数里，每次启动都生效。
  特意**不**写在「只在第一次启动时执行的初始化脚本」里 —— 那种脚本改了不会重跑，
  很容易出现「配置里明明写了、实际没生效」这种最难查的状态。
- **缓存写满时宁可报错，也不悄悄丢数据**：缓存在本项目里还承担着「排队等处理的任务」的角色。

  而且事后查不到任何痕迹。改成直接报错后，问题会当场暴露、可以重试。
- **数据库账号不用最高权限账号**：应用使用单独的低权限账号，最高权限账号只用于容器初始化。

### 验证

- **决定性验证：把容器整个删掉再重建，数据库与缓存里的数据都还在。**
  （验证方式特意用「删除 + 重建」而不是「重启」——重启只是重启进程，证明不了数据存在容器之外的独立空间里。）
- 应用配置未受影响：新增的配置项被安全忽略，业务代码**一行未改**。

### 复盘 · 半小时的「下载卡死」其实是两个假象

| | |
|---|---|
| 现象 | 执行启动命令后，镜像一直下载不动，界面上只有计时器在走，看不到任何进度。 |

## v2.0.0-p0.1b · 让问答记录真正「存得住、查得到」

**这一版解决了什么问题**：上一轮把「会话与问答记录」存进了缓存服务，这次推翻重做。
原因不复杂 —— 缓存服务为了速度把数据放在内存里，重启、内存吃紧、容量保护都可能让它
悄悄消失；而聊天记录是**用户随时会回来翻**的东西，丢了就是事故，且找不回来。
更要紧的是，存进缓存之后这些记录**没法用 SQL 查**：按用户查、按时间统计、用量对账、
抽查回答质量，全都没有落脚点。

这一版把它们搬进了关系型数据库（MySQL），并立下一条项目级规矩：
**「真相」只能存在数据库里；缓存服务只负责「丢了能重来」的东西**（比如排队等解析的文档）。

### 新增

- **问答历史真正持久化**：消息正文、每一轮的引用资料、置顶、自定义标题、token 用量，
  全部落到数据库的表里。重启服务，甚至停掉隔天再开，历史一条不丢。
- **数据可以「直接查」了**：所有记录都在结构化的表里，一条 SQL 就能按会话、按时间、
  按用量做统计。这是这一版最实在的收益 —— 以前这些数据只能通过程序接口一条条读出来。
- **表结构变更有了正规流程**：引入迁移工具，每次改动都留下一个可追溯、可回退的版本记录。
  以后给表加字段，不会再出现「开发机能跑、线上库缺列」的问题。
- **新增 5 条数据库操作命令**：升级结构、查看当前版本、回退一版、新增一版，
  以及「只打印 SQL 不执行」（给需要走审批的场合用）。

### 修复

- **配置写错不再「悄悄降级」**：上一版如果配置里写了已废弃的存储类型，程序会安静地
  退回内存模式，日志里只留一行警告 —— 生产上这等于**悄悄把持久化关掉了**，
  重启就丢光数据，而且往往要等到用户投诉才发现。
  现在这种情况会**直接启动失败并说明原因**。启动失败五分钟就发现了；静默丢数据找不回来。

### 优化

- **同一会话的并发提问不会互相覆盖**：多个标签页同时对着一个会话提问时，
  靠数据库的行级锁保证「读—改—写」串行。实测 12 路并发，一轮对话都不丢。
- **过期会话只隐藏、不销毁**：闲置太久会被判定为过期（从列表里消失），
  但记录**仍然留在库里**。这类永久资产不该被一个过期计时器抹掉 ——
  真正的清理策略会另行设计。
- **一次问答的所有写库动作在一个事务里完成**：不会出现「消息写进去了、
  引用资料没写进去」这种半截状态。
- **表定义与迁移脚本分开维护，并用一条自动断言盯着它们别分叉**：
  迁移脚本是「历史快照」，写下去就不再改（否则在新代码下重放旧迁移会出错）；
  查询用的定义是「当前结构」，随业务演进。两者的分歧由测试断言兜住，而不是靠人盯。

### 验证

- **测试从 497 项增加到 559 项，全部通过**。新增的 62 项专门针对数据库存储：
  表结构一致性、真的按行落库、重启后数据仍在、并发不丢轮次、过期与归档行为、
  删除不留残留数据。
- **「业务代码一行未改」再次得到验证**：这已经是第二次更换存储后端
  （内存 → 缓存 → 数据库），三次都只改存储层，问答链路、接口、路由一行没动。
  这正是当初决定「把存储抽象出来」的目的。
- **两个后端行为逐字段一致**：同一串操作分别在内存版和数据库版各跑一遍，
  结果（消息、引用资料、置顶标题、用量、会话列表）完全相同 ——
  这条断言的意义是保证「换后端」不等于「换了个 bug」。
- **数据库不可用时整模块跳过而不是误报失败**，并在输出里给出明确的排查提示。

### 复盘 · 顺带发现的一个既有缺陷

| | |
|---|---|
| 发现方式 | 为新存储写「两个后端结果必须一致」的对照断言时，对照断言直接红了。 |
| 现象 | 连续 3 轮问答，第 1 轮的「引用资料」会串到后面去，且末尾多出一个空位 —— 每轮整体错位一格。 |
| 关键判断 | 立刻改用**内存版**跑同样的操作 → **一模一样**。说明这不是新写的存储层引入的，而是上一版就已经存在的缺陷。 |
| 为什么之前没被发现 | 断言只查「元数据条数对不对」（条数确实是对的），没人查「第 N 轮的元数据是不是第 N 轮的」。 |
| 处理 | **本次刻意不修**。本轮验收红线之一是「问答逻辑代码一行未改」，修它就把这条证据毁掉了。已记录在案并给出修法（把补位调用挪到新消息入队**之前**即可），留作下一次独立迭代。 |
| 教训 | 「条数对」不等于「内容对」。断言必须断言到**语义**，否则只是在给缺陷盖章。 |

## v2.0.0-p0.2 · 给系统装上一道门

**这一版解决了什么问题**：v1.0.0 上线即裸奔——任何人都能上传文档、提问，直接消耗大模型额度。
这一版在业务后端前面加了一个独立的鉴权网关，所有请求必须先登录才放行。

### 新增

- **独立鉴权网关**（NestJS，`:3000`）：JWT 登录、全局默认拒绝的守卫、按用户限流（防止别人白嫖
  大模型额度）、请求白名单机制。
- **请求转发**：网关校验通过后把请求转给后端。**关键要求是流式输出不能被破坏**——
  问答接口是逐字返回的，中间多一层缓冲就会把「打字机效果」变成「等 30 秒一次性吐出来」。
- **统一错误格式**：无论鉴权失败、请求过频、参数不合法还是后端不可达，前端拿到的错误结构都一致，
  不必写四套解析。
- **身份透传**：网关验完 token 后把用户身份放进请求头传给后端，**后端一行代码没改**，不用自己解析 JWT。
- **前端登录页与登录态联动**：token 失效自动回登录页；主动/被动登出都会清空本地会话数据
  （不清的话下一个登录的人会看到上一个人的聊天记录）。
- **网关自身探活接口**（免登录），用于监控判断「网关进程是否活着」——它有意识地和「后端是否活着」分开，
  否则后端挂掉会把网关一起判死。

### 修复

- **★ 一个 POST 请求就能把整个网关进程打挂。** 最严重的一个 bug，值得完整记一笔：
  为了让被框架提前消费掉的请求体能重新转发，用了官方的 `fixRequestBody`。
  但它内部会**结束掉请求**——此后任何「往请求上加一个头」的操作都会抛异常。
  真正致命的是：这个异常发生在一个事件回调里，**没有任何地方捕获它**，
  于是整个 Node 进程直接退出。症状极具迷惑性——只要有人提交一次表单，网关就凭空消失，
  而日志里只有一行看不出严重性的提示。

  修法是两层的：先调整语句顺序（所有加头的操作都提到结束请求之前），
  再给回调整体加上异常捕获，最后在进程级也加一道兜底。
  **这个 bug 的教训是：异常发生在回调里时，「有没有人捕获」比「异常本身」更要命。**
- **参数校验提示答非所问**：漏填密码时提示的是「密码不能超过 128 个字符」——
  框架遍历校验规则的顺序不确定，取到了最后一条。改为优先取「不能为空」这类更贴切的提示。
- **限流提示透出英文类名**：只显示 `ThrottlerException: Too Many Requests`，用户看不懂，
  已换成中文文案。
- **前端登出提示语病**：出现过「登录状态已失效（登录状态无效，请重新登录），请重新登录」
  这种同义反复嵌套，已收口成两种固定文案。
- **（修订）漏放行两个上游健康检查**：计划书明确要求放行，首轮实现只放了登录和网关自身探活。
  功能上不影响前端，但上线后监控探活会一直是红的。
  **这次的意外收获是暴露了测试的盲区**：原来的断言只检查「无 token 要被拒绝」，
  从没反过来问「该放行的放行了吗」——只测「该拒的拒了」不够。
  而且一旦引入白名单，就同时引入了「白名单被放得太大」的反向风险，两者必须成对断言。
  已补上双向断言（该放的放行 + 同前缀的受保护接口仍然拦得住）。

### 优化

- **防止用户名枚举**：即使账号不存在也照样做一次密码哈希比对，耗时一致，
  攻击者无法通过响应快慢判断某个用户名是否真实存在；密码错误统一提示「用户名或密码错误」。
- **生产环境不静默降级**：缺少 JWT 密钥或账号配置时直接启动失败，而不是悄悄用默认值把服务跑起来。
- **不让监控失效变成拒绝服务**：Redis 内存信息读不到时只告警、不阻断写入，
  业务按「没有历史」降级继续，不会因此报错。

### 验证

- 网关端到端冒烟 **25 项全绿**（含伪造 token、无 token 打流式接口、限流触发、白名单双向断言）。
- 浏览器实测全流程：登录 → 提问 → 退出 → 失效 token 自动登出 → 错误密码提示。
- 后端全量回归 **497 项全绿**。

## v2.0.0-p0.1 · 会话不再「重启即丢」

**这一版解决了什么问题**：v1.0.0 的会话历史、置顶、标题、用量全都存在**进程内存**里，
后端一重启就全没了；而且将来部署成多副本时，每个副本各存各的，
用户会感觉「聊着聊着模型失忆」。这一版把存储抽出来，可切换到 Redis。

### 新增

- **可插拔的存储抽象层**：把「会话怎么存」从业务逻辑里切出来，
  一行配置就能在「内存」和「Redis」之间切换（本地开发不必为了跑测试先装 Redis）。
- **Redis 存储实现**：会话用一个 Hash 存、另用一个有序集合维护索引，配一把分布式锁；
  锁的释放用 Lua 脚本保证「只释放自己加的锁」。
- **Redis 内存预警（重点新增）**：问题的背景是「数据量和访问量上来之后 Redis 会满」。
  做法是三级水位 + 自动止损：
  - 达到警戒 → 提示确认驱逐策略、缩短会话过期时间；
  - 达到严重 → 自动清理索引残留；
  - **达到致命 → 写入降级为只读保护**（宁可这一轮记不住对话，也不让整个问答返回 502），
    水位回落自动解除。
  - 每条预警都给**可直接执行的处置建议**，而不是只报一个百分比。
- **新接口 `GET /api/v1/system/memory`**：对外暴露存储后端、会话数、内存水位与建议，供监控抓取。
- **20 项新配置**：Redis 连接、锁参数、预警阈值全部可配。

### 修复

- **过期会话被「复活」**：会话过期时间在两处各存了一份，两处不一致导致已经过期的会话
  被读回来时又被当成新的存了一遍。已改为单一下传。
- **元数据与消息错位**：元数据是按轮记录的，但「没有元数据的那一轮」不占位，
  于是裁剪历史之后意图标注就整体错位了。已改为空占位保证一一对应。

### 优化

- **读操作不再隐式创建会话**：以前读取一个不存在的会话会凭空造出一条空会话，
  查询会话列表时越查越多。已改为「不存在就是不存在」。
- **翻会话列表不会让冷会话永生**：只有真正「续聊」才刷新过期时间，浏览列表不刷新。
- **业务侧零改动**：`rag_chain.py` 与问答接口一行都没改，这是抽象层设计到位的直接证据。
- **顺手解决「换后端 = 换了个 bug」的风险**：两个存储后端跑**同一套语义断言**，
  保证行为完全一致。

### 验证

- 新增 `module6`（107 项）：两个后端同套语义断言 + Redis 专有行为 + 内存预警分级与降级。
- 新增 `module7`（43 项）：**走真实 socket** 的联调。
  为什么单独做这个：`module6` 用的假 Redis 数据活在测试进程里，
  **永远验不出「进程重启后数据还在不在」**——而这恰恰是本次改造的全部目的。
  `module7` 起一个真实监听端口的服务，再用真实客户端连上去，
 于是能硬断言「换一个客户端（等价换一个进程）后，历史对话、置顶、标题、用量全都还在」。
- 既有测试回归 347 项全绿（含直接受影响的问答接口）。

## `v2.0.0-p2.15a` — Token 额度的聚合与口径

| | |
|---|---|
| **日期** | 2026-10-07 |
| **计划任务** | P2-15a（聚合与口径） |
| **性质** | 计划内 |

### 新增

- **按人 × 自然月的 token 用量统计**。这一版只做「算准」，界面与提醒在后续两版。
  为什么先算准：口径一旦定错，后面的看板、提醒、权限全要跟着改。
- **三类用量分开报** —— 读进去的（input）、写出来的（output）、命中服务商缓存的（cache_read）。
  第三类**不计入**总额：它的单价和前两类不同，混在一起算出来的「谁超了」是错的。
  而算错钱比算得粗严重：它会让「该找谁」这件事本身失真。
- **每个账号可以设置自己的月度额度**（数据库字段已就位，0 表示不限）。

### 口径上做的几个选择（都是「看起来小事、错了就全盘要改」的地方）

- **按消息记录统计，不按会话汇总**。会话被删时汇总数字会跟着消失，
  于是「他这个月用得少」——而消息记录是历史真相。
- **按「消息产生的时间」归月**，不是「会话创建的时间」。
  上个月开的会话、这个月聊了十次，那十次就属于这个月。
- **没设额度的人显示为「不限」，不是「用量 0%」**。这两件事不一样：
  一个是「不管他」，一个是「他一个都不能用」。
- **「查不到归属」的用量分两种数**（会话没主人 / 主人的账号已被删除）。
  库里有 6894 个 token 属于后者，是之前手工删测试账号留下的。
  把它单列出来，是为了**让漏算变得可见** —— 一个不允许被发现的漏算，
  比一个会报警的漏算危险得多，因为前者没有人会去查。

### 修复

- **🔴 用量统计里「命中缓存」那一项被按对话轮数放大了**。
  本轮写测试时用一条临时样本（3 条消息、缓存 777）量出 2331 —— 正好是 3 倍。
  原因：最初写法是「先按会话分组再关联进来」，看起来已经先聚合了，
  但**会话编号本身就是唯一键**，按它分组等于没分组，外层求和时仍然按消息条数累加。
  修法：先把消息按会话收敛成一行，再汇总。
- **「请求次数」一个字段两个口径**：汇总页按消息条数、单个会话页按问答次数，
  同一个字段名给出 3 和 2 两个值。已统一为**问答次数**（用户发一条算一次）。
- 修复单个会话用量的一个取数错误 —— 该路径此前从未真正跑通。

### 优化

- **本次的测试判据本身也修了一遍**。
  原先的反向验证写的是「改了函数值会不会变」，那只能证明「那行代码被执行了」，
  证明不了「那行代码被测试守着」。改成「拆掉防护 → 相关断言必须变红」，从 5 条扩到 9 条。
- 顺带改掉一条**站不住的技术注释**：原来说时间区间写法是为了「不漏掉微秒」，
  但实测本库所有时间列都是秒级精度，这个理由今天并不成立。已换成真正成立的理由。

### 验证

- 本模块测试 **64 项全通过**（含 9 条反向验证），连跑两遍结果一致。
- 账号、管理端权限、知识库写权限、审计四组既有测试全部通过（141 / 79 / 47 / 177项）。
- 数据库回到测试前的状态，临时样本**零残留**。
