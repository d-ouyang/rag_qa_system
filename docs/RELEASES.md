## v2.0.0-p0.4c · 刷新之后，每一轮的引用都还在

**这一版解决了什么问题**：一个很具体、也很影响信任感的毛病 ——

> 同一个对话里连着问几个问题，**只有第一个问题的回答带着引用资料**，
> 后面几轮的引用不见了；重新打开页面（刷新）之后尤其明显。

引用资料是这个系统最重要的东西：它告诉用户「这句回答是从哪份文档的哪一段来的」。
引用不见了，回答就退化成一句没有根据的话。

### 这个毛病为什么难查

它有三个特点，凑在一起非常容易误判：

1. **当场看是对的。** 提问的那一刻，引用直接跟着回答一起返回，一切正常。
   只有**刷新页面、重新加载历史**之后，引用才消失。
   —— 所以「点一下就好了」这种验证方式永远试不出来。
2. **只有第一个问题有引用**，看起来像「后面的问题没检索到」，
   很容易被当成检索或知识库的问题去查，而它其实是**记录引用时的位置错位**。
3. **只问一轮时完全正常。** 问题要连着问三轮以上才现形 ——
   而之前的测试基本都是「写一轮、读一轮」。

### 根因

每一次问答，系统都要记两样东西：对话内容，以及这一轮的引用资料。
两样都按「第几轮」对齐存放，取的时候按编号取。

问题出在记的顺序上：**本轮内容先写进去，然后才去补引用资料的空位** ——
于是每写一轮，就凭空多出一个空位，紧接着又被清理逻辑砍掉一个；
砍掉的恰恰是**最早那一轮的引用**。

净效果：每问一轮，就把最老一轮的引用挤掉。问到第三轮时，
第一轮和第二轮的引用已经蒸发，中间还留下空洞。

修法本身只有一行（调整记的顺序），难的是定位它。

### 修复

- **调整记录顺序**：先补齐历史，再写本轮 —— 引用资料与轮次严格一一对应。
- **补上能抓住它的测试**：刻意「连写三轮、中间一轮不带引用」，并逐条写死「第几轮应该有什么」。
  只断言「条数对不对」抓不住它 —— 条数在出错时反而是对的，错的只是内容。
- **反向验证过**：把这一行改回错误位置再跑一遍测试，14 条断言里 8 条立刻变红，
  证明这组断言真的守得住，不是摆设。
- **走真实接口验证了完整操作序列**：连问三轮 → 刷新 → 检查每一轮的引用。
  三轮各自拿回自己的引用（入职问题挂着入职文档的片段、离职问题挂着离职文档的片段，没有串台）。

### 顺带修掉的

- **单元测试不再连真实数据库**：有一组测试没指定存储后端，于是跟着配置走 ——
  配置改成用数据库后，这组「单元测试」就连上了真实业务库，
  既产生假失败，还差点把真实会话归档掉。已改为固定使用进程内存储。
  单元测试不该碰业务数据，也不该随配置漂移。

### 验证

- 回归测试（9 个模块，666 项）全绿；新增 14 条专门守这个不变量的断言。
- 端到端：连问三轮后刷新，每轮引用都在。

### 已知边界

- **修复只管之后新写的对话**。修复前已经错乱的历史对话不会自动纠正 ——
  这类数据属于可重建资产，不值得为它写一个一次性脚本（脚本本身会成为长期负担）。
  将来真要修，应该是一次性的数据订正，而不是在代码里加兼容分支。

## v2.0.0-p0.4b · 引用真的能点了

**这一版解决了什么问题**：上一版给每条引用发了一张身份证（编号），
数据、接口、清理能力都齐了 —— 但**界面上那条引用还是一段死文本**，
点它没有反应。用户看到的仍然只有 200 字摘要：想知道这句话在原文里是怎么说的、
前后文是什么、出自哪份文档，一概查不到。

一句话说就是：**能力已经在后端了，界面还没接上。**

这一版把它接上：**点引用 → 展开切片全文 + 源文档信息。**

### 新增

- **引用条变成可点的按钮**。点文件名展开，再点收起。
- **点开看到的是切片全文，不是那 200 字摘要**。摘要只是全文的开头一小段，
  而真正回答「这句话在原文里是怎么说的」的是全文。
- **同时告诉你它出自哪儿**：文件名、第几页、第几片、多少字、什么时候上传的 ——
  这些信息来自数据库里的文档记录，不是从文件路径猜出来的。
- **一次只展开一条**。引用条本身很窄，同时展开几条会把对话挤得读不下去。

### 修复

- **没有编号的引用不再假装可点**。有一批早期入库的切片压根没有编号，
  本来就查不到。以前它们和能查的引用长得一模一样，点了必然失败。
  现在它们渲染成普通文本，鼠标悬停会说明「这条引用没有可反查的编号」——
  **一个点了就报错的按钮，比没有按钮更让人恼火**。
- **展开过的不会再反复取**。包括「取失败」的结果也记下来：
  否则关掉再点开，会看到一次假的「正在取回…」然后又弹同一个错，像网络在抽风。

### 优化

- **后端说「查不到」时，界面显示的是后端那句原话**，前端不自己重写一遍。
  后端已经把情况分清楚了（「引用内容已随文档删除」是永久的、
  「引用片段已失效，请刷新后重试」是暂时的），前端重写一次就多一处对不上的风险。
- **正文还在、但数据库记录没了的情况下，照常显示正文**，只额外标一个「文档记录缺失」。
  内容确实还在，不该给用户报错 —— 那个标记是给运维看的：该跑一次重建了。
- **顺手消掉一处重复定义**：问答接口返回类型里把「引用长什么样」又抄了一遍，
  抄一份就多一处漂移点（后端加字段时只有一处会记得改）。改成共用同一份定义。

### 验证

- **浏览器端到端验收 18 项、0 失败，连跑两遍**：真实浏览器登录 → 真问一个问题
  （真检索 + 真重排 + 真大模型）→ 点引用 → 读展开出来的 DOM。
  它验的是接口测试看不见的东西：按钮到底能不能点、展开的是全文还是摘要、
  再点会不会收起、点开第二条时第一条有没有自动收起。
- **类型检查 + 生产构建 0 错误**：类型检查是开着严格模式跑的，
  这一条同时覆盖了「可能为 null 的字段没判空」这类问题。
- **后端全套测试没有重跑**：这一版**后端一行未改**，Python 侧不存在受影响的代码路径。
  上一版的 812 项基线不变 —— 「项数不变」本身就是「这次改动对后端零影响」的证据。

### 已知边界

- **刷新页面后同一条引用会重新取一次**。缓存挂在界面组件上，没做全局缓存：
  全局缓存要额外处理「文档被删了缓存要不要失效」，收益不抵复杂度。
- **没编号的老引用仍然点不开**，跑一次知识库重建之后它们就有编号了。
- **不做「打开源文档原文」**：前端没有 PDF/Word 的渲染能力；
  真要核对原件，走知识库页的「下载原文件」。

### 复盘 · 验收脚本差点又骗了我一次

这一轮第一版跑出来是 16 通过 / 1 失败，失败项是「文档已删除」那个分支。
查下来不是功能坏了，是**验收脚本自己挑错了对象**：它点的是一条**已经被展开过**的引用，
而展开过的结果已经进了缓存，再点不会发请求 —— 于是那个「假装接口返回 404」的桩
永远拦不到，那一组实际上是在验缓存，不是在验错误分支。

改法是显式挑一条没展开过的引用，并在代码注释里写明为什么。
**一个看起来在验 A、实际在验 B 的断言，比直接失败更危险** —— 它会一直绿着。

（另有一处小坑：验收脚本里侧边栏选择器写错了，表现是「登录失败」而不是
「找不到元素」，很容易往鉴权方向查。）

## v2.0.0-p0.4a · 引用有了身份证：点得开、溯得到源、删得干净

**这一版解决了什么问题**：系统回答问题时会在下面附几条「引用资料」。
但那些引用实际上是**死的**——它们只是 200 字的摘要片段，点不开、看不到完整原文，
也查不出它出自哪份文档的哪一页。更要命的是，向量库里那些片段只记了一个磁盘文件路径，
**没记它属于哪份文档、是第几片**。于是：

- 文档删掉之后，它留下的片段可能还躺在库里，**能被引擎检索到、却溯不回源**；
- 想按文档删除切片，只能拿文件路径去字符串匹配——文件一改名、一挪位置就对不上了；
- 历史回答里的引用，删档之后到底该显示什么，没有依据可判断。

一句话说就是：**引用只有样子，没有身份。**

这一版给每个切片发一张身份证，叫 `chunk_id`，长成 `284:7`（284 号文档的第 8 片）。
有了它，引用才第一次变成一条**可点击、可溯源、可清理**的数据。

### 新增

- **每条引用都能点开看全文**。新增反查接口：拿 `chunk_id` 就能取回这个切片的完整正文，
  以及它出自哪份文档、什么时候上传的、属于哪个项目 —— 文件信息来自数据库，不是猜的。
- **四种情况各说清楚，不再笼统报错**：

  | 点开一条引用时 | 系统怎么说 |
  |------|------|
  | 链接本身不合法 | 明确是请求的问题 |
  | 那份文档已经被删了 | 「引用内容已随文档删除」（这是预期内的终态） |
  | 文档还在、但这一片刚被重新解析过 | 「引用片段已失效，请刷新后重试」（暂时的，刷新就好） |
  | 正文还在、但数据库记录没了 | 照常显示正文，同时**如实标记「记录缺失」**——这是给运维的信号，不是给用户添堵 |

  把「永久失效」和「暂时不一致」分开说，是为了让用户知道**下一步该干什么**，而不是干瞪眼。
- **能查出并清理「无主切片」**。识别出两类：一类是早期写入、压根没记文档编号的；
  另一类是文档记录没了、片段却还在的。都能列出来、能清掉。
- **`make reindex` 知识库重建**：扫描已上传的文件重新灌一遍向量库。默认**只报告不动手**
  （先告诉你它打算做什么），确认后加 `--apply` 才执行；中途失败可以接着跑，不会把库清空了跑一半。

### 修复

- **引用键在接口里被静默丢掉了**（本版最贵的修复，实际改动只有一行）。
  现象是：后端日志里明明带着引用键，浏览器拿到的响应里却一个都没有，而且**不报任何错**。
  根因是接口层会按预先声明的字段清单过滤返回值，没声明的键直接丢弃。
  顺手加了一道通用守卫：以后再往引用里加字段却忘了登记，测试会立刻红——不管新字段叫什么。
- **跑一次回归测试会把真实文档记录抹掉**。这是测试脚本自己的毛病：
  它的清理动作写成了「清空整张表」，于是在开发机上跑一遍测试，知识库记录就没了，
  而切片还留在库里，变成一堆查得到正文、溯不到源的「幽灵引用」，且没有任何提示说是谁干的。
  已改成只清理测试自己创建的数据。

### 优化

- **老切片不用为了一个派生字段整库重建**。文档编号和序号都在，引用键可以在读取时现拼。
  代价是「为一个字段重灌整个库」这种不划算的事不用做了。
- **重建脚本自带两道闸门**：后台解析进程在跑、或者后端服务在跑，它都拒绝执行并说明原因。
  这不是保守——多个进程同时改写同一个向量库目录会让索引损坏，
  表现是问答接口直接报 500。**重建这种一次性动作，停服是值得的。**
- **重建可中断、可重跑**：不是「先清空再重灌」（那样中途失败就什么都没了），
  而是「补登记 → 逐份重灌 → 最后清无主切片」，最坏情况也只是多跑了一遍。

### 验证

- **新增 87 项离线测试、0 失败**：覆盖身份证的格式拼装与解析（含全角数字这类会让程序
  「校验通过但转换崩溃」的边界）、写入后自洽、无主切片识别与清理、引用键三级取值、
  历史引用的落库、反查接口的四种返回。
- **新增 41 项验收、一处不打桩**（真实数据库、真实向量库、真实检索），
  计划书 4 条标准逐条实测全部成立：删除文档后磁盘/向量库/数据库三处均无残留；
  点引用能拿到切片正文与源文档信息；重建后同一问题检索到的内容与重建前**逐字一致**；
  向量库里不存在缺文档编号的切片。
- **后端全套 812 项、0 失败**（上一版 725 项，本版新增 87 项，项数差正好等于新增测试）。
- **上一版的验收标准全部重跑，5 条依然成立**，与上一版基线一字不差。
- **真实浏览器链路留证**（三件套全部跑起来、全程走登录网关）：版本号、登录、问答（9.5 秒出答案）、
  引用带键、点开拿到 380 字全文并溯源到《离职流程与注意事项.pdf》、非法链接正确报错。

### 已知边界

- **界面上引用还是点不了**。这一版只做后端：数据、接口、清理能力都齐了，
  但页面上那条引用仍然只是一段文本。把它变成可点的按钮是下一版（`p0.4b`）的全部内容，
  交接物已经备好，不需要再回头改后端。
- **文档删掉之后，历史回答里那条引用的正文查不到**。这是刻意的选择：
  不保留引用内容的副本，换来的是**删得干净**——敏感文档不会以副本形式残留在历史记录里。
- **重建必须停服**（后台进程与后端服务都要停）。这是向量库的硬限制，不是脚本偷懒。

### 复盘 · 两个「测试全绿但功能其实是断的」

这一轮最有价值的东西不是加了什么，而是**两个差点带着上线的问题**，
它们的共同点是：测试全绿、日志正常、功能却是坏的。

第一个是上面「修复」里的引用键丢失。接口层按字段清单过滤返回值，
我加了字段却忘了登记，于是**后端有、接口没有**。单元测试测的是内部函数（有），
接口测试没覆盖这个字段（所以也没红）。教训是：断言不能只测「代码里产出了什么」，
要测「接口真的带出去了什么」——现在这条守卫是通用的，不绑定具体字段名。

第二个是测试脚本清空了真实数据表。它照抄了另一个测试模块的清理写法，
而那个写法是「清空整张表」。在开发机上这等于跑一次测试就删一次业务数据，
而且**没有任何报错**，只会表现为「引用突然溯不到源了」这种离真相很远的症状。
教训是：测试脚本的清理动作必须和它的创建动作**用同一把尺子**（同样的前缀），
三处清理口径一致才不会误伤。

## v2.0.0-p0.3b · 后台在做什么，页面上看得见

**这一版解决了什么问题**：上一版把上传改成了「提交立刻返回、解析交给后台慢慢做」。
这条路是对的，但它把一个问题推到了前台：**界面上看不出后台在干什么**。

上一版的界面还在问「这一次入库了多少片段」——而这个数字在提交那一刻根本不存在，
要等后台解析完才知道。于是上一版上线之后，知识库管理页实际上是**坏的**：
点了上传，页面不给任何反馈，用户不知道文件到底进去了没有，只能反复点、
或者关掉重试。**能力做对了，界面还在按旧节奏说话。**

这一版把界面接到新的节奏上，核心就一句话：**后台在做什么，页面上要看得见。**

### 新增

- **状态列：排队中 / 解析中 / 已完成 / 失败**。提交之后不用猜，看着它从「排队中」
  走到「解析中」再到「已完成」；一段时间没动静也不会误以为卡死——状态自己会更新。
- **完成时弹一次提示**，写明这份文档被切成了多少片段。片段数不是装饰：
  检索、引用、喂给模型的都是片段，不是原文档整体，所以这个数是用户判断
  「这份文档有没有被好好处理」的唯一依据。
- **失败可以一键重试**。以前失败就是失败，用户只能把文件删掉重传；
  现在失败那一行直接给一个「重试」按钮，点一下重新排队。
- **「解析进程是不是在跑」会显示出来**（重点新增）。这是异步化带来的新故障类型：
  后台那个常驻进程如果没启动，提交上去的任务会**静静地躺在队列里**，
  页面看起来就是「一直在转圈」，而且**转多久都不会好**。
  这一版会明确告诉用户「有几份文档在等待解析，但没有检测到解析进程在运行」，
  并给出该执行哪条命令 —— 这是用户唯一能自己修的一类故障，不告诉他等于让他干等。
- **可以下载原文件**。排查「我上传的到底是不是那份」时不用再去服务器上找。

### 修复

- **上传后不会再因为「没反应」而重复上传**。这是上一版最直接的副作用：
  用户点上传、页面没反馈，于是再点一次，于是又提交一份。
  这一版提交后立刻给一句「已提交，正在后台解析」，并且**刻意不说「成功」**——
  受理不等于完成，这时候说成功就是在骗人。

### 优化

- **轮询只在有必要的时候才转**。三道限制：全部文档都处理完了就不转；
  页面切到后台（切走标签页）就不转，切回来立刻补一次；请求连续失败就逐步拉长间隔
  （最多拉长到 30 秒一次）。一个不做限制的轮询器，就是一台持续消耗服务器的机器。
- **切走页面、关掉标签页，回来照样能看到结果**。这一点是刻意设计的：
  解析要几十秒甚至更久，用户在等的时候一定会去干别的。如果进度和完成提示
  「一离开页面就没了」，那用户就只能在知识库页干等——那等于没做成异步。
  做法是把「盯着进度」这件事放在页面之外的地方，而不是挂在某个具体的页面上。
  验收里专门验了这条：切到别的页面之后，完成提示照样弹出来。
- **失败原因整行展开，写成人话**。它要回答的是「我下一步该干什么」，
  所以必须完整可见、指明是哪个文件；塞进一个小格子里被截断，等于没给。
- **按钮置灰时必须说明原因**。比如「已成功解析的文档不支持重试」——
  置灰而不解释，用户只会以为页面坏了。
- **下载按钮带上了登录凭据**。下载链接如果直接点，浏览器不会带上登录信息，
  结果就是一个「未授权」的错误页；改成一键保存，并且文件名保持中文原样不乱码。

### 验证

- **浏览器端到端验收 56 项、0 失败，连跑两遍**。专门写了一个用真实浏览器跑的验收脚本：
  用真实账号登录 → 真实上传 → 等真实的后台进程解析 → 读页面上的状态与提示 → 真实下载 → 真实删除，
  全程零控制台报错。它验的是那些用接口测试**看不见**的东西：
  状态列到底有没有在动、按钮到底有没有灰、失败原因到底能不能读懂。
- **连跑两遍才算数**：第一遍 57 项里挂了 1 项、第二遍挂了 2 项，
  查下来都是**验收脚本自己的毛病**（一次是把两条一模一样的提示当成一条、少算了一次；
  一次是在片段还没加载完就去数，结果数到 0 —— 而第一遍那次「通过」其实是在赌时间）。
  修完连续两轮全绿。**同一次绿不算数**，这是这一轮最有价值的教训。
- **上一版的验收标准全部重跑一遍，5 条依然成立**：50MB 上传响应立即返回（实测 0.60 秒）、
  关掉浏览器任务照常跑完、同一任务入队两次不会产生重复内容、损坏文件标记失败且原因可读、
  杀掉后台进程再重启任务继续被消费。
- **后端全套 725 项、0 失败，项数与上一版一字不差**。本轮是纯界面改造，
  没加任何后端测试，也不该改变任何既有行为——「项数不变且全绿」本身就是
  「这次改动对后端零影响」的证据。

### 已知边界

- **提示条会盖住页面顶部的一段说明文字**。同时出现两三条提示时比较明显。
  之所以这一版没动它：这个提示条是所有页面共用的，改位置会影响问答页和设置页的观感，
  超出了这次「把知识库页接上后台节奏」的范围。已截图留证，留作一次独立的界面打磨。
  （顺带说明：这一版之前这里最多同时出现一条提示，所以看不太出来。）
- **侧边栏的「片段总数」里含一批旧数据**。知识库列表为空时它显示 15，
  那是早期（切片还没带文档编号时）写入的遗留内容，列表里看不到、也管不了。
  这不是本版的缺陷，而正是**下一步要做的「知识库重建」**要清理的对象。

### 复盘 · 一次「假通过」的验收

这一版一共在验收脚本上栽了两次。第二次特别值得记：

| | |
|---|---|
| **发现方式** | 第一次跑全绿了。为了确认不是运气，又跑了一遍 —— 第二遍挂了 2 项。 |
| **现象** | 「抽屉里列出了片段」数到 **0 个**。但同一个断言第一次跑是**通过**的。 |
| **关键判断** | 不是渲染坏了，是**数得太早**：抽屉打开时会异步去取片段，那一刻列表还是空的。第一遍恰好在数据回来之后才数，所以通过了。 |

| **教训** | **一次通过不算通过。** 一个在赌时间的断言，跑十次会绿九次，然后把一个真问题盖住。所以这一版的验收结论是「连跑两遍」，而不是「跑过了」。 |

## v2.0.0-p0.3a · 上传大文件不再「转圈等到超时」

**这一版解决了什么问题**：在这之前，用户点「上传」之后，浏览器要**一直等到文档解析完**才能收到响应。
解析包括读取文件、切分、把每一段转成向量、写进向量库 —— 一本几十 MB 的 PDF 要几十秒甚至几分钟。

这段时间里发生的事很难看：浏览器等不及会超时，用户以为上传失败于是再传一次（于是又挂一次），
而服务器那边其实一直在干活。更糟的是**换个页面、关掉浏览器，这次上传就白做了** ——
因为「正在解析」这个状态只存在于那个请求里。

这一版把上传拆成两步：**浏览器只负责把文件交出去，解析交给一个常驻的后台进程慢慢做**。
上传接口在一秒内返回，用户提交完就可以关掉页面；下次打开，页面从数据库读到的就是最新的处理进度。

### 新增

- **上传秒回**：上传接口不再等解析，收到文件就返回「已受理」。
  实测 50MB 文件与 1KB 文件的响应耗时几乎一样（0.575 秒 vs 0.495 秒）——
  这说明耗时只取决于往硬盘写文件，和文件内容、大小基本无关。
- **解析交给独立后台进程**：不再是「在上传请求里顺手做」，而是有一个常驻工作进程专门消费待解析的任务。
  这么做不只是为了快：解析要加载模型、吃 CPU 和内存，跟网站进程放在一起会把网站一起拖慢；
  分开之后，两台角色可以按各自需要分配资源。
- **关掉浏览器，任务照常跑完**：提交后关掉页面，解析继续；重新打开时状态从数据库读回来。
  实测就是这样做的：提交 → 断开连接 → 三秒后重新连上读状态，显示已完成、切片数正确。
- **一次提交只会被解析一次**：即使同一条任务被投递两次（用户连点、队列重投），
  也只会有一个进程真正抢到它。实测推两条消息，最终只解析了一次、切片数与单次完全一致。
- **失败原因写成人话**：上传损坏的文件不再是一个沉默的失败。数据库里会记一句
  「解析失败或没有可提取文本（文件可能已损坏）：报销单.docx」——
  **指明是哪个文件**、没有一行看不懂的报错堆栈，用户可以据此重新上传或用「重解析」按钮再试一次。
- **多了一个「队列体检」接口**：能一眼看到「还有几个任务在排队」「工作进程活着没有」「待解析/解析中/成功/失败各几个」。
  工作进程没启动时它也不会报错，而是如实显示「没有进程应答」。
- **50MB 上限与超限提示**：超过 50MB 的文件直接被挡回并说明上限，不会先写盘再失败。

### 修复

- **工作进程被强制杀掉后，任务永远卡住的问题**：这是异步化必然带来的新问题 ——
  进程被杀的那一刻，文档状态停在「解析中」，而「解析中」既不是「待解析」也不是「失败」，
  于是**没有人会再去捡起它**，表现是「一篇文档永远在转圈，点多少次重试都不动」。
  这一版给文档加了一个「本次解析开始时间」字段：解析中但开始时间已经过去太久的，视为上一次的残留，
  允许重新被抢走。判定依据是**数据本身**，不是「某个进程什么时候启动的」——
  后者在多进程场景下会误伤正在干活的进程。
- **被拒绝的路径不再有可乘之机**：下载接口按编号取文件，所以文件路径全部由数据库记录推导。
  这一版把路径校验写得更严：先把 `..` 这类相对路径**展开**再判断，
  而不是比较字符串开头 —— 比较字符串开头的话，`upload/../../某个系统文件` 是能蒙过去的。

### 优化

- **删文档变成「一次都不能少的三件事」**：硬盘上的原文件、向量库里的所有切片、数据库里的记录。
  顺序也是刻意定的：**先删可以重新生成的（切片、文件），最后删那条「指向它们」的记录**。
  反过来的话，中途失败就再也没有东西能告诉我们「该清哪些切片」，库里会留下永远查不到也删不掉的残留。
- **切片的写入顺序改成「先解析、后删、再写」**：直觉上「先删旧的再解析」更整齐，
  但那样一个大文件会造成几分钟的空档 —— 这段时间里这篇文档检索不到、引用也查不到正文。
  改到解析之后删，空档缩短到毫秒级；附带好处是解析失败时**旧切片原封不动**，
  文档仍然可被检索到，而不是「越重试越查不到」。
- **「重解析」这个动作被收紧了**：已经解析成功的文档不允许重解析（会明确拒绝并说明原因），
  必须先删除再重新上传。否则「重解析」的含义就模糊了：是删掉旧的重新生成，还是在旧的上面再叠一份？
- **依赖锁定只增不改**：加一个新库时，锁定文件里应当**只多出这个库和它自己的依赖**。
  这一版做到了 —— 没有出现任何与本次改动无关的版本漂移。这件事听起来像常识，
  但工具默认会把整个依赖图重新解一遍，需要显式地让它复用已有的锁定结果。

### 验证

- **按计划书的 5 条验收标准逐条实测，全部成立**：专门写了一个「一处都不打桩」的验收脚本 ——
  真的数据库、真的队列、真的工作进程、真的向量库，全部走接口。结果：

  | # | 验收标准 | 结果 |
  |---|---|---|
  | 1 | 上传 50MB 文件，响应立即返回 | 成立（实测 0.57 秒） |
  | 2 | 提交后关闭浏览器，任务照常跑完，重开页面状态正确 | 成立 |
  | 3 | 同一文档入队两次，向量库不出现重复切片 | 成立（5 片，与单次解析一致） |
  | 4 | 上传损坏文件 → 标记失败 + 原因可读、可重试 | 成立 |
  | 5 | 手动杀掉工作进程后重启，待解析任务继续被消费 | 成立 |

- **新增 166 项回归测试**，全部通过；全套测试从 559 项增加到 **725 项**，0 失败。
  新增部分覆盖：状态流转、**16 个线程同时抢同一条任务只能有一个成功**、
  被杀残留任务的回收边界、重复解析的幂等、入队失败时的降级、7 个接口的形状、
  以及用真实工作进程跑一次端到端。
- **问答链路一行未改**：异步化只影响「文档入库」这条支路，检索、重排、大模型回答完全没碰。
- **数据库结构变更与查询用的定义零分叉**：迁移脚本和查询用的表定义由一条自动断言盯着，
  本次加了新字段之后该断言仍然全绿。

### 复盘 · 一个把验收写假的断言

| | |
|---|---|
| 发现方式 | 验收脚本第一轮跑出 2 项失败，都在第 3 条。 |
| 现象 | 我原本的写法是「对一份已经解析成功的文档再投两次消息」，期望看到「只解析一次」。但断言先红了：`重置为 pending` 这一步返回失败。 |
| 关键判断 | 一看设计就明白了 —— 这一版刻意**不允许重解析已成功的文档**（见「优化」第三条）。于是那两条消息**都被状态机挡掉了**，「没有重复切片」是因为**压根没跑**，什么也证明不了。 |
| 处理 | 换一份**全新**的文档，在后台进程抢到它之前连推两条消息，并补一条关键断言：`attempt_count == 1`（只有一条真的抢到）。这样「没重复」才是**证出来**的，而不是碰巧。 |
| 教训 | 断言要能**失败**才有意义。一个「无论对错都会通过」的断言，等于给缺陷盖章。这和第 5 条里不用 `/etc/passwd` 当越权靶子是同一个道理 —— 那边也是要求靶子能被验证，而不是断一个恒为真的条件。 |

**这一版解决了什么问题**：在这之前，要让项目跑起来，得先在电脑上单独装好数据库和缓存两个服务，
再手工调字符集、时区、内存上限；换一台机器就要重来一遍，而且很容易漏掉某一项而查不出原因。
这一版把它们装进容器：一条命令起停，参数全部写死在配置文件里，
并且增加了「一条命令做 14 项体检」的自检脚本。

### 新增

- **一条命令起停的两个基础服务**：数据库（MySQL）与缓存（Redis）改用容器运行，
  起来、看日志、停掉、彻底移除各对应一条命令。容器只是**运行方式**，
  里面的数据存在容器之外的独立空间里 —— 所以删掉容器重建，数据依然在。
- **端口只对本机开放**：两个服务的端口只绑定本机地址，同一网络下的其他机器连不上。
  开发机经常连公司网或公共 Wi-Fi，这个默认值比顺手写一个「对所有地址开放」安全得多。
- **启动自检脚本（14 项）**：一条命令检查服务是否健康、账号能不能连上、
  中文和 emoji 会不会存坏、时间会不会差 8 小时、缓存的内存上限是否真的生效、
  本机端口是否通。以前这些要挨个手动验，且「验过没有」无法追溯。
- **建表权限的提前检查**：自检里会真的建一张临时表再删掉。
  下一步要用迁移工具创建业务表，如果账号只有读写权限没有建表权限，
  到那时才会卡住 —— 而那时代码已经写了一堆。提前 3 行 SQL 就能避免。

### 修复

- **（环境问题）镜像下载不下来**：本机网络下 Docker 官方镜像仓库不可达，
  容器因此一直起不来。排查确认**不是代理故障** —— 代理正常工作、能访问其他站点 ——
  而是那个仓库地址在当前网络下被阻断。改用国内加速源解决。完整排查过程见下方复盘。

### 优化

- **中文与时区一次性配好**：字符集、排序规则、时区都写在服务的启动参数里，每次启动都生效。
  特意**不**写在「只在第一次启动时执行的初始化脚本」里 —— 那种脚本改了不会重跑，
  很容易出现「配置里明明写了、实际没生效」这种最难查的状态。
- **缓存写满时宁可报错，也不悄悄丢数据**：缓存在本项目里还承担着「排队等处理的任务」的角色。
  如果内存满了就自动删掉最旧的内容，被删的可能正是排队中的任务，
  而且事后查不到任何痕迹。改成直接报错后，问题会当场暴露、可以重试。
- **数据库账号不用最高权限账号**：应用使用单独的低权限账号，最高权限账号只用于容器初始化。

### 验证

- 自检脚本 **14 项全绿**。
- **决定性验证：把容器整个删掉再重建，数据库与缓存里的数据都还在。**
  （验证方式特意用「删除 + 重建」而不是「重启」——重启只是重启进程，证明不了数据存在容器之外的独立空间里。）
- 应用配置未受影响：新增的配置项被安全忽略，业务代码**一行未改**。

### 复盘 · 半小时的「下载卡死」其实是两个假象

| | |
|---|---|
| 现象 | 执行启动命令后，镜像一直下载不动，界面上只有计时器在走，看不到任何进度。 |
| 第一个假象 | 查到系统代理指向本机一个端口，而查监听状态的工具显示那个端口**没有**在监听，于是判断「代理挂了」。实际上那个端口是通的 —— 只是在这种受限环境里，工具看不到其他程序的监听状态。换成直接连一下，真相立刻出来。 |
| 第二个假象 | 命令的输出在**非交互终端**下会被缓冲 —— 它可能正在正常下载，只是不往外打印。中途因此两次误判为卡死，把进程杀掉重来，白白浪费时间。 |
| 真正的根因 | 分段测试后确认：代理没问题，能正常访问其他站点；问题出在 Docker 官方镜像仓库的地址在当前网络下被阻断，**无论走不走代理都不通**。给 Docker 配上国内加速源即解决。 |
| 教训 | 判断「是不是卡住了」不能看界面输出安静不安静，要看**实际产生的数据量或落盘日志**。另外，这个环境里用 `lsof` 这类工具查监听端口会给出假阴性，要换直连测试来确认。 |

## v2.0.0-p0.1b · 让问答记录真正「存得住、查得到」

**这一版解决了什么问题**：上一轮把「会话与问答记录」存进了缓存服务，这次推翻重做。
原因不复杂 —— 缓存服务为了速度把数据放在内存里，重启、内存吃紧、容量保护都可能让它
悄悄消失；而聊天记录是**用户随时会回来翻**的东西，丢了就是事故，且找不回来。
更要紧的是，存进缓存之后这些记录**没法用 SQL 查**：按用户查、按时间统计、用量对账、
抽查回答质量，全都没有落脚点。

这一版把它们搬进了关系型数据库（MySQL），并立下一条项目级规矩：
**「真相」只能存在数据库里；缓存服务只负责「丢了能重来」的东西**（比如排队等解析的文档）。

### 新增

- **问答历史真正持久化**：消息正文、每一轮的引用资料、置顶、自定义标题、token 用量，
  全部落到数据库的表里。重启服务，甚至停掉隔天再开，历史一条不丢。
- **数据可以「直接查」了**：所有记录都在结构化的表里，一条 SQL 就能按会话、按时间、
  按用量做统计。这是这一版最实在的收益 —— 以前这些数据只能通过程序接口一条条读出来。
- **表结构变更有了正规流程**：引入迁移工具，每次改动都留下一个可追溯、可回退的版本记录。
  以后给表加字段，不会再出现「开发机能跑、线上库缺列」的问题。
- **新增 5 条数据库操作命令**：升级结构、查看当前版本、回退一版、新增一版，
  以及「只打印 SQL 不执行」（给需要走审批的场合用）。

### 修复

- **配置写错不再「悄悄降级」**：上一版如果配置里写了已废弃的存储类型，程序会安静地
  退回内存模式，日志里只留一行警告 —— 生产上这等于**悄悄把持久化关掉了**，
  重启就丢光数据，而且往往要等到用户投诉才发现。
  现在这种情况会**直接启动失败并说明原因**。启动失败五分钟就发现了；静默丢数据找不回来。

### 优化

- **同一会话的并发提问不会互相覆盖**：多个标签页同时对着一个会话提问时，
  靠数据库的行级锁保证「读—改—写」串行。实测 12 路并发，一轮对话都不丢。
- **过期会话只隐藏、不销毁**：闲置太久会被判定为过期（从列表里消失），
  但记录**仍然留在库里**。这类永久资产不该被一个过期计时器抹掉 ——
  真正的清理策略会另行设计。
- **一次问答的所有写库动作在一个事务里完成**：不会出现「消息写进去了、
  引用资料没写进去」这种半截状态。
- **表定义与迁移脚本分开维护，并用一条自动断言盯着它们别分叉**：
  迁移脚本是「历史快照」，写下去就不再改（否则在新代码下重放旧迁移会出错）；
  查询用的定义是「当前结构」，随业务演进。两者的分歧由测试断言兜住，而不是靠人盯。

### 验证

- **测试从 497 项增加到 559 项，全部通过**。新增的 62 项专门针对数据库存储：
  表结构一致性、真的按行落库、重启后数据仍在、并发不丢轮次、过期与归档行为、
  删除不留残留数据。
- **「业务代码一行未改」再次得到验证**：这已经是第二次更换存储后端
  （内存 → 缓存 → 数据库），三次都只改存储层，问答链路、接口、路由一行没动。
  这正是当初决定「把存储抽象出来」的目的。
- **两个后端行为逐字段一致**：同一串操作分别在内存版和数据库版各跑一遍，
  结果（消息、引用资料、置顶标题、用量、会话列表）完全相同 ——
  这条断言的意义是保证「换后端」不等于「换了个 bug」。
- **数据库不可用时整模块跳过而不是误报失败**，并在输出里给出明确的排查提示。

### 复盘 · 顺带发现的一个既有缺陷

| | |
|---|---|
| 发现方式 | 为新存储写「两个后端结果必须一致」的对照断言时，对照断言直接红了。 |
| 现象 | 连续 3 轮问答，第 1 轮的「引用资料」会串到后面去，且末尾多出一个空位 —— 每轮整体错位一格。 |
| 关键判断 | 立刻改用**内存版**跑同样的操作 → **一模一样**。说明这不是新写的存储层引入的，而是上一版就已经存在的缺陷。 |
| 为什么之前没被发现 | 断言只查「元数据条数对不对」（条数确实是对的），没人查「第 N 轮的元数据是不是第 N 轮的」。 |
| 处理 | **本次刻意不修**。本轮验收红线之一是「问答逻辑代码一行未改」，修它就把这条证据毁掉了。已记录在案并给出修法（把补位调用挪到新消息入队**之前**即可），留作下一次独立迭代。 |
| 教训 | 「条数对」不等于「内容对」。断言必须断言到**语义**，否则只是在给缺陷盖章。 |

## v2.0.0-p0.2 · 给系统装上一道门

**这一版解决了什么问题**：v1.0.0 上线即裸奔——任何人都能上传文档、提问，直接消耗大模型额度。
这一版在业务后端前面加了一个独立的鉴权网关，所有请求必须先登录才放行。

### 新增

- **独立鉴权网关**（NestJS，`:3000`）：JWT 登录、全局默认拒绝的守卫、按用户限流（防止别人白嫖
  大模型额度）、请求白名单机制。
- **请求转发**：网关校验通过后把请求转给后端。**关键要求是流式输出不能被破坏**——
  问答接口是逐字返回的，中间多一层缓冲就会把「打字机效果」变成「等 30 秒一次性吐出来」。
- **统一错误格式**：无论鉴权失败、请求过频、参数不合法还是后端不可达，前端拿到的错误结构都一致，
  不必写四套解析。
- **身份透传**：网关验完 token 后把用户身份放进请求头传给后端，**后端一行代码没改**，不用自己解析 JWT。
- **前端登录页与登录态联动**：token 失效自动回登录页；主动/被动登出都会清空本地会话数据
  （不清的话下一个登录的人会看到上一个人的聊天记录）。
- **网关自身探活接口**（免登录），用于监控判断「网关进程是否活着」——它有意识地和「后端是否活着」分开，
  否则后端挂掉会把网关一起判死。

### 修复

- **★ 一个 POST 请求就能把整个网关进程打挂。** 最严重的一个 bug，值得完整记一笔：
  为了让被框架提前消费掉的请求体能重新转发，用了官方的 `fixRequestBody`。
  但它内部会**结束掉请求**——此后任何「往请求上加一个头」的操作都会抛异常。
  真正致命的是：这个异常发生在一个事件回调里，**没有任何地方捕获它**，
  于是整个 Node 进程直接退出。症状极具迷惑性——只要有人提交一次表单，网关就凭空消失，
  而日志里只有一行看不出严重性的提示。

  修法是两层的：先调整语句顺序（所有加头的操作都提到结束请求之前），
  再给回调整体加上异常捕获，最后在进程级也加一道兜底。
  **这个 bug 的教训是：异常发生在回调里时，「有没有人捕获」比「异常本身」更要命。**
- **参数校验提示答非所问**：漏填密码时提示的是「密码不能超过 128 个字符」——
  框架遍历校验规则的顺序不确定，取到了最后一条。改为优先取「不能为空」这类更贴切的提示。
- **限流提示透出英文类名**：只显示 `ThrottlerException: Too Many Requests`，用户看不懂，
  已换成中文文案。
- **前端登出提示语病**：出现过「登录状态已失效（登录状态无效，请重新登录），请重新登录」
  这种同义反复嵌套，已收口成两种固定文案。
- **（修订）漏放行两个上游健康检查**：计划书明确要求放行，首轮实现只放了登录和网关自身探活。
  功能上不影响前端，但上线后监控探活会一直是红的。
  **这次的意外收获是暴露了测试的盲区**：原来的断言只检查「无 token 要被拒绝」，
  从没反过来问「该放行的放行了吗」——只测「该拒的拒了」不够。
  而且一旦引入白名单，就同时引入了「白名单被放得太大」的反向风险，两者必须成对断言。
  已补上双向断言（该放的放行 + 同前缀的受保护接口仍然拦得住）。

### 优化

- **防止用户名枚举**：即使账号不存在也照样做一次密码哈希比对，耗时一致，
  攻击者无法通过响应快慢判断某个用户名是否真实存在；密码错误统一提示「用户名或密码错误」。
- **生产环境不静默降级**：缺少 JWT 密钥或账号配置时直接启动失败，而不是悄悄用默认值把服务跑起来。
- **不让监控失效变成拒绝服务**：Redis 内存信息读不到时只告警、不阻断写入，
  业务按「没有历史」降级继续，不会因此报错。

### 验证

- 网关端到端冒烟 **25 项全绿**（含伪造 token、无 token 打流式接口、限流触发、白名单双向断言）。
- 浏览器实测全流程：登录 → 提问 → 退出 → 失效 token 自动登出 → 错误密码提示。
- 后端全量回归 **497 项全绿**。

## v2.0.0-p0.1 · 会话不再「重启即丢」

**这一版解决了什么问题**：v1.0.0 的会话历史、置顶、标题、用量全都存在**进程内存**里，
后端一重启就全没了；而且将来部署成多副本时，每个副本各存各的，
用户会感觉「聊着聊着模型失忆」。这一版把存储抽出来，可切换到 Redis。

### 新增

- **可插拔的存储抽象层**：把「会话怎么存」从业务逻辑里切出来，
  一行配置就能在「内存」和「Redis」之间切换（本地开发不必为了跑测试先装 Redis）。
- **Redis 存储实现**：会话用一个 Hash 存、另用一个有序集合维护索引，配一把分布式锁；
  锁的释放用 Lua 脚本保证「只释放自己加的锁」。
- **Redis 内存预警（重点新增）**：问题的背景是「数据量和访问量上来之后 Redis 会满」。
  做法是三级水位 + 自动止损：
  - 达到警戒 → 提示确认驱逐策略、缩短会话过期时间；
  - 达到严重 → 自动清理索引残留；
  - **达到致命 → 写入降级为只读保护**（宁可这一轮记不住对话，也不让整个问答返回 502），
    水位回落自动解除。
  - 每条预警都给**可直接执行的处置建议**，而不是只报一个百分比。
- **新接口 `GET /api/v1/system/memory`**：对外暴露存储后端、会话数、内存水位与建议，供监控抓取。
- **20 项新配置**：Redis 连接、锁参数、预警阈值全部可配。

### 修复

- **过期会话被「复活」**：会话过期时间在两处各存了一份，两处不一致导致已经过期的会话
  被读回来时又被当成新的存了一遍。已改为单一下传。
- **元数据与消息错位**：元数据是按轮记录的，但「没有元数据的那一轮」不占位，
  于是裁剪历史之后意图标注就整体错位了。已改为空占位保证一一对应。

### 优化

- **读操作不再隐式创建会话**：以前读取一个不存在的会话会凭空造出一条空会话，
  查询会话列表时越查越多。已改为「不存在就是不存在」。
- **翻会话列表不会让冷会话永生**：只有真正「续聊」才刷新过期时间，浏览列表不刷新。
- **业务侧零改动**：`rag_chain.py` 与问答接口一行都没改，这是抽象层设计到位的直接证据。
- **顺手解决「换后端 = 换了个 bug」的风险**：两个存储后端跑**同一套语义断言**，
  保证行为完全一致。

### 验证

- 新增 `module6`（107 项）：两个后端同套语义断言 + Redis 专有行为 + 内存预警分级与降级。
- 新增 `module7`（43 项）：**走真实 socket** 的联调。
  为什么单独做这个：`module6` 用的假 Redis 数据活在测试进程里，
  **永远验不出「进程重启后数据还在不在」**——而这恰恰是本次改造的全部目的。
  `module7` 起一个真实监听端口的服务，再用真实客户端连上去，
 于是能硬断言「换一个客户端（等价换一个进程）后，历史对话、置顶、标题、用量全都还在」。
- 既有测试回归 347 项全绿（含直接受影响的问答接口）。
