# RAG 智能问答系统：性能优化与工程实践总结

> 项目：企业知识库 RAG 问答系统（Chroma/FAISS + bge-m3 嵌入 + CrossEncoder 重排 + Qwen 生成 + Vue3 前端）
> 技术栈：Python / FastAPI / LangChain(LCEL) / Vue3 + TS + Pinia / siliconflow OpenAI 兼容网关 / Ollama 本地小模型
> 统计口径：全部数字来自本机实测（同一场景、同一知识库、改造前后各跑一遍基准），非估算。

---

## 一、端到端效果：优化前后量化对比

### 1.1 响应耗时（端到端，同场景基准）

| 场景 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 首轮 RAG 问答（无历史重写） | 9.9 s | **1.2 s** | **8.3×** |
| 多轮 RAG 问答（含问题重写） | 19.6 s | **2.1 s** | **9.3×** |
| 闲聊（不检索） | 12.0 s | **0.9 s** | **13.3×** |
| 用户可感知「首字出现」时间 | 47.6 s | **2.6 s** | **18.3×** |
| 单轮气泡空窗（无正文） | 70.5 s | ≈ 0（思考占位） | 消除 |

### 1.2 链路分节点耗时（优化后稳态，3 次采样中位数）

| 节点 | 耗时 | 说明 |
|---|---|---|
| 意图识别（Ollama qwen2.5:3b） | **85 ms** | 冷启动首次 1865 ms，之后稳态 |
| 向量检索 + CrossEncoder 重排 | **407 ms** | 首次含 reranker 懒加载 2966 ms |
| 问题重写（有历史时） | **308 ms** | 无历史时跳过 |
| LLM 生成（Qwen2.5-7B，136 字） | **1879 ms** | 剩余耗时几乎全在这里 |

- 优化前串行合计：**7000 ms**
- 优化后并行前段（意图 ∥ 检索 ∥ 重写，取最慢者）+ 生成：**4845 ms**
- 并行化净省：**2156 ms（前段耗时下降 31%）**

### 1.3 成本与吞吐

| 指标 | 优化后实测 |
|---|---|
| 单轮 token 消耗 | 输入 865 / 输出 71（≈936 tok） |
| 缓存命中 | 实测 `cache_read_tokens = 32`（网关侧自动 prompt 缓存生效） |
| 回归测试 | module4 **85/85**、module5 **44/44** 全通过 |
| 知识库规模（基准场景） | 单文档 3 片段，重排 top1 得分 0.486~0.708 |

## 二、有害节点定位与清除

> 定义：**有害节点** = 链路中既吃掉性能、又啃食正确性的环节。分两类——
> **性能型**（串行等待 / 空转 / 参数误配）与**正确性型**（丢字段 / 幻觉 / 展示截断 / 状态未持久化）。

### 2.1 性能型有害节点

#### 有害节点 ①：模型 thinking 模式在流式链路里空转

- **症状**：用户提问后气泡长时间只有光标闪烁，实测 **70.5 s 无正文**；RAG 单轮端到端 93 s。
- **根因**：硅基流动 `Qwen3-8B` 默认开启思维链，思考 token 走 `reasoning_content` 通道，**不进入 `content` 流**；后端 `if chunk:` 过滤后前端长时间收不到任何帧。
- **参数形态坑**：只有**顶层** `enable_thinking: false` 被网关识别；vLLM 风格的 `chat_template_kwargs.enable_thinking` 会被静默忽略（思考照常，排障时极易误判"改了没生效"）。
- **修复**：`settings.SILICONFLOW_ENABLE_THINKING=False` + 经 `extra_body` 下发；并把该参数**条件化为仅 qwen3 系列模型名才传**（非混合模型收到未知参数可能直接 400）。
- **量化结果**：闲聊 50.3 s → **4.2 s**，RAG 93 s → **4.8 s**；首字 47.6 s → **2.6 s**。
- **同族问题**：Ollama `qwen3.5:9b` 默认开 thinking，流式返回 99% 是空 chunk；`ChatOllama(reasoning=False)` 后 **27.4 s → 3.9 s（7×）**。

#### 有害节点 ②：意图识别 / 问题重写 / 向量检索三者串行

- **症状**：每次提问固定多等 2~5 s，与生成无关，纯等待浪费。
- **根因**：三者互不依赖却按顺序执行（意图 85 ms ∥ 检索 407 ms ∥ 重写 308 ms）。
- **修复**：`ThreadPoolExecutor(max_workers=4)` 并行前段 —— 意图识别 ∥ **投机检索**（先用原问题检索）∥ 问题重写。
  - 投机命中规则：首轮无重写必中；多轮时若重写结果与原问题一致直接复用投机结果，只有重写真正改写了问题才重新检索。
  - chitchat 路由时丢弃投机结果（本地检索成本可忽略）。
- **量化结果**：前段 7000 ms → 4845 ms（**省 2156 ms / 31%**）；端到端首轮 9.9 → 1.2 s。

#### 有害节点 ③：模型选型不当（混合思考模型做流式问答）

- **修复**：`.env` 由 `Qwen/Qwen3-8B` 换为 **`Qwen/Qwen2.5-7B-Instruct`**（无思考模式、生成更快），并条件化 thinking 参数。
- **量化结果**：`done` 时间从 10~20 s 降到 **1~2 s**，是端到端提速的最大单项贡献者。
- **排障要点**：`.env` 不被 `uvicorn --reload` 监听，改完必须重启进程才生效。

### 2.2 正确性型有害节点

#### 有害节点 ④：流式链路丢 token 用量（`StrOutputParser` 拍扁 chunk）

- **症状**：流式接口拿不到 `usage`，无法做 token 统计与缓存命中分析。
- **根因**：`prompt | llm | StrOutputParser()` 会把 `AIMessageChunk` 拍扁成字符串，`usage_metadata` 随之丢失。
- **修复**：`ChatOpenAI(stream_usage=True)`（末帧带 usage）+ 生成路径绕开 `StrOutputParser`，直接 `llm.stream(PromptValue)` 取文本与用量。
- **量化结果**：流式用量打通，实测单轮 865/71 tok、缓存命中 32 tok 可见，并逐轮累加进会话。

#### 有害节点 ⑤：零召回时模型编造答案

- **症状**：空库 + "数据统计"指令下，模型编造 **"5.2 亿元"** 这类数字。
- **修复**：**零召回短路** —— 检测 `docs` 为空则不进 LLM，直接返回固定拒答；同步链路与流式链路同口径。
- **量化结果**：从"编造具体数值"变为"干净拒答且 `sources=[]`"。

#### 有害节点 ⑥：无关文档混入上下文（重排阈值未启用）

- **症状**：幻觉问句召回报销文档（重排分 **0.000296**，相关文档 0.99），模型正确拒答但前端仍显示"引用资料 1 条" —— 答案与引用自相矛盾。
- **修复**：启用 `RERANK_SCORE_THRESHOLD = 0.1`（retriever 本已支持 `score_threshold`，只是没启用）。
- **量化结果**：无关引用 **1 条 → 0 条**，拒答与引用状态一致。

#### 有害节点 ⑦：问题重写模型违规直接作答

- **症状**：重写模型输出"根据公司规定，员工每年享有 10 天带薪年假。"（知识库根本没有年假政策，纯幻觉），该句既污染 `standalone_question` 又被拿去检索。
- **修复**：`_sanitize_rewrite` 消毒 —— 空/超长/含拒答话术 → 回退原问题；新增**陈述句形态判定**（含 。/！且不以 ？结尾即判为作答）。并补 warning 日志。
- **量化结果**：消毒触发后 `standalone_question` 回退为原问题，`sources=0`，干净拒答。

#### 有害节点 ⑧：每轮详情未持久化（刷新丢引用）

- **症状**：刷新页面后，助手回答的引用资料、token、耗时全部丢失。
- **根因**：`MemoryManager` 只存纯文本消息，`GET /sessions/{id}` 只返回 `role + content`；`sources / intent / usage / elapsed_ms / ts` 压根没落库。
- **修复**：`_exchange_meta[session_id]` 按轮存展示元数据（第 k 轮 ↔ 消息索引 2k / 2k+1），`add_exchange(meta=...)` 随轮写入，历史接口按轮回填到该轮 assistant 消息；`trim` / `truncate` 时元数据与消息同构裁剪（**奇数条向下取偶**，保证轮边界不错位）。
- **量化结果**：实测刷新后「引用资料 2 条」、`usage`、`elapsed_ms`、`ts` 原样恢复。

#### 有害节点 ⑨：UI 展示截断造成"引用与回答对不上"的假象

- **症状**：模型回答婚假/产假完全正确，但引用 snippet 显示的却是病假条款，看起来像召回了错文档。
- **根因**：`test.docx` 只切成 **3 个片段**，婚假产假条款在**片段 3 的中后段**；而 UI 的 snippet 只截取片段**前 200 字**（开头恰是病假工资条款）。**不是召回错，是展示截断。**
- **修复**：新增 `GET /api/v1/documents/chunks?source=`（片段全文/字数/页码）+ 知识库管理页「片段」抽屉，逐片段展示完整内容。
- **量化结果**：排查"模型到底看到了什么"从猜变成可直接验证；同类误判归零。

#### 有害节点 ⑩：前端响应式失效（空气泡）

- **症状**：`meta` / `done` 帧正常，气泡始终空白。
- **根因**：`messages.value.push(rawObj)` 后在 NDJSON 回调里直接改 `rawObj.content`，依赖追踪收不到通知，子组件永不重渲。
- **修复**：从 reactive 数组里取出**代理对象**再做增量更新；`http.ts` 回调异常必须 `console.error` 而非静默吞掉。

## 三、工程化能力补齐（可观测性与交互）

| 能力 | 实现要点 | 对外价值 |
|---|---|---|
| Token 全链路统计 | `stream_usage=True` + 绕开 `StrOutputParser`；`input_token_details.cache_read` 取缓存命中；按 session 累加（随清空/过期回收） | 成本可观测、可归因 |
| 每轮详情展示 | 每条回答尾部「Tokens: N」「耗时: N s」徽章 + hover 明细浮层（输入 / 缓存命中 / 缓存未命中 / 输出 / 命中率双色条） | 对齐 CodeBuddy 体验，成本下钻到每一轮 |
| 会话管理 | PATCH 重命名/置顶（后端持久化）、置顶分组、hover「⋯」下拉菜单 | 刷新不丢，交互对齐 WorkBuddy |
| 编辑重发 | `POST /sessions/{id}/truncate{keep_messages}` 截断 → 改写 → 重问；截断点自动对齐轮边界 | 语义等价于 WorkBuddy「从此处重新开始」 |
| 会话记忆 | 按 session_id 隔离 + 窗口裁剪（max_turns=10）+ TTL 惰性过期 + 每会话一把锁 | 隐私隔离、防 OOM、并发不串线 |
| 意图路由 | 七类意图（6 类知识型 + 闲聊）；小模型分类 + **打分制规则兜底**（命中词数×100 + 类别优先级）解决关键词冲突 | 闲聊免检索省成本，意图驱动回答模板 |

## 四、简历 / 面试可直接陈述的点

1. **主导企业级 RAG 问答系统全链路性能优化，端到端响应从 9.9 s 降至 1.2 s（8.3×），多轮场景 19.6 s → 2.1 s（9.3×）；用户可感知首字延迟 47.6 s → 2.6 s（18×）。**
2. **定位并清除"思维链空转"这一隐蔽瓶颈**：识别到 thinking token 走独立通道导致流式前端 70 s 空白；同时发现厂商参数形态差异（顶层 `enable_thinking` vs `chat_template_kwargs`），把参数下发条件化，规避非混合模型 400 风险。
3. **设计并行化前段管线**：意图识别 ∥ 投机检索 ∥ 问题重写三路并行 + 投机结果复用判定，前段耗时下降 **31%**，且保证改写命中时结果不劣化。
4. **构建三层防幻觉护栏**：零召回短路、重排分数阈值（0.1）、重写结果形态消毒（陈述句判定），分别消灭"编造数值""无关引用混入""重写幻觉污染检索"三类故障，均有实测复现与修复前后对比。
5. **打通流式 token 与缓存命中统计**：绕开 `StrOutputParser` 丢弃 `usage_metadata` 的陷阱，实现会话级/轮次级用量归因与缓存命中率可视化。
6. **修复引用溯源"看起来出错"的展示缺陷**：通过片段级详情能力定位到是 snippet 截断而非召回错误，并据此把每轮 `sources/usage/耗时/时间戳` 完整持久化，解决刷新丢引用的问题。
7. **工程质量**：module4 85/85、module5 44/44 回归全通过；链路分层（接口层薄、业务在 core）保证换协议时 core 零改动。

## 五、方法论沉淀（可展开的面试问答）

- **怎么定位性能瓶颈？** 先分节点打点（意图 / 检索 / 重写 / 生成），再算串行合计与并行上界的差值，只优化净收益为正的节点；模型类问题优先用 curl 直连网关验证参数是否真的生效，避免"改了没生效"的误判。
- **并行化会不会牺牲效果？** 投机检索只在"重写结果与原问题一致"时复用；一旦改写真正改变了查询语义，就丢弃投机结果重新检索，保证检索输入与最终语义一致。
- **防幻觉为什么做三层？** 三层对应三个不同的失效面：无依据时禁言（短路）、弱相关时过滤（阈值）、上游污染时消毒（重写形态判定）。单点护栏拦不住组合失效。
- **内存态会话的边界？** 按 session_id 隔离 + 窗口裁剪 + TTL 回收，元数据与消息同生命周期；接口不变，量大了换 Redis 即可（本系统的 `MemoryManager` 已按此边界设计）。
