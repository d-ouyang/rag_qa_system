# 上线部署踩坑总表（上线前必读）

> **用法**：每次上线前从上到下过一遍，尤其是 §1（什么才算部署成功）、§2（镜像内容）、§3（配置）、§4（数据）。
> **更新纪律**：踩到新坑就追加到**对应章节的表格**里，同类型合并进同一张表，不要按时间新开流水章节；
> 每条都要写清「现象 / 根因 / 处置 / 是否根治」，「已根治」要注明版本号，否则下次还会踩。
> 最近更新：2026-11-05（v4.0.0-p4.15e）。

## 0. 部署形态速览

```
push origin main
   └─ GitHub Actions「Deploy to server」(self-hosted runner, 42.192.111.82)
        └─ cd /opt/qa && git fetch && git reset --hard origin/main && git clean -fd
             └─ bash scripts/deploy.sh
                  ① 拉代码 ② 起 mysql/redis/chroma ③-④ build 三个镜像
                  ⑤ alembic upgrade head ⑥ up -d ⑦ 健康检查
                  ⑧（可选）灌种子 ⑨ 构建 admin-console 静态产物 → /var/www/admin
```

服务七个：`rag-backend / rag-worker / rag-gateway / rag-frontend / rag-mysql / rag-redis / rag-chroma`。
管理端是**独立静态站**（`admin.nianan.site`），不在 docker 镜像体系里。

## 1. 「部署成功」的判定（最容易误判的一类）

| # | 现象 | 根因 | 处置 | 状态 |
|---|---|---|---|---|
| 1.1 | 站点 200、页面能打开，但功能还是旧的 | build 失败的中间态：`git reset` 已把代码换成新的，容器没重建 → **代码新、镜像旧** | 只看 CI run 的 `conclusion`，再看 `/api/v1/system/health` 的 version 是否等于目标版本；两者都过才算成功 | 流程性，永久适用 |
| 1.2 | 打了 tag、push 了，CI 一直 `queued` 不跑 | self-hosted runner 服务静默挂了（日志 `A session for this runner already exists`）。历史事故：office 项目因此连续多次 tag 没部署 | `sudo systemctl start actions.runner.<repo>...service`，确认日志出现 `Listening for Jobs`；**打 tag ≠ 部署成功** | 流程性，永久适用 |
| 1.3 | 只想发个文档，结果把未完成的代码发上线了 | 触发条件是 push main（早期配置里 tag 也触发） | 未完成的功能别进 main；文档类提交只推 develop | 流程性 |
| 1.4 | 部署过程中改服务器文件，最后被覆盖/冲突 | `deploy.sh` 会 `git reset --hard` + `git clean -fd` | build 期间只读不写；要改配置等部署完再改 | 流程性 |
| 1.5 | 部署耗时远超预期 | backend 镜像 `pip install` 为主，冷构建 6–10 分钟 | 别在 build 期间反复重试或手动重建 | 流程性 |

## 2. 构建与镜像内容（最隐蔽的一类：代码发了，数据和静态资源没发）

| # | 现象 | 根因 | 处置 | 状态 |
|---|---|---|---|---|
| 2.1 | build 卡 1000+ 秒后失败 `ReadTimeoutError` | `Dockerfile` 里 `pip install uv` 那行没配镜像源，走官方 PyPI，云上到 files.pythonhosted.org 偶发读超时 | 已给 uv 本体安装补 `--index-url` 腾讯镜像 + tuna fallback | ✅ p4.13b |
| 2.2 | QA 直击在生产**永远不命中**，但代码、开关都对 | `.dockerignore` 里有一行 `data`，把整个 `data/` 排除 → `data/qa/kb_qa_set.jsonl`（48 条离线策划问答）从没进过镜像 | 改成 `data/*` + `!data/qa`。**注意语义**：`.dockerignore` 里父目录被整体排除后，子目录用 `!` 是拉不回来的，必须先把父目录写成 `data/*` | ✅ p4.15d |
| 2.3 | 管理端没更新，但主站更新了 | admin-console 是 deploy.sh ⑨ 单独构建的静态产物，失败**不阻塞**主服务（脚本里是 best-effort） | 部署后单独看这一段日志 + 打开 `admin.nianan.site` 核对标题/版本；必要时在服务器手动 `cd admin-console && npm run build` | 流程性 |
| 2.4 | 改了 `.env` 但行为没变 | `docker compose restart` **不重读** env 文件，也不会换镜像 | 必须 `docker compose up -d --no-deps <service>`（会重建容器） | 流程性 |
| 2.5 | 新加的依赖/脚本在容器里找不到 | 只 build 了部分服务，或文件被 `.dockerignore` 排除 | 部署后进容器 `ls` 一眼（如 `wc -l /app/data/qa/kb_qa_set.jsonl`） | 流程性 |

## 3. 配置（本地有、线上没有，或反过来）

| # | 现象 | 根因 | 处置 | 状态 |
|---|---|---|---|---|
| 3.1 | UI/health 显示的版本号长期是旧的 | `.env` 被 gitignore，`git reset` 带不过去；服务器 `.env` 里写死了 `PROJECT_VERSION` | 版本真相源移到入库的 `config/version.py`；服务器 `.env` **删掉** `PROJECT_VERSION` 一行 | ✅ p4.1 |
| 3.2 | 本地 PDF 解析有表格结构，线上没有（PDF 片数也不一样） | 生产 `.env` 一条 `MINERU_*` 都没有 → 静默退回 PyMuPDF | 同步 7 个键（ENABLED/API_KEY/API_BASE/MAX_BYTES/MODEL_VERSION/POLL_*）+ 重建容器；启动日志确认「MinerU PDF 结构化解析已启用」 | ✅ p4.15d |
| 3.3 | 功能「代码在、开关也在」，但线上就是不生效 | 开关缺省 fail-closed（`QA_DIRECT_HIT=false`），线上没人打开过 | 部署后用能力矩阵逐项验（见 §6.6），不要看代码猜 | ✅ p4.15d |
| 3.4 | 改了 `.env` 阈值，行为没变 | DB `system_config` 优先级高于 env（如 `rerank_score_threshold=0.1`） | 排查时两边都查：`select * from system_config` + `.env` | 流程性 |
| 3.5 | 本地脚本报 `SettingsError: ALLOWED_ORIGINS` | shell 里 `source .env` 后再跑 Python，pydantic 拿到的是裸字符串而非 JSON 列表 | 脚本别 `source .env`；需要单个值时用 `grep` 取一行传给环境变量 | 流程性 |
| 3.6 | 生产 `.env` 里没有 `CHUNK_MODE` 就以为没配置 | 该键缺省即 `fixed`（settings 默认值） | 核对默认值，别凭「有没有写」判断 | 流程性 |

## 4. 数据与知识库（破坏性最强的一类）

> 前置原则：**切分规则一变（loader / CHUNK_MODE / 表格切分），线上必须整库重建**；增量灌新文档会导致新旧切片语义混在一起。
> 重建流程与逐条验证见 `docs/线上部署-知识库重建清单.md`。

| # | 现象 | 根因 | 处置 | 状态 |
|---|---|---|---|---|
| 4.1 | 备份没了 | `deploy.sh` 的 `git clean -fd` 会删 `/opt/qa` 下所有未入 git、也没被 `.gitignore` 排除的文件 —— 实测把放在 `/opt/qa/backups/` 的备份整目录删掉 | **备份放仓库目录外**：`/opt/qa-backups/<日期>/` | 流程性（已写进清单） |
| 4.2 | 重建跑了一小时零写入、CPU≈0 | `.md` 走 `UnstructuredMarkdownLoader`，缺 NLTK `punkt_tab` 时**联网下载** raw.githubusercontent.com；服务器连得上但不回，且无超时 → 阻塞在 `read()` | 临时：容器 `/etc/hosts` 把该域名指 127.0.0.1；根治：`.md` 改直读文本（p4.15c）。排查手法见 §6.3 | ✅ p4.15c |
| 4.3 | 修了 prompt 但线上答案没变 | 旧答案还在 QA 缓存里（同问题直接命中） | 部署后清 `rag:qa_cache:*`（重建脚本会按 KB 版本清，但纯 prompt 改动不会） | 流程性 |
| 4.4 | 清完会话，用户本月的额度显示变了 | quota 从 `chat_message` 明细实时算 | 清会话前想清楚：等同重置本月用量；或先导出明细 | 流程性 |
| 4.5 | 重建与 worker 抢同一批 doc_id，切片翻倍 | worker 在跑时重建 = 两个进程交错写 | 先 `docker compose stop worker`；后端是否要停取决于 Chroma 形态（server 模式可不停） | ✅ 脚本内置拦截 |
| 4.6 | 重建后旧会话的引用点开是**别的内容** | 重建只保证 doc_id 不变，chunk_index 会重排；旧 `ref_ids` 指向了不同正文 | 重建后清 `qa_trace / chat_message / session`（用户已同意可抛弃旧会话） | 流程性 |
| 4.7 | 想开 title 切分，结果检索明显变差 | title 把 500 字一片拆成 200–350 字四五片，top_k=5 下证据被切散（实测 recall@5 0.909→0.817，2 题退化成零召回） | **维持 `CHUNK_MODE=fixed`**；要再试先做「短节贪心打包」再评测，见 p4.15 迭代文档 §附 | ✅ p4.15b 结论 |
| 4.8 | 用 `reset_kb.py --apply` 把原件删了 | 该脚本默认会删 `upload/`，而 `upload/` 是唯一重建源 | 生产禁用或加 `--no-upload`；重建只清 Chroma 的 `rag_qa_knowledge` collection | 流程性 |
| 4.9 | MinerU key 到期后 PDF 静默降级 | key 过期只打 WARNING，不报错 | 记录到期日（当前 2026-12-02），到期前续；部署后看启动日志有无 MinerU 行 | 待办 |

## 6. 验证与排障手法（把"猜"换成"看"）

| # | 场景 | 手法 |
|---|---|---|
| 6.1 | 端到端验证需要真实账号 | `POST /api/auth/login`（返回字段是 `access_token`）→ 带 `Authorization: Bearer` 调业务接口。**登录限流 8 次/分钟**，探接口时极易 429，串行 + 间隔 |
| 6.2 | 想绕过登录直接调后端 | 后端在 gateway 模式下要求**网关 HMAC 证明**，只带 `INTERNAL_SHARED_SECRET` 是 401；验证一律走公开登录链路，不要伪造凭证 |
| 6.3 | 进程"卡住"（无输出、CPU 接近 0） | `sudo strace -p <pid> -f -e trace=network,read,write -tt` 看阻塞在哪个 fd；再 `sudo ls -l /proc/<pid>/fd` 看那个 fd 指向什么文件/socket。p4.15c 的 NLTK 卡死就是这么定位的（fd 指向 `punkt_tab.zip.tmp`） |
| 6.4 | 长任务跑一半 SSH 断了 | 服务器端 `nohup bash /tmp/x.sh > /tmp/x.log 2>&1 &` 记 pid，本地只轮询日志；不要在前台挂着 ssh |
| 6.5 | `pkill -f <脚本名>` 把自己的命令也杀了 | 你自己的 ssh 命令行里含同样字符串 → `pkill -f` 命中自身，输出突然消失 | 用 pid 杀，或加 `-o`/排除自身 |
| 6.6 | 「部署成功」后确认能力真的上线 | 按 `线上部署-知识库重建清单.md` §3.5 **能力矩阵**逐项验（md/xlsx/PDF-MinerU/docx 各抽一片看内容特征、QA 直击试着命中、各格式抽 1 题检索）。2026-11-05 就是靠这一条发现「48 条 QA 没进镜像」 |
| 6.7 | 判断某条慢是谁慢 | 回答的 `timings`（prepare/generate/grounded）+ `llm_timeout_ms`；`eval_stats.py` 聚合看趋势 |

## 7. 回滚

1. **代码**：`git revert` 或重新部署上一个 tag（部署=push main）。
2. **数据**：`/opt/qa-backups/<日期>/` 下有 `mysql-rag_qa.sql.gz`、`upload.tar.gz`、`chroma_data.tar.gz`、`env.bak`；按「停服务 → 恢复三个目录/库 → 起服务 → 清 qa 缓存 → 健康检查」顺序。
3. **只改配置**（如 `CHUNK_MODE`）：等于没回滚——切分/embedding 已经变了，**必须再整库重建一次**。

## 8. 一句话清单（贴在部署前看）

- [ ] 目标 main 的 CI run 是 success，站点 version 等于目标版本
- [ ] `.dockerignore` 没有把该发的数据排除（`data/qa`、`admin-console/dist` 等）
- [ ] 线上 `.env` 有本地新增的全部能力开关（尤其 `MINERU_*`、`QA_DIRECT_HIT`、`CHUNK_MODE`）
- [ ] 改过 env → 用 `up -d --no-deps` 重建容器，不是 `restart`
- [ ] 备份在 `/opt/qa-backups/`（**不在** `/opt/qa`）
- [ ] 重建前停 worker；重建后清 QA 缓存
- [ ] 按能力矩阵逐项用真实数据验，不看开关看行为
