## 0. 结论先行

### 0.1 先回答你问的两件事

**Q1：现在的用户数据库有多少字段？**

`user` 表**目前只有 6 个字段**，而且**一个都没在用**：

| 字段 | 类型 | 现状 |
|---|---|---|
| `id` | BIGINT 自增 | 建了表，无数据 |
| `username` | VARCHAR(64) 唯一 | 建了表，无数据 |
| `display_name` | VARCHAR(128) | 建了表，无数据 |
| `password_hash` | VARCHAR(255) | 建了表，无数据 |
| `is_active` | BOOL | 建了表，无数据 |
| `create_time` | DATETIME | 建了表，无数据 |

表注释就是这么写的：`用户表（本期未启用，见 PLAN-v2.0.0 §11 D2）`。

**现在真正管登录的是 `.env` 里的 `GATEWAY_USERS`**（格式 `用户名:bcrypt哈希,用户名:哈希`）。
你说的 `admin/admin123` 是**开发兜底**：没配 `GATEWAY_USERS` 且非生产环境时，网关用内置账号
`admin/admin123` 并在启动日志里 warn；**生产环境缺这个变量会直接启动失败**。
也就是说：现在的「用户系统」= 一个环境变量 + 一张没人读的空表。

**Q2：员工的密码一般怎么保存？**

一句话：**单向哈希，不可逆，绝不明文**。

| 做法 | 结论 | 说明 |
|---|---|---|
| bcrypt（`$2b$` 前缀） | ✅ **本项目沿用** | 网关已经在用 `bcryptjs`，逻辑现成；salt 自动内嵌在哈希串里（不用单独存 salt 列），cost 建议从 10 提到 12（约 250ms，登录可接受，暴力破解成本 ×4） |
| argon2id | ✅ 更优（可选） | 抗 GPU 更强，OWASP 首选；但 Node 侧要引原生模块（`argon2`），Docker 构建要编解码器。**不建议本期换**，收益不抵构建复杂度 |
| SHA-256 / MD5 / SHA-1 | ❌ 禁止 | 太快，GPU 每秒可算几十亿次；不加盐还会被彩虹表秒破 |
| AES 可逆加密 | ❌ 禁止 | 能加密就能解密，密钥一泄露全公司口令泄露；而且「能找回密码」本身就是个反需求 |
| 明文 | ❌ 禁止 | — |

所以密码相关要存的是**四件东西**，不是一件：

1. `password_hash` —— bcrypt 哈希（唯一的口令落点）
2. `password_changed_at` —— 上次改密时间（算到期）
3. `must_change_password` —— 标记「管理员重置过，必须先改」（改用完清零）
4. `user_password_history` —— 最近 N 个历史哈希，用来**禁止复用**（否则「到期 → 改回原密码」等于没改）

配套两条准则（企业系统的实施惯例，也决定了接口形状）：

- **管理员看不到、也设不了别人的密码**，只能「重置为一次性临时密码 + 强制首次登录改密」。
  所以接口里**不该存在**「查看密码」「直接设置某个人的密码」这两个动作。
- **密码到期是 pull 模型**：登录时算 `now - password_changed_at > PASSWORD_EXPIRE_DAYS`。
  本项目没有邮件/短信通道，做 push 就得先建通道 —— 不划算。到期前 N 天在前端提示、到期后
  除改密接口外一律 403，这才叫「强制」。**只提醒不拦 = 没做**。

### 0.2 体检：现在的「多用户」到底缺什么

这是本节最重要的一条，也是你需求里最容易漏掉的一条：

> **登录已经能分人了，但数据完全不隔离。**

具体到代码：

| 环节 | 现状 | 后果 |
|---|---|---|
| 网关签发 JWT | payload = `{sub: username, username}` | 只有登录名，没有用户 id、没有角色 |
| 网关转发时注入身份 | ✅ **已经注入了** `X-User-Id` / `X-Username` 两个请求头 | 身份送到了后端门口 |
| 后端读身份 | ❌ **全仓库没有任何 Python 代码读这两个头** | 后端根本不知道是谁在请求 |
| `session.user_id` | 列存在，**从不写入** | 所有会话不属于任何人 |
| `GET /api/v1/qa/sessions` | 不带任何过滤，返回**全部**会话 | 张三能看见李四的会话与历史 |
| 文档 / 检索 | `document.project_id` 固定 `default`，检索不带 project 过滤 | 所有人共享同一个知识库，跨部门内容互相可见 |

**结论**：如果只做「多个账号能登录」而不做查询侧过滤，那就是**假隔离** ——
比不做更危险，因为它看起来像做完了。所以本设计把「账号」与「隔离」拆成两个独立任务
（P2-11 / P2-12），且**明确标注 P2-11 完成后仍处于「谁都能看到全部数据」的中间态**。

| 8 | （未提） | **改密/停用后旧 token 仍在 12h 内有效** | 加 `token_version` 进 JWT，改密/停用就 +1，校验不过即失效。成本很低，不做则「停用了人还能用半天」 |
| 9 | 管理端「开一个前端界面」 | **管理端不要再起一个常驻后端进程** | 4C4G 很紧（见 PLAN §11.1）。管理端 = 静态前端（Vite/nginx）+ 复用现有 FastAPI 的 `/api/v1/admin/*` 接口 |

| 11 | 你问「隔离校验能否都放网关」 | **身份与粗粒度授权放网关，数据范围过滤必须留后端** | 隔离判据（归属关系）在数据库里；列表类要解析响应体、检索类要下推 `where`、流式响应无解。详见 §5.1。**另外实测到网关只覆写不剥离入站身份头，白名单路径可伪造身份** —— 这是 P2-12b 必须先修的一条 |

## 1. 目标与范围

**目标**：把「一个 `admin` 账号 + 一个公共知识库」变成「可模拟真实企业的多用户系统」：
人事可分部门/职位地建员工，员工各看各的（或各看本部门的），管理员能在独立的管理端做增删改查与密码管理。

**本期做**：

- 组织模型：部门（树）、职位（含职级）、用户
- 账号真相源迁到 MySQL，网关查库校验
- 密码策略：bcrypt + 到期 + 历史不可复用 + 强制改密 + 失败锁定
- 模拟员工种子数据（可反复重放）
- 全链路数据隔离：会话按人、知识库按部门/项目、检索侧过滤、切片反查鉴权
- **知识库写权限分发**：上传 / 删除 / 重灌索引按 `project` 授权，重灌只给超管（P2-14）
- 独立管理端服务（员工 CRUD / 密码管理 / 审计日志查看）

**本期明确不做**：

- 自主注册、找回密码（无邮件通道）
- 单点登录 / 企业微信钉钉对接
- 细粒度按钮级权限 —— 系统角色只到 `admin / hr / user` 三档；
  **知识库写权限不靠加全局角色解决，而是按 `project` 授**（见 §8 D13）
- 文档上传 UI 迁移到管理端（只做归属与权限维度预留）
- 多租户的物理隔离（同一个 MySQL / Chroma，靠逻辑隔离）

## 2. 领域模型

```
department（部门，自关联树）
   └── position（职位：名称 + 职级）        ← 部门下有哪些岗位
user（员工）
   ├── department_id → department
   ├── position_id   → position            ← 组织信息
   ├── role                                ← 系统权限（与上面两者正交）
   └── status（active/disabled/resigned）  ← 离职用停用，不删行

project（知识库 / 隔离单元）
   ├── owner_dept_id → department          ← 部门共享库
   └── owner_user_id → user（可选）        ← 个人库
user_project（授权表：谁对这个库能读 / 能写）
   ├── role ∈ {owner, writer, reader}      ← **项目内角色**（第 4 版新增）
   └── 跨部门借用也走这张表，复用同一个字段
```

**三个关键裁决**：

1. **`role` 与 `position/level` 正交**。`role` 只有三档：
   `admin`（管人、管密码、管知识库归属）/ `hr`（管人事资料，不能重置密码）/
   `user`（普通员工）。职位是 P6 高级工程师还是 P7 专家，**不自动决定**系统权限。
2. **隔离单元是 `project`，不是 `user`**。会话是个人私有（`session.user_id`），
   知识库是组织共享（`document.project_id`）。这样才像真实企业；
   如果做成「人人一个私有库」，部门内的知识就无法共享，等于退化成个人网盘。
3. **写权限按 `project` 授，不靠加全局角色**（第 4 版新增，D13）。
   「他只能维护锅圈知识库、不能动别的库」这句话，用全局 `role` 表达不了 ——
   一加 `kb_admin` 就变成「要么全公司都能改，要么只有超管能改」。
   所以写权限落在 `user_project.role`：`owner` / `writer` 可写，`reader` 只读，
   全局 `admin` 例外（可写所有库）；**重灌索引（`reindex`）只给全局 `admin`**，
   因为改切分参数 = 整库重建。

## 3. 表设计

### 3.1 `user`（改造现有 6 字段表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 不变 |
| `username` | VARCHAR(64) UK | 登录名。**建议等于工号**（企业习惯），但保留独立列以便以后改 |
| `employee_no` | VARCHAR(32) UK | 工号。唯一、不随人变；与 `username` 分开是因为「登录名可以改，工号不能改」 |
| `display_name` | VARCHAR(128) | 姓名 |
| `email` | VARCHAR(128) UK | 公司邮箱。可作唯一标识，也留作将来找回密码的通道 |
| `phone` | VARCHAR(20) | 手机号。**属个人信息**，展示时脱敏（`138****8000`） |
| `gender` | VARCHAR(8) | 可选，仅展示，不参与任何逻辑 |
| `department_id` | BIGINT | → `department.id` |
| `position_id` | BIGINT | → `position.id`（职级挂在职位上，见 §3.2） |
| `role` | VARCHAR(16) | `admin` / `hr` / `user`，默认 `user` |
| `status` | VARCHAR(16) | `active` / `disabled` / `resigned`，默认 `active`。**只有 active 能登录** |
| `password_hash` | VARCHAR(255) | bcrypt 串；**绝不放明文** |
| `password_changed_at` | DATETIME(6) | 算到期用。微秒精度理由同 `session.last_active_at` |
| `must_change_password` | BOOL | 管理员重置后置 1；用户改完清 0 |
| `token_version` | INT | 改密/停用/改角色时 +1；JWT 里带上，不匹配即失效 |
| `failed_login_count` | INT | 连续失败次数 |
| `locked_until` | DATETIME(6) | 锁定到什么时候（连续失败 N 次锁 M 分钟） |
| `last_login_at` | DATETIME(6) | 最后一次登录 |
| `created_by` / `updated_by` | BIGINT | 谁的这次人事操作，留痕 |
| `create_time` / `update_time` | DATETIME | 不变 / 新增 |
| `deleted_at` | DATETIME(6) NULL | 软删除；面试题：**默认不删行**，离职走 `status=resigned` |

> ⚠️ **不要**把 `is_active` 换成 `status` 时丢掉旧列兼容：迁移里用 `ADD COLUMN` + 数据回填，
> 不 `DROP` 旧列（老迁移要能在新代码下原样重放）。

**索引**：`uk_username` / `uk_employee_no` / `uk_email` / `idx_user_dept(dept_id, status)` / `idx_user_role(role)`。

### 3.2 `department` / `position`

- `department`：`id` / `code` UK / `name` / `parent_id` / `leader_user_id` / `sort_order` / `create_time`。
  用 `parent_id` 自关联表达「中心 → 部门 → 组」，**不建闭包表**（规模到不了那个量级）。
- `position`：`id` / `code` UK / `name` / `level`（如 `P6`）/ `sequence`（技术/管理/职能）/ `create_time`。
  **职级放这里而不是放 user**：同岗位的人职级一般一致，改一次动一处。

### 3.3 `project`（知识库，隔离单元）

`id` / `code` UK / `name` / `owner_dept_id` / `owner_user_id`（可空，个人库） / `create_time`。

现有 `document.project_id` 是字符串（默认 `default`），本期改为指向 `project.id` 的强关联，
并做一次数据迁移：把现存文档全部挂到一个 `default`（全员可见）的 project 上，**保证已有知识库不丢**。

**`user_project`（第 4 版新增，写权限的落点）**：
`id` / `user_id` / `project_id` / `role`（`owner` / `writer` / `reader`）/ `granted_by` / `create_time`，
唯一键 `uk_user_project(user_id, project_id)`。

三条规则：

1. **无记录 = 只读**（默认拒绝）。不给 reader 显式建行，想给谁的库读权限就建一行 —— 让表里只有例外；
2. 部门共享库的初始 `writer` 是 `department.leader_user_id`（部门负责人）；
3. 全局 `admin` 对任何 project 都可写，**不落表**（否则每建一个库都要给超管补一行）。

### 3.4 `user_password_history`

`id` / `user_id` / `password_hash` / `changed_at`。保留最近 5 条（配置化）。
改密时校验新密码不得与历史 5 条命中（`bcrypt.compare` 逐条比，5 次约 1.2s，可接受；若嫌慢可把上限降到 3）。

### 3.5 `audit_log`

`id` / `actor_user_id` / `action`（`user.create` / `user.disable` / `password.reset` / `login.fail` …） /
`target_type` / `target_id` / `detail` JSON / `ip` / `create_time`。
只追加，不更新不删除；管理端提供只读查询。

## 4. 密码策略（细节口径）

| 项 | 取值 | 说明 |
|---|---|---|
| 哈希算法 | bcrypt，cost **12** | 与网关一致；老 cost 10 哈希首次登录成功后**顺带重算**升级（渐进迁移，不强制全员改密） |
| 最小长度 | 10 | 长度比复杂度更有效；同时要求**不能全数字 / 不能与用户名或工号相同** |
| 复杂度 | 至少 2 类字符 | 不要强制「大写+数字+符号全满足」，那会逼出 `Abc123!@#` 这类模式化口令 |
| 有效期 | `PASSWORD_EXPIRE_DAYS`，默认 **90**（演示可设 30） | 到期判据：`now - password_changed_at > 天数` |
| 到期提醒 | 剩余 ≤ 7 天，登录后前端横幅提示 | 复用 `/me` 接口返回 `password_expire_in_days` |
| 到期强制 | 除「改密」与「登出」外一律 403 | 网关/后端统一拦截，别只在后端拦（前端绕过就没了） |
| 历史不可复用 | 最近 5 条 | — |
| 失败锁定 | 连续 5 次失败锁 15 分钟 | 锁定响应与密码错误**同文案**，不泄露「这个账号存在」 |
| 重置密码 | 管理员生成一次性临时密码 + `must_change_password=1` | 临时密码强度仍要够，且**只在创建/重置的响应里显示一次** |
| 改密后 | `token_version += 1` | 其他设备的旧 token 立即失效 |

## 5. 数据隔离

### 5.1 分层边界：网关做什么、后端做什么（D12）

> 这一节回答「能不能把隔离校验放到 NestJS 网关层直接拦截」。
> **结论：身份与粗粒度授权放网关（应该放），数据范围过滤必须留后端（放不了）。**
> 这个划分不是折中，而是由「隔离判据的物理位置」决定的 —— 判据在数据库里，判断就得在数据库能碰到的那一层。

**网关能做的（而且必须做）**

| 事项 | 说明 |
|---|---|
| 认证 | 校验 JWT 签名与有效期（已有） |
| 身份归一 | 从 token 解出 `uid` / `role` / `dept_id`，注入下游请求头 |
| **剥离入站身份头** | 客户端自带的 `X-User-Id` / `X-Role` / `X-Dept-Id` **必须先删掉再注入**（见 §5.1.2，当前存在真实缺口） |
| 粗粒度授权 | 路径级规则：`/api/v1/admin/*` 要 `role=admin`、数据接口要登录；不满足直接 401/403，请求不进后端 |
| 限流 | 已有（按用户维度） |

这些都在请求到后端之前就拦掉了 —— 你要的「在这一层拦截」对这部分完全可行。

**网关做不了的（必须留后端）**

| 场景 | 为什么网关做不了 |
|---|---|
| 列表类：`GET /sessions` | 网关不知道「7 号会话属于谁」——这是 MySQL 里的事实。要拦就得**解析响应体**逐行判断归属，于是网关得知道每个接口的 schema；而问答接口是 **NDJSON 流式**，中间层根本没法拦 |
| **检索类（最致命）** | 租户过滤必须在**检索那一刻**下推成 Chroma 的 `where`。网关只看到 HTTP 请求体，读不懂向量查询语义。若等后端查完再在响应里过滤，**泄漏已经发生了** —— 别的部门的切片已经被召回、可能已经被模型写进答案，而界面上完全看不出来 |
| 对象级鉴权 | `GET /chunks/284:7`、`DELETE /documents/12`、下载、重解析：判断这个 chunk / 文档归谁，需要 Chroma metadata + 项目成员关系，纯数据层知识 |
| 写入归属 | 上传时 `document.project_id` 取哪个项目、新会话归谁 —— 都要读用户与项目的归属表 |

**若硬要在网关做隔离，只剩两条路，都更差**

1. **网关维护一份「谁拥有什么」的映射表 + 缓存** → 双真相源，必然漂移，还要处理失效。
   本项目已经在「谁当真相源」上栽过一次（P0-1 把会话放进 Redis 又搬回 MySQL），不该再犯。
2. **网关解析并改写响应体做过滤** → 网关变成数据层，每个接口 schema 一变它就得跟着改；
   流式响应（问答）无解；写请求（POST body）也没法按行过滤。

**§5.1.2 当前存在的真实缺口（已实测）**

`proxy.controller.ts` 的身份注入写成了**条件式**：

```ts
if (incoming.user) {
  proxyReq.setHeader('X-User-Id', incoming.user.userId);
  proxyReq.setHeader('X-Role', ...);
}
```

对**受保护路径**没问题（守卫保证了 `req.user` 存在，`setHeader` 会把伪造值覆写掉）。
但对**白名单放行路径**（`api/v1/system/health`、`api/v1/qa/health`），守卫不跑、`incoming.user` 为空，
而入站的 `X-User-Id` 会**原样转发给后端**。

用与网关同版本的 `http-proxy-middleware@3.0.7` 实测（脚本：`gateway/scripts/probe-header-strip.cjs`）：

```
A 受保护路径（现状）      后端收到 X-User-Id="7"    X-Role="user"     ← 伪造值被正确覆写
B 白名单路径（现状）      后端收到 X-User-Id="999"  X-Role="admin"    ← 客户端伪造头穿透
C 白名单路径（先剥离）    后端收到 X-User-Id=null   X-Role=null       ← 修法有效
D 受保护路径（先剥离）    后端收到 X-User-Id="7"    X-Role="user"     ← 修法不影响正常链路
```

**今天无害**（后端没有一行代码读这两个头），但**P2-12b 一旦实现 `current_user`，这就是身份伪造通道**：
只要有一条数据接口被误标成 `@Public()`，或者以后新增了不走守卫的路径，
客户端带上 `X-User-Id: 999` 就能以别人的身份读数据 —— 而且不会有任何报错。
**所以 12b 的第一件事是「无条件剥离」，第二步才是「注入」。**

**§5.1.3 推荐的落地方式（并加固）**

1. **网关**：无条件 `removeHeader('x-user-id' / 'x-role' / 'x-dept-id')` → 再按真实身份 `setHeader`。顺序不能反。
2. **后端**：新增 `current_user` 依赖，读这两个头；**只认由网关注入的**。信任边界用两道：
   - **必做（A）**：后端 8000 不对外（compose 已如此，`backend` 不映射端口）；`IDENTITY_MODE=gateway|dev` 开关 ——
     生产 `gateway` 模式**缺头即 401（fail-closed）**；测试与裸跑调试走 `dev` 模式回落默认身份。
     测试里更干净的做法是用 FastAPI 的 `app.dependency_overrides[current_user]` 覆盖依赖，而不是靠开关。
   - **选做（B，纵深）**：网关额外带一个只有网关与后端知道的 `X-Internal-Auth`（共享密钥/HMAC），后端验过才认头。
     收益是**即使** 8000 被误暴露也伪造不了；代价是密钥要轮换与下发。
3. **不做**：网关直连 MySQL 查归属再拦截（等于把数据层职责塞进网关，见上面的两条路）。

**否掉的替代方案与代价**

| 方案 | 否掉的理由 |
|---|---|
| 隔离全部放网关 | 列表/检索/对象级鉴权都需要数据层知识；检索侧过滤做不到「召回前」；流式响应无解 |
| 后端不信头，每个请求自己验 JWT | 安全性更好（无伪造面），但要在后端再放一份 JWT 密钥、每条请求多一次 HMAC 验签，且「认证只有一个入口」这条边界被打破。**如果将来 8000 必须对外暴露，就应该改选这个** —— 它和 A 是互斥的两条路线，选 A 的前提正是「后端只在内网可达」 |
| 用 boolean 的 `TRUSTED_PROXY` 一把开关 | 比 A 更弱：开关一开就完全信任头，没有「头必须由网关注入」的强制手段。A 的「先剥离」本身就是强制手段 |

## 6. 管理端服务形态

| 项 | 决定 | 理由 |

| 部署 | 生产加一个 server block（如 `admin.nianan.site`），nginx 托管静态产物 + 反代 `/api` | 与 P1-7 TLS / P2-9 一起做 |

但与你要的「独立服务 + 独立命令」不符，且以后文档上传要挪过来时会和聊天界面耦合在一起。

### 8.1 D11 与「隔离能不能放网关」不是同一个问题

你问的「D11 是不是和我上面第一点讨论的是一个问题」——**不是，但两者都落在网关**：

| | D11 | D12（你的第 1 点） |
|---|---|---|
| 回答的问题 | 网关**怎么认人**：密码对不对、账号是否停用 | 认完人之后**管到哪一步**：能看哪些数据 |
| 专业名字 | 认证（Authentication） | 授权 / 数据范围（Authorization） |
| 落在哪 | 网关（读 `user` 表校验） | **网关做入口与粗粒度**，**后端做数据范围** |
| 典型实现 | 网关连 MySQL 查 `password_hash` / `status` | 网关剥头+注头+路径规则；后端 `WHERE user_id` + Chroma `where` |

一句话：**D11 决定「你是谁」，D12 决定「你能看什么、在哪一层判断」。**
D11 选「网关直连 MySQL」之后，网关顺带就能拿到 `role` / `dept_id` / `token_version`，
这正好是 D12 里「注入给后端的身份」的来源 —— 两条决策是**接力关系**，不是同一个问题。

**顺带说清 D11 的代价**（之前只写了 RTT）：要让「改密/停用立刻失效」，
网关每次请求都得知道最新的 `token_version` 或 `status`。三条路：

1. 每请求查一次库 → 最准确，但登录之外的每个请求都多一次 DB 往返；
2. 网关缓存 `status`/`ver` 30~60 秒 → 停用/改密最多延迟这么久生效，绝大多数场景够用；
3. 把 `ver` 放进 JWT，由**后端**比对（后端本来就要查库）→ 零额外往返，但吊销依赖后端参与。

**建议 3 为默认，2 作为网关侧的补充**（登录时写缓存、改密/停用时主动失效该用户缓存）。

### 8.2 D13 补充：写权限为什么按 `project` 授，而不是加一个角色

| 方案 | 结论 |
|---|---|
| 新增全局 `kb_admin` 角色 | ❌ 一刀切：给了就**全公司所有库**都能改，表达不了「他只能维护锅圈知识库」 |
| 用 `position / level` 判（如 P7 以上可传） | ❌ 与 §2 裁决 1 冲突：职级是组织信息，一调级就动系统权限；且 P7 未必负责知识库 |
| 只在前端隐藏上传入口 | ❌ 绕过 UI 直接调接口就破了。前端收敛只算**防误操作** |
| 拆到按钮级权限表（permissions） | ❌ 本期不需要，工期与内存预算都不划算；到 `project` 粒度刚好够 |
| **按 `user_project.role` 授**（采用） | ✅ 能表达「他只管这个库」；读与写共用一张表；**无记录 = 只读**，所以漏配的后果是「少给权限」而不是「漏权限」 |

**为什么把 `reindex` 单独提到「仅全局 `admin`」**：改切分参数 = **整库重建**。
切片 id 是派生值（`chunk_id = "<doc_id>:<chunk_index>"`），切分参数一变，老的 `chunk_id`
就会解析出错误正文 —— 这是本项目已经踩过并写进约定的坑（见 `docs/注意事项/踩坑清单.md`）。
影响面是全库，所以它不该由「某个库的 owner」决定，而该是超管的事，并且每次留审计。

## 9. 风险与代价

- **一次性迁移成本**：`document.project_id` 从字符串变强关联，必须写迁移脚本并在真实数据上验证
  「迁移前后同一问题检索结果一致」。这是本设计里唯一有数据损坏风险的一步。
- **假隔离的诱惑**：做完 P2-11 时系统"看起来"已经多用户了。**必须**在 11d 的迭代文档顶部
  写明「隔离未完成」，否则下一步很容易被当成"已经做完了"而跳过 P2-12。
- **内存**：管理端不新增常驻后端进程，但 `admin-console` 的构建产物 + nginx server block 有部署成本；
  4C4G 上同时跑主前端 + 管理前端时注意 nginx 是静态托管，内存增量可忽略（~10MB）。
- **合规**：手机号/性别属个人信息，展示脱敏、导出受限；若真给公司用，`audit_log` 是底线。
- **JWT 无状态与吊销**：加 `token_version` 后，**所有**已签发 token 都需要校验它 ——
  意味着网关每次请求要么查库、要么把 `ver` 放进 JWT 由后端比对。本期选后者（零额外查询），
  代价是「改密后旧 token 失效」需要后端参与校验，而纯静态资源请求不涉及。
