## 一、模块职责与配置

| 模块 | 职责 | 关键配置（`config/settings.py`） |
|---|---|---|
| `core/embedding.py` | 加载嵌入模型（单例），把文本转成向量 | `EMBEDDING_MODEL_NAME` / `EMBEDDING_DEVICE` / `MODELS_DIR` |
| `core/vector_store.py` | 向量库的初始化 + 增 / 删 / 查 + 状态 + 清空 | `VECTOR_STORE_TYPE` / `VECTOR_DB_DIR` / `SEARCH_TOP_K` |

**职责边界（重要）**：本模块只做「存 / 删 / 查」，**检索不接大模型**。
返回的是原始片段（`Document` 或 `Document + 分数`），重排与答案生成属于 `retriever` / `rag_chain`。

实测数据（本机 `bge-small-zh-v1.5`）：向量维度 **512**、`max_seq_length` **512**（与 `CHUNK_SIZE=500` 的关系见 `文档切分.md`）、归一化后 L2 范数 = 1.0。

## 二、Chroma vs FAISS：四个必须知道的差异

这一节是面试高频题，也是本模块写法差异的由来。

| # | 差异点 | Chroma | FAISS |
|---|---|---|---|
| 1 | **持久化** | 指定 `persist_directory` 后**写入即自动落盘** | **纯内存索引，必须显式 `save_local()`**，否则进程退出数据全丢 |
| 2 | **删除** | 支持按 id、也支持按元数据条件（`where=`） | 只支持按 id，没有元数据条件删除 |
| 3 | **元数据过滤** | 数据库侧**先过滤再召回**（精确） | **先取 `fetch_k` 个候选、再在内存里过滤**，过滤后可能不足 k 条 |
| 4 | **分数类型** | Python `float` | `numpy.float32`（已在本模块统一转成 `float`） |

> **修正**：两个后端的**量纲其实一致**——默认配置下返回的都是**平方 L2 距离**（Chroma 的
> `hnsw:space` 默认 `"l2"`，FAISS 的 `IndexFlatL2` 刻意不开方省算力），都是越小越相似。
> 真正的差异是「一个是 HNSW 近似搜索、一个是 Flat 精确搜索」，top-k 集合本身可能不同。
> 本模块已用 `1 - d/2` 把距离换算成余弦相似度（越大越像，[-1,1]，前提是嵌入已归一化）。
> ⚠️ 别给 Chroma 配 `hnsw:space="cosine"`：那会返回 `1 - cos`（范围 [0,2]），换算公式就不成立了。

> 面试说法：「这两个库表面接口一样，但**失效模式完全不同**——FAISS 忘调 `save_local` 是**静默丢数据**（不报错），
> Chroma 调了废弃的 `persist()` 也只是打个警告。所以我用了一个『重新打开同一目录』的测试来兜底验证持久化，
> 而不是靠『我调了保存方法』这种自我安慰。」

## 三、设计决策（面试官爱问的「为什么」）

| 决策 | 理由 |
|---|---|
| 嵌入模型用**双检锁单例** | 权重约 92 MB、加载耗时数秒，而向量化是高频调用；不单例则内存成倍增长 + 重复加载 |
| 加载策略是「本地目录 → 加载失败 → 远程」 | 不只是「本地不存在才走远程」：本地目录可能只有残缺文件（下载中断），参考实现只判断 `exists()`，残缺时直接失败 |
| 向量库管理器也做单例 | 它持有数据库连接 / 内存索引；每次请求新建会重复开连接，FAISS 还要重新读索引文件 |
| `store_type` / `persist_dir` 开放为**构造参数** | ① 可测试——要同时验证两个后端，且必须写临时目录；② 多知识库——换个目录就是一个新库 |
| 后端分派用 `isinstance` 而不是比较 `store_type` 字符串 | 既让类型收窄（Chroma 没有 `save_local`），又保证「配置与实例不一致」时不会误操作 |
| FAISS 空库用 `None` 作哨兵、延迟创建 | 见坑 2，避免用假文档建索引污染数据 |
| 分数统一转成 Python `float` | 见坑 6，`numpy.float32` 无法 JSON 序列化 |

## 四、踩坑清单

### 坑 1 · FAISS 删除后不落盘 → 重启后「删掉的数据复活」

- **现象**：删除某来源的片段，当前进程内检索确实没了；但重新构造管理器（模拟进程重启）后，被删的片段又回来了。
- **根因**：FAISS 是纯内存索引，`delete()` 只改内存。参考实现只在 `add_documents` 后 `save_local()`，**删除后没有保存**。
- **修法**：`add_documents` / `delete_by_source` 之后都调用统一的 `_save_faiss()`；并加「删除 → 重开 → 计数仍减少」的断言防回归。
- **面试说法**：「FAISS 的持久化是**手动模式**，漏一次保存就是静默丢数据——不报错、不崩溃，只是重启后数据对不上。这种 bug 只能靠『重新打开一次』的测试抓出来。」

### 坑 2 · 用「假文档」初始化空索引，污染检索与计数

- **现象**：参考实现用 `Document(page_content="初始化向量库")` 来创建空 FAISS 索引。后果是这条假数据**能被检索召回**，且被 `count()` 统计进去。
- **根因**：`FAISS.from_documents` 必须至少给一条文档才能建索引，作者为了绕过这个限制塞了条假的。
- **修法**：空库就让 `self._store = None`（哨兵），**等第一次真正写入时**用 `from_documents` 创建索引；检索/统计遇到 `None` 直接返回空。
- **面试说法**：「为了绕开 API 限制而往业务数据里塞假数据，是典型的『解决了眼前问题、制造了长期问题』。空态应该是**显式的空**，不是**一条假数据**。」

### 坑 3 · `metadata={"source", "init"}` 是 set 不是 dict（切 FAISS 必崩）

- **现象**：默认用 Chroma 一切正常，一旦把 `VECTOR_STORE_TYPE` 切成 `faiss`，初始化直接抛 pydantic 校验错误。
- **根因**：`{"source", "init"}` 用的是**花括号而非键值对**，这是 set；`Document.metadata` 要求 dict。
- **修法**：随坑 2 一起解决——不再需要初始化文档。
- **面试说法**：「默认路径不触发的代码分支最容易藏 bug。这个错误只在切换后端时才暴露，所以我后来把**双后端都跑一遍**写进了单测。」

### 坑 4 · FAISS 删除时把 id 传给了要求 Document 的接口（删除必崩）

- **现象**：FAISS 模式下按来源删除直接抛类型错误。
- **根因**：参考实现收集 `to_keep.append(doc_id)`，然后传给 `FAISS.from_documents(to_keep, ...)`——那个接口要的是 `Document` 列表。而且每次删除都**重建整个索引**，代价很大。
- **修法**：根本不需要重建——`FAISS.delete(ids)` 是公开 API，会**同时**从索引和 docstore 移除并维护 `index_to_docstore_id` 映射。改成先筛出目标 id，再 `delete(target_ids)` + 落盘。
- **面试说法**：「很多人以为 FAISS 删数据只能重建索引，其实它提供 `delete(ids)`。**动手看源码比按印象写代码便宜得多**——这一步同时修掉了 bug 和性能问题。」

### 坑 5 · `k = k or settings.SEARCH_TOP_KNone`（一调用就崩）

- **现象**：`similarity_search()` 任何调用立刻 `AttributeError: 'Settings' object has no attribute 'SEARCH_TOP_KNone'`。
- **根因**：手滑把 `SEARCH_TOP_K` 打成了 `SEARCH_TOP_KNone`。
- **修法**：改为 `settings.SEARCH_TOP_K`。
- **面试说法**：「这类笔误在『只在特定分支执行』的代码里能躺很久。检索方法是核心路径，所以**每个公开方法都要有单测**，哪怕只是最简单的冒烟调用。」

### 坑 6 · FAISS 返回 `numpy.float32`，直接 JSON 序列化会失败

- **现象**：带分数的检索在 FAISS 下断言 `isinstance(score, float)` 失败；将来接口层直接返回分数会报 `Object of type float32 is not JSON serializable`。
- **根因**：FAISS 内部用 numpy 计算，`similarity_search_with_score` 返回 `numpy.float32`；Chroma 返回的是原生 `float`。两个后端不一致。
- **修法**：在管理器内统一转换 `[(doc, float(score)) for doc, score in raw_results]`，把差异**收口在封装层**，不泄漏给上层。
- **面试说法**：「这是 numpy 生态的经典坑——**数值类型能算但存不了**。封装层的价值之一就是抹平这种实现差异，而不是把差异一路传到 API 层才炸。」

### 坑 7 · `Chroma.persist()` 已废弃（调了没用）

- **现象**：按老教程调用 `store.persist()`，得到 `DeprecationWarning: Since Chroma 0.4.x the manual persistence method is no longer supported`。
- **根因**：Chroma 0.4+ 改为**写入即持久化**，langchain 把 `persist()` 标记为 deprecated（`since=0.1.17`, `removal=1.0`）。
- **修法**：不调用；并在注释里写明原因，避免以后有人「照着教程补上」。
- **面试说法**：「教程和依赖版本会脱节。判断该不该调一个方法，最快的办法是**读一眼它的源码有没有 `@deprecated`**。」

### 坑 8 · FAISS 的元数据过滤必须放大 `fetch_k`

- **现象**：带 `filter_dict` 检索时，FAISS 返回的条数少于 k。
- **根因**：Chroma 在数据库侧先过滤；FAISS 是**先取 `fetch_k` 个候选、再在 Python 侧过滤**，候选池不够大时过滤完就没剩几条。
- **修法**：封装 `_build_filter_kwargs()`，FAISS 分支返回 `fetch_k = max(k * 4, 20)`，把差异收口。
- **面试说法**：「同样是 `filter` 参数，两个库的**语义不同**：一个是下推过滤、一个是后置过滤。不读源码就会写出『有时候少几条』的玄学 bug。」

### 坑 9 · `HuggingFaceEmbeddings` 取维度用的是私有属性 `_client`

- **现象**：`model.client` 抛 `AttributeError: 'HuggingFaceEmbeddings' object has no attribute 'client'`。
- **根因**：`langchain-huggingface 0.1.2` 把 `SentenceTransformer` 存在 **`_client`**（私有），不是 `client`；不同版本还改过。
- **修法**：`getattr(model, "_client", None) or getattr(model, "client", None)` 兼容两种命名，并包 try/except —— 维度只是元信息，拿不到不应该让主流程失败。
- **面试说法**：「对第三方对象取属性时，用 `getattr(..., default)` 而不是硬点，是**降低版本耦合**的廉价手段。」

### 坑 10 · `clear_all()` 不能直接 `rmtree` 整个目录

- **现象**：清空 FAISS 时若用 `shutil.rmtree(VECTOR_DB_DIR)`，会把同目录下不属于 FAISS 的数据一起删掉。
- **根因**：`VECTOR_DB_DIR` 是**共用的**——你曾把后端切成 chroma，目录里就躺着 `chroma.sqlite3`；反之亦然。
- **修法**：FAISS 只删自己那两个文件（`index.faiss` / `index.pkl`）；Chroma 只 `delete_collection()` 再重建。
- **面试说法**：「『清空当前库』和『删掉这个目录』是两件事。共用目录时用 `rmtree` 属于**越权删除**。」

### 坑 11 · 测试必须隔离到临时目录（可测试性反向驱动了设计）

- **现象**：如果用 `settings` 里的真实 `vector_db/` 跑测试，`clear_all()` 会把生产数据清空。
- **根因**：管理器的所有配置都从全局 `settings` 读，测试无法隔离。
- **修法**：把 `store_type` / `persist_dir` / `collection_name` 开放为**构造参数**，测试用 `tempfile.TemporaryDirectory()`；生产仍走 `get_vector_store_manager()` 单例。
- **面试说法**：「**可测试性会反过来改进设计**。为了能测两个后端，我把隐式的全局依赖改成了显式参数——顺手还支持了『多知识库』这个未来需求。」

### 坑 12 · chromadb 遥测报错刷屏（噪音，不影响功能）

- **现象**：日志里反复出现 `ERROR - chromadb.telemetry.product.posthog - Failed to send telemetry event ...: capture() takes 1 positional argument but 3 were given`。
- **根因**：chromadb 0.5.x 内置的 posthog 遥测与新版 posthog SDK 不兼容。
- **修法（可做）**：在 chromadb 的 `Settings` 里关闭匿名遥测（`anonymized_telemetry=False`），或把 `chromadb.telemetry` 的日志级别调到 ERROR 以上以抑制噪声。
- **面试说法**：「ERROR 日志不一定代表你的程序有问题——先确认它来自谁。**但也不能放着不管**，否则真正的 ERROR 会被淹掉。」

## 五、测试覆盖（`tests/test_module3_vectorstore.py`，98 项断言）

| 用例组 | 覆盖内容 |
|---|---|
| 0 前置检查 | 嵌入模型可加载（不可用则直接终止，避免后续用例全是假失败） |
