## I. 测试与验收方法论（最贵的一类）

25. 验收脚本自己会骗人：按**文案**去重记 DOM 事件错（按 DOM 元素记账 `WeakSet`）；动作后「立刻」数 DOM 错（`tryWait`）。**一次通过不算通过，连跑两遍才算**。
35. 「假装失败」的桩挑没命中缓存的对象；看起来验 A 实际验 B 的断言比失败更危险（一直绿）。
8. 测试断言成对写：「该拒的拒了」+「该放的放了」。
11. 冒烟脚本 `/tmp/smoke_*` 残留会让失败用例误报 PASS → 重跑前删。
7. 勿对同一文件并行多个 Edit（第二处基于旧快照静默覆盖）→ 逐个改 + 复查。
47. **BSD `grep` 不支持 `\|` 交替**（macOS）：`grep -n "A\|B"` 搜的是**字面量**，不是「A 或 B」，会给出「一条都没有」的**假结论**。
   → 一律写 `grep -nE "A|B"`，或用专用 Grep 工具。**同日踩了两次，每次都差点把假结论写进文档。**
48. **客户端的「文件改动回滚」（`file-rollback`）会把旧内容写回工作区**（2026-10-06 实测两次，每次约在提交后 1 分钟）。
   症状：`git status` 又显示某文件被改、`git diff` 是「某几节整段消失 + 表格被重排」，**但该文件不是任何一次提交过的版本**。
   **不要猜是编辑器**（我第一次就误判成「Cursor 的过期缓冲区」，是错的）。定位方法：

   - 备份存放：`~/.workbuddy/workspace/sessions/<sessionId>/modify_backup/`，
     命名 `<轮次>.m.<路径哈希>.<文件名>`（`.m`=改动前备份，`.a`=新增前）；
   - 回滚标记：同目录 `.modify_backup_meta/<轮次>.<base64(file-rollback:requestId)>.<轮次>.commit`；
     开关在 `.modify_backup_meta/backup_settings.json`（`{"enabled":true,"thresholdMb":100}`）；
   - **确认被写回的是哪一份**：拿旧版独有字符串去 `grep -rlI` 这两个目录，命中的那份就是被写回的内容
     （本次命中 `2.m.c8deb183.PLAN-v2.0.0.md`，即第 2 轮改动前的 22:06:46 快照）；
   - 排除编辑器：查 `~/Library/Application Support/Cursor/User/History/`，
     若该文件无条目、目录 mtime 停在很久以前，就是编辑器无关。

   应对：**内容没丢**，`git checkout -- <file>` 从 HEAD 救回即可；**每轮开头先 `git status` 复查一次**，
   别假设工作区还等于自己上次写完的样子。
49. **验证「清理干净了」的条件必须独立于清理本身的条件**（P2-11a 实测踩到）。
   起因：迁移往返会把新列冲成默认值（`employee_no` 变空串），于是
   `DELETE ... WHERE employee_no LIKE 'p211a_%'` 漏掉了那一行；而我「验证清理干净」
   用的 **同一个 WHERE** —— 该断言永远为真，测试全绿而库里留着残数据。
   →清理锚点要选**不受本次操作影响**的列（如唯一键 `username`）；
   验证时至少再加一条更宽的判据（如「该表总行数为 0」）。**这是坑 35「看起来验 A 实际验 B」的又一例。**
50. **别写概率性的断言**（P2-11b 实测踩到，15 遍里漏 13 遍）。
   症状：断言「生成的 24 位临时密码不含易混字符 0/O/1/l/I」，
   但单次抽样含易混字符的概率约 **28%** —— 于是它 15 次只红 2 次，
   很容易被当成「偶发」放过，而**真正的 bug 还在线上代码里**。
   根因更值得记：第一版只过滤了「强制的那一位数字」，小写位照样能抽到 `l`、
   大写位能抽到 `I`/`O`。
   → 两条纪律：
     ① **断言不变量，不要断言样本**。「候选池不含易混字符」是确定性的；
        「抽 24 个字符看看有没有」是概率性的。前者一劳永逸。
     ② **在生产代码里加一道兜底自检**（`if set(out) & CONFUABLES: raise`），
        让「越界」在结构上不可能，而不是指望每次改动都记得过滤。
   配套：**验收脚本必须连跑多次**（本项目规矩「一次通过不算通过」），
   否则低频 bug 根本不会出现在你眼前。
51. **断言与验收的判据，不能依赖「这张表本来是空的」**（P2-11d 实测，一天咬了两次）。
   两次都是同一个形状的错：
     · `tests/test_module11_account.py` 断言「按序列过滤为空时返回空列表」——
       11a 交付时职位表是空的，成立；P2-11d 灌进 6 个职位后这条红了，
       而它**本来就不该关心别人的数据**。
     · `tests/acceptance_p2_11a.py` 断言「user 表总行数为 0」—— 同一个毛病。
   → 判据一律改成「**按业务键数自己造的那些行**」（`username LIKE '前缀%'`），
     再单独加一条「别人的行数没被改动」。**总行数为 0 这种判据只在一次性脚本里成立。**
52. **迁移往返会毁掉 `DROP TABLE` 掉的表里的数据 —— 验收脚本必须自己兜着**（P2-11d 实测）。
   `downgrade` 会 `DROP TABLE department / position / user_password_history`，
   于是员工的 `department_id` / `position_id` **变成悬空引用**（没有 FK，不会报错）。
   修法：往返前把这几张表**连数据一起快照**、往返后**按原 id 写回**（保留 id 很重要，
   员工的引用靠它才继续有效）。同理，`ADD COLUMN` 类迁移会把已有列的值冲成默认值，
   也要快照-还原（本项目是 `employee_no` → `LEGACY-<id>`）。
   → **教训**：`downgrade` 之后再 `upgrade`，得到的不是「原样」，而是「只剩 DDL 形状」。
   凡是要在有数据的库上跑的验收脚本，都得自带快照/还原。
53. **改完路由先看「运行中的进程」认不认** —— 手工起的 uvicorn 不带 `--reload`（P2-13bc 实测）。
    症状：新写的 `/api/v1/admin/password/board` 一直 404，第一反应是「路由注册漏了」，
    对着 `api/main.py` 反复看。判据别猜进程：`curl :8000/openapi.json` 数一数运行中注册的路由
    —— 实际只有旧的两条，是**进程旧了**不是代码错了。`make api` 本来就带 `--reload`，
    手起图快省掉的那两个字符要用半小时还。
54. **两个都写 `user` 表的测试脚本不能并行跑；「全表总数」不是不变量**（P2-13bc 实测）。
    症状：module12 收尾断言「`SELECT COUNT(*) FROM user` == 10」，与 module11 并行跑时红了
    （对方正在造自己的账号）—— 73 条全对却红了一条，像 flaky，实则是拿共享状态当判据。
    → 不变量要说「**这 10 个种子用户名还在**」（`username IN (...)` 按业务键）：
      不受别人新增影响，也更严格（认名字不认数量）。这与坑 51 是同一家族：
      「总行数为 0 / 恰好 N」只在一次性脚本里成立。
55. **curl 验接口全 200 ≠ 页面能用：登录闭环必须浏览器真点一遍**（P2-13bc 实测，13a 漏网）。
    两个 bug，curl 各自验都是通的，串起来死在半路：
      ① `LoginView.submit` 调完 `auth.login()` 就结束 —— 没写 `router.replace`，
         登录成功后页面停在登录页「什么都不发生」；
      ② store 里 `fetchProfile()` 写在 `setSession()` **之前** —— 发 `/me` 时 token 还没落，
         `getToken()` 返回空串 → 裸请求 401 → **所有人**都报「账号已停用或不存在」。
    第②条尤其毒：报错文案把人指向「账号问题」，而两个接口单独 curl 都 200。
    → 带页面的交付，验收终点是浏览器跑通完整用户路径（本项目已把「curl + 浏览器双路」立为交付前规矩）。
56. **前后端之间的「字符串契约」没有任何类型检查，得手动钉住**（P2-13d 实测）。
    症状：审计页的「变更系统角色 / 变更员工状态」明细列整列显示 `—`。
    根因：后端对这两类动作统一写 `{"from": ..., "to": ...}`，前端按 `detail.status` / `detail.role`
    去读 —— `from` 恒为 `undefined`，`if (from !== undefined)` 直接不进。
    **为什么全绿**：后端测试全绿、接口 200、前端不报错不空指针，页面上完全像「这条日志没有明细」。
    纯后端断言**永远发现不了**这类 drift（第 55 条的延长线：那条是登录闭环串不起来，
    这条是两个各自都自洽的模块对着一份没人校验的约定）。
    → 修法**不能只是改前端**。要同时：
      ① 把 `action → detail 必需键` 写成契约表断言（后端改了形状而前端没改 → 当场红）；
      ② **正扫前端源码**里出现的动作名，确认全在服务端白名单内（不然页面上会出现
         一个永远查不到记录的下拉项，用户以为「坏了 / 没人干过」）。
    一般化：**只要一个值在后端是字符串字面量、在前端也是字符串字面量**，
    就要么共享一份（生成的 TS 常量），要么加一条跨端断言。
57. **测试自己的残留会让下一轮直接撞唯一键**（P2-13d 实测）。
    症状：第二轮跑，第一条业务动作就报「登录名 `m13d_newbie` 已被使用」，
    第一反应是「代码重复创建了」或「有人改了种子数据」。真因：**上一轮在抛异常之前
    已经把这行建出来了**，而收尾清理那组永远跑不到（异常直接终止脚本）。
    → 症状极具误导性（看起来像业务 bug），所以每个写库测试的**开头**要有一段
      「先删本模块残留」（按 `username LIKE '<前缀>%'` 这类本模块专属标记，
      以及它在历史表/审计表里的关联行），而不是只在结尾清理。
    测试**开头**的清理会掩盖「这行本来就该被唯一键挡住」吗？不会 —— 唯一键另有独立断言（module11 验过）。
58. **测试组的顺序能悄悄让断言失去意义**（P2-13d 实测，第 49 条的形状）。
    症状：手机号回归组排在「清理与零残留」**之后**，而它要读的那行临时员工已被清理删掉。
    不报 AttributeError 也会发生 —— 只要断言写成 `repo.get(id).phone`，
    就会变成「拿 `None` 静默判 False」，让人去查一个根本不存在的 bug。
    → 凡是要读数据的组，**排在清理组之前**；断言里加 `is not None` 保护，
      让「数据没了」和「数据不对」是两种不同的红。
59. **`Makefile` 里少一个 tab，只有真跑 `make test` 才现形**（P2-13d 实测）。
    追加一行测试到 `test:` 目标时缩进丢了，`py_compile` 查不出（那管 .py 不管 Makefile），
    `grep -n` 也很难一眼看出来 —— 表现是 `Permission denied`，
    第一反应是「文件权限坏了」，实际是 recipe 行没被识别成 recipe。
    → 改完 Makefile 至少跑一次目标本身；或用 `cat -A` 看行首是不是 `^I`。
60. **Node 的全局 `fetch` 会读 `HTTP_PROXY`/`http_proxy`，且不尊重 `NO_PROXY`**（P2-11c 实测，本机开着代理时 100% 触发）。
    症状：`fetch failed`，`cause` 是 `ECONNREFUSED`，**没有 HTTP 状态码** ——
    第一反应必然是「后端没起」，而 `curl /api/health` 明明 200。
    和第 2 条是同一个根因的另一面：`curl` 可以用 `--noproxy '*'` 绕，**`fetch` 没有对应开关**。
    → 实测过的三条路都不通：TS 的 `RequestInit` 没有 `dispatcher` 字段（编译就红）；
      `require('undici')` / `import 'node:undici'` 在 Node 22.22 上取不到模块；
      `setGlobalDispatcher` 是 `undefined`。
    **唯一稳定解：`node:http` / `node:https` 原生模块**（完全不读代理环境变量，已实测）。
    代价：得手写 JSON 序列化、超时、响应大小上限（本项目做了 8s + 1MB 上限，
    因为它是个内网接口，不设上限等于把后端内存当自己的）。
    一般化：**Node 侧凡是「打本机/内网地址」的 HTTP 调用，一律不用 `fetch`**。
61. **`password_changed_at` 这类「列是 NOT NULL，所以一定有值」的推断，不成立**（P2-11c 实测）。
    `create_user` 的 `password_changed_at` 漏传 → 建出来的账号**一登录就报「密码已过期」**。

    → 修法不是「把测试写对」，是**在仓储层兜底**（`password_changed_at or now_db()`）

    否则两个 fail-closed 规则会撞在一起，让新建的账号必然登不进去。

62. **`RELEASES.md` / `releases.html` 这类「跨多版本累积的文档」，会被单次提交悄悄弄坏**（P2-11c 收尾实测）。

    说明它不是「从来没写过」，是被下一次编辑吞掉的。

    → 每次收尾跑一次全量拿真实数（**没实测的那一档就写「未实测」，别编**，同第 50 条）。
63. **新加一道守卫后，旧测试红了 —— 把断言改成「应该被拒」是最坏的处理**（P2-12b 实测）。

64. **辅助函数「顺手恢复全局状态」，会让后面所有断言失去意义**（P2-12b 实测，第 58 条的形状）。

65. **反向验证自己出错时，「崩掉」和「测出东西了」长得一样**（P2-12b 实测）。

66. **`_owns()` 用 `==` 而不是「无主或本人」，认领功能就永远触发不了**（P2-12c 实测）。
    内存版的归属判定初版是 `return self._owners.get(session_id) == owner_id`。
    而**无主会话的归属就是 `None`** —— 对 `owner_id=440` 判出来是 `False`，
    于是「无主会话可以被认领」这条语义**永远走不到**，而且**测试会绿**：
    契约里那条断言如果写成「认领后归属变成新主人」，会先在别处失败，
    看起来像是别的问题。
    → 正确形态：`return actual is None or actual == owner_id`（MySQL 版是
      `user_id = ? OR user_id IS NULL`，Redis 版是三态判断，三处**必须同构**）。
    连带一条：`_owns()` **不判断存不存在**，所以每个调用方必须**先判存在再问归属**，
    否则不存在的 sid 会被判成「无主可见」，`delete()` 会返回 True（假成功）。
    一般化：**「无主」是一个真实的取值，不是 null 的同义词**——
    凡是把 `None` 当「没设置」用的地方，都要检查它是不是也承载了「没主人」这个语义。
67. **多状态判断里漏掉一个「中间态」，测试会在最不像它的地方崩**（P2-12c 实测，第 66 条的形状）。
    Redis 版 `save()` 初版：
    `if current_owner is not _MISSING and current_owner != owner_id: raise ...`
    漏了 `current_owner is not None`。而 `None` 在这里表示「无主、可以认领」，
    于是**无主会话被判成越权** —— 崩在module6 的「无主会话被认领」那条，
    而那条离改动点隔了整个三态。
    → 修法是加 `is not None`，并**把这个判断的形状与 MySQL 版逐字对齐**
      （两处写成同一个三态结构，将来只改一处的时候另一处会明显不一样）。
    一般化：**三态以上的判断，先把每个取值列出来再写代码**，
    然后去读一遍「每个取值分别会命中哪个分支」—— 漏掉的那一支往往不是漏在第一处。
68. **只拆第二道防线，什么都测不到**（P2-12c 实测）。
    反向验证第一版只拆了 `SessionStore.save()` 里的越权抛错 → **主测试全绿**。
    根因不是「隔离有多层所以拆一道测不出」，而是**接口层的预检先把请求挡了**，
    请求根本没走到 `save()`。
    → 改为**两道一起拆**（接口预检 + `save` 抛错），并额外**断言「其他路由仍然绿」** ——
      那才是「每条路由各自有守卫」的证据（truncate / PATCH / DELETE / 流式各有独立的
      `is_foreign` 调用，拆一处不影响它们）。
    连带一条：**反向验证里写的桩要返回正常响应，不能抛异常**。
    初版桩链「一被调用就抛 `AssertionError`」→ 预检被拆后请求进桩 →

    `ExceptionGroup` → **整个测试文件崩掉**（第 65 条：崩 ≠ 红）。

    一般化：**拆守卫时，只有「请求被放行到下一层」才能验到下层的守卫**。
69. **「崩掉」与「测出东西了」长得一样**（P2-12c 实测，第 65 条的又一次复现）。
    浏览器验收第一版崩在 `finally` 的第一条（SQL 多一个右括号），

    `restorePwd()` 没跑到，两个账号的密码留在库里成了探针值。

    ⚠️ 前提是 **Chroma 是 server 模式且容器还在**（`.env`: `CHROMA_HOST=127.0.0.1`）。
    如果索引也在本地磁盘目录被一起删了，这条路就不通 ——
    所以**别把 Chroma 目录和 upload/ 放在同一个会被一起清掉的边界里**。
    **一般化**：做「从副本当重建」的脚本前，先确认副本的**元数据里有没有重建所需的
    原始标识**（文件名/路径/顺序）。有 → 能重建；没有 → 重建出来的只是一堆碎片。
78. **静态检查自己把自己判成违规**（第75 条的护栏第一版就有这个 bug）。
    `kb_guard.py` 第一版跑在「剥离了注释和字符串」的源码上，于是：
      · docstring 里写的反例示范 `sa_delete(document_table)` → 被判违规；
      · 行号是**剥离后**的行号，与原文对不上 → 排查的人会怀疑检查本身有问题。
    一条永远红的检查等于没有检查（所有人都会学会忽略它的输出）。
    → 修法两条：① 剥离时**用等量空格替换**而不是删除，保住行号；
      ② 本文件加进 `EXEMPT_FILES` 自我豁免（它的docstring 里全是反例）。
    **反向验证**是唯一发现它的办法：埋一个探针文件看能不能抓到 ——
    埋完发现「报出来的行号打开一看是段注释」，才知道自己判错了。
79. **原生 SQL 里的 `DELETE FROM` 在字符串里，剥离字符串就等于自废武功**（同上，第一版缺陷）。
    `c.execute("DELETE FROM document")` —— 扫「剥离了字符串」的源码扫不到它，
    而检查却显示「✓ 通过」。**一个永远绿的检查比没有检查更坏。**
    → 拆成两路：① `sa_delete(表)` 是**代码**，扫剥离后的源码；
      ② 原生 SQL 必然在**字符串字面量**里，扫未剥离的源码 + 提取字符串内容判定。
    反向验证要覆盖四种情形（全删/ 带 WHERE 放行 / SQLAlchemy 形式 / 多语句里混一个），
    只测「能抓到一种」会漏掉另外三种。

80. **「判定对了」与「拒权路径能正常返回」是两件独立的事**
    （P2-14a 实测，2026-10-08）。`kb_acl.describe()` 的参数名写成 `kb_role`，
    函数体里用的是 `action` → `NameError` → 响应是 **500 而不是 403**：

        WARNING - core.identity - 知识库写操作被拒 | action=upload | actor=chen.jie   ← 判定是对的
        NameError: name 'action' is not defined
        INFO: POST /api/v1/documents/upload HTTP/1.1" 500 Internal Server Error

    危险之处：**只看「普通员工的写操作没成功」会以为守卫做完了**，
    而前端拿到 500 完全不知道是权限问题，只知道「系统坏了」。
    → 权限类断言要写两条：**① 该拒的是 403 ② 拒权的响应体不是 500**。
    「越权会 403」这一条单独自足时，**永远绿**也能通过。
81. **写守卫时的参数名/签名不一致，症状出现在「拒权」这一侧**
    （同上根因的通用形状）。守卫函数本身是对的（判定生效），
    错的是它**抛 403 时构造文案**的那一行。
    → 与第 80 条同源：凡是把「允许」和「拒绝」写在一起的地方，
    **两条路径都要单独跑一次**。允许路径测一百遍也发现不了拒绝路径的语法错误。
82. **`compare_metadata` 抓的是「列注释」，而列注释在两处各写一份**
    （P2-14a 实测）。`core/schema.py`（查询侧视图）与 `alembic/versions/*.py`
    （DDL 快照）是**刻意不合并**的两份文件（11a 立下的分工），
    所以改了其中一处的注释，另一处不改就会报 `modify_comment`。
    这条守卫的价值在本轮真的体现了：它当场抓到迁移 0006 与 schema.py 差一个 `(P2-14a)`。
    ⚠️ **但代价要知道**：迁移一旦跑过、**再改迁移文件里的注释不会重新执行**，
    要对齐已有库必须手工 `ALTER TABLE ... MODIFY COLUMN`。
    → **迁移文件 tag 之后不要再改注释**；要改就连 schema.py 一起改 + 手工 ALTER，
    并写进迭代文档（否则下一个人会以为库里已经是对的了）。
