# 线上部署：知识库重建清单（2026-11）

> 触发场景：切分规则变化（`CHUNK_MODE` / `CHUNK_SIZE` / loader / 表格行级切分）、或需要把开发环境重切后的知识库同步到线上。
> 结论：**只要切分规则变了，线上必须整库重建**；不能只增量灌新文档，否则新旧切片语义、chunk_id、embedding 全都不一致。

## 0. 先回答三个问题

1. **线上文档库要不要全部更新？**
   **要。** 切分是全局规则：同样一份文档，fixed/title、表格行组/行级、PDF 走 MinerU/PyMuPDF，都会产生不同的 chunk 边界与数量；embedding 也是按 chunk 内容算的。只灌新文档 = 旧切片仍是旧规则，检索结果两套语义混在一起，无法保证一致性。
2. **旧会话历史可以抛弃吗？**
   可以（已确认）。旧 `session/chat_message/qa_trace` 里的 `turn_meta/ref_ids` 指向旧 chunk_id，重建后这些引用会 404 或错位；直接清空最干净，不做兼容。
3. **旧切片可以覆盖吗？**
   可以。清空 `rag_qa_knowledge` 后从**原件**全量重建；`upload/` 里的原文件必须保留，它是唯一重建源。

## 1. 影响面（先列清楚再动手）

| 对象 | 重建后的变化 | 处置 |
|---|---|---|
| Chroma `rag_qa_knowledge` | 全部 chunk/向量重建，chunk_id 重新生成 | 只清本 collection，**不要** drop 整个 Chroma / 共享 collection |
| `document` 表 | `chunk_count`/`status` 重算；用 reindex 可保留 doc_id | `reindex.py` 从 `upload/` 重解析（保留 doc_id），不要重新 upload（会换 doc_id） |
| `session` / `chat_message` / `qa_trace` | 旧轮次引用旧 chunk_id | 按确认**直接清空**；先备份 |
| QA 缓存 Redis | 旧答案来自旧切片 | 清 `rag:qa_cache:*`；KB 变更后版本号要抬 |
| 额度统计 | **quota 从 `chat_message` 明细计算**；清空会话会把本月已用量归零 | 若不想重置，先导出/保留本月 `chat_message`，或调整额度口径后再清；否则公告“额度统计重置” |
| QA 直击索引 | QA 集答案独立于切片，但 `source_doc` 映射可能变 | 重建后重载索引，核对 source_doc → doc_id |
| MinerU | 扫描件/复杂版面依赖 | 生产 `.env` 常开：`MINERU_ENABLED=true` + key + ≤20MB；看启动日志 |
| 前端预览 | 走 doc_id 取原件 | 重建后新 doc_id 正常；旧会话已清空，不受影响 |

## 2. 前置：冻结与备份（缺一不可）

> ⚠️ **备份必须放在仓库目录之外**（如 `/opt/qa-backups/<日期>/`）。
> `scripts/deploy.sh` 里有 `git clean -fd`，会删掉 `/opt/qa` 下所有未入 git 也没被
> `.gitignore` 排除的文件 —— 2026-11-04 实测把放在 `/opt/qa/backups/` 的备份整目录删掉了
> （当晚数据本身无恙，但回滚快照没了）。

1. **公告维护窗口**：重建要跑全量解析 + embedding（PDF 还走 MinerU），预留足够时间。
2. **停写入**：停 Celery worker；入口挂维护页/停网关；避免重建时新上传/新问答插进来。
3. **备份**：
   - MySQL：`document`、`session`、`chat_message`、`qa_trace`、`quota_usage_monthly`（如有）、`user`；
   - `upload/` 原件目录；
   - Chroma 数据卷/目录（`vector_db` 或 Chroma server data）；
   - `.env`（含 `MINERU_API_KEY`、`CHUNK_MODE`、额度配置）。
4. **切片正文快照**（切 title 时 golden 重映射用）：
   `scripts/snapshot_kb_p37a.py --out /tmp/kb_snapshot_fixed.json`
5. **基线评测**：`make eval-retrieval TAG=prod-fixed-baseline`（记录 recall@5/MRR/拒答）。
6. **记录现状**：`total_documents` / `total_chunks` / 每份 `chunk_count`。

## 3. 部署与重建步骤

1. **部署代码**（tag/发布分支），记录 commit。
2. **生产 `.env` 配置**：
   - `CHUNK_MODE`：如决定切 title 就 `title`；否则保持 `fixed`（但仍要重建以应用 loader/表格行级变更）；
   - `CHUNK_SIZE=500`、`CHUNK_OVERLAP=50`；
   - `MINERU_ENABLED=true`、`MINERU_API_KEY=...`、`MINERU_MAX_BYTES=20971520`；
   - 额度 `TOKEN_QUOTA_DEFAULT_MONTHLY` 按运营策略（注意清会话会重置本月统计）。
3. **重启 backend / worker** 让配置生效；启动日志确认：
   - `MinerU PDF 结构化解析已启用 | 最大文件=20MB ...`
   - `DocumentLoader 初始化完成 | chunk_size=500 ...`
4. **清空会话/历史**（按确认）：
   ```sql
   -- 先备份，再按外键顺序清
   TRUNCATE TABLE qa_trace;
   TRUNCATE TABLE chat_message;
   TRUNCATE TABLE session;
   ```
   ⚠️ quota 从 chat_message 算，清空会把本月已用量归零；如不能接受，先导出/保留本月消息，或改用其他额度口径。
5. **清 QA 缓存**：
   ```bash
   .venv/bin/python -c "from core.redis_store import get_redis_client; r=get_redis_client(); ks=list(r.scan_iter('rag:qa_cache:*')); r.delete(*ks) if ks else None"
   ```
6. **清空向量 collection（只清 rag 的）**：
   - 重建脚本会 purge 旧切片；**不要**用默认会删 `upload/` 的 `reset_kb.py --apply`；
   - 共享 Chroma 时只清 `rag_qa_knowledge`，不要动其他应用 collection / 整个 server。
7. **全量重建（从原件）**：
   ```bash
   .venv/bin/python scripts/reindex.py --apply
   # 或从源目录（doc_id 可能变）：
   # .venv/bin/python scripts/rechunk_kb.py --apply --src docs/guoquan-kb
   ```
   - 监控 worker 日志：每份 status / chunk_count / 失败原因；MinerU PDF 更慢；
   - 失败文档单独重试（`POST /documents/{doc_id}/reparse`），不要整批回滚。
8. **重建后验证**：
   - `GET /api/v1/documents`：`total_documents` / `total_chunks`；每份 success、`chunk_count>0`；
   - 抽样切片：无空片、`chunk_index` 连续；PDF 标题/表格；xlsx 行级（表头随行、无半行）；docx 文本；md 标题；
   - 切 title 时先重映射 golden：
     ```bash
     cp data/eval/golden.jsonl /tmp/golden.bak.jsonl
     .venv/bin/python scripts/remap_golden_p37a.py --snapshot /tmp/kb_snapshot_fixed.json --apply
     ```
     再 `make eval-retrieval TAG=prod-title CMP=prod-fixed-baseline`，对比 recall@5 / MRR@10 / 拒答率；
   - `make verify-kb-extras`（若生产也部署了这 6 份扩展资料）；
   - 冒烟问答：每份文档 1–2 题，检查 sources/doc_id/答案。
9. **清缓存、重启、健康检查**：backend/worker/frontend 健康；QA 缓存为空；MinerU 日志正常。
10. **小流量开放**：观察错误率、P95 延迟、429（额度）、grounded 误报；再全量。

## 4. 回滚

- 恢复 MySQL dump、`upload/`、Chroma 数据卷、`.env`；重部署上一 tag；清 QA 缓存；健康检查。
- 如果只是 **title 效果不如 fixed**：恢复 `CHUNK_MODE=fixed`，**再次整库重建**（不能局部混切），恢复 golden 备份；不要只改配置不重建。

## 5. 常见坑（逐条对照）

- ❌ **只增量灌新文档**：切分规则变了必须全量；增量会新旧混切。
- ❌ **删 `upload/`**：原件是唯一重建源；`reset_kb.py --apply` 默认会删 upload，生产禁用或 `--no-upload`。
- ❌ **清整个 Chroma / 其他 collection**：只清 `rag_qa_knowledge`；共享服务先确认 tenant/collection。
- ⚠️ **清会话会重置额度统计**：quota 从 `chat_message` 明细算；清空前决定是否保留本月用量。
- ⚠️ **不清 QA 缓存**：会返回旧切片答案，必须清。
- ⚠️ **golden 不重映射**：切 title 后 chunk_id 全变，评测会失真；先 snapshot 再 remap。
- ⚠️ **MinerU 未开/无 key**：扫描件会回退 PyMuPDF，可能空切片；看 WARNING。
- ⚠️ **worker 未停**：重建时与新上传任务竞争；先停 worker。
- ⚠️ **备份不全**：MySQL / upload / Chroma 三者缺一不可。
- ❌ **备份放在 `/opt/qa` 里**：`deploy.sh` 的 `git clean -fd` 会把它删掉（实测踩过）；放 `/opt/qa-backups/`。
- ❌ **md 上传/重建卡死**：`UnstructuredMarkdownLoader` 缺 NLTK `punkt_tab` 时会联网抓
  raw.githubusercontent.com，服务器不通且无超时 → 进程永久阻塞（实测卡 1 小时零写入）。
  p4.15c 起 `.md` 直接按文本读，已消除；老镜像排查看 `strace -p <pid> -e trace=network,read`
  与 `/proc/<pid>/fd`（出现 `punkt_tab.zip.tmp` 即命中）。
